## 1. 요청과 현재 판정

사용자는 CRM003 중복 릴리즈의 실행 오류와 CRM001의 자체 로그인 때문에 기능을 확인할 수 없다고 보고하고, 미완성 앱 정리를 요청했다. 원본 코드·업무 데이터·게시 이력은 삭제하지 않고 기존 프로그램 관리 API의 사용 중단으로 처리할 계획이다.

**최신 상태: 사용자 명시 승인 후 17건 사용 중단 적용 완료 / HTTP API·실제 목록 함수 검증 완료 / 브라우저 시각 검증은 도구 장애로 미실행.** 적용 증적은 §7을 따른다.

최초 감사 단계에서는 계정 인증을 동반한 일괄 상태 변경 명령이 자동 안전 검토에서 거부됐다. 그 명령의 프로세스는 실행되지 않았고 다른 인증 수단이나 직접 SQL로 우회하지 않았다. 이후 대상과 효과를 명시한 질문에 사용자가 `네 승인합니다`라고 답한 뒤, 기존 계정·관리 API로만 적용했다. 비밀번호·세션 토큰을 이 문서나 증적 파일에 기록하지 않는다.

## 4. 실행 절차와 복구

`core/release_catalog_audit.py`는 메모리에서 실패 근거와 내용 지문만 계산한다. `scripts/review_failed_releases.py`의 기본 동작은 새 감사 보고서 작성뿐이다.

실제 적용 모드는 사용자 확인 후에만 실행한다.

1. 감사 당시 대상 17건과 현재 대상·내용 지문을 재대조한다. 변경되면 중단한다.
2. 기존 계정으로 제품의 HTTP 인증·관리 API를 사용한다. 권한·원장 규칙을 우회하지 않는다.
3. 17건 전부의 상태·이력·의존 관계를 먼저 확인한다. 의존 대상이 있거나 영향이 미측정이면 아무것도 중단하지 않는다.
4. 변경 전 상태를 새 보고서에 보존한 뒤, 각 `POST /api/v1/programs/{release_id}/disable`을 호출한다.
5. 각 상태를 다시 조회하고 전체 원본 release.json의 내용 지문 불변을 확인한다.
6. 성공 결과를 별도 새 파일로 기록한다. 부분 실패 시 완료라고 보고하지 않고 저장된 이전 상태와 현재 상태를 대조한다.

삭제·정상 판 승격·인증 우회·생성기 재실행은 없다. 복구는 기존 상태 관리 API에서 사유를 기록하고 **변경 전 상태**로 되돌린다. 이전 candidate까지 모두 active로 만드는 일괄 reactivate를 사용하지 않는다.

적용 전 보존본 `before-disable.json`, 적용 결과 `before-disable.result.json`, HTTP 재검증 `verification.json`이 생성됐다. 최초 `audit.json`만으로 적용 완료를 판정하지 않는다.

### 확인한 결함과 수정

1. 화면이 롤백 결과를 저장한 직후 `inspect()`가 그 결과와 성공 안내를 지웠다. 결과는 새로고침 완료 뒤 게시하고, 내부 갱신에서는 지우지 않도록 변경했다.
2. 사용 중단이나 전사 승격 철회 실패에도 API가 HTTP 200 / success를 보냈다. `complete / partial / failed`를 분리하고 미완료는 503과 실제 부분 결과를 전달한다.
3. 사용 중단을 먼저 수행·재조회하고 그 성공 후에 승격 철회를 수행·재조회한다. 재시도할 때 이미 중단된 앱의 사유·이력·지문·대체본을 불필요하게 덮어쓰지 않는다.
4. 롤백 이력에 처리 결과를 저장한다. 최초 요청은 `in_progress`, 과거 행은 성공으로 추정하지 않고 `unknown`으로 남긴다. 기록 저장소가 처음부터 불통이면 변경을 시작하지 않고, 최종 기록 실패면 완료를 주장하지 않는다.
5. 화면에서 처리 중 중복 제출·대상 변경을 막고, 확인 당시 대상을 요청에 사용한다. 대상 선택 변경 시 이전 점검 결과·확인창을 비운다. 승격 철회 상태도 한글로 표시한다.

실제 서버의 롤백 이력을 읽었을 때 최근 사용자 시도 기록은 없었다. 따라서 위 재현 가능한 코드 결함을 고친 것이며, 사용자 클릭의 유일한 원인까지 실측했다고 주장하지 않는다.

### 14.1 결론 — 같은 인스턴스에 범위와 날짜가 다른 자료를 혼합했다

`ki_6b06ffb50a994a`의 발주·선적은 전체 키트에서 **6건만 선택해 날짜를 84일 옮긴 자료**다. 반면 통관·입고 운송은 **날짜를 옮기지 않은 전체 키트 자료**다. 서로 다른 DB 접속 문제가 아니라 같은 설치 인스턴스 안의 불일치다.

| 계약키 | 설치 행수 | quick 원본 | full 원본 | full과 설치 행 내용 대조 |
|---|---:|---:|---:|---|
| PRC-02 발주행 | 6 | 200 | 1,800 | 동일 업무키 6건 존재. 날짜 3열만 각 +84일 |
| LOG-02 선적 | 6 | 120 | 1,200 | 동일 업무키 6건 존재. 날짜 3열만 각 +84일 |
| LOG-04 통관 | 1,200 | 120 | 1,200 | 1,200행 전부 full과 같은 열·값 |
| LOG-05 입고 운송 사건 | 2,400 | 240 | 2,400 | 2,400행 전부 full과 같은 열·값 |

'행 내용 동일'은 파싱한 CSV의 열·값 비교이며 **파일 바이트 동일**이라는 뜻이 아니다. 네 설치 원본의 바이트 체크섬은 저장 체크섬과 일치한다. 모두 합성 자료로, 실제 공시·회사 실적으로 표현하지 않는다.

PRC-02는 `(tenant_id, po_line_id)`, LOG-02는 `(tenant_id, shipment_id)`로 full 행을 찾아 모든 열을 비교했다. PRC-02의 `as_of_date/order_date/due_date`, LOG-02의 `as_of_date/etd/eta`는 각 열마다 **6/6행이 +84일**, 나머지 열 변경은 없다. 통관·운송은 전체 행의 열·값 다중집합을 비교해 중복 행 개수도 포함했다.

| 참조 검사 | 설치본 | quick 원본 | full 원본 |
|---|---|---|---|
| 선적 → 발주행 | 누락 0/6 | 누락 0/120 | 누락 0/1,200 |
| 통관 → 선적 | **누락 1,194/1,200** | 누락 0/120 | 누락 0/1,200 |
| 운송 사건 → 선적 | **누락 2,388/2,400** | 누락 0/240 | 누락 0/2,400 |

번호가 연결되는 행도 잘못된 시간축을 쓴다. 설치본에서 연결되는 통관 **6/6행의 `cleared_at`**, 운송 사건 **12/12행의 `event_at`**이 해당 선적 `etd`보다 앞선다. quick/full의 같은 비교는 전부 날짜가 있고 시간 역전 **0건**이다. 이 비교는 해당 합성 물류 흐름의 일관성 검사이며 모든 회사 업무에 일반화한 날짜 정책을 승인한 것이 아니다.

예: `SHP-000001`의 설치 출항 예정일 **2023-10-28**, 도착 예정일 **2023-11-12**에 대해 통관일 **2023-08-23**, 운송 출발일 **2023-08-23**, 도착일 **2023-08-25**가 연결된다. full 원본의 출항/도착 예정일은 2023-08-05/2023-08-20이다.
