## 1. 무엇이 틀렸었나 — 「됐는지 모른다」를 「안 됐다」로 말했다

```tsx
const r = await saveRelease(currentProjectId);
if (r.ok) { alert("✅ 최종 결과물이 라이브러리에 저장되었습니다. …"); }
else      { alert(`❌ 결과물 저장에 실패했습니다.\n\n${r.message}`); }   // ← 여기
```

이 명령의 `outcome` 은 셋이다. `r.ok` 하나로 가르면 **UNKNOWN 이 REJECTED 와 같은 말**이 된다.

| outcome | 실제 사실 | 사용자가 할 일 | 종전 화면의 말 |
|---|---|---|---|
| ACCEPTED | 서버가 접수하고 `release_id` 를 줬다 | 목록에서 확인 | 「저장되었습니다」(완료로 단정) |
| REJECTED | 서버가 거절했다 | 사유를 보고 고친다 | 「실패했습니다」 ✔ |
| **UNKNOWN** | **됐는지 모른다** — 응답 유실·5xx·문맥 변경 | **다시 누르지 않고** 목록에서 확인 | 「**실패했습니다**」 ✘ |

실패라고 들으면 사람은 **다시 누른다.** 그러면 같은 결과물이 두 벌 저장된다 —
`saveProjectRelease` 가 원키(`client_request_id`)로 막으려던 **바로 그 사고**다.
그 함수의 주석이 이미 그 사고를 적어 두었는데, 화면이 그 대비를 무효로 만들고 있었다.

두 번째 결함도 같은 자리에 있었다. `alert` 는 **전역**이라, A 에서 저장을 요청하고 B 로 옮긴
뒤 응답이 오면 **B 화면 위에** A 의 결과가 떴다. 게다가 그때 store 가 돌려주는 값은
`CONTEXT_CHANGED`(ok=false) 여서, B 화면에 「❌ 실패했습니다」가 뜬다 — **A 는 저장됐을 수도
있는데** 실패했다고 읽는다.

## 2. 고친 모양

```tsx
const requested = currentProjectId;
const r = await saveRelease(requested);
if (useFactoryStore.getState().currentProjectId !== requested) return;   // 완료 «시점» 의 화면
if (r.ok) {
  alert(`✅ 검토용 버전 저장을 접수했습니다.\n\n${r.message}`);
} else if (r.outcome === 'UNKNOWN') {
  alert(`⚠️ 저장 여부를 확인하지 못했습니다. 다시 누르지 마십시오 — 같은 결과물이 두 벌 저장될 수 있습니다.\n\n${r.message}`);
} else {
  alert(`❌ 결과물을 저장하지 못했습니다.\n\n${r.message}`);
}
```

* 성공 문구도 **화면이 지어내지 않는다.** 공용 함수가 준 문구(`r.message`)를 싣는다 —
  「접수」와 「저장 완료」는 다르고, 정본은 라이브러리 목록이다.
* 완료 시점 비교는 **직전 라운드의 내려받기 보완과 같은 모양**이다. 같은 화면의 두 비동기
  버튼이 서로 다른 규칙을 쓰지 않게 맞췄다.
* **새 정책을 넣지 않았다** — 중복 방지는 이미 공용 함수의 원키가 한다. 이 보완은
  「무엇이 일어났는지 어떻게 말하는가」다.

## 3. §10.1 parity 표 — 검토용 버전 저장

| 항목 | 기존(구 통제실) | 신규(새 Studio) |
|---|---|---|
| 입구 | 「🚀 최종 결과물 저장 (배포)」 (모든 단계 완료 시) | 「검토용 버전 저장」 (추가 작업 안) |
| 사전 확인 | `confirm()` — 수용검수 미통과면 경고 문구 | `activeReason`·`hasResult` 로 **버튼을 잠근다** |
| 호출 | `store.saveRelease` → `saveProjectRelease` → `POST …/execution-commands` (원키) | **같은 경로** |
| 서버 권한 | `execution-commands` = `PROJECT_RUN`, 그리고 `assert_project_writable` + `_command_authority(…, 'RELEASE')` | 동일(같은 엔드포인트) |
| 문맥 | store 가 요청 **시작 시** 현재 프로젝트를 확인, 응답 후 `CONTEXT_CHANGED` 반환 | 동일 + 화면이 완료 시점 재확인 |
| 성공 | 접수 문구를 싣는다 **(이번 수정)** | 「…저장했습니다. **배포·운영 승인은 별도입니다**」 |
| 거절 | 사유를 싣는다 | `command` 가 사유를 그대로 note 로 |
| **미확정** | **다시 누르지 말라고 말한다 (이번 수정)** | `command` 가 **잠근다** — 「결과 확인 필요」 배너, 입력 보존, 새 요청 차단, 자동 재전송 없음 |
| 상태 갱신 | `fetchReleases()` (ACCEPTED·UNKNOWN 모두) | 동일 + `fetchLatestState`·`fetchWBS`·`checkHotl` |

★ **남는 비대칭 1건(수정하지 않음):** 구 화면에는 미확정 **잠금**이 없다 — 버튼이 그대로
열려 있어 사용자가 다시 누를 수 있다. 문구로 말리기만 한다. 잠금을 넣으려면 구 화면에
미확정 상태를 들여야 하는데, 그것은 §10 이 C3 에서 지우기로 한 화면이다. **판단을 구한다.**

## 5. ★ 먼저 봐 달라는 것

1. **§3 의 남는 비대칭** — 구 화면에 미확정 잠금을 넣을지, 문구까지로 둘지.
2. **문구 수위** — 성공을 「접수했습니다」로 낮췄다. 구 화면 사용자는 이 명령을 「배포」로
   알고 있었는데(버튼 이름이 「최종 결과물 저장 (배포)」다), 접수 표현이 오히려 **덜
   끝난 것처럼** 읽힐 수 있다. 버튼 이름까지 손대는 것은 §10 C2/C3 범위로 보고 하지 않았다.
3. **UNKNOWN 문구가 「다시 누르지 마십시오」로 충분한지** — 잠그지 않는 한 사람은 누를 수 있다.

### ⚠️ 정정 — 「두 벌 저장」은 **미확정 중 중복 전송의 증거가 아니었다**

내가 UNKNOWN 안내에 「다시 누르면 두 벌 저장될 수 있습니다」라고 쓰고, 한 번 더 눌러
2건을 만든 뒤 두 릴리스 본문이 같음을 확인했습니다(길이 2177 · 지문 50a27303 동일).
**관측 자체는 맞지만 해석이 틀렸습니다.**

> [2026-09-19 Codex 정정 · 수용] `studioExecutionApi.executeStudioCommand` 는 **첫 POST 전에**
> UNKNOWN 을 기록하고, `hasExecutionPending` 이 참이면 **PAUSE/STOP 외의 새 명령을 거절**한다.
> 구 화면도 같은 공용 명령을 쓰므로 **버튼이 열려 있다고 재전송되는 것이 아니다.**
> 내가 만든 2건은 **각각 확정(ACCEPTED)된 두 번의 명시적 저장**이지, 미확정 중 중복 전송이
> 아니다. 즉 **멱등성 결함을 실증한 것이 아니다.**

제품 문구와 주석, 시험 단언에서 그 과장을 걷어냈습니다. 지금은 이렇게 말합니다 —
「저장 여부를 확인하지 못했습니다. **다시 누르지 말고** 아래 «실행 요청 기록»에서
**원래 요청을 조회**하십시오.」 사용자가 할 일은 겁내는 것이 아니라 **결과를 확정하는 것**입니다.

남는 사실은 그대로입니다: 구 화면은 미확정을 **실패로 단정**했고, 그것은 「됐는지 모른다」를
「안 됐다」로 말한 것입니다. 그 수정은 유효합니다.

### 아직 아닌 것

- 구 통제실 버튼은 `progressPercent === 100` 조건이라 이 합성 프로젝트에서 열리지 않는다.
