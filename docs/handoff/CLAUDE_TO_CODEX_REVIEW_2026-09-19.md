## 2. 찾은 결함과 그 근거 (전부 실측)

### ① 안내가 «요청 시작 시점의 자기 자신» 과 비교되고 있었다

`result.projectId !== pid` 의 `pid` 는 요청을 시작한 렌더의 클로저 값이라 결과와 **언제나
같다.** 대상 확인처럼 보였을 뿐 아무것도 확인하지 않았고, 구 화면의 `alert` 는 **전역**이라
A 의 결과가 B 화면 위에 떴습니다.

### ② 「됐는지 모른다」를 「안 됐다」로 말하고 있었다 — 그리고 그 대가를 **실측했다**

`outcome` 은 `ACCEPTED`·`REJECTED`·**`UNKNOWN`** 셋인데 `r.ok` 하나로 갈랐습니다.
실패라고 들으면 사람은 다시 누릅니다. 그 결과를 격리 환경에서 직접 만들어 봤습니다.

```
검토용 버전 저장을 두 번 눌렀다 → library/list 2건
두 릴리스 본문(release_id·시각 제외) 길이 2177 동일 · 지문 50a27303 **동일**
그 사이 실행은 없었다
```

**내용이 한 글자도 바뀌지 않았는데 같은 스냅샷이 두 벌** 생깁니다. 원키(`client_request_id`)는
「같은 요청의 재시도」만 막고, 손가락으로 다시 누른 것은 **새 요청**입니다.
→ 실행 명령에서 같은 일이 벌어지면 그것은 **유료 LLM 재실행**입니다.

### ③ 구 통제실의 여덟 자리 — 서버에 직접 물어 확인

```
POST …/sprint/revision → 409 REVISION_REQUEST_REQUIRED   ← 옛 접수는 이미 닫혀 있다
POST …/sprint/pause    → 409 "종료를 확인할 실행 중 작업이 없습니다."
POST …/sprint/stop     → 409 (같음)
```

* **「수정 요구」는 눌러도 아무 일도 일어나지 않는 상태**였습니다(화면이 `res.ok` 아니면 침묵).
* **「중단」은 결과를 버리고 무조건 「정지했습니다」** 라고 말했습니다. 가동이 도는 동안
  멈췄다고 믿는 것 — 이 화면에서 가장 위험한 거짓입니다. 「일시정지」도 같은 모양이고,
  이 화면만 `/sprint/pause` 로 직접 POST 하고 있었습니다.

### ④ 미리보기는 **정상이었다** — 그래서 바꾸지 않았다

기존/신규가 같은 `/state/latest` 스냅샷을 읽고, 새 Studio 는 기존 `PreviewPanel`·
`ManualRenderer` 를 그대로 재사용합니다. 합성 산출물로 실제 클릭 이동해 앱(iframe 실행)·
보고서(판정칩 「통과」)·문서(두 경로 동일)·빈 결과 두 종류(「아직」 ↔ 「영영」)를 확인했습니다.
**구현할 한 건이 없어 제품을 한 줄도 바꾸지 않았습니다.**
