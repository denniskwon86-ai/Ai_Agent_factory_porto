# 문맥/SSE 마감 검토 · 내려받기 마지막 보완

작성: Codex · 2026-09-19 KST. CLOSEOUT 요청서·내려받기 공용 함수/양쪽 버튼·서버 export/CORS를 읽기 검토했다. 제품 수정/시험 재실행 없음.

## 판정

- 문맥 재확인·비가시404·거절 화면 복귀와 합성 생산자 기반 SSE 전달/필터/store/mapper/DOM, 옛 연결 차단은 이 묶음의 마감 항목으로 관리한다. 실제 화면 결과는 Claude 보고이며 Codex 독립 재실행은 아니다. 영향 변경이 없는 한 다시 전체 반복하지 않는다.
- 내려받기를 인증 헤더가 붙는 apiFetch 공용 함수로 묶고 두 화면에서 사용하는 방향은 타당하다. 앵커 직접 요청401/인증 fetch200의 기존 결함 수정으로 인정한다.
- 실제 버튼 클릭은 아직 미검증이다. 실제 산출물 생성/LLM까지 시작할 필요 없이 격리 합성 코드·문서 fixture로 닫을 수 있다.
- 전체21/40=52.5%, 로컬18/28=64.3% 현재 유지. 코드 연결과 사용자 클릭 수용을 분리한다.

## CORS 결정 — 이번에는 서버 변경하지 않는다

api/routes/factory_control.py export는 현재 Content-Disposition을 project_id.zip으로 고정한다(3500행 부근). 클라이언트 폴백도 동일한 pid.zip이다. 따라서 지금 서버 파일명과 다른 이름으로 저장되는 기능 결함은 없다.
expose_headers 추가는 향후 다른 파일명 계약이 실제로 필요할 때 별도 검토한다. main.py/허용 origin/credentials/권한표를 이번 내려받기 마감 때문에 변경하지 않는다. 파일명 헤더 노출을 이번 완료 차단 조건으로 두지 않는다.

## 보완 1 [P2] 응답 본문 실패가 결과 계약 밖으로 샌다

frontend/src/factory/sprintActions.ts downloadProjectArchive는 apiFetch만 try/catch로 감싼다. 이후 res.blob(), createObjectURL, 저장 준비/클릭은 실패하면 Promise reject가 된다. RunControls와 ControlPanel의 void async 호출부에도 catch가 없어 실패 안내가 사라진다.

첫10~15분:

- 수신부터 저장 준비까지 실패를 ArchiveDownload 실패 결과로 일관되게 돌린다. 빈 문자열 원문/서버 상세를 그대로 노출하지 말고 연결·파일 준비 실패를 구분한다.
- 앵커 제거와 objectURL 해제는 실패 경로에서도 보장한다. 브라우저 저장 시도가 시작된 것과 사용자 디스크 저장 완료는 구분하여 성공 문구를 '내려받기를 시작했습니다' 수준으로 고친다.
- blob() reject, 저장 준비 실패, HTTP401/403/404, 정상 ZIP 한 건을 좁게 검사한다. 실패하면 파일 클릭0회·실패 안내이며 미처리 rejection이 없어야 한다.
- exportArchiveUrl의 'fetch하지 않고 링크로 연다'는 낡은 주석도 현 동작에 맞춰 정리한다. 함수 삭제/전체 모듈 개편은 하지 않는다.

## 보완 2 — 늦은 다운로드 결과의 문맥 경계

현재 함수는 요청 전 identity를 고정하거나 응답 후 재확인하지 않는다. A 사용자가 요청하고 B 문맥/로그인으로 바뀐 뒤 본문이 끝나도 a.click() 및 성공 안내를 실행한다.
이전 초안 진입에서 정한 문맥 수명과 일치시킨다. 사용자/tenant/scope/mode 변경 또는 로그아웃 후에는 아직 시작되지 않은 파일 저장과 현재 화면 안내를 진행하지 않는다. 요청 시점 identity와 취소 신호를 이용하고 응답·blob 이후, 클릭 직전에 확인한다. 이미 브라우저로 넘긴 다운로드를 취소/회수했다고 주장하지 않는다.
단순 탭 이동/프로젝트 이동만으로 사용자가 명시 요청한 다운로드를 모두 취소하는 정책까지 확대할 필요는 없다. 호출부가 다른 프로젝트에 성공/오류 안내를 붙이지 않도록 요청 대상을 보존한다.
api helper에 store import를 새로 넣어 순환 의존을 만들지 말고 기존 identity 유틸/호출부 옵션을 재사용한다. 지연 본문→문맥 변경 한 건으로 검증한다. 중복 클릭 방지는 요청 중 해당 버튼에 한정해 필요한 경우 보완한다.

## 실제 클릭 수용 — 후속15~20분 예상

1. 기존 격리 프로젝트 fixture에 작은 합성 코드 파일과 문서 파일을 준비하고, 기존 제품 로더가 읽는 결과 메타데이터와 일치시킨다. 브라우저 store를 직접 바꿔 버튼을 강제로 켜거나 제품 활성 조건을 약화하지 않는다. 운영 산출물을 복사하거나 LLM을 실행하지 않는다.
2. 새 Studio 및 기존 ControlPanel의 정상 진입 경로에서 각 버튼을 클릭한다. 기존 UI가 현 진입에서 노출되지 않으면 테스트 전용 mount와 실제 제품 노출을 구분해 보고한다.
3. 다운로드 시작 이벤트/파일명/실제 ZIP 항목과 합성 코드·문서 내용을 확인한다. 기존 제외 디렉토리 규칙이 유지되는지도 확인한다. 브라우저 fetch200만으로 파일 저장/내용 검증을 대체하지 않는다.
4. 좁은 권한 계정 실패와 파일 생성0을 확인한다. 없는 프로젝트404 안내는 존재를 확정하는 문구보다 '결과를 찾을 수 없거나 현재 문맥에서 조회할 수 없습니다'처럼 기존 은닉 계약을 존중한다.
5. 관련 프런트 검사/build 한 번. 서버 무변경이면 전체 pytest/CORS 시험을 추가하지 않는다. 계측/fixture 재기동 절차는 기존 문서에 추가하고 별도 긴 검증 배치를 만들지 않는다.
