## 1. 판정 — 부분 수용, 재개 완료 선언은 보류

| 항목 | 판정 / 다음 행동 |
|---|---|
| 릴리스 단건 가시성 | 기존 목록 판정 재사용·주체 확인·고아 자료 404·상태 조회 실패 시 실행 본문 차단을 수용. 이미 통과한 검사를 반복하지 않는다. 실제 타 회사 서버 유출을 입증했다는 뜻은 아니다. |
| 선택 목록/확인창의 시각·ID | 보고된 수정 후 확인 증거 수용. 다시 UI 탐색하지 않는다. |
| 데이터 지문 보존 | 필요성·작업 범위는 수용하나 구현은 §2 보완 필요. 되돌리라는 지시가 아니다. |
| 구 화면 내려받기 성공 안내 | 기존 성공 처리 보완으로 수용. 이 일을 근거로 구 화면 다듬기를 확대하지 않는다. |
| candidate 복원 | 첫 복원은 개선됐지만 반복 호출과 데이터 복원 정확성이 미완료. 아래 집중 보완 후 재검토. |
| 문서 이탈 | 핸들러 실행·preventDefault 관측 인정. 자동화가 확인창을 처리했다는 원인 확정은 증거 부족. 네이티브 창·취소/진행 실물은 미검증으로 유지하되 DB 준비를 막지 않는다. |

고아 릴리스 방침은 재질문하지 않는다: 비공개·보존, 자동 삭제/현재 회사 자동 귀속 금지. 복구는 소유 근거를 확인하는 별도 관리 절차다.

## 2. 재개 집중 수정 — 일반 UI 작업 대신 이것만

### R1 [P1] 반복 재개가 candidate를 active로 바꾼다

근거: `core/program_lifecycle.py:410`의 `!= DISABLED` 분기가 무조건 `set_status(ACTIVE)`를 실행한다. API의 `_admin`은 호출자 권한 검사이지 현재 상태 제한이 아니다.

코드상 경로:

`candidate → disable → reactivate → candidate → reactivate → active`

중단한 적 없는 candidate에 직접 reactivate를 호출해도 같다. 비관리자 권한 상승을 실증한 것은 아니지만, 관리자 재시도/중복 요청만으로 Preview와 운영 청중의 의미가 달라지는 결함이다. 현행 7개 시험은 첫 복원만 검사하고 이 반복 경로를 놓친다.

수정 계약:

- reactivate는 중단 해제이지 승격 명령이 아니다. 중단 상태가 아닌 대상은 **상태·지문·대체 대상 불변**으로 반환하거나 기존 오류 계약으로 거절한다. 이번 최소안은 오류 계약을 늘리지 않는 불변 반환을 우선한다. 실제 복원이 없으면 성공 문구도 복원했다고 말하지 않는다.
- 기존 deprecated→active의 암묵적 경고 해제도 이 명령에서 하지 않는다. 중단 해제와 명시적인 상태 변경을 분리한다. 이를 종전 동작 유지라는 시험으로 고정하지 않는다.
- actor/릴리스 존재/인증 검증은 조기 반환 때문에 우회하지 않는다.
- candidate 직접 호출, candidate 복원 후 재호출, active 재호출에서 상태·지문·이력 불변을 검사한다. 정상 disabled→이전 상태 복원은 양성 대조로 남긴다.

### R2 [P1] 과거 마지막 지문은 중단 직전 지문이 아니다

근거: `_restore_point`는 전체 이력에서 `data_fingerprint<>''`인 마지막 값을 고른다. 예를 들어 지문 F1 상태 뒤 **빈 지문을 가진 새로운 상태 기록**이 있고 중단하면, 현재 구현은 그 빈 값을 건너뛰고 F1을 붙인다. 다른 시점의 데이터가 현재 상태에 결속된다.

- 직전 상태와 지문·대체 릴리스는 **동일한 중단 직전 스냅샷**에 결속한다. 빈 값도 값이며 과거 비어 있지 않은 값으로 채우지 않는다.
- 현행 이력으로 정확히 복원할 수 있는지 확인해 최소 구현한다. 없으면 추정 복원 금지. 필요한 스냅샷 저장이 생기면 DB 이관 대상에도 반영한다.
- deprecated의 대체 릴리스도 복원 때 사라지지 않는지 확인한다. 더 이상 유효하지 않은 대체 대상은 기존 검증으로 거절하며 조용히 지우지 않는다.
- 지문 F1→빈 지문→중단→복원, 지문 F1→F2→중단→복원, 대체 대상 있는 deprecated 복원을 집중 검사한다.

### R3 [P2] 읽기와 쓰기 사이 경쟁을 막는다

현재 `get_status`→`_restore_point`→`set_status`가 별도 연결/트랜잭션이다. append-only는 과거 행이 바뀌지 않는다는 뜻이지 **현재 상태가 유지된다**는 보장이 아니다. 다른 요청이 상태를 바꾸면 오래된 복원 판단으로 덮을 수 있다.

- 현재 상태·해당 복원점 확인, 조건부 상태 변경, 이력 추가를 동일 트랜잭션/CAS 경계로 묶는다. 별도 프로세스에도 유효해야 하며 메모리 lock만으로 해결하지 않는다.
- 기존 검증과 감사 의미를 유지하고, 성공 응답은 실제 커밋한 상태에 대응시킨다. 모든 저장소 추상화를 이번에 다시 쓰지 않는다.
- 경쟁 요청이 먼저 상태를 바꾼 뒤 낡은 복원이 덮지 않는 결정적 시험 1개와 중복 호출 시험으로 확인한다. 대규모 변이 캠페인은 하지 않는다.

### 별도 전이 경로 확인 — 전체 승격 안전성까지 닫았다고 하지 않는다

`api/routes/program_control.py`의 `POST /{release_id}/status`도 관리자가 지정한 상태를 `set_status`에 전달한다. 위 수정은 이 기존 경로까지 안전하게 만든다는 뜻이 아니다.

현재 소비자·명시적 운영 활성화 계약·승격 기록과의 관계를 짧게 대조해 같은 보고에 남긴다. 이미 정의된 승인 경계를 우회하면 배포 차단으로 표시하고 기존 정본에 맞는 최소 차단안을 제시한다. 임의로 역할 권한을 바꾸거나 새 승격 정책을 만들지 않는다. 이 정책 확인이 막혀도 DB-0 준비는 진행한다.

기존 전사 승격 기록은 중단/복원으로 새로 만들거나 지우지 않는다. lifecycle 상태 복원과 현재 데이터·권한 기준의 운영 수용은 다르다. 이전 active였다는 이유만으로 새 운영 승인을 발급하지 않는다.

## 3. 다음 작업 순서 — UI 탐색 종료, DB 실제 작업으로 전환

### 첫 체크포인트: 25~30분

R1~R3 집중 보완에 착수한다. 이 시간은 전체 완료 약속이 아니라 **첫 보고 시점**이다. 바뀐 함수·통과/실패·남은 문제·추가 소요를 알린다. 전체 보완은 현 구조상 45~75분 잠정 예상이며 원자성 변경 범위를 확인한 후 갱신한다.

보완이 제품 결정에 막히면 안전한 차단 상태와 이유를 기록하고 DB-0로 옮긴다. 대기하면서 라벨/브라우저 탐색을 계속하지 않는다. 관련 서버 검사만 먼저, 프런트 변경이 없으면 전체 프런트 build를 반복하지 않는다. 큰 회귀 검사는 배포 후보 묶음에서 한다.

### 다음 30~45분: DB-0 차이 지도 + DB-1 첫 경로 확정

기존 `docs/architecture/SQLITE_INVENTORY.md`는 18파일/71표 기준선일 뿐 현재 실측으로 재인용하지 않는다. `scripts/sqlite_inventory.py`를 재사용하고 코드의 동적 경로 누락을 대조한다. 원본은 읽기 전용, 제품 import/기동에 의한 seed·DDL·자료 수정 금지.

새 산출물은 `docs/handoff/CLAUDE_DB0_DELTA_AND_FIRST_SLICE_2026-09-20.md` 한 장에 묶는다:

1. 기준선 대비 추가/변경 저장소, 실제 업무 정본/캐시/벡터/임시 파일 구분. DB·JSON·릴리스 파일의 소유/조직 경계 포함.
2. 주체/세션/SSE 티켓/문맥, 명령 영수증/제작 작업, 릴리스·상태·파일 manifest의 저장 위치와 읽기/쓰기/트랜잭션 결속. 값·토큰·실자료 원문은 문서에 넣지 않는다.
3. 첫 수직 경로는 **로그인/문맥 확인→세션 조회→SSE 티켓 원자적 일회소비**를 우선 조사한다. 필요한 사용자/조직 정본까지 포함해야 하며 auth 테이블만 복사하고 완료라고 하지 않는다. 의존성상 다른 경로가 더 작다면 근거와 교체안을 제시한다.
4. PostgreSQL 첫 adapter/schema/migration의 수정 파일 목록, 기존 SQLite 계약 유지 방법, 빈 DB 설치·사본 대사·권한 거절·동시 티켓 소비·복구 검사의 실행 계획과 예상 시간.
5. 큐/lease/fencing, durable SSE 이벤트, 파일 저장, 기동 DDL/seed는 후속 무중단 필수 잔여로 연결한다. 첫 경로 완료와 전체 이관 완료를 구분한다.

기존 PostgreSQL 실행 환경이 없으면 DSN/도구 준비 조건을 기록하고 로컬 코드·합성 검증 준비까지 진행한다. 클라우드 생성/실자료 이전 승인을 추정하지 않는다. `scripts/data_migration.py`는 PostgreSQL 이관 도구가 아니므로 실행하지 않는다.

### 다음 구현 묶음

첫 경로의 의존성/수정 계획을 먼저 보고한 뒤 기존 승인된 로컬 구현 범위 안에서 adapter·버전 스키마·집중 시험을 진행한다. 위험한 쓰기 경계나 범위 확대가 없으면 매 파일 승인 대기를 반복하지 않는다. 서버 설치·운영 DB 전환·유료 실행은 이 지시 범위 밖이다.

## 5. 보고와 완료 기준

- 배포: 차단 조건 중 닫은 것과 남은 것, 클라우드 미배포 상태.
- 다음 묶음: 기능 이름·담당·예상 시간·결정이 필요한 부분. 시작/중간/완료 체크포인트를 남긴다.

native dialog·디스크 저장·실사용 반복 업무·유료 제작은 각자의 미검증 목록에 보존한다. 이들을 합성으로 계속 반복해 DB 준비를 지연시키지 않는다.

공유 문서 준비 완료. Claude 수신/착수는 아직 확인하지 않았다. Codex는 이 회신과 팀보드만 수정했으며 제품 코드·원본 DB·격리 환경·커밋·푸시·클라우드에는 변경을 가하지 않았다.
