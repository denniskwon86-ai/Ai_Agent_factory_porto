## [P2] 1. 취소 복원이 뒤로 한 칸만 가정함

App.tsx 362~378행: 모든 popstate에서 미저장 입력이 있으면 history.go(1), 승인 시 history.back()을 실행한다.
사용자가 앞으로 이동한 경우에는 반대로 뒤로 되돌려야 한다. 현재 구현은 더 앞으로 가거나, 마지막 항목이면 이동이 없어 skipNextPop이 남는다. 다중 칸 이동도 원위치로 돌아오지 못한다.
check-project-entry.mjs도 go(1)을 정답으로 고정하므로 해당 시험은 방향 일반성을 검증하지 않는다.

보완: 앱이 관리하는 항목의 위치/이동 delta를 식별해 정확히 역이동하고 승인 시 원래 목적지로 이동한다. 기존 history.state는 보존한다. 앱 밖/식별 불가 항목에 인덱스를 지어내지 말고 안전한 처리 범위를 명시한다. 복원 popstate 완료와 승인 클릭의 순서도 제어해 빠른 클릭으로 잘못된 이동을 하지 않게 한다.
검사: 같은 문서에서 뒤로/앞으로 각각 취소/승인, 마지막 항목 앞으로 취소, 가능하면 두 칸 이동. URL·화면·입력·현재 항목 위치가 함께 맞아야 한다. history.length만 같다고 성공이 아니다.

## [P2] 2. popstate 복원 표시가 다음 클릭까지 남음

App.tsx URL 동기화 effect(407~428행)는 search가 현재 URL과 같으면 즉시 return한다. restoringFromPop=false는 그 뒤에 있다.
정상 복원은 대개 이미 URL이 일치하므로 true가 남고, 다음 사용자 명시 이동이 push가 아니라 replace가 되어 기록을 잃는다.

보완: 복원 완료 여부와 URL 쓰기 필요 여부를 분리한다. 조회 대기/실패에도 오래된 복원 상태가 다음 사용자 이동을 덮지 않게 한다.
검사: 목록→초안→목록→뒤로(초안)→다른 대상 클릭. 마지막 클릭은 한 칸 추가되어야 하고, 그 뒤 뒤로가기가 초안으로 돌아와야 한다. 순수 effect 단독 검사보다 전이 연속 검사로 잠근다.

## [P2] 3. 열린 대상의 배타적 정리와 비동기 URL 수명이 아직 불완전

확인한 구체 지점:

- applyStudioEntry의 project/kitApp/draft 분기는 이전 viewingRelease/업무앱 모달을 닫지 않는다. openTarget은 release를 최우선으로 택하므로 릴리스에서 초안으로 이동해도 이전 릴리스가 새 주소를 덮을 수 있다.
- 업무앱 PathCalcPanel의 onClose(935행)는 setShowPathCalc(false)만 실행하고 openedKitApp을 지우지 않는다. 방금 수정한 draft 닫기와 같은 URL 잔존 문제다. 목록 목적지 복원에서도 showPathCalc 정리가 빠져 있다.
- openTarget에는 new 분기가 없다. new 화면이 열려도 URL 동기화는 목록 주소로 바꾼다.
- release 진입은 viewRelease를 기다리지 않고 routeRestored=true로 둔다. 로딩/실패 때 viewingRelease가 비어 있으면 목적지 release URL을 잃고 성공 시 불필요한 항목을 만들 수 있다.

보완: 전환 전 이전 대상 화면·요청을 일관되게 정리하고, 활성 진입 의도/조회 상태/열린 화면을 같은 계약으로 관리한다. 여섯 대상에 별도 땜질 분기를 계속 늘리지 않는다. 기존 closeRelease/초안 abort를 재사용한다.
검사: 릴리스→초안, 업무앱 닫기→새로고침, 업무앱→목록, new 새로고침, 릴리스 지연 성공/실패 주소 보존. 실제 표시 화면과 URL의 대상이 일치해야 한다.

## [P2] 4. 보호 UI 예외 시 무조건 떠나지 않기
