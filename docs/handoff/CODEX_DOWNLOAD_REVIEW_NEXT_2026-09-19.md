# 내려받기 보완 검토 / 다음 parity 지시

작성: Codex · 2026-09-19 KST. DOWNLOAD 요청서·공용 함수·두 호출부·검사 로더·다음 후보 연결 위치 읽기 검토. 제품 수정/검사 재실행 없음.

## 판정

- blob/저장 준비 실패 결과화, finally 앵커/URL 정리, 성공 '시작' 표현, 응답 이후 신원·signal 확인 보완을 정적으로 수용한다. CORS/서버 무변경 유지가 맞다.
- check-studio-contracts는 이미 적재하던 실제 studioInputMemory를 sprintActions 의존성에 연결했다. 신원 함수를 무조건 통과하는 대역으로 바꾼 것이 아니므로 약화로 보지 않는다. HTTP/신원 공급은 여전히 합성이라는 시험 범위 표기는 유지한다.
- 세 지점의 호출 수 검사는 불필요한 본문/URL 작업을 조기에 중단하는 회귀 검사로 유지 가능하다. 동일 기능의 새 결함 세 개를 닫은 것으로 세지 않고, 모든 방어 줄의 변이를 추가로 강제하지 않는다. 전면 변이 재실행은 불필요하다.
- 프런트186PASS/contracts157/tsc/build 및 ZIP 내용은 Claude 보고값이며 Codex 독립 실행값이 아니다.

## 남은 P2 한 건 — 대상 비교가 오래된 클로저끼리임

RunControls는 downloadProjectArchive(pid) 이후 result.projectId !== pid를 검사한다. ControlPanel도 호출 시 currentProjectId와 결과를 비교한다. 두 변수는 비동기 호출을 시작한 렌더의 클로저 값이다. A 요청 뒤 B로 전환해도 결과A와 캡처A가 같아 통과한다.
따라서 이번 '대상 확인 후 안내'는 현재 화면 확인이 아니다. 특히 기존 ControlPanel의 alert는 화면이 바뀌어도 뜰 수 있다.

첫10~15분 보완:

1. 완료 시점의 useFactoryStore.getState().currentProjectId 또는 최신 ref와 비교한다. 호출부가 이미 store를 쓰므로 공용 API helper에 store를 import하지 않는다.
2. unmount/문맥 변경/같은 A로 재진입한 새 화면에도 이전 안내를 붙이지 않도록 호출부 수명/요청 식별을 일관되게 확인한다. 아직 시작 전인 파일 저장 차단은 기존 identity 검사로 유지한다.
3. 한 번의 연속 시험: A에서 요청→B로 화면 전환→A 성공/오류 완료. B의 note/전역 alert가 변경되지 않아야 한다. 결과 반환 필드나 문자열 단언만으로 대체하지 않는다. 현재A의 정상 안내 양성 대조를 둔다.
4. 사용자가 요청한 다운로드 자체를 단순 프로젝트 전환만으로 모두 취소하는 새 정책은 도입하지 않는다. 이 보완은 안내를 어디에 붙이는지에 관한 것이다.

## 수용 증거 정정 — 코드 연결과 물리적 사용성은 분리

onClick 직접 호출은 제품 핸들러/저장 시작 코드 실행 증거다. 포인터 hit test, 키보드 포커스, 버튼 접근성, 실제 사용자 클릭을 증명하지 않는다. 요청서 §1·§4·§6의 '실제 클릭' 완료 표기를 '핸들러 실행'으로 고친다.
같은 세션의 서버 응답 ZIP 내용 검증과 브라우저의 다운로드 시작 표시도 별도 증거다. 디스크 저장 성공으로 합치지 않는다.
제품 기능 연결/ZIP 내용/권한 오류 경로는 수용 가능한 진전이며 도구의 디스크 제한을 제품 결함으로 만들지 않는다. 다운로드 행은 '기능 연결 수용, 사용자 활성화·로컬 저장 실환경 미확인'으로 구분한다.
기존 브라우저에서 안정적인 DOM locator의 정상 click 또는 실제 focus+Enter/Space가 가능하면 최대5분 안에 한 번 확인한다. React 내부 onClick 직접 호출로 이를 대체하지 않는다. 불가하면 NOT_RUN 사유를 남기고 같은 좌표 클릭을 반복하지 않는다. 저장 가능한 브라우저 확보는 별도 수용 항목이다.
새 Studio와 구 ControlPanel 중 어느 쪽을 실행했는지도 각각 기록한다. 양쪽 코드 연결만으로 양쪽 실화면 통과라고 쓰지 않는다.

## 다음 우선 후보 — 앱/보고서/문서 미리보기
