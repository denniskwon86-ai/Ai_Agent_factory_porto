**즉 시험이 없는 게 아니라 덮을 대상이 없다.** 대응표는 이 둘을 구분해 적었다.

⚠️ 다만 **T21(책임자만 변경)은 단독 공백**이다. `owner_scope_node_id` 필드는 있으나
사용자가 바꾸는 명령이 없고, 위 여섯과 달리 **미착수로 선언된 기록도 찾지 못했다.**

### 11.2 구현이 있는데 시험이 0건인 곳이 있었다

메운 것은 §12 에 적는다. 남은 물음은 이것이다 — **프로세스 계열 오류 코드 66개 중 25개가
`tests/` 전체에서 문자열조차 나오지 않는다.**

⚠️ 오류 코드가 시험에 없다는 것이 곧 결함은 아니다. **도달 불가능한 방어 코드일 수도
있다.** 오늘 그중 하나를 답했다(§12.4). 나머지 24개는 **시험을 쓰기 전에 「도달 가능한가」
부터 물어야 한다.** 순서를 뒤집으면 닿을 수 없는 코드에 헛수고한다.

### 11.3 가짜 통과 둘 — 규약이 내 역할로 못박은 유형

AGENTS 가 「**가짜 통과**(오류 없이 조용히 기능이 죽는 경우)를 찾아 회귀로 잠근다」를
Claude Code 역할로 지정한 그것이다. 둘 다 메웠다(§12.3).

## 12. 메운 것 — 전부 줄 단위로 검증했다

**통과했다는 사실만으로는 근거가 되지 않는다.** 차단하는 줄을 하나씩 제거해 대응하는
시험이 실패하는 것을 확인하고 복원했다. 아래 모든 항목이 이 절차를 거쳤다.

### 12.1 준비 미완료 프로젝트의 실행·릴리스 차단 (U23)

### 12.2 같은 표준 업무의 재사용과 충돌 (T11)

### 12.3 가짜 통과 둘 (T07·T23)

두 시험 모두 **데이터가 실재함을 전제로 걸었다.** 비면 검사에 들어가기 전에 실패한다.

- **T23** — 기존 시험은 `ADD_NODE` 합성 문서 위에서 409 와 노드 단계만 본다. 그 문서에는
  바인딩이 없어 「바인딩 손실 없음」은 검사 대상이 없었다. **실제 팩 설치판** 위에서
  같은 저장을 시도하고 세 DB 전체와 해석 문서가 그대로인지 본다.
- **T07** — 기존 `kit_app_contracts` 는 항상 `[]` 였다. **앱 계약을 실제로 승인해 둔 뒤**
  다음 업무키트를 설치하고, 앱 계약이 그대로이며 기존 노드·바인딩이 모두 살아 있고 새
  표준만 더해졌는지 본다. 앱 계약 승인을 빼면 전제에서 실패하는 것을 확인했다.

### 12.4 복구 요청의 클라이언트 차단 4사유 (U26)

다섯 중 `COMMAND_PENDING` 하나만 시험됐다. 나머지 넷(`PROJECT_REQUIRED`·
`CONNECTION_REQUIRED`·`LOCAL_RETRY_LIMIT`·`HEAL_IN_FLIGHT`)을 메웠다.

**서버로 나가지 않고**, 요청 횟수를 쓰지 않으며, 원 실패 근거를 지우지 않고,
**사유마다 다른 안내**를 남기는지 본다 — 문구가 겹치면 실패한다. 뭉뚱그린 안내는
명세가 요구한 「다음 행동」을 알려 주지 못한다.

⚠️ 이 검사에서 **대역 응답을 한 번 감쌌다.** 접수 뒤 store 가 도는 상태 재조회
(`/state/latest`·`/hotl/check`)가 실행 세계의 허용 밖 경로라 stderr 에 스택을 12줄 남겼다.
감싼 것을 **검사에도 썼다** — 접수한 한 건만 재조회를 만들고 차단된 쪽은 만들지 않는다.

### 12.5 못 메운 것 하나 — `PROCESS_PACK_UPGRADE_REQUIRED`

**지금 도달할 수 없다.** `api/routes/process_installation_control.py:28` 이 `(kit_id, version)`
