- 재실행은 동일 결과의 안전한 재사용 또는 명시적 거절 중 실제 구현 계약을 고정한다. 실패 주입 한 번으로 원본/기존 대상 불변을 확인하고, 다음 복원/소비로 결과를 증명한다. 매 함수별 변이 시험은 추가하지 않는다.

## 3. P03.1 — 명시 설치 명령·runtime DDL 분리

**배점15 / 선행 P02.1 수용됨 / 외부승인 없음 / 예상1~2시간(잠정)**.

### 구현 산출물

1. **명시적 설치 CLI**를 만든다. 새 이름은 예를 들어 `scripts/install_first_db_schema.py`이며 이는 제안 파일명이지 기존 파일이 아니다. 도움말·대상 명시·쓰기 없는 계획 확인과 명시 적용을 구분한다. 알려지지 않은 backend, 필수 연결 정보 누락은 실패한다. 연결 문자열/토큰은 출력·보고·커밋하지 않는다.
2. SQLite 기존 설치 경로와 PG 설치 SQL 선택을 재사용 가능한 함수로 연결한다. PG SQL 문장을 SQLite에서 실행한 결과로 PG 성공을 주장하지 않는다. 트랜잭션/중간 실패/재실행 계약을 적고, 실패한 설치를 성공/ready로 기록하지 않는다. 파괴적 DROP·초기화·자동 데이터 삭제는 범위 밖이다.
3. Auth/첫 ECM 경로에 **명시적 관리 스키마 모드**를 연결한다. 관리 모드의 실제 store 인스턴스에서 시작/첫 조회/재조회에 DDL이 없어야 한다. 미설치/불일치는 식별 가능한 실패로 처리하고 자동 CREATE/ALTER, 다른 SQLite로의 fallback, 성공처럼 보이는 빈 목록으로 숨기지 않는다.
4. 기존 기본 SQLite 사용은 보존한다. 전역 환경 변수 하나로 아직 미이관 저장소까지 ready라고 표시하지 않는다. 기존 기본 모드의 새 DB 및 구 schema 보강 순서도 회귀를 막는다.
5. 설치된 schema의 필요한 표·컬럼/버전 확인은 읽기만 사용한다. 관리 모드에서 `_ensure_tables`의 DDL 복구나 `_ready` 캐시가 경계 변경/설치 실패를 숨기지 않는지 확인한다.
6. 실제 application 소비자가 사용할 수 있는 명시적 factory/선택 경로와 집중 실행 검사를 남긴다. 호출되지 않는 플래그만 추가해서 완료 처리하지 않는다. 전체 `main.py` 연결이 필요하면 변경 지점·이유를 먼저 Codex에 보고하고 공동 파일 충돌을 피한다.

### 연결 실행에서 확보할 증거 — 소단계별 별도 검증 묶음 아님

| 사례 | 요구 관측 |
|---|---|
| 명시 installer 적용 | 격리 임시 DB에 실제 schema 생성, 재실행/의도적 실패 처리 계약 확인 |
| 관리 모드 최초 기동·첫 조회·반복 조회 | 실제 store 호출 + SQL trace/연결 경계 계측으로 DDL 호출0 |
| 없는/불일치 schema | 실패, 자동 보강/복구 DDL0, 다른 DB 생성0 |
| 기존 기본 SQLite 새 DB/구 schema | 기존 인증/문맥 사용 유지, 구 컬럼 보강 순서 회귀 없음 |
| 연결/backend 선택 | 주입 연결 실제 사용, 미설정 PG가 SQLite로 바뀌지 않음 |
| 핵심 실패 대조 | 미설치/불일치에서 실제 실패·DDL0을 관측. 모든 가드의 변이 시험은 요구하지 않음 |

일반 동작의 DML까지 모두0으로 요구하는 것이 아니다. 인증/티켓 등의 정상 쓰기는 보존하고 **runtime DDL0**을 검사한다. 미설치 조회의 자동 복구/다른 DB 생성은 별도 차단한다.

실PG 환경이 없어도 **P03.1의 설치/runtime 분리 계약**은 격리 SQLite 실실행과 연결 계측으로 검토받을 수 있다. PG용 installer 경로는 구현하되 실제 PG 적용은 NOT_RUN으로 표기한다. 이것으로 P03.2/3 점수나 전체 PG 호환성을 인정하지 않는다. 기존 SQL 파일을 복사하거나 grep만 통과한 결과로 P03.1을 닫지 않는다.

**실행 순서:** CLI 구현 → 그 CLI로 다음 단계 개발 DB 설치 → 실제 관리 store로 로그인/문맥 사용 → 그 세션으로 티켓 소비 → 재시작/대사. 앞 세 동작의 trace로 P03.1 증거를 얻으며 별도 모의 실행을 중복하지 않는다. PG가 없을 때만 같은 소비 경로의 격리 SQLite 실행을 사용한다. 설치/미설치 위험을 확인한 후에는 Codex 회신을 기다리며 멈추지 말고 승인된 후속 구현을 계속한다. 가산 시에는 앞 단계 수용을 순서대로 기록한다.

### 파일 소유 범위

- 허용: `core/db/`, 필요한 범위의 `core/auth.py`·`core/enterprise_context/repository.py`, 전용 설치 CLI, 직접 관련 시험, 본인 수신/결과 기록.
- 집중 신규 시험 이름 예: `tests/test_db_managed_schema_first_slice.py`(신규 제안). 기존 테스트의 의미를 약화하지 않는다.
- 이번 제외: `frontend/`, `ops_control/`, 정식 release manifest/CI workflows, 전역 startup 전면 변경, 13저장소 전체 이관, 권한 정책·기본 비밀번호 정책·릴리스 승격 정책 변경.

## 4. 후속 두 단계 — 조건 충족 시 이어서 구현/검증

### P03.2 실제 PG 로그인·문맥: 20점 / 예상1~3시간 + 환경 대기

- 실행 선행: P03.1 설치 산출물 사용 가능·미설치 안전 경계 확인, `ENV-PG` 승인 증거. 점수 수용 시에는 P03.1 수용이 먼저다. P03.1의 일반 검토 회신을 기다리느라 안전한 P03.2 구현을 멈추지 않는다. 로컬 구현 지시를 클라우드 생성/유료 환경/운영 DB 쓰기 승인으로 해석하지 않는다.
- 사용 가능한 **승인된 격리** PG/driver 존재부터 읽기 전용으로 확인한다. 없으면 필요한 PG endpoint/전용 DB·schema/설치·runtime 권한/접속정보 전달 방식/담당을 요청한다. DSN 원문은 문서에 남기지 않는다.
- 실제 PG에 첫 schema와 합성 데이터를 명시 설치한다. 로그인·세션·실제 조직 문맥 조회 및 다른 범위 거절을 기존 제품 경로로 수행한다. 별도로 만든 SQL 데모만 성공한 결과는 불충분하다.
- 앞서 확인한 ECM 초안/제품 SQL 차이를 첫 경로 범위에서 해결한다. 권한을 우회해 성공시키거나 미지원 필드를 버려서 맞추지 않는다. 추가 의존 저장소가 필수라면 정확한 호출/최소 변경을 보고한다.
- 설치 권한과 runtime 권한 경계를 명시하고, PG측 관측/권한으로 runtime DDL0을 검증한다. 실제 서버/DB 신원은 비밀 제외한 증거로 남긴다.

### P03.3 실제 PG 티켓·재시작: 20점 / 예상2~3시간

- 실행 선행: P03.2 실제 로그인/세션 산출물 사용 가능 + `ENV-PG` 승인. 점수는 P03.2 수용 뒤 기록한다. 별도 검증 패키지 완료 대기는 넣지 않는다.
- 서로 독립된 PG 연결의 동시 티켓 소비에서 정확히1건만 성공해야 한다. 같은 Python lock으로 직렬화한 시험만으로 대체하지 않는다. 성공 행 수·실패 결과를 함께 기록한다.
- 만료/잘못된 audience/다른 문맥/재소비 거절과 정상 대조를 실행한다.
- SQLite의 빈 문자열 시간값과 PG의 NULL/TIMESTAMPTZ 차이는 이관 변환과 소비 조건을 함께 맞춘다. 특히 `consumed_at`의 `'' → NULL`만 바꾸고 SQL 조건을 유지하지 않는다. 세션 revoked 값과 시간대도 대사한다.
- 합성 자료의 키/건수/중요 필드 대사, 새 process/연결로 재시작 후 유지, runtime DDL0을 확인한다. 서비스의 in-memory 상태를 DB 유지 증거로 쓰지 않는다.
- P03.3 이후에는 결과/잔여 저장소 지도를 넘긴다. P04 전면 이관·cloud 배포·운영 데이터 이동을 자동 착수하지 않는다.

### 환경이 막혔을 때

P03.1 결과를 먼저 검토에 넘긴다. PG 대기 때문에 P03.1을 미완료로 묶어 두지 않는다. 승인 없이 가능한 P03.2/3의 합성 fixture·대사/재시작 harness 준비는 계속할 수 있으나 실PG 수용점수를 미리 주지 않는다. 준비가 끝났다면 같은 시험을 반복하며 시간을 쓰지 말고 **환경 요청 한 건과 준비 완료 범위**를 보고한다. Codex는 독립 C02/D05 작업을 계속한다.

## 5. 시험 운영과 안전 경계

기본은 **P03.1→2→3 하나의 이어지는 소비 시나리오와 묶음 끝 관련 회귀 1회**다. 각 단계마다 아래 명령을 반복 실행하지 않는다. 설치된 같은 DB/합성 자료/발급 세션을 후속 단계에서 사용하고 증거도 재사용한다. 오류가 나면 실패 집합만 재실행한다. 권한 우회·원본 손상·자동 DDL 같은 위험은 해당 경계를 넘기 전에 확인한다. 보안/자료 경계 독립 검토는 실제 적용 전에 유지하되, 다른 구현을 기다리게 하지 않는다.

기존 격리 러너 예시(저장소 루트, 명령은 실행 전 옵션 확인):

```powershell
venv/Scripts/python.exe -X utf8 -B scripts/verify_data_usage_holds.py --target tests/test_db_adapter_first_slice.py --target tests/test_auth_password_verify.py --target tests/test_sse_ticket.py --target tests/test_sse_org_isolation.py --strict-writes
```

위 명령은 묶음 끝 회귀용이다. 꼭 필요한 신규 시험만 추가하고 실제 변경 영향에 따라 ECM 시험을 선택한다. 러너가 읽지 않는 conftest fixture에 의존하면 전용 합성 fixture를 명시 구성한다. 격리/쓰기 보호를 꺼서 통과시키지 않는다. 실행 명령·exit code·pytest 결과·isolation 기록을 결과에 남긴다. 후속 단계가 이미 입증한 정상 경로를 또 다른 대역 시험으로 재작성하지 않는다.

- 운영 `data/`, `library/`, 실제 사용자/원료 자료를 건드리지 않는다. 상대 경로 저장소까지 격리됐는지 확인한다.
- 기존 다른 세션 서버/워크트리/미커밋 파일은 보존한다. 새 외부 DB 생성·서비스 설치·과금·LLM 호출은 별도 승인 필요다.
- 이번 지시에는 fetch/pull/push·공동 변경의 일괄 커밋·운영 배포·운영 DB migration 실행 승인이 포함되지 않는다.
- 동작 시험과 변이 시험을 구분한다. 변이는 자기 변경 범위의 격리 사본에서 수행하고 원복 해시/최종 집중 시험을 확인한다.

## 6. 진척 반영 — P03 전체 완료를 기다리지 않는다

정본 R3: **5300 고정점수 / 53목표 / 139수용 단계**. 발행 시 인정치는 **1800/5300=34.0%**다. 과거21/40=52.5%, 임시22/52, 단순18/53 계산을 현재 점수로 쓰지 않는다.

1. Claude는 단계 구현 결과와 현재 확보된 실행 증거를 같은 결과 문서에 누적하며 후속 단계로 진행한다. 매번 새 검토 요청서를 쓰고 회신을 기다리지 않는다. 수신/실행 상태는 본인 상태 파일에 갱신한다.
2. Codex는 병행 검토하고 P03 연결 흐름 끝에 잔여 검토를 묶는다. 앞 단계가 충분히 입증되면 즉시 수용한다. 전체 PG 이관/전제품 수용을 새 완료 조건으로 덧붙이지 않는다. 결함이면 해당 조건/수정 범위만 회신한다.
3. 검토 수용 즉시 Codex가 실행 원장 해당 step의 evidence/review_status/status와 `PROGRESS.md`를 갱신한다. 공용 원장 단일 기록자는 Codex다. Claude는 자기 검토 요청을 독립 검토 완료로 표기하지 않는다.
4. 수용 뒤 아래 계산기로 실제 동시 작업 결과를 포함해 계산·보고한다. 검토 대기 중에는 **인정점수 / 수용 대기점수**를 분리해서 보여 준다.

```powershell
venv/Scripts/python.exe -X utf8 -B scripts/check_trial_progress.py --markdown --forecast
```

다른 작업 수용이 전혀 없다는 가정에서만 P03.1 수용 후1815/5300=34.2%, P03.2 후1835/5300=34.6%, P03.3 후1855/5300=35.0%다. 이는 **조건부 예시**다. 실제 보고는 계산 결과를 사용한다. 문서 작성·시간 경과·시험 건수·승인 대기에는 가산하지 않는다. 검토 대기가 길어져도 다른 안전한 준비 작업을 막지 않는다.

## 7. 보고·회신 형식

진행 중 첫20~30분 및 이후30분 이내마다 아래를 간략히 보고하고, 단계 완료 즉시 별도 보고한다. 예상시간이 틀어지면 원인/잔여 산출물/새 예상시간을 갱신한다. 4시간 이상 걸릴 단계로 판명되면 의미 있는 산출물 경계로 재분할 제안을 먼저 내고 기존 점수 합을 보존한다.

```text
지시 CLAUDE-P03-R3-01 / 단계 P03.x / 상태 RUNNING 또는 READY_FOR_REVIEW
현재 HEAD / 내 변경 파일 / 다른 세션 변경 보존 여부:
이번에 가능해진 것(사용자·운영 관점 1문장):
완료 코드·실행 증거(명령/결과/증거 경로):
남은 기능 이름·개수 / 다음 작업 / 예상시간:
전체 실제 인정점수·% / 이번 단계 수용 대기점수(혼합 금지):
승인·환경 장애물 / 필요한 한 가지 조치 / 담당:
미실행과 제외 범위 / 운영 자산 불변 확인:
```

결과는 새 날짜 문서를 계속 늘리지 말고 `docs/handoff/CLAUDE_P03_EXECUTION_RESULT.md`(신규 권장)에 단계별로 축적하고 팀보드에서 연결한다. 검토 요청에 파일별 핵심 diff, As-Is 대비 결과, 재현 명령, 실제 PG 여부, 남은 위험, 되돌릴 임시 자산을 담는다. Codex가 검토하지 않은 항목을 완료로 만들지 않되, 이미 수용된 작은 단계를 상위 목표 미완료를 이유로 되돌리지 않는다.

**지금 할 일: 수신 기록 → P03.1 구현 → 그 산출물을 소비하는 P03.2/3의 승인된 경로로 계속 진행. 단계별 검증·리뷰 대기를 만들지 않는다. 기존 OPS-P1/DEP 보완 재수행이나 새 진척 분모 설계로 돌아가지 않는다.**
