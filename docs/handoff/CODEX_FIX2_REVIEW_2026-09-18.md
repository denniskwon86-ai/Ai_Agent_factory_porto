## 1. 기존 지적의 판정

- FIX2의 네 기존 지적(방향 delta, 조기 return 전 복원 표시 소비, 대상 배타 정리/new·release 주소 의도, 보호 예외 fail-closed)은 코드에 반영됐다. 이 네 수정의 정적 검토는 수용한다.
- 이전 P1 초안 응답 오염은 앞선 검토에서 종결한 상태를 유지한다. 다시 같은 검사를 전면 반복하지 않는다.
- 브라우저 같은 문서 표식과 앞/뒤 취소·승인, 다음 클릭의 기록 확인은 이전 보고보다 증거가 명확하다. Claude 실측이며 Codex 독립 실행으로 표시하지 않는다.
- 전체 SINGLE-ENTRY 수용은 아래 경계 처리와 명시된 실화면 잔여를 닫은 뒤 판정한다. 범위를 새로운 기능 설계로 확대하지 않는다.

## 2. ROUTE-AUTHORITY: fixture 오류 해결 방향 수용

enforced_org + 임시 auth.db + 실제 세션 토큰 + 권한 강제/비무제한 대조군은 적절하다. real_auth 표식 등록은 principal 주입을 추가한 것이 아니다. 제품 권한 정책을 바꾸지 않았다.
격리9PASS/exit0 및 보호자산 불변은 Claude 보고로 기록한다. 검토 요청서에 해당 실행의 isolation.json/pytest 결과 경로 또는 보존된 증거 파일을 추가하면 4 ERROR 부채를 증거와 함께 종결할 수 있다. 운영에서 재실행하지 않는다.

program disable의 변이 미탐지는 라우트 자체 _admin의 이중 방어로 설명된다. 이를 탐지하려고 제품 역할 조합을 만들거나 _admin을 제거하거나 문구 단언을 추가하지 않는다.
- 기존 probe는 viewer 거절의 증거로 유지한다.
- 해당 경로의 표 등록 자체를 고정할 필요가 있으면 시험에서 정확한 method/path→cap 매핑을 직접 단언한다. 이것은 선언 계약 검사이지 런타임 표 단독 효력 증명은 아니다.
- 나머지 세 probe/라우터 의존성 변이의 범위와 구분한다. 6/6 변이 달성 자체를 완료 목표로 삼지 않는다.

## 4. 남은 P2 한 묶음: 히스토리 번호의 안전 경계

App 436~444행은 incoming/here가 null이면 canLeaveNow를 거치지 않고 move()한다. 번호가 없다는 것은 앱 밖이라는 증거가 아니다. 같은 문서에서 다른 코드가 history 항목을 만든 경우에도 state가 없을 수 있고, 이때 beforeunload로 대신 보호된다고 볼 수 없다. 번호 없는 항목에서는 입력 보호가 없다는 보고를 안전한 동작의 승인으로 해석하지 않는다.
또한 두 항목의 __studioIndex가 같으면 delta=0인데, 현재는 그대로 go(-delta)/go(delta) 경로로 들어간다. 시험의 historyStub은 이동 위치가 같으면 무조건 아무 동작도 하지 않게 되어 있어 이 경계를 증명하지 못한다. 번호에는 유효한 정수/동일 관리 구간 여부 검사도 없다.

다음 첫10~15분:

1. 같은 문서의 미관리(state 없는) 목적지로 이동할 때 미저장 편집기를 무조건 내리는 경로를 좁은 시험으로 재현한다. 동일 번호/0 delta도 한 건 검사한다.
2. 위치를 모르면 방향/칸 수를 추측하지 않는다. 확인 전 파괴적 apply를 막고 입력을 보존하며 명시적인 이동 선택을 제공하는 안전한 fallback을 정한다. URL·화면 불일치를 조용히 숨기지 않는다. 외부 문서로 나가는 정상 이동은 기존 보호를 유지한다.
3. 동일 번호/유효하지 않은 번호에서 go(0) 또는 잘못된 delta 이동을 하지 않는다. 앱이 관리하는 구간의 유효한 번호일 때만 현재 역이동 방식을 사용한다. 구현은 기존 history 처리에 한정하며 새 라우터 도입 금지.
4. 일반적인 번호 있는 앞/뒤 취소·승인 동작은 보존한다. 이 묶음을 완료하려고 전체 변이/서버 회귀를 반복하지 않는다.
