## 1. 검토 판정과 순서

**단건 릴리스 조회의 가시성 누락은 P1. 첫 실행 묶음으로 보완한다.** 서버 역할/권한표를 새로 정하는 것이 아니라 목록에 이미 있는 열람 경계를 단건에도 적용한다. Codex는 소스·보고서 정적 대조만 수행했다. 197 PASS·contracts157·build·변이6종은 Claude 보고값이며 독립 실행값이 아니다.

앞 회신의 공용 useExecutionPending 재사용·기존 원요청 조회 UI·저장 라벨 정렬·폐쇄 수정 POST 제거 방향은 수용한다. 앱 전체 재설계/구 화면 추가 기능 개발로 확대하지 않는다.

다만 ControlPanel 상단 tellCommandResult 주석에는 아직 「유료 LLM 재실행 … 둘 다 실측했다」가 남아 있다. LLM0 보고 및 앞선 과장 정정과 충돌하므로 **주석의 실측 주장만 정정**한다. 위험 가능성과 실제 관찰을 나눈다. 이를 위해 제품·시험 전면 작업을 다시 열지 않는다.

## 2. 첫 묶음: RELEASE-READ-VISIBILITY-01

### 확인한 코드

- api/routes/factory_control.py의 list_releases는 assert_identified와 viewing_context, _visible_projects_with_reasons를 사용하고 project_id가 가시 집합 밖이면 제외한다.
- get_release는 경로 ID를 확인하고 JSON을 읽지만 같은 주체/프로젝트 가시성 검사가 없다. 이어서 승격·lifecycle 정보와 본문을 반환한다.
- 따라서 보고된 목록/단건 불일치를 코드에서도 확인했다. **타 회사 자료 유출 실증**과는 구분한다. fixture의 소유 프로젝트가 없다는 것과 실제 타 문맥 자원이라는 것을 섞지 않는다.

### 결정: 기존 목록 규칙에 맞춘 fail-closed

1. 목록과 같은 식별 주체 검사·검증된 viewing_context·가시 프로젝트 판정을 재사용한다. 새로운 역할/관리자 예외를 만들지 않는다.
2. release의 project_id가 비었거나, 소유 프로젝트가 없거나, 가시 집합에 없으면 단건에서 본문을 반환하지 않는다. **없는 릴리스와 같은404 응답 계약**으로 은닉한다. 제목·코드·문서·승격·감사 정보도 응답에 싣지 않는다.
3. 사용자에게 보이지 않는 원인을 「타 회사」「소유자 없음」 등으로 세분해 노출하지 않는다. 기존 인증 오류 및 문맥 해석 실패503 등은 기존 계약대로 유지한다. 모든 장애를404로 덮거나 예외를 공개 허용으로 처리하지 않는다.
4. project_id를 읽기 위해 JSON을 읽는 것은 가능하나, 가시성 확인 전에 승격/lifecycle 등 부가 조회와 응답 구성을 진행하지 않는다. 기존 경로 ID 검증 유지. 잘못된 JSON/ID 불일치 등 손상 자료에서 예외 원문·파일 경로를 노출하지 않는다.
5. **고아 릴리스는 자동 귀속·삭제·공개하지 않는다.** 현재 API에서 차단하고 자료는 보존한다. 운영 자료의 소유권 교정/마이그레이션은 별도 승인 사항이다. 격리의 정상 양성 fixture는 실제 존재하고 가시성이 있는 합성 프로젝트에 명시적으로 결속한다. 기존 고아 fixture도 음성 대조로 유지할 수 있다.
6. 읽기 경로에서 파일/DB를 자동 생성·수정하지 않는다. 권한표·역할·contexts/select·CORS 변경 없음.

### 같은 함수에서 추가로 확인한 안전 경계

get_release의 lifecycle 처리 마지막 except는 현재 lifecycle을 unknown으로만 바꾸고 실행 payload가 남은 data를 반환한다. **상태 조회 장애 시에도 코드가 제공될 수 있는 경로**다. 실서버 장애 유발 증거는 아니며 정적 발견이다.
이번 동일 함수 보완에서 상태 확인 실패를 사용 가능으로 취급하지 않게 한다. 기존 실패 계약에 맞는 안전한 오류 또는 실행 payload 제거 중 호환되는 최소안을 사용하고, 임의 예외 문자열을 반환하지 않는다. 비가시404와 가시 대상의 상태 조회 장애를 혼동하지 않는다. 기존 disabled의 메타데이터 보존/실행 payload 차단은 유지한다. candidate Preview 정책을 임의로 바꾸지 않는다.

### 집중 검증 / 완료 기준

- 현재 가시 프로젝트의 정상 릴리스: 목록 포함/단건200, 기존 소비자 정상.
- **실재하는** 다른 문맥 또는 읽기 권한 없는 프로젝트의 릴리스: 목록 제외/단건404, 없는 릴리스와 응답 동일. 없는 프로젝트를 넣고 권한 검증이라 하지 않는다.
- project_id 없음·존재하지 않는 소유 프로젝트: 동일404, fixture/원문 불변.
- 비식별 주체·문맥 판정 장애·가시성 없음: 기존 계약대로 거절, 본문0.
- 가시 대상 disabled: 메타데이터 정책 유지/실행 payload0. lifecycle 조회 장애도 실행 payload0.
- 가시성 가드 제거 시 타 문맥 음성 시험이 실패하고, 양성은 통과하도록 최소 극성1건. 전체 변이 캠페인을 새로 시작하지 않는다.
- 기존 test_release_list_visibility의 가시 집합 대역만으로 실제 권한을 입증하지 않는다. 격리 안 존재하는 프로젝트/소유 메타와 실제 판정 경로를 이용한 대조를 적어도 하나 둔다.
- 시험용 계정·프로젝트·릴리스 결속은 **격리 뿌리에서만** 허용한다. 운영 자료/권한 수정이나 외부 전송은 허용하지 않는다. 임의 회사 소유라고 이름 붙인 것만으로 교차 회사 증거가 되지 않는다.
- 수정 후 동일 직접 링크가 거절되고 가시 릴리스는 열리는 브라우저 대조. 변경 전 증거를 수정 후 수용으로 재사용하지 않는다.

예상: 첫20~30분에 보완·집중 시험 중간 결과, 후속10~20분에 회귀/브라우저 대조. 시간은 추정이며 미완료를 통과로 표시하지 않는다. 관련 서버 시험만 실행, 프런트 제품 미변경이면 전체 프런트 build 반복 불필요.

## 3. 판단 요청 세 건

### A. 사용 재개 active: 「원래 상태 원복」 판정 보류

core/program_lifecycle.py의 reactivate는 무조건 set_status(ACTIVE)다. 같은 파일은 candidate를 아직 승인되지 않은 Preview 후보로 정의하고, core/app_preview.py의 audience_for_state는 candidate와 active의 실행 청중을 구분한다.

**candidate→disabled→active를 원복 완료로 인정하지 않는다.** 현행 코드대로 움직였다는 것과 제품 정책상 옳다는 것은 다르다. 실제 운영 실행/권한 우회가 입증됐다고도 쓰지 않는다.

첫 권한 묶음 후 **10~15분 한정 조사**: 재개와 일반 status 경로, 승격 경로가 ACTIVE에 부여하는 의미를 대조한다. candidate 출신은 candidate로, deprecated 출신은 경고를 유지하는 복원이 가능한지 이력·데이터 지문 보존·원자성을 포함한 최소안을 제시한다. 이력 불명확하면 임의로ACTIVE를 추정하지 않는 방향이다. 서버 전이 정책을 이번 문서만으로 일괄 변경하지 않는다. 실제 승격/운영 실행도 금지.

보고 수정: 「사용 중단·이력 보존 확인 / 사용 재개 호출 확인 / 이전 상태 복원 미완료」. 이미 active가 된 격리 fixture를 원복 완료라 쓰거나 감사 이력을 지우지 않는다.

### B. 같은 이름의 두 판: 최소 라벨 보완 진행 가능

기존 이름에 **생성 시각 + 구별 가능한 release_id**를 붙인다. 시각만 같을 수 있으므로 시각만으로 구별하지 않는다. 시각 미기록은 미기록으로 표시하고 만들지 않는다. 상태 변경 확인창에도 실제 선택한 판 ID를 보여 준다. 선택값은 기존 release_id 유지, 제목/저장 데이터 변경 없음. 기존 formatter가 있으면 재사용하고 롤백 선택 목록·확인창 중심으로 제한한다. 전체 앱 라벨 개편 불필요. 첫 보안 묶음 이후 예상10~15분.

### C. 문서 이탈 보호: 보고의 원인 해석 정정 필요

BuildStartDialog.tsx에는 입력/미저장·PENDING/UNKNOWN 조건의 beforeunload가 이미 있고, AdaptiveProductionStudio.tsx에도 studioInputMemory.hasInputs를 보는 beforeunload가 있다. studioLeaveGuard 주석은 **문서 이탈 보호가 앱 내부 보호를 대신하지 못한다**는 뜻이지, 문서 이탈을 보호하지 않는 설계라는 뜻이 아니다.

앱 내부 이동 증거는 수용한다. 문서 이동에서 사라진 관찰도 보존하되 **원인은 미확인**으로 고친다. 새 beforeunload를 중복 추가하지 않는다. 어떤 컴포넌트·입력 상태에서 기존 보호가 등록됐는지, 실제 사용자 입력 후 이벤트/브라우저 확인창/취소/계속 이동이 각각 어떻게 됐는지 제한 재현한다. 브라우저 또는 자동화가 확인창을 처리했는지도 분리한다. 도구 한계이면 NOT_VERIFIED이지 의도된 무보호가 아니다. 새로고침·종료·강제 종료의 영구 저장을 보장하지 않는다.

## 4. 수용·진척·다음 보고

이번 기록은 **합성 자료를 사용한 개발 검증**이다. 실제 로그인/실포인터 사용만으로 영역 전체의 실제 업무 반복 수용을 대체하지 않는다.

- 진입·앱 내부 이동·오류: 보고된 합성 범위 수용 증거 인정.
- 사용 중단·감사·옆 판 불변: 증거 인정. 원래 상태 복원은 보류.
- 권한: P1 보완/수정 후 재검증 필요.
- 문서 이탈 보호: 원인 미확인.
- 반복 업무: 실제 사용자·자료·범위 필요. D07/유료 제작 승인 대기는 별도.

따라서 「4건 완전 마감/잔여2건」을 그대로 전체 D01 출구로 쓰지 않는다. **3흐름 범위 내 확인, 중단/재개 부분 확인, 미해결 권한·복원 의미·문서 이탈·반복 업무**를 각각 기록한다. 라벨은 선택 안전성 보완이다.
전체21/40=52.5%, 로컬18/28=64.3%는 **마지막 인정치** 유지. 이번 검토는 전영역 재인증이 아니며 연결 단계 재개방 대상인지 권한 보완 후 증거에 대조한다. 현재 결함을 둔 채 해당 경로 연결 정상이라고 보고하지 않는다.

다음 보고는 우선 권한 한 건의 수정 파일·정상/거절 대조·남은 조건·다음 예상 시간만 간결히 낸다. 이미 닫힌 SSE/문맥·미리보기 재조사, 전체 pytest/변이 반복, 구 UI 기능 확장은 하지 않는다.

Codex는 제품·시험을 수정/실행하지 않고 본 회신/팀보드만 기록했다. Claude 수신/착수는 미확인. 커밋·푸시·서버 철수·원복 실행 지시 없음. 운영 사용자 로그·기존 dirty 파일·타 세션 보존. 비용 발생/외부 게시/실데이터 변경은 별도 사용자 승인 필요.
