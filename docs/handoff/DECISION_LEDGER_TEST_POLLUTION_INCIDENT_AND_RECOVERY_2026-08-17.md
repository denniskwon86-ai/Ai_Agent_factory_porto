# Decision Ledger 시험 오염 사고 및 복구 인계서

- 사고 ID: `INC-LEDGER-20260817-01`
- 작성 주체: Codex
- 작성 사유: I-4 4c-2 시험이 운영 `data/decision_ledger.db`에 기록된 사고의 범위와 복구 결정을 팀 전체에 인계하기 위함
- 상태: **4c-2 HOLD / 운영 원장 쓰기 금지**
- 기준일: 2026-08-17 (Asia/Seoul)

## 1. 최종 판정

현재 `data/decision_ledger.db`에서 행을 삭제하거나 수정하지 않는다. 시험 행마다 `CORRECTION` 이벤트를 추가하지도 않는다. 정상 백업이 확인되지 않았고, 오염이 이번 36건에 국한되지 않으므로 선택적 복원도 수행하지 않는다.

다음 방식으로 복구한다.

1. 현재 원장 전체를 **읽기 전용 포렌식 원장**으로 보관한다.
2. 해시·행 수·체인 검증 결과·오염 분류 규칙을 포렌식 매니페스트에 남긴다.
3. 신규 빈 `data/decision_ledger.db`를 활성 운영 원장으로 시작한다.
4. 시험 하니스가 원장 경로를 구조적으로 격리하고, 운영 원장 불변 검사를 통과한 뒤에만 4c-2 시험을 재개한다.

이 결정은 운영 데이터 삭제가 아니다. 기존 원장은 증거로 보존하고, 신뢰 가능한 활성 기준선만 새로 시작한다. 과거 행 중 일부를 선별 이관하지 않는다. 현재 증거만으로 실제·데모·시험 기록을 완전하게 구분할 수 없기 때문이다.

## 3. 근본 원인

`tests/conftest.py`가 여러 운영 DB와 파일을 격리하지만 `decision_ledger.db`는 격리 대상에 없었다. 새 시험의 `DecisionLedger()`가 기본 경로를 사용하면서 운영 원장에 직접 기록했다.

추가 함정이 있다.

```python
_DB_PATH = data_path("decision_ledger.db")

class DecisionLedger:
    def __init__(self, db_path: str = _DB_PATH):
        ...
```

파이썬 기본 인자는 함수 정의 시점에 결속된다. 시험에서 모듈의 `_DB_PATH`만 바꿔도 이후 `DecisionLedger()`는 원래 운영 경로를 계속 사용할 수 있다. 또한 이미 다른 모듈이 가져간 전역 `decision_ledger` 객체의 별칭은 모듈 변수 재할당만으로 바뀌지 않는다.

## 4. P0 복구 절차

### P0-L1. 생성자와 전역 싱글턴 격리

1. `DecisionLedger.__init__`의 기본 경로를 호출 시점에 해석하도록 바꾼다.

   ```python
   def __init__(self, db_path: str | None = None):
       self.db_path = _DB_PATH if db_path is None else db_path
   ```

   `db_path or _DB_PATH`는 사용하지 않는다. 호출자가 빈 문자열을 명시한 오류를 운영
   기본 경로로 조용히 되돌리기 때문이다. 명시된 빈 경로는 경로 검증에서 실패해야 한다.

2. autouse fixture에서 `_DB_PATH`를 `tmp_path / "decision_ledger.db"`로 바꾼다.
3. 기존 전역 `decision_ledger` 객체를 교체하는 데 그치지 않고, 그 객체의 `db_path`를 같은 임시 경로로 바꾼다. 이미 import된 별칭까지 잡기 위함이다.
4. 격리 초기화가 실패하면 즉시 `pytest.fail`한다. 운영 경로로 폴백하지 않는다.
5. autouse fixture 이전의 **테스트 수집·모듈 import 시점**도 격리한다. 전역
   `decision_ledger = DecisionLedger()`는 fixture 실행 전에 DB를 열기 때문이다. pytest가
   테스트 모듈을 import하기 전에 전용 임시 경로를 환경으로 주입하거나 전역 원장을 지연
   초기화해야 한다. fixture에서 사후 교체하는 것만으로는 수집 시점 운영 DB 접촉을 막지 못한다.

### P0-L2. 하니스 불변 조건

다음 회귀가 모두 필요하다.

1. 인자 없는 `DecisionLedger()`가 임시 경로를 사용하는가.
2. 소비자 모듈이 미리 import한 전역 싱글턴을 통해 기록해도 임시 DB에만 쓰는가.
3. 임시 원장에 시험 이벤트가 실제 기록되는가.
4. 전체 pytest 세션의 시작·종료 시 운영 원장의 경로·행 수·최대 seq·tail event hash가 동일한가.
5. 운영 원장과 `-wal`·`-shm` 파일을 시험이 새로 만들거나 변경하지 않는가.
6. 격리 경로가 workspace의 운영 `data/` 아래로 해석되면 즉시 실패하는가.
7. 새 Python 프로세스가 테스트용 경로를 받은 뒤 `core.decision_ledger`를 최초 import해도
   운영 원장과 WAL/SHM을 건드리지 않는가.

파일 해시만 검사하지 않는다. SQLite checkpoint만으로 파일 바이트가 달라질 수 있으므로
**논리적 센티널(행 수·최대 seq·tail hash)**도 함께 검사한다. 활성 WAL을 무시하는
`immutable=1` 조회 결과만으로 불변을 판정하지 않는다. 별도 프로세스에서 `mode=ro`로
읽거나 SQLite Backup API로 만든 일관된 읽기 사본을 사용해 WAL까지 포함한 최신 상태를
비교한다. 센티널 검사가 운영 원장에 `-shm`을 만들 수 있으므로 메인 pytest 프로세스에서
직접 열지 않는다.

### P0-L3. 포렌식 보관

백엔드·시험 프로세스를 모두 정지한 뒤 수행한다.

1. WAL이 존재하면 SQLite checkpoint 또는 SQLite Backup API로 일관된 사본을 만든다.
2. 보관 예시: `data/archive/decision_ledger_polluted_20260817.db`
3. 원본 SHA-256, 사본 SHA-256, 행 수, tail hash, `verify_chain` 결과를 대조한다.
4. 포렌식 매니페스트에 본 문서 경로와 오염 분류 쿼리를 기록한다.
5. 보관 파일은 제품의 활성 원장 조회 대상에서 제외하고 읽기 전용으로 둔다.

### P0-L4. 신규 활성 원장

1. 포렌식 사본 검증이 끝난 뒤 기존 파일은 포렌식 이름으로 이동한다.
2. 제품 초기화 경로로 신규 빈 `data/decision_ledger.db`를 만든다.
3. 구 원장에서 행을 선별 복사하지 않는다.
4. 별도 사고 매니페스트가 구·신 원장을 연결한다. `CORRECTION` 이벤트를 초기 이벤트로 오용하지 않는다.
5. 원장 재시작을 원장 자체에도 기록하려면 전용 이벤트/subject 계약을 먼저 설계하고 테스트한다.

### P0-L5. 재검증

1. 원장 집중 회귀 실행.
2. 4c-2 집중 회귀 실행.
3. 깨끗한 checkout 전체 회귀 실행.
4. 작업 트리 전체 회귀 실행.
5. 두 실행 모두 운영 신규 원장의 논리적 센티널과 파일 상태가 불변인지 확인.
6. 실패 0건과 오염 0건을 확인한 뒤 4c-2 HOLD를 해제.

## 5. 금지사항

- 현재 11,627행의 삭제·수정 금지
- 11,585건에 대한 대량 `CORRECTION` 생성 금지
- 정상 백업이 없는 상태에서 추정 복원 금지
- 실제·시험 행을 이름만 보고 선별 이관 금지
- 원장 격리 전 pytest 재실행 금지
- `except: pass` 또는 경고 후 운영 경로 폴백 금지
- 사용자 지시 없이 `origin` push 금지

## 6. Claude Code 수행 지시

1. 현재 4c-2 제품 변경은 폐기하지 말고 그대로 보존한다.
2. 다른 기능 구현보다 P0-L1·L2를 먼저 별도 원자 커밋으로 완료한다.
3. 격리된 DB에서 4c-2 회귀를 다시 실행한다.
4. P0-L3·L4는 파일 이동을 수반하므로 실행 직전 대상 경로·프로세스 정지·사본 검증 결과를 Supervisor에게 보고한다.
5. P0-L5가 끝날 때까지 4c-2를 완료로 표시하지 않는다.
6. 보고마다 누가, 왜, 무엇을 기록했는지 남긴다.
