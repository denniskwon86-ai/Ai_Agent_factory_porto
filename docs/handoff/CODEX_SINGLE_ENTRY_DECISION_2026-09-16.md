# SINGLE-ENTRY-01 — 히스토리 UX 결정 및 실행 지시

작성: Codex · 2026-09-16 KST. 사용자 전달 Claude 보고와 공유 App/상태 문서를 읽기 검토.
로드맵 권고10/G3의 기존 진입 수용 범위다. 구현·검사는 Claude 단독, Codex는 지시·검토 담당.

## 결정: A — 히스토리 항목의 URL을 현재 권한으로 다시 연다

뒤로/앞으로는 실제 이전/다음 URL의 화면으로 간다. 대상 링크면 재검증하여 열고, 목록 URL이면 목록을 연다.
B처럼 모든 뒤로가기를 목록으로 치환하지 않는다. 현재 앱 밖의 이전 페이지로 나가는 정상 뒤로가기를 붙잡지 않는다.
재실행은 조회와 화면 복원만 뜻한다. 저장·승인·배포·생성을 재실행하거나 과거 권한을 복원하지 않는다.
인증 대기 중에도 진입 URL을 보존하고 로그인/회사 보정 완료 뒤 현재 문맥으로 확인한다.

## 현재 수정 검토

- routeRestored 초기값에 kitApp/draft를 포함한 변경을 소스에서 확인했다. 대기 중 대상 유실 방지에 맞는 수정이다.
- 하지만 App의 URL 동기화 effect는 routeRestored=true가 되면 target/draft_kind/draft/revision/instance/app/release/mega/child를 지운다. 따라서 초기값 시험 하나로 열린 대상의 새로고침/히스토리 수용까지 입증되지는 않는다.
- release/new도 초기값 대상에는 없다. 각각 열린 상태를 어떻게 주소로 표현할지 함께 처리해야 한다. 완료한 mega가 일반 project로 바뀌며 부모/자식 의미를 잃는지도 확인한다.
- 프런트 44+17+25+25+14+36=161 PASS와 build PASS는 Claude 보고값. Codex는 재실행하지 않았다.
- DRAFT-OPEN-01의 Gate children 연결은 존재한다. 그 전체 기능/실화면 수용을 이번 정적 검토만으로 승인하지 않는다.
- 서버 중지/워크트리 삭제/타 세션 보존은 Claude 보고다. Codex가 별도 실측한 사실로 쓰지 않는다.

## 구현 계약 — 단순하고 좁게

1. 주소 복원, 앱 내부 이동, 뒤로/앞으로가 동일한 진입 해석/적용 경로를 사용하게 한다. 초기 useRef 값을 한 번 소비하는 구조만으로 popstate를 처리하지 않는다. 새 라우팅 프레임워크 도입과 앱 전체 재설계는 이번 범위 밖이다.
2. 사용자가 다른 공간/대상을 여는 명시적 이동은 히스토리 한 칸을 추가한다. 동일 대상/동일 의미의 중복 이동은 추가하지 않는다. URL 정규화·상태 정리는 현재 칸만 교체한다. popstate에 대한 화면 복원에서는 새 칸을 만들지 않는다.
3. 열려 있는 대상은 새로고침으로 재현 가능한 URL을 유지한다. project ID, mega 부모/자식, kit_app instance/app, draft kind/ID/revision, release ID를 잃지 않는다. 파서가 인정하는 정규형을 사용하고 관련 없는 쿼리/hash/history.state를 무단 제거하지 않는다.
4. target=new는 빈 만들기 화면 복원이며 자동 생성이 아니다. 닫은 뒤에는 목록 등 실제 목적지 URL로 이동한다. 뒤로가기로 new에 돌아오면 빈 화면 또는 같은 문맥의 보호된 기존 입력만 복원한다. URL/history.state에는 초안 원문·자격 증명·권한 판정을 넣지 않는다.
5. popstate/대상 변경 시 이전 Gate·요청을 무효화하고 목적지를 현재 사용자/회사 문맥에서 다시 검증한다. 실패는 그 대상의 거절 화면으로 표시한다. 목록으로 조용히 대체하거나 이전 대상 내용을 남기지 않는다. release 기존 요청 세대 통제도 유지한다.
6. 미저장 입력은 앱 이동과 뒤로/앞으로 모두 보호한다. 확인 취소 시 현재 입력/화면/URL을 일치시키고 히스토리를 증식시키지 않는다. 브라우저 이동 후 이미 URL이 바뀐 경우의 취소 복원까지 좁은 계획에 명시한다. 외부 페이지 이동/새로고침은 기존 beforeunload 보호를 사용한다. 단순 preventDefault만으로 popstate 취소가 된다고 가정하지 않는다.
7. StrictMode 개발 재마운트 자체를 결함으로 보거나 서버 확인을 생략하지 않는다. 늦은 결과 미반영·중복 화면 commit/쓰기 0회를 우선 검증하고, 안정된 동일 진입에서 불필요한 중복 조회가 있으면 원인을 좁혀 제거한다. 광범위한 권한 캐시를 추가하지 않는다.

## 순서와 시간 제한

- 첫 20~30분: ACK/RUNNING → 짧은 상태 전이 계획 → 공통 진입 적용 및 URL 보존/히스토리 연결 구현. 실제로 작동하는 왕복 경로 하나를 먼저 보고한다.
- 후속 15~25분 예상: 아래 수용 검사와 실제 브라우저 확인. 첫 묶음 미완료면 남은 구현과 수정 ETA를 보고하며 완료로 포장하지 않는다.
- 검사 범위: project/mega/kit_app/draft/release/new의 처음 열기 및 새로고침; 목록→초안→릴리스→뒤로→앞으로; 로딩 중 다른 대상 이동; 문맥 변경; 미저장 입력 이동 취소; 닫기; 잘못된/거절 링크.
- 초기식 실행 시험은 보존하되 실제 전이 결과(URL·화면 대상·요청·commit)를 확인하는 검사를 추가한다. 안정된 수정 후 관련 프런트 회귀/build 한 번, 서버 무변경이면 전체 서버 회귀 반복 금지. 모든 줄의 변이 검사를 확대하지 않는다.
- 최소 실제 제품 브라우저 경로: 로그인→지정 초안 열기→새로고침→목록 이동→뒤로/앞으로. mock/fixture 검사는 실서버 제품 연결 결과와 구분한다. 도구/환경 제약은 NOT_RUN으로 정직하게 기록한다.

## 격리 환경과 진척 관리

- 이미 확보한 격리 기동 절차는 개인 메모리에만 두지 말고 저장소 문서의 정확한 경로를 보고한다. 명령·포트·합성 데이터·검증 절차·종료/복구 방법을 남기되 운영 데이터/비밀키를 추가하지 않는다.
- 이번 히스토리 수용 검사가 끝나기 전에 재사용할 환경을 다시 만들었다 지우는 반복을 피한다. 필요한 동안 유지하되 불필요한 서버는 종료한다. 추가 worktree 삭제/force 제거는 이번 지시가 아니다.
- 전체21/40=52.5%, 로컬18/28=64.3% 유지. 구현 결함 1건 종결과 전체 수용 관문은 분리한다. 정본 완료 조건과 증거가 충족된 칸만 가산한다.
- 20~30분 보고: 사용자 동작의 변화, 완료/남음, 검증 종류별 결과, 전체 진척, 다음 ETA. 기존 미검증/권한표 오류를 숨기지 않는다.
- 사용자 변경/데이터/타 세션 작업 보존. 제품 단독 작성자는 Claude. Codex는 문서만 작성했다. 커밋·푸시·pull·데이터 복원 지시 없음.
- 수신 확인 전 자동 전달/착수로 보고하지 않는다.
