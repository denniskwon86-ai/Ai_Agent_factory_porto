# 업무키트·초기 데이터 보강 실행 기록

기록일: 2026-09-08 · 기획 및 개발: 권혁일(Hyuk il Kwon)

## 1. 이번 작업의 목적과 범위

업무키트는 CSV 묶음이 아니라 **데이터 계약·현업 입력·규칙·에이전트 구성·계산·결과 활용**을 묶은 실행 자산이다. 구매·생산·판매의 업무 결과가 같은 회사, 기준일, 기준선, 전사 시나리오에 연결되는 것을 완료 기준으로 한다.

진행 순서는 짧은 업무키트 사용성 보강 → PostgreSQL 전환 → 서비스 서버 → 현업 사용 및 데이터 확장이다. 저장소 전환 준비는 병행하지만 이번 변경으로 DB를 바꾸거나 새 서버를 구매하지 않는다. 샘플과 실제 입력은 같은 제품 경로를 사용하되 **자료의 성격·출처·사용 가능 상태는 구분**한다.

## 2. 정확한 모수

정본: `core/data_preparation/business_kits.py`, 비철금속 패키지 `1.0.0/manifest.json`.

| 구분 | 데이터 계약 수 | 현업이 할 일 | 관련 앱/현재 주의점 |
|---|---:|---|---|
| 공통 기반팩 | 11 | 조직·품목·거래처·창고·BOM·계정·단위 정렬 | 모든 앱의 공통 참조; 조직 파일과 실제 권한 설정은 별개 |
| 구매·원료 도입관리 | 2 | 계약·발주·납기와 도입 지연 검토 | 원료 도입 앱; 환율/가격 모델까지 실행된다고 확대하지 않음 |
| 국제물류·도착관리 | 5 | 예정/실제 사건과 도착 현황 확인 | 물류 사건 앱은 현재 조회 중심 |

| 품질·Lot 추적 | 2 | 검사·Lot·근거 문서 조회 | 품질 데이터가 있다고 자동 품질 판정이 완성된 것은 아님 |

인사·투자·자산 등 기업 전체 업무가 8영역으로 모두 구현됐다는 의미도 아니다. 우선 비철금속 구매→생산→판매→재무 경로를 실제로 사용할 수 있게 만들고, 후속 영역은 같은 6요소 계약으로 확장한다.

## 3. 이번 구현

### 현업 시작 안내와 자료 등록 연결

- 데이터 준비 화면에서 업무영역을 펼치면 **예시 질문 / 준비할 자료 / 대조할 것 / 결과 활용 / 현재 사용 범위**를 제공한다. 공통 기반팩을 포함한 9개 안내가 있다.
- 서버가 돌려준 업무영역과 데이터만 표시한다. 정본 패키지와 개정이 다른 경우 이 안내를 억지로 재사용하지 않는다.
- 데이터 행의 `자료 준비`로 해당 자료의 원천·등록 행에 이동한다. 회사/범위를 대신 선택하거나 파일을 자동 업로드하지 않는다.
- 자료 등록과 품질·대사 검사 이후 준비도를 새로 조회한다. 문구만 초록으로 바꾸지 않는다.
- 적용본을 빠르게 바꿨을 때 이전 응답이 다른 적용본의 데이터로 표시되는 것을 막는다.
- 일반 자료 등록 행의 기술 계약키 표시를 제거한다. 이름 없는 자료는 결손 문구로 표시한다.
- 등록된 행 수를 원천 행 수로 그대로 넘기던 자기 대조를 제거했다. 원천 파일/추출 보고서에서 독립적으로 확인한 행 수를 입력해야 검사 버튼이 활성화된다. 행 수가 같다고 금액·수량·업무 연결 대사까지 통과한 것으로 간주하지 않는다.

### 초기 데이터 읽기 전용 검사기

`python -m scripts.audit_business_kit_initial_data --profile quick` 또는 `--profile full`.

검사 범위: 파일/필수열, 선언된 복합 업무키, 회사별 참조키, 샘플 조직 범위, 합성 표시, 발주↔계약 속성, **부분 선적 누적량**, 단위, 유효 BOM, 제품 산식을 사용한 저장 소요량 대사, 통화별 전표 차대 대사.

검사는 샘플 파일만 읽는다. RAW 등록·품질 인증·실행 승인·라이브 DB 쓰기는 하지 않는다. 정상 코드 0도 `PASS_CHECKED_SCOPE`이지 제품에서의 준비 완료가 아니다. 실패는 1, 검사 자체가 불가능하면 2이며 오류 종류별 표본을 따로 남긴다.

생산 대사는 제품의 `calc_projection.project()`와 `calc_models.material_shortage()`를 사용한다. 재고 0은 대사 함수 실행을 위한 진단 입력일 뿐이며 산출된 생산량·부족량을 시연 결과로 내보내지 않는다. 대체 BOM의 동시 유효, 단위 변환 부재는 임의로 고르거나 합치지 않는다.

## 4. 실측된 데이터 공백 — 무조건 대량 등록하지 않는 이유

대상은 **저장소의 샘플 CSV**이며 운영 DB에 현재 연결된 인증판 전체를 검사한 결과가 아니다.

| 샘플 | 행 수 | 확인 결과 |
|---|---:|---|
| quick | 13,585 | 조직 범위 미등재 3,215행, 소요량 대사 실패 333행, 동시 유효 BOM 충돌 167행 (§8 재측정 정정) |
| full | 155,508 | 계획 시점에 유효 BOM 없음 843행, 소요량 대사 실패 5,157행 |

- quick 조직 파일은 7개 노드이며 `plant-afs-smelting-01`이 없다. 해당 범위를 사용하는 자료와 패키지 조직 구성이 맞지 않는다. 현재 운영 ECM에 이 노드가 없다는 뜻은 아니다.
- full 생산계획의 날짜 범위는 2023-08-01~2026-07-30이다. 2024-01-01 전의 계획이 843행이며 BOM 유효 시작 이전이다. 과거 유효기간을 근거 없이 소급 확장하지 않는다.
- quick 첫 생산행의 저장 소요량은 66.4다. 이전에 적은 67.347은 서로 다른 BOM 판을 구분하기 전 값이며 정답으로 사용하면 안 된다. 해당 행은 동시 유효 BOM 충돌 대상이다. §8에서 BOM 판별과 소요량 불일치를 구분했다.
- 이 불일치를 시험에서 감추거나 검사 기준을 낮추지 않는다. 기존 샘플·manifest·엑셀을 덮어쓰지 않았다. `build(clean=True)` 재생성도 실행하지 않았다.
- 검사 통과가 아직 보증하지 않는 것: 재고 이동 전체 대사, 공시 총계와의 대사, 실제 소유권/인증판, 생산→판매 배분 근거, 실제 브라우저 실행, 전체 손익/현금 모델.

## 5. 후속 실행 순서와 완료 기준

### K1. 첫 입력 동선 — 이번 보강 다음 확인

1. 실제 서버에서 업무 데이터 준비 → 구매/생산/판매 영역 → 자료 준비 → 해당 원천 등록 위치를 확인한다.
2. 빈 파일, 필수값 누락, 잘못된 단위, 중복 거래의 행 단위 수정 안내를 확인한다.
3. 파일 등록 직후/검사 후 화면의 준비도 갱신을 확인한다.
4. 잘못된 입력이 기업 전체 수치를 바꾸지 않는지 확인한다.

남은 작업: 사용자용 한글 입력 양식/열 매핑·미리보기, 기준정보 이름 선택과 내부 ID 자동 생성 경로 대조. 기존 관리용 CSV만으로 이 조건이 충족됐다고 하지 않는다.

### K2. 서로 맞물리는 초기 업무 데이터

1. **회사·조직 기준 확정:** 샘플 회사 프로필과 조직도를 대조하고 누락 조직/부서 및 공장별 소유권을 정렬한다. 실제 회사·가상 상세·인증 성격을 별도로 유지한다.
2. **BOM·기간 정렬:** 제품/자재/역할/단위/수율/유효기간을 정본으로 선택하고 저장 소요량을 재계산한다. 과거 BOM 근거가 없으면 그 기간은 자료 보강 대상으로 남긴다.
3. **업무 사슬:** 계약→발주행→분할 선적→도착 사건→창고 입출고→생산→수주→전표를 연결한다. 생산→판매는 제품명이 같다는 이유만으로 자동 배분하지 않는다.
4. **결정론과 대사:** 동일 입력 재실행, 수량 보존, 기초+입출고=기말, 차변=대변, 단위/통화 변환, 중복/누락/타 조직의 부정 사례를 검사한다.
5. **검토 후 등록:** 신규 후보 개정에 원본 지문·변환 규칙·변경 목록을 보관한다. 등록 전에는 이전 인증판을 교체하지 않고, 제품 등록·검사 경로를 통해 반영한다. 두 개의 별도 시연/기능 서버나 이중 정본 DB를 만들지 않는다.

출구: 같은 기준일의 구매·생산·판매가 하나의 전사 시나리오에 저장되고, 부서별 기여 및 그 근거를 사람이 확인할 수 있다. 데이터의 양보다 이 조건을 우선한다.

### K3. 공개자료 기반의 현실성

| 자료 | 수집/정렬 단위 | 반드시 남길 근거 | 대사/제한 |
|---|---|---|---|
| DART 최근 10개 결산연도 + 당기 | 법인·연도·보고서·연결/별도·계정·누적/기간 | 접수번호, 원문, 정정공시, 단위, 수집시각 | 손익·재무상태·현금흐름 총계 대조; 비공개 구매/거래 원장은 얻었다고 하지 않음 |
| 환율·금리 | 지표·통화·관측일·빈도 | 제공자·시리즈·공표시각·이용범위 | 일/월 평균과 말일 값 구분; 회사 실제 결제환율과 별도 |
| 금속가·외부지표 | 상품·품위·시장·가격종류·통화/단위 | 출처와 재배포 가능 범위 | 공개 접근과 재배포 권한 구분; 무단 유료 원천 수집 금지 |
| 회사/산업 공개 분석 | 발행자·발행일·대상·문서 근거 | 원문과 인용 범위·주장/사실 구분 | 분석 의견을 거래 실적으로 전환하지 않음 |
| 합성 업무 상세 | 회사·부서·월·거래·업무 사슬 | 연결한 공개 집계, 배분 가정, 생성 seed, 생성 판 | 공개 총계와 대사하되 모든 상세는 SYNTHETIC 표시 |

중요 정정: 현재 `data_kind`는 공개/비공개 축이 아니라 실제/합성 축이고 `data_origin`이 공개 출처를 표현한다. 실제 공개 관측을 합성으로 바꿔 인증을 통과시키지 않는다. 현재 확인된 공백은 **실제 자료를 위한 인증 경로**이며, 외부 수집기 세션과 공동 계약이 필요하다. 수집 완료와 계산에 사용할 수 있는 인증 완료를 분리한다.

### K4. 앱별로 사람이 실제 수행

구매/생산/판매 앱의 준비자료 선택 → 자료 확인 → 가정 입력 → 실제 계산 → 같은 전사 시나리오 반영 → AI 경영비서 설명 → 안건/보고서 순으로 확인한다. 물류/공급위험의 조회 기능을 신규 입력·자동 추천까지 완성된 것처럼 제시하지 않는다. 타 부서 접근, 자료 누락, 기준선 불일치에서도 올바른 다음 행동이 보여야 한다.

### DB 준비 및 이전 경계

이번에는 코드와 파일명만 조사했다. 기존 SQLite 인벤토리의 라이브 DB 열기 기능은 실행하지 않았다.

- 소스의 DB 파일명 리터럴 21종, `data/` 최상위 DB 파일 20개. 실제 운영 저장소 수와 동일하다고 단정하지 않는다.
- 기존 정규식 검사로 열 추가 구문 11곳/10모듈. 모든 DDL·트리거·마이그레이션을 센 값은 아니다.
- 우선 이관 접점: `data_preparation`(판/결속/색인), `master`·ECM(기준/조직), `app_data`(업무 입력), `planning`·전사 시나리오(결과), 원장·보고(추적), 외부 수집 저장소.
- 다음 준비: 저장소별 단일 쓰기 경계, 스키마/트리거 목록, 날짜·Decimal·JSON·유일성·조회 순서의 동등성 시험, RAW 파일과 판 지문 보존, 복원 사본 검증.
- PostgreSQL 전환 시 쓰기를 잠시 멈추고 사본 이관→대사→전환→복구 확인. 이번 턴에서 전환/이중 쓰기/상용 배포를 시작하지 않았다.
- 위 첫 입력·데이터 계약이 잡힌 후 PostgreSQL 및 최대 10명 서비스 준비로 진행한다. 업무키트 전 영역을 모두 완성할 때까지 이전을 무기한 미루지 않는다.
