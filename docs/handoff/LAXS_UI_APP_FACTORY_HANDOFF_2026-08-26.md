## 1. 이번 인계의 목적

경영 홈을 확정한 뒤 상단 메뉴를 제품 기능 기준으로 정리하고, 다음 화면인 `앱 제작`을

현재 남은 결속 문제를 단순 문구 문제로 오인하지 않도록 다음을 한곳에 고정한다.

1. 지금까지 확정한 제품 명칭·로고·공통 셸
2. 경영 홈과 회사별 업무 연결구성의 현재 상태
3. 앱 제작 목록과 새 업무 생성 창에 적용한 선행 보정
4. 브라우저에서 재현한 실제 결함과 아직 닫히지 않은 항목
5. 다음 작업 순서와 완료 조건

## 3. 상단 메뉴 확정안

화면 상단의 주요 기능은 다음 일곱 개다.

```text
경영 홈 · 앱 제작 · 앱 운영 · 시뮬레이션 · 결정·보고 · 지식 · 에이전트
```

중요한 배선:

- `결정·보고`는 협업 받은함이 아니라 의사결정 목록에서 시작한다.
- `앱 제작`은 공통 `ProductShell`을 사용한다. 별도 Software Factory 머리 바를 다시 만들지 않는다.
- 화면당 주요 생성 행동은 상단의 `＋ 새 업무` 한 개다.
- 전체 메뉴에는 핵심 여정 다섯 단계가 순서대로 유지된다.

```text
1 업무 데이터 준비
2 계산 실행 승인
3 경로 계산
4 의사결정 안건
5 경영 브리핑
```

### 4.1 실행 문맥 결속 — 2026-08-26 완료

최초 실제 브라우저에서 다음 불일치를 확인했다.

```text
회사 정본에 등록된 표시명: LS MnM
회사 정본 tenant_id: tenant-afs-demo-materials
현재 인증 세션 tenant_id: tenant_default
현재 선택 범위: node_hq
```

`LS MnM`을 `tenant_default`에 화면에서 임의 대입하지 않았다. `data/instance.json`을
설치본 문맥의 정본으로 두고 `run.py`가 기동 시 다음을 한 tenant 축에 멱등 결속한다.

```text
tenant/company      tenant-afs-demo-materials · LS MnM
legal entity/node   ent-laxs-mnm-installation · org-laxs-mnm
data scope nodes    plant-afs-smelting-01 · plant-afs-battery-02
department mapping  hq · demo_smelting
```

`core/installation_context.py`는 같은 ID가 다른 tenant에 있으면 덮어쓰지 않고 기동을
중단한다. 모든 ID를 먼저 검증한 뒤 저장하므로 검증 실패로 반쪽 결속을 남기지 않는다.

두 번째 원인은 브라우저에 남은 이전 tenant였다. 인증 세션은 새 tenant를 반환했지만
전역 fetch가 이전 tenant·scope 헤더를 계속 보냈고, 회사 구성 조회가 새 정본을 보지 못했다.
인증 게이트와 `useOperatingContext()`가 서버 세션 tenant를 정본으로 동기화하고, 회사가
바뀌면 이전 scope도 함께 비운 뒤 다시 조회하도록 보정했다.

최종 실제 브라우저 확인:

```text
OPERATING CONTEXT  LS MnM · 권한 범위 전체  REAL
회사 연결 필요      0건
조직 연결 필요      0건
```

`권한 범위 전체`는 조직 미설정이 아니다. 관리자가 별도 조직으로 좁히지 않은 상태에서 서버가
실제로 적용하는 범위를 표시한 것이다. 임의로 `hq`를 자동 선택해 조회 범위를 좁히지 않는다.

- 화면 전용 어두운 헤더와 공통 셸이 혼재
- `Mega`, `Releases`, `Archive` 등 영문·기술 용어 혼재
- `tenant_default`, `node_hq`가 회사·조직 이름처럼 본문에 노출
- 문맥 밖 63건 안내가 화면 상단을 과도하게 차지
- 빈 상태와 주요 행동의 위계가 약함

적용한 변경:

- 경영 홈과 같은 `ProductShell` 적용
- 화면 제목을 `앱 제작`으로 통일
- 필터를 `미완료 · 내 프로젝트 · 통합 프로젝트 · 릴리스 · 보관함`으로 정리
- 제외 사유 상세를 접힌 영역으로 이동
- 본문의 중복 `새 업무 만들기` 버튼 제거
- 빈 상태가 상단 `＋ 새 업무`를 안내하도록 변경
- 회사·조직 내부 식별자 대신 결속 상태 또는 정본 이름 표시
- 검색 문구를 `이름 또는 ID로 찾기`로 정리

브라우저 실측 결과:

```text
보이는 미완료 프로젝트 0

보이는 통합 프로젝트 0
```

이 숫자는 프로젝트가 0건이라는 뜻이 아니라 현재 실행 문맥과 결속되지 않아 목록에서
제외됐다는 뜻이다. 회사·조직 결속이 다음 P0인 이유다.

### 6.1 실제 기능 결함 — 보이는 선택과 제출값 불일치

템플릿 목록은 비동기로 도착한다. 창이 먼저 열리면 내부 상태는 `default`였지만, HTML
`select`는 첫 번째 옵션 `소프트웨어 개발 팩토리`를 선택한 것처럼 보였다. 사용자가 그대로
만들면 화면에서 본 절차와 서버에 제출하는 값이 달라질 수 있었다.

조치:

- 목록이 도착했을 때 현재 값이 정본 목록에 없으면 첫 템플릿 ID로 상태를 동기화
- `지금 정해진 것` 요약도 내부 ID가 아니라 선택한 실제 절차 이름을 사용

### 6.2 하단 실행 버튼

1280×720에 가까운 화면에서 `이 조건으로 만들기`가 첫 화면 아래로 밀렸다. 생성 창의

### 7.1 앱 제작의 업무키트 진입 — 2026-08-26 완료

`＋ 새 업무`의 첫 선택을 다음 두 갈래로 명시했다.

```text
업무키트 기반 앱(추천)  현재 조직에 적용된 패키지 → 앱 준비도 → 계약 → 생성·운영 전환
일반 앱 제작            업무 절차·지식팩·기준정보를 직접 선택하는 기존 프로젝트 생성
```

업무키트 경로는 임의 `kit_instance_id` 입력을 받지 않는다. 서버가 현재 사용자에게 보여 줄 수
있는 조직 적용본만 `listInstances()`로 가져오며, 적용본을 고른 뒤 기존 `KitAppPanel`을 통해
다음을 한 화면에서 확인한다.

- 앱별 준비 가능·경고·차단 상태
- 계약 없음·승인 대기·승인됨 상태
- 승인 전 생성 행동 차단
- 생성된 데이터셋 수와 후보/운영 상태
- 운영 앱 열어 보기

적용본이 0건이면 빈 목록을 정상으로 표시하고 `업무 데이터 준비 열기`로 연결한다. 조회 장애는
0건으로 접지 않는다. 일반 앱 제작은 별도 분기로 그대로 유지하며 보이는 템플릿과 제출값의
동기화, 최초 화면의 생성 버튼 노출도 유지한다.

실제 브라우저 확인:

```text
조직 적용본       첫 수직 시연 — 비철 제련 · REAL · active
업무 앱           APP-01~05
APP-03·APP-04     준비 가능 · 계약 승인됨 · 데이터셋 6개 · 운영 중
APP-01·02·05      준비 가능 · 계약 없음 · 앱 분류 선택 전 초안 버튼 비활성
```

## 8. 릴리스 카드 — 2026-08-26 완료

최초 릴리스 5건은 보였지만 카드가 다음 값을 그대로 사용했다.

```text
kitapp_ki_…_APP-04
test_a1_…
2026-08-24T05:53:49+00:00
```

적용한 보정:

- 사람용 앱 이름·업무기능·상태를 첫 줄에 표시
- 내부 릴리스 ID는 접힌 `식별 정보`로 이동
- UTC 원문을 사용자 현지시각으로 표시
- `앱 실행`과 `릴리스 관리`의 차이를 카드에서 설명
- 운영 중·후보·중단 예고·중단 상태를 카드에서 먼저 확인

키트 앱 이름을 릴리스 ID에서 잘라 만들지 않는다. 현재 조직에서 볼 수 있는 적용본의
`listKitApps()` 응답을 릴리스 ID로 결속해 앱 계약이 준 이름을 사용한다. 이름 보강 조회가
실패해도 릴리스 목록 자체를 0건으로 만들지 않는다.

실제 브라우저 확인:

```text
구매원가·현금 전망       업무 앱 APP-04 · 운영 중 · 게시 2026년 8월 24일 오후 02:53
재고·생산 영향 분석      업무 앱 APP-03 · 운영 중 · 게시 2026년 8월 24일 오후 02:53
옛 릴리스 3건            사용 상태 미기록(운영 승인으로 추정하지 않음)
```

### 8.1 릴리스 관리 상세 — 2026-08-26 완료

최초 화면은 키트 앱의 사람용 이름을 카드에서만 사용하고 상세로 들어가면 다시
`kitapp_ki_…_APP-04`를 제목으로 표시했다. `PROGRAM/STATUS/BLAST RADIUS/CHANGE/HISTORY`,
이메일, UTC 원문, `active/candidate` 상태도 본문에 우선 노출됐다.

적용 결과:

```text
제목              구매원가·현금 전망
상태              사용 중
행위자            조직 정본의 사람 이름 우선
시각              2026년 8월 24일 오후 02:53
이력              사용 중 → 운영 후보 → 사용 중
내부 릴리스 ID     접힌 식별 정보
감사 원문 이메일   삭제하지 않고 title에 보존
```

현재 상태에서 불가능한 행동은 비활성화한다. 예를 들어 사용 중인 프로그램의 `사용 재개`는
비활성화된다. 서버의 상태 전이·사유 필수·영향 확인·대체본 검증은 계속 최종 판정이며, 화면은
서버 규칙을 새로 만들지 않는다.

### 8.2 업무키트 앱 직접 운영 진입 — 2026-08-26 완료

최초에는 이미 만들어진 업무키트 앱도 `＋ 새 업무 → 업무키트 기반 앱`으로 들어가야만 찾을 수
있었다. 만들기 화면이 기존 앱의 유일한 입구가 되면 사용자는 앱을 매번 새로 만들어야 하는 것으로
오해한다. 상단 `앱 운영`을 독립 진입점으로 연결하고 두 화면의 책임을 분리했다.

```text
앱 제작    업무키트 선택 → 앱 분류 → 계약 작성·승인 → 앱 생성
앱 운영    회사·조직 적용본 선택 → 운영/후보/승인 대기 상태 확인 → 운영 앱 열기
```

실제 브라우저에서 `앱 운영`을 눌러 다음을 확인했다.

```text
적용본    첫 수직 시연 — 비철 제련 · REAL · active
APP-01   원료 도입계획·추적          계약 없음 · 제작 안내
APP-02   물류 사건 확인·입력         계약 없음 · 제작 안내
APP-03   재고·생산 영향 분석         승인됨 · 운영 중 · 앱 열어 보기
APP-04   구매원가·현금 전망          승인됨 · 운영 중 · 앱 열어 보기
APP-05   공급 위험·대체안            계약 없음 · 제작 안내
```

운영 화면은 내부 `kit_instance_id`를 입력받지 않고 현재 조직에서 접근 가능한 적용본을 조회한다.
적용본이 하나이면 자동 선택하고, 여러 개이면 사람용 이름으로 선택한다. 운영 화면에서는 계약 작성·
재생성 버튼을 숨기고, 새 앱이 필요할 때만 `새 업무키트 앱 만들기`로 제작 화면에 이동한다.

### 9.1 URL 상태 계약

최초 프로젝트 화면은 메모리 상태만 사용해 새로고침하면 경영 홈으로 돌아갔다. 프로젝트를
공유하거나 장애 뒤 복구할 수 없는 구조였다. 별도 라우터를 도입하지 않고 다음 최소 계약을
적용했다.

```text
앱 제작 목록                 ?space=build
프로젝트 제작 작업공간        ?space=build&project=TEST001
```

실제 브라우저에서 프로젝트 열기 → 주소 확인 → 새로고침을 수행해 같은 `TEST001` 화면으로
복귀함을 확인했다. URL은 화면 복원 정보일 뿐 권한 근거가 아니며, 데이터 접근 판정은 기존
서버 세션·조직 범위 정책을 그대로 사용한다.

## 13. 금지사항

- `tenant_default`에 `LS MnM` 이름을 화면에서 하드코딩하지 않는다.
- 업무키트와 Starter Package와 앱 Blueprint를 한 목록으로 섞지 않는다.

- 업무키트 선택을 사용자의 ID 직접 입력으로 대체하지 않는다.

- `origin/dev`는 보존 기준선이므로 강제 갱신하지 않는다. 현재 통합 브랜치에만 푸시한다.
