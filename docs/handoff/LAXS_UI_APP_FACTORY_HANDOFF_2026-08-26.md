## 1. 이번 인계의 목적

경영 홈을 확정한 뒤 상단 메뉴를 제품 기능 기준으로 정리하고, 다음 화면인 `앱 제작`을

현재 남은 결속 문제를 단순 문구 문제로 오인하지 않도록 다음을 한곳에 고정한다.

2. 경영 홈과 회사별 업무 연결구성의 현재 상태
3. 앱 제작 목록과 새 업무 생성 창에 적용한 선행 보정
4. 브라우저에서 재현한 실제 결함과 아직 닫히지 않은 항목

## 3. 상단 메뉴 확정안

화면 상단의 주요 기능은 다음 일곱 개다.

```text
경영 홈 · 앱 제작 · 앱 운영 · 시뮬레이션 · 결정·보고 · 지식 · 에이전트
```

중요한 배선:

- `결정·보고`는 협업 받은함이 아니라 의사결정 목록에서 시작한다.
- `앱 제작`은 공통 `ProductShell`을 사용한다. 별도 Software Factory 머리 바를 다시 만들지 않는다.
- 화면당 주요 생성 행동은 상단의 `＋ 새 업무` 한 개다.
- 전체 메뉴에는 핵심 여정 다섯 단계가 순서대로 유지된다.

```text
1 업무 데이터 준비
2 계산 실행 승인
3 경로 계산
4 의사결정 안건
5 경영 브리핑
```

### 4.1 실행 문맥 결속 — 2026-08-26 완료

최초 실제 브라우저에서 다음 불일치를 확인했다.

```text
회사 정본에 등록된 표시명: LS MnM
회사 정본 tenant_id: tenant-afs-demo-materials
현재 인증 세션 tenant_id: tenant_default
현재 선택 범위: node_hq
```

`LS MnM`을 `tenant_default`에 화면에서 임의 대입하지 않았다. `data/instance.json`을
설치본 문맥의 정본으로 두고 `run.py`가 기동 시 다음을 한 tenant 축에 멱등 결속한다.

```text
tenant/company      tenant-afs-demo-materials · LS MnM
legal entity/node   ent-laxs-mnm-installation · org-laxs-mnm
data scope nodes    plant-afs-smelting-01 · plant-afs-battery-02
department mapping  hq · demo_smelting
```

`core/installation_context.py`는 같은 ID가 다른 tenant에 있으면 덮어쓰지 않고 기동을
중단한다. 모든 ID를 먼저 검증한 뒤 저장하므로 검증 실패로 반쪽 결속을 남기지 않는다.

두 번째 원인은 브라우저에 남은 이전 tenant였다. 인증 세션은 새 tenant를 반환했지만
전역 fetch가 이전 tenant·scope 헤더를 계속 보냈고, 회사 구성 조회가 새 정본을 보지 못했다.
인증 게이트와 `useOperatingContext()`가 서버 세션 tenant를 정본으로 동기화하고, 회사가
바뀌면 이전 scope도 함께 비운 뒤 다시 조회하도록 보정했다.

최종 실제 브라우저 확인:

```text
OPERATING CONTEXT  LS MnM · 권한 범위 전체  REAL
회사 연결 필요      0건
조직 연결 필요      0건
```

`권한 범위 전체`는 조직 미설정이 아니다. 관리자가 별도 조직으로 좁히지 않은 상태에서 서버가
실제로 적용하는 범위를 표시한 것이다. 임의로 `hq`를 자동 선택해 조회 범위를 좁히지 않는다.

- `tenant_default`, `node_hq`가 회사·조직 이름처럼 본문에 노출
- 문맥 밖 63건 안내가 화면 상단을 과도하게 차지
- 빈 상태와 주요 행동의 위계가 약함

- 필터를 `미완료 · 내 프로젝트 · 통합 프로젝트 · 릴리스 · 보관함`으로 정리

- 본문의 중복 `새 업무 만들기` 버튼 제거
- 빈 상태가 상단 `＋ 새 업무`를 안내하도록 변경
- 회사·조직 내부 식별자 대신 결속 상태 또는 정본 이름 표시
- 검색 문구를 `이름 또는 ID로 찾기`로 정리

브라우저 실측 결과:

```text
보이는 미완료 프로젝트 0
```

이 숫자는 프로젝트가 0건이라는 뜻이 아니라 현재 실행 문맥과 결속되지 않아 목록에서
제외됐다는 뜻이다. 회사·조직 결속이 다음 P0인 이유다.

### 6.1 실제 기능 결함 — 보이는 선택과 제출값 불일치

템플릿 목록은 비동기로 도착한다. 창이 먼저 열리면 내부 상태는 `default`였지만, HTML
`select`는 첫 번째 옵션 `소프트웨어 개발 팩토리`를 선택한 것처럼 보였다. 사용자가 그대로
만들면 화면에서 본 절차와 서버에 제출하는 값이 달라질 수 있었다.

조치:

- 목록이 도착했을 때 현재 값이 정본 목록에 없으면 첫 템플릿 ID로 상태를 동기화
- `지금 정해진 것` 요약도 내부 ID가 아니라 선택한 실제 절차 이름을 사용

### 6.2 하단 실행 버튼

### 7.1 앱 제작의 업무키트 진입 — 2026-08-26 완료

`＋ 새 업무`의 첫 선택을 다음 두 갈래로 명시했다.

```text
업무키트 기반 앱(추천)  현재 조직에 적용된 패키지 → 앱 준비도 → 계약 → 생성·운영 전환
일반 앱 제작            업무 절차·지식팩·기준정보를 직접 선택하는 기존 프로젝트 생성
```

업무키트 경로는 임의 `kit_instance_id` 입력을 받지 않는다. 서버가 현재 사용자에게 보여 줄 수
있는 조직 적용본만 `listInstances()`로 가져오며, 적용본을 고른 뒤 기존 `KitAppPanel`을 통해
다음을 한 화면에서 확인한다.

- 앱별 준비 가능·경고·차단 상태
- 계약 없음·승인 대기·승인됨 상태
- 승인 전 생성 행동 차단
- 생성된 데이터셋 수와 후보/운영 상태
- 운영 앱 열어 보기

적용본이 0건이면 빈 목록을 정상으로 표시하고 `업무 데이터 준비 열기`로 연결한다. 조회 장애는
0건으로 접지 않는다. 일반 앱 제작은 별도 분기로 그대로 유지하며 보이는 템플릿과 제출값의
동기화, 최초 화면의 생성 버튼 노출도 유지한다.

실제 브라우저 확인:

```text
조직 적용본       첫 수직 시연 — 비철 제련 · REAL · active
업무 앱           APP-01~05
APP-03·APP-04     준비 가능 · 계약 승인됨 · 데이터셋 6개 · 운영 중
APP-01·02·05      준비 가능 · 계약 없음 · 앱 분류 선택 전 초안 버튼 비활성
```

## 8. 릴리스 카드 — 2026-08-26 완료

최초 릴리스 5건은 보였지만 카드가 다음 값을 그대로 사용했다.

```text
kitapp_ki_…_APP-04
test_a1_…
2026-08-24T05:53:49+00:00
```

적용한 보정:

- 사람용 앱 이름·업무기능·상태를 첫 줄에 표시
- 내부 릴리스 ID는 접힌 `식별 정보`로 이동
- UTC 원문을 사용자 현지시각으로 표시
- `앱 실행`과 `릴리스 관리`의 차이를 카드에서 설명
- 운영 중·후보·중단 예고·중단 상태를 카드에서 먼저 확인

키트 앱 이름을 릴리스 ID에서 잘라 만들지 않는다. 현재 조직에서 볼 수 있는 적용본의
`listKitApps()` 응답을 릴리스 ID로 결속해 앱 계약이 준 이름을 사용한다. 이름 보강 조회가
실패해도 릴리스 목록 자체를 0건으로 만들지 않는다.

실제 브라우저 확인:

```text
구매원가·현금 전망       업무 앱 APP-04 · 운영 중 · 게시 2026년 8월 24일 오후 02:53
재고·생산 영향 분석      업무 앱 APP-03 · 운영 중 · 게시 2026년 8월 24일 오후 02:53
옛 릴리스 3건            사용 상태 미기록(운영 승인으로 추정하지 않음)
```

### 8.1 릴리스 관리 상세 — 2026-08-26 완료

최초 화면은 키트 앱의 사람용 이름을 카드에서만 사용하고 상세로 들어가면 다시
`kitapp_ki_…_APP-04`를 제목으로 표시했다. `PROGRAM/STATUS/BLAST RADIUS/CHANGE/HISTORY`,
이메일, UTC 원문, `active/candidate` 상태도 본문에 우선 노출됐다.

적용 결과:

```text
제목              구매원가·현금 전망
상태              사용 중
행위자            조직 정본의 사람 이름 우선
시각              2026년 8월 24일 오후 02:53
이력              사용 중 → 운영 후보 → 사용 중
내부 릴리스 ID     접힌 식별 정보
감사 원문 이메일   삭제하지 않고 title에 보존
```

현재 상태에서 불가능한 행동은 비활성화한다. 예를 들어 사용 중인 프로그램의 `사용 재개`는
비활성화된다. 서버의 상태 전이·사유 필수·영향 확인·대체본 검증은 계속 최종 판정이며, 화면은
서버 규칙을 새로 만들지 않는다.

### 8.2 업무키트 앱 직접 운영 진입 — 2026-08-26 완료

최초에는 이미 만들어진 업무키트 앱도 `＋ 새 업무 → 업무키트 기반 앱`으로 들어가야만 찾을 수
있었다. 만들기 화면이 기존 앱의 유일한 입구가 되면 사용자는 앱을 매번 새로 만들어야 하는 것으로
오해한다. 상단 `앱 운영`을 독립 진입점으로 연결하고 두 화면의 책임을 분리했다.

```text
앱 제작    업무키트 선택 → 앱 분류 → 계약 작성·승인 → 앱 생성
앱 운영    회사·조직 적용본 선택 → 운영/후보/승인 대기 상태 확인 → 운영 앱 열기
```

실제 브라우저에서 `앱 운영`을 눌러 다음을 확인했다.

```text
적용본    첫 수직 시연 — 비철 제련 · REAL · active
APP-01   원료 도입계획·추적          승인됨 · 운영 중 · 앱 열어 보기
APP-02   물류 사건 확인              승인됨 · 운영 중 · 조회 전용 앱 열기
APP-03   재고·생산 영향 분석         승인됨 · 운영 중 · 앱 열어 보기
APP-04   구매원가·현금 전망          승인됨 · 운영 중 · 앱 열어 보기
APP-05   공급 위험·대체안            승인됨 · 운영 중 · 근거 조회 앱 열기
```

운영 화면은 내부 `kit_instance_id`를 입력받지 않고 현재 조직에서 접근 가능한 적용본을 조회한다.
적용본이 하나이면 자동 선택하고, 여러 개이면 사람용 이름으로 선택한다. 운영 화면에서는 계약 작성·
재생성 버튼을 숨기고, 새 앱이 필요할 때만 `새 업무키트 앱 만들기`로 제작 화면에 이동한다.

최초 APP-03 열기에서는 상단이 `권한 범위 전체`인데 앱 증명은 `조직 범위를 선택해야` 한다며
409로 막혔다. 서버의 D-014(미지정은 전사 허용이 아니라 비노출)는 옳았고, 문제는 승인 시안의
새 상단 셸이 종전 `CompanyContextBar`의 조직 선택 행동을 잃은 것이었다. 조직 관리 화면의
부서 상세에 `이 조직으로 전환`을 추가했다. 이 행동은 조직 정본을 고치는 `적용`과 분리되며,
범위가 없는 부서에서는 비활성화된다.

실제 브라우저 재확인:

```text
회사 문맥 버튼 → 제련공장 (시연 자료) → 이 조직으로 전환
상단 문맥      LS MnM · 제련공장 (시연 자료) · REAL
앱 운영        APP-03 재고·생산 영향 분석 → 앱 열어 보기
결과           qlt_01 등 데이터셋 6개 · 20건 표시 · 총 12,000건
데이터 표식     시연용 합성 데이터 · 인증판 기준 · 기준일 2026-08-11
```

`권한 범위 전체`를 앱 증명에 강제로 허용하지 않았다. 사용자의 명시적 조직 선택과 새로고침 뒤
서버가 기존 세션·조직 정책으로 증명을 발급하고 인증된 업무 데이터를 읽는 경로를 유지한다.

### 8.4 APP-01 계약·생성·운영 폐루프 — 2026-08-26 완료

APP-01 `원료 도입계획·추적`은 구매·물류·입고 여러 부서가 함께 쓰므로 `전사용`으로 분류해
계약 초안 개정 1을 실제 제품 화면에서 생성했다.

```text
작성자        hikwon@lsmnm.com

앱 분류       전사용
자기승인 대조 서버 403 · 상태 불변
```

최초 업무키트 조회가 일시적으로 `Failed to fetch`를 반환했는데 화면에는 재시도 행동이 없어
대화상자를 닫고 다시 여는 방법밖에 없었다. 오류를 0건으로 접지 않는 기존 원칙은 유지하면서

`/auth/me`의 현재 사용자가 `drafted_by`와 같으면 승인 근거 입력과 버튼을 비활성화하고
`다른 승인 권한 사용자로 로그인해 검토`하도록 먼저 안내한다. 현재 사용자를 확인하지 못한
경우에도 서버의 자기승인 거부가 최종 판정이므로 보안 규칙은 약해지지 않는다.

작성자와 다른 승인 권한 사용자로 다시 로그인해 다음 행동을 실제 제품 화면에서 연속 수행했다.
사용자 비밀번호는 자동화 코드·문서·로그에 기록하지 않았다.

```text

업무 탭                 발주 현황 · 구매 계약 · 입고 운송 · 통관 현황 · 운송 마일스톤
```

제목에서 제거하되 보조 진단 정보로 보존한다. 승인되지 않은 후보 판은 업무 데이터를 읽지 못하고,
운영 전환 뒤에만 `앱 열어 보기`가 실제 인증 데이터 화면을 연다.

### 9.1 URL 상태 계약

최초 프로젝트 화면은 메모리 상태만 사용해 새로고침하면 경영 홈으로 돌아갔다. 프로젝트를

복귀함을 확인했다. URL은 화면 복원 정보일 뿐 권한 근거가 아니며, 데이터 접근 판정은 기존
서버 세션·조직 범위 정책을 그대로 사용한다.

## 13. 금지사항

- `tenant_default`에 `LS MnM` 이름을 화면에서 하드코딩하지 않는다.
- 업무키트와 Starter Package와 앱 Blueprint를 한 목록으로 섞지 않는다.
- 내부 ID를 사람용 제목으로 사용하지 않는다.
- 후보 릴리스와 운영 릴리스를 같은 상태로 표시하지 않는다.
- 업무키트 선택을 사용자의 ID 직접 입력으로 대체하지 않는다.
- 다른 작업자의 미커밋 백엔드·문서·데이터 파일을 본 UI 커밋에 섞지 않는다.
- `origin/dev`는 보존 기준선이므로 강제 갱신하지 않는다. 현재 통합 브랜치에만 푸시한다.

## 14. 2026-08-27 증분 — 공통 제품공간과 로컬 경영 폐루프

### 14.1 오늘의 범위

오늘 작업은 경영 홈 한 화면을 더 꾸미는 데 그치지 않고, 상단 일곱 제품공간을 같은 제품 문법으로
정렬하고 핵심 경영 폐루프를 실제 브라우저에서 닫는 데 초점을 두었다.

```text
경영 홈 · 앱 제작 · 앱 운영 · 시뮬레이션 · 결정·보고 · 지식 · 에이전트
```

공통 기준은 다음과 같다.

- 모든 독립 제품공간은 `ProductShell` 아래에서 회사·조직·REAL/VIRTUAL 문맥을 유지한다.
- 앱 제작·앱 운영·시뮬레이션·결정/보고·지식·에이전트는 좌측 탐색, 중앙 업무면,
  우측 자비스의 역할을 분리한다.
- 자비스는 첫 화면과 같은 짙은 남색 톤과 정보 구조를 사용하며, 화면별 추천 질문과 현재 선택
  문맥을 받는다.
- 메뉴 이름과 첫 화면 제목을 맞추고, 사용자가 내부 ID를 입력해 화면을 여는 방식은 제거한다.
- 페이지 전환 뒤에도 상단 전체 메뉴 26개와 회사 문맥 전환기를 사용할 수 있다.

### 14.2 회사·조직 문맥 전환

상단 회사 문맥을 누르면 바로 조직 관리 화면으로 보내던 구조를 `OperatingContextSwitcher`로
분리했다. 선택기는 서버가 반환한 회사·조직만 보여 주고, 선택 뒤 서버가 확정한 문맥을 다시 읽어
요청한 범위와 일치할 때만 적용한다. 회사 관리와 조직 관리는 별도 행동으로 남겼다.

회사나 조직을 바꾸면 다음 화면들이 이전 문맥의 캐시를 버리고 다시 조회한다.

- 업무키트 적용본과 열린 업무 앱
- 온톨로지 객체·관계·제안 문맥
- 상단 회사명과 조직명

### 14.3 앱 제작·앱 운영·시뮬레이션

- 앱 제작과 앱 운영은 같은 목록/상세 탐색 문법을 사용한다.
- 앱 운영은 현재 회사의 업무키트 적용본을 먼저 고르고 APP-01~05의 운영 상태와 실제 업무
  데이터를 연다.
- 시뮬레이션은 조건 설정과 비교 결과를 분리하고, 실행 전 빈 차트나 0을 결과처럼 표시하지 않는다.
- 세 화면 모두 좌측 작업 단계와 우측 자비스를 갖고 1280×720에서도 본문과 행동이 겹치지 않게
  독립 스크롤을 사용한다.

### 14.4 결정·보고 폐루프

결정·보고는 협업 받은함이 아니라 의사결정 안건 목록에서 시작한다. 경로 계산 안건은
`query_id`와 근거 지문으로 표시하며, 시뮬레이션이 아닌 것을 `시뮬레이션 연결 없음`으로
오표시하지 않는다.

실제 브라우저에서 다음 폐루프를 완주했다.

```text
인증된 업무키트 데이터
  → 승인된 온톨로지 경로
  → 경로 계산 결과
  → Decision Package dec_a040b013ca00
  → 다른 검토자 세션의 DEFERRED 결정
  → 내부 경영 보고 pub_9f57dd46fe30 렌더링
```

이 실행에서는 기존 계산 승인 상태를 임의로 변경하지 않았다. 생성·결정·발간은 제품 API와 실제
인증 세션으로 수행했고, 보고서 본문과 근거 지문을 브라우저에서 재조회했다.

### 14.5 지식 제품공간

지식 화면을 다음 일곱 하위 화면으로 확장했다.

1. 지식팩
2. 내용 확인
3. 자료 등록
4. 검색 품질 확인
5. 원본 등록부
6. 업무 온톨로지
7. 대외 인텔리전스

`내용 확인`은 지식팩 이름만 보여 주지 않고 실제 문서·청크·출처를 조회한다. 자료가 없거나
변환이 필요하거나 권한 밖인 상태를 같은 빈 화면으로 접지 않는다.

### 14.6 업무 온톨로지 제품 화면

온톨로지 화면은 다음을 실제 제품 API에 연결했다.

- 설치된 의미계약과 계약 원문 상세
- 현재 회사·조직·기준 시각에서 보이는 업무 객체
- 관계 초안 제안, 검토 요청, 승인·반려·폐지
- 승인 관계의 근거·계산 참조·Decision Ledger 결속
- 시작 객체를 고른 영향 경로 조회
- 실제 관계를 노드와 간선으로 표현하는 읽기 전용 상관 그래프

상관 그래프는 관계 등록부와 같은 응답을 사용한다. 숨겨진 관계 수를 추정하거나 빈 구간을
임의 연결하지 않는다. 노드 선택은 영향 경로 시작점과, 간선 선택은 관계 상세와 같은 상태를
사용한다. 실제 브라우저에서 다음 승인 경로 3개·객체 4개를 확인했다.

```text
shipment
  → inventory-snapshot
  → production-plan-line
  → sales-line
```

### 14.7 대외 인텔리전스 현재선과 확장 결정

현재 제품에 실제로 있는 것은 다음 두 경로다.

- 승인 원천에 귀속된 CSV 예행·적재
- 등록된 `base_url` 아래 JSON API 예행·적재

없는 기능도 명시적으로 확인했다.

- 주기 작업 스케줄러
- 승인 도메인 HTML 수집
- RSS/공시/뉴스 사건 후보 수집
- 회사 기준 기초조사 봇
- 수집 작업 이력과 후보 검토 화면

따라서 대외 인텔리전스 완료를 선언하지 않는다. 후속 기능은 범용 크롤러가 아니라 회사와 업무
목적에 결속된 통제형 에이전트로 만든다. 봇이 발견한 원천과 값은 모두 후보이며, 사람 승인 전에는
기준계획·Actual·Gold로 승격하지 않는다. 상세 계약과 순서는
`docs/roadmap/FULL_MENU_UI_ONTOLOGY_EXTERNAL_AGENT_EXECUTION_PLAN_2026-08-27.md`가 정본이다.

### 14.8 전체 메뉴 26개 UI 모수 정정

종전 계획은 대표 제품공간 중심이라 전체 메뉴 26개 중 다수를 UI 개선 대상에서 빠뜨렸다.
오늘 코드와 실제 메뉴를 대조해 전체 모수를 다음처럼 확정했다.

### 14.9 단일 사전검증 데이터 평면과 시험 격리

실제 현장 적용 전까지 기능 확인용 데이터와 시연용 데이터를 별도 서버·별도 루트로 나누지 않는다는
제품 결정을 반영했다. 로컬 제품 서버와 시드의 정본은 모두 저장소의 `data/`이며, 별도
`demo_data/`를 제품 데이터처럼 구동하는 경로는 허용하지 않는다.

- `run_local_demo.py`는 별도 데모 데이터 루트 생성을 거부하고 단일 사전검증 평면만 사용한다.
- `seed_starter_data.py`는 같은 `data/`에 결정론적 합성 자료를 준비한다.
- 합성 사용자와 행위자는 실재할 수 없는 `@afs.invalid` 식별자만 사용한다.
- 시험은 운영 `Decision Ledger`, 협업 저장소, LLM 캐시를 각각 임시 경로로 격리한다.
- 운영 불변식 검사는 협업·결정·발간 저장소의 보호 표에 대해 행 수뿐 아니라 내용 지문도 비교한다.
- 브라우저 폐루프와 화면 검증은 같은 사전검증 데이터 평면을 읽되, 운영 데이터에 쓰는 탐침으로
  격리 여부를 확인하지 않는다.

이 결정은 개발·시연 간 데이터 불일치를 줄이기 위한 현재 단계의 정책이다. PostgreSQL 전환과
최대 10명 파일럿은 별도 후속 단계이며, 그때 환경 분리·백업·복구·배포 승격 정책을 다시 적용한다.

## 17. 2026-08-27 U1 핵심 여정 구조 정렬

### 17.1 변경한 화면

레거시 대화상자였던 다음 네 화면을 공통 3열 제품 구조로 전환했다.

1. 업무·데이터 설계 상담
2. 업무 데이터 준비
3. 계산 실행 승인
4. 경로 계산

각 화면은 왼쪽 단계 탐색, 중앙 실제 업무, 오른쪽 자비스 문맥으로 구성한다. 아직 사용할 수 없는
단계를 누르면 조용히 무시하거나 빈 화면으로 보내지 않고, 현재 무엇이 선행되어야 하는지 화면에서
말한다. 경로 계산은 `NO SILENT ZERO`를 명시해 차단된 계산을 0으로 표시하지 않는다.

후속 확인에서 네 화면과 경영 브리핑은 내부 3열만 맞고 상단은 여전히 전체화면 대화상자라는
결함을 발견했다. 완료 판정을 취소하고 다섯 화면을 공통 `ProductShell` 아래 독립 페이지로
올렸다. 전체 메뉴에서 열면 앱 제작·운영·시뮬레이션과 같은 상단 브랜드·회사 문맥·전역 메뉴를
유지하며, 페이지에서는 대화상자 전용 제목 바를 중복해 그리지 않는다. 프로젝트 안의 보조
진입은 포커스 복귀가 필요한 작업이므로 기존 대화상자를 유지한다.

협업·의사결정·발간은 기존 제품 셸의 화면 문맥, 좌측 레일, 자비스 근거 전달을 코드 기준으로
다시 확인했다. 따라서 U1의 구조 정렬은 일곱 화면 모두 완료다.

## 23. 2026-08-27 U7 26화면 브라우저 전수감사와 긴 상태 보정

### 23.1 전수 측정

5174 제품 서버에서 전체 메뉴 26개를 1280×720과 1440×900으로 각각 실제 진입했다. 두 해상도
모두 공통 제품 셸, 왼쪽 단계/허브, 중앙 업무면, 오른쪽 자비스가 존재했고 문서 가로 넘침은

### 23.2 브라우저가 발견한 결함과 보정

1. 1280 상단 셸의 사용자명·새 업무 버튼 잘림: 헤더 그리드와 이름 최대폭을 조정해
   `clientWidth == scrollWidth == 1280`, 새 업무 버튼 오른쪽 1276px 이내를 확인했다.
2. 온톨로지 전체범위 혼동: 전체범위는 읽기 문맥이며 관계 저장에는 명시 회사/조직이 필요하다는
   경고로 바꿨다. 빈 범위는 경고 1건으로 보이고 오류 경보로 과장되지 않는다.
3. 의사결정 상세의 원시 JSON: 공통 `StructuredValue`로 배열·객체를 카드와 한글 필드명으로
   렌더링하고 발간 상세에도 적용했다.
4. 발간 77건 장문 목록: 20건 페이지로 전환해 `1–20 / 77건`, 다음 페이지
   `21–40 / 77건`을 실제로 확인했다.
5. 운영승격 후보 범위 누설: 릴리스 목록을 현재 사용자가 볼 수 있는 프로젝트 집합으로 제한하고,
   프로젝트 없는 레거시 릴리스와 타 범위 릴리스는 이름조차 반환하지 않도록 fail-closed 처리했다.

회사 업무 연결구성의 하단 저장 버튼은 중앙 독립 스크롤 안에 있고 자비스와 겹치지 않았다.

## 28. 2026-08-27 U12 저장소 장애 503 통일

외부정보 저장소의 SQLite 판독 실패가 라우트에서 잡히지 않아 기본 500으로 빠지는 것을 확인했다.
`api/storage_errors.py`에 제품 공통 처리기를 두고 `main.py`가 `sqlite3.Error`를 503으로 등록한다.
응답에는 DB 파일·표·SQL을 노출하지 않는다. 도메인 입력 오류 4xx와 저장소 장애 503을 구분하며,
프런트 공통 `DataState`는 이를 `조회 불가`와 재시도 행동으로 표시한다.

운영 저장소를 고장 내지 않고 가짜 ASGI 요청으로 상태 코드와 비노출을 확인했다. 외부 인텔리전스
인접 회귀를 함께 돌렸고, 최신 서버 startup complete 뒤 지식팩 4개·문서 27개가 복구됨을 실제
브라우저에서 확인했다.
