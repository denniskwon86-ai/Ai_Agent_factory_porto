## 1. 훑은 방법과 결과

`SprintResult`/`ReleaseResult` 를 돌려주는 명령과 `/sprint/*` 직접 POST 의 **호출부를 전부**
찾아 하나씩 읽었다. 새 Studio 쪽은 전부 공용 `command` 를 지나므로 **결함이 없었다.**
결함은 구 통제실 한 파일에 **여덟 자리** 모여 있었다.

## 2. 서버 실측 — 세 가지가 «추측이 아니라 사실» 이다

격리 서버(8086)에 직접 물었다. 읽기만으로 판단하지 않았다.

```
POST …/sprint/revision  → 409  {"reason_code":"REVISION_REQUEST_REQUIRED",
                                 "message":"… /sprint/revision-requests 로 제출하십시오."}
POST …/sprint/pause     → 409  "종료를 확인할 실행 중 작업이 없습니다."
POST …/sprint/stop      → 409  "종료를 확인할 실행 중 작업이 없습니다."
```

* ③ **수정 요구의 옛 접수는 이미 닫혀 있다.** 서버가 기준 산출물·저장 초안·요청 ID 없는
  경로를 막았고, 그 뒤로 이 화면의 「수정 요구」는 **눌러도 아무 일도 일어나지 않는다.**
  사용자는 자기가 잘못 눌렀다고 읽는다 — 화면이 아무 말도 하지 않기 때문이다.
* ①② 실행 중 작업이 없으면 정지·일시정지는 **409** 다. 그런데 화면은 둘 다 성공으로 보였다.
  **가동이 도는 동안 멈췄다고 믿는 것**이 이 화면에서 가장 위험한 거짓이다.

## 3. 고친 모양 — 판정을 한 곳으로 모았다

여덟 자리가 각자 문구를 지어내지 않도록 **공용 판정 하나**를 두고 전부 그것을 지난다.

```tsx
type CommandVerdict = 'ok' | 'stale' | 'unknown' | 'failed';
function tellCommandResult(label, r, requested): CommandVerdict {
  if (useFactoryStore.getState().currentProjectId !== requested) return 'stale';  // 남의 화면엔 말 안 함
  if (r.ok) return 'ok';
  if (r.outcome === 'UNKNOWN') { alert(`⚠️ ${label} 요청의 결과를 확인하지 못했습니다.
    다시 누르지 마십시오 — 같은 작업이 두 번 실행될 수 있습니다. …`); return 'unknown'; }
  alert(`❌ ${label} 요청이 받아들여지지 않았습니다.…`); return 'failed';
}
```

★ **`'ok'` 일 때만 후속 상태를 갱신한다.** 나머지는 상태를 건드리지 않는다 — 특히

* ④ 미확정에 `activeSprintId` 를 **버리지 않는다.** 접수됐을 수도 있는데 손잡이를 잃으면
  사용자는 진행을 보지도 멈추지도 못한 채 **다시 누른다.** 실행 명령에서 그것은 **유료 LLM
  재실행**이다(릴리스에서 같은 사고를 이미 실측했다 — 앞 라운드 §6).
* ⑤ 미확정에 `clearSuspendedQuota()` 를 **부르지 않는다.** 보류 지점을 지우면 다음 재개가
  「처음부터」로 떨어지고 이미 쓴 비용을 다시 쓴다.
* ⑥ 미확정에 `clearSprintData()` 를 부르지 않는다.

개별 수정:

* ② **새 Studio 와 같은 공용 `pauseSprint`** 로 바꿨다(원키·영수증이 따라온다).
  서버 쪽은 `execution-commands` 의 `PAUSE` 가 **같은 `factory.pause_sprint` 핸들러**로
  들어가는 것을 확인하고 바꿨다 — 동작이 달라지지 않는다.
* ③ 409 를 **사람 말로** 알린다(서버 원문의 내부 경로는 보이지 않는다). **입력을 지우지
  않는다.** 새 화면의 「수정 요청」으로 안내한다.
* ⑦⑧ 응답을 보고, 거절이면 말하고 「가동 중」 표시를 남기지 않는다.
* ①에서 성공 문구도 「**접수**했습니다」로 낮추고 서버 문구를 싣는다(접수 ≠ 정지 완료).

## 5. ★ 먼저 봐 달라는 것

1. **③ 의 처리 방향.** 옛 접수를 「안내로 막는」 것으로 끝냈다. 대안은 구 화면을
   `/sprint/revision-requests` 로 **다시 배선**하는 것인데, 그러면 기준 산출물·저장 초안·
   원키 UI 를 구 화면에 새로 들여야 하고 **새 Studio 의 흐름이 두 벌**이 된다. §10 이
   C3 에서 지울 화면이라 배선 대신 안내를 골랐다. 판단을 구한다.
2. **② 의 엔드포인트 교체.** 구 화면의 직접 POST 를 공용 명령으로 옮겼다. 같은 서버
   핸들러로 들어가는 것은 확인했으나, `/sprint/pause` 직접 호출을 쓰는 **다른 소비자**가
   있는지는 내가 보지 못했다.
3. **미확정 잠금.** 앞 라운드에서 남긴 질문과 같다 — 구 화면은 문구로 말릴 뿐 버튼을
   잠그지 않는다. 이번에 자리가 여덟으로 늘었으니 한 번에 정하는 편이 낫다.

## 6. 실화면 — **실클릭 NOT_RUN(사유 있음)**

이 여덟 자리는 실화면에서 **누를 수 없거나 눌러서는 안 된다.**

* 「기획 및 작업분해 시작」·「작업 시작」·「재시도」·「재분할」·「재가동」은 **유료 LLM 실행**을
  시작한다. 시험 목적으로 누르지 않는다(팀 표준).
* 「중단」·「일시정지」는 **실행 중 작업이 있어야** 화면에 나타난다. 그 상태를 만들려면 위의
  LLM 실행이 필요하다.
* 「수정 요구」 입력칸도 실행/일시정지 상태에서만 렌더된다.

대신 **그 명령들이 서버에서 실제로 무엇을 돌려주는지**를 격리 서버에 직접 물어 확인했다(§2).
화면 쪽은 **제품 핸들러를 뽑아 실행**한 증거까지다(§4). 두 층을 섞지 않는다.
