## 훑은 결과 — 구 통제실 한 파일에 여덟 자리

새 Studio 는 전부 공용 `command` 를 지나 결함이 없었다. 구 통제실만 각자 처리하고 있었다.

```
중단        결과를 버리고 무조건 「정지했습니다」
일시정지    이 화면만 /sprint/pause 직접 POST · 응답 미확인 · 무조건 「멈춤」
수정 요구   서버가 «항상 409» 인 옛 접수 · res.ok 아니면 무반응
기획 시작   미확정을 실패로 단정 + 진행 손잡이 폐기 + catch 침묵
한도 재개   미확정을 실패로 단정
재분할      미확정을 실패로 단정 + catch 침묵
작업 시작   응답을 통째로 버림 — 거절당해도 「가동 중」
재시도      거절 시 아무 말 없이 상태만 되돌림
```

## 서버 실측 — 읽기로 판단하지 않았다

```
POST …/sprint/revision → 409 REVISION_REQUEST_REQUIRED   ← 옛 접수는 이미 닫혀 있다
POST …/sprint/pause    → 409 "종료를 확인할 실행 중 작업이 없습니다."
POST …/sprint/stop     → 409 (같음)
```

즉 **수정 요구는 눌러도 아무 일도 일어나지 않는 상태였고**, 정지·일시정지는 **실패해도
성공으로 보였다.** 가동이 도는 동안 멈췄다고 믿는 것이 이 화면에서 가장 위험한 거짓이다.

## 고침 — 판정을 한 곳으로

공용 `tellCommandResult` 하나를 두고 여덟 자리가 전부 그것을 지난다.
`'ok'` 일 때만 후속 상태를 갱신한다 — **미확정에는 손잡이(`activeSprintId`)·보류 지점
(`clearSuspendedQuota`)·작업 기록(`clearSprintData`)을 건드리지 않는다.** 잃으면 사용자는
진행을 보지도 멈추지도 못한 채 다시 누르고, 실행 명령에서 그것은 **유료 LLM 재실행**이다.
일시정지는 **새 Studio 와 같은 공용 명령**으로 옮겼다(서버 핸들러가 같은 것을 확인).

## 찾은 결함 — 「됐는지 모른다」를 「안 됐다」로 말했다

구 통제실은 `r.ok` 하나로 갈라 **UNKNOWN 을 REJECTED 와 같은 말**로 냈다. 이 명령의
UNKNOWN 은 응답 유실·5xx·문맥 변경이라 「안 됐다」가 아니다. 실패라고 들으면 사람은
**다시 누르고**, 그때 같은 결과물이 두 벌 저장된다 — `saveProjectRelease` 가 원키로
막으려던 사고를 화면이 되살리고 있었다. 게다가 `alert` 는 전역이라 A 의 결과가 B 화면 위에
떴고, 그때 값이 `CONTEXT_CHANGED`(ok=false)여서 **저장됐을 수도 있는 것**을 실패로 말했다.

```
고침(프런트 1파일)
  완료 «시점» 의 열린 프로젝트와 비교한 뒤에 말한다
  ACCEPTED  「접수했습니다」 + 공용 함수가 준 문구(화면이 지어내지 않는다)
  UNKNOWN   「저장 여부를 확인하지 못했습니다. 다시 누르지 마십시오 — 두 벌 저장될 수 있습니다」
  REJECTED  「저장하지 못했습니다」 + 사유
```

## 보완 1 — 실패가 «전부» 결과로 돌아온다


## 묶음 2 — 거절 검증용 격리 fixture (**서버 판정까지 완료**)

### 추가만 했다 — 정책은 손대지 않았다

기존 격리 생성 절차(`org_directory.create_department` · `upsert_user` · `set_user_roles`)만
썼다. **운영 계정·권한 정책·실사용자·키는 바꾸지 않았다.** role 우회·principal 모의 주입·
localStorage 로 없는 권한을 만드는 일은 하지 않았다. 합성 계정은 `.invalid` 규약을 따른다.

```
부서 추가   demo_battery → 기존 ECM 노드 plant-afs-battery-02  (노드를 새로 만들지 않았다)
계정 추가   t_scope_probe@afs.invalid   비관리자 · 두 부서 member
              readable = [battery, smelting]      ← A/B 둘 다 «고를 수 있다»
            t_narrow_probe@afs.invalid  비관리자 · battery 만 member
              readable = [battery]                ← 제련공장에 role 이 **없다**
```

⚠️ 둘 다 **관리자 아님**이다. 관리자면 범위 제한이 애초에 안 걸려 아무것도 증명하지 못한다.
(기존 `hikwon`·`demo.admin` 은 관리자라서 이 검증에 쓸 수 없었다 — 그래서 «추가» 했다.)

### 두 거절을 분리해 실측했다 — 실제 세션 + 실제 제품 API

세션은 제품 인증 저장소가 발급한 **진짜**다(`auth_store.create_session`). 서버는 같은
`C:\sentwt\datauth.db` 를 읽는다. 토큰은 기록하지 않는다.

```
① 선택 범위 거절  — 같은 계정, 고른 범위만 바꾼다
   t_scope_probe / A 제련공장(소유 부서) → 200  프로젝트 메타
   t_scope_probe / B 배터리공장          → 404  「현재 문맥에서 프로젝트를 찾을 수 없습니다」
② 사용자 권한 거절 — 제련공장에 role 이 없는 좁은 계정
   t_narrow_probe / B 배터리공장(자기 범위) → 404
   t_narrow_probe / A 제련공장(권한 없음)   → 404
③ 대조군 — 같은 호출이 «되는» 것
   hikwon / A 제련공장 → 200
```

★ ①은 **계정을 바꾸지 않고 고른 범위만 바꿔** 200 → 404 로 뒤집혔다. 그래서 그 404 는
계정 탓이 아니라 **선택 범위 탓**이다. ③이 없으면 「원래 다 404 아니냐」를 배제할 수 없다.

### ⚠️ 한계 — 정직하게

- ②의 거절도 **404(비가시)** 다. 그 계정에게 그 프로젝트는 «안 보이는» 것이지,
  «보이지만 권한이 없는» 것이 아니다. **403 을 만들려고 상태코드를 고치지 않았다** —
  지시대로 비가시는 404 그대로 둔다. 「보이지만 못 하는」 거절(403)은 조회가 아니라
  **쓰기 행동**에서 생기는 별개 경우이며 이번 범위 밖이다.
- 이 증거는 **서버 판정**이다. 브라우저 화면 증거와 섞지 않는다.

### ★★★ 화면 확인 중 나온 제품 소견 — **문맥 전환이 manager 이상만 된다**

사용자가 합성 계정으로 로그인해 전환을 눌렀더니:

```
문맥을 바꾸지 못했습니다
권한이 없습니다: ['admin.organization'] — 관리자 센터의 해당 탭 권한이 필요합니다.
```

서버 판정으로 재현했다.

```
표:   POST /api/v1/enterprise-context/contexts/select → ('admin.organization',)
역할: viewer ✗   member ✗   manager ✓
member 계정 → 자기 범위 A·B 둘 다 403
관리자(대조군) → 200
```

⚠️ 그런데 **그 엔드포인트는 아무것도 저장하지 않는다.** 자기 docstring 이 「서버가 상태를
저장하지 않는다 … 그 범위를 고를 수 있는가만 판정해 준다」고 적고 있고, 안에 이미
`can_read_node` 검사가 있다. **viewer·member 는 그 검사에 닿지도 못한다.**
표에서 이웃한 항목(`tenants` 회사 이름 세우기 · `profiles/approve` 승인)은 진짜 기준정보
수정이라 성격이 다르다 — 이 항목만 「고르기」인데 같은 칸에 있다.

★ **권한 정책은 고치지 않았다**(지시 범위 밖). 의도인지 결정이 필요하다:
  「일반 사용자는 자기 문맥을 바꿀 수 없다」가 맞는가, 아니면 이 한 줄이 잘못 분류됐는가.

### ⚠️ 그리고 내 fixture 결함 하나 — 고쳤다

배터리공장 ECM 노드의 `dept_id` 가 비어 있었다. **부서 쪽만**(`departments.scope_node_id`)
묶고 **노드 쪽**은 안 묶었다 — 저장소의 `seed_ecm` 이 굳이 **양쪽을** 묶는 이유가 그것이다.

(403 「이 조직 범위를 볼 권한이 없습니다」). 노드에 `dept_id` 를 채워 고쳤다.
★ 「쓰는 곳과 찾는 곳은 출처가 같아야 한다」를 또 어겼다.

계정은 `member` → **`manager`** 로 올렸다. **역할 «배정» 만 바꿨고 역할이 가진 권한

## 묶음 3 — SSE 합성 표식 (**전달·필터 실측 / 화면 소비는 미확인**)

### 하네스 — 지시한 모양 그대로

```
tests/b6_sse_probe.py        재사용 가능한 하네스(시험 영역). 부르지 않으면 아무 일도 안 한다
C:/sentwt/run_isolated.py    임시 접근점을 **격리 런처에서만** 붙인다(워크트리 전용)
  → POST /__isolated__/b6-sse-probe   로컬 전용 · fixture project_id 전용 · 이벤트 종류 고정
제품 라우터에는 디버그 발행 API 를 **넣지 않았다.**
```

발행은 `uvicorn.run("main:app")` 과 **같은 프로세스**에서 일어난다 — 별도 파이썬 프로세스의
브로드캐스터는 전송 증거가 되지 못하므로 런처에서 `main.app` 을 먼저 import 해 붙였다.

안전(소스로 확인하고 적는다): 브로드캐스터의 내부 리스너는 `SupervisorDaemon.handle_event`
**하나뿐**이고, 그것은 `NODE_COMPLETED` **그리고** 감시 노드일 때만 움직인다. 이 표식은 둘 다
아니므로 **LLM 0 · 외부 전송 0**. `_broadcast_scope='global'` 은 싣지 않았다.

### 계측기부터 증명했다 — 첫 음성 시험은 **내 계측 오류**였다

처음에 B 범위 관찰 연결로 A 소유 표식이 **들어왔다.** 「실시간 경계가 뚫렸다」로 볼 뻔했는데,
원인은 제품이 아니라 내 계측기였다:

> `POST /auth/sse-ticket` 은 **요청 헤더의 범위를 일부러 무시**하고 **본문의
> `scope_node_id`** 만 본다(`auth_control` 주석: 「요청자가 scope 를 지정하지 않는다」).
> 나는 헤더로만 보냈다 → 티켓이 «전체» 로 발급됐고, 전체 구독에는 오는 것이 맞다.

본문으로 고쳐 다시 쟀다. **「재는 도구부터 증명한다」를 또 어겼다.**

### 결과 — 양성/음성 둘 다, 같은 계측기로

```

      → B6_SCOPE_PROBE|B6-PROBE-POS-004 수신     ← 계측기가 살아 있다는 증거
경로  /auth/sse-ticket(실제) → /ws/timeline(실제) → 서버 소유권·문맥 필터(실제) → EventSource(실제)
```

★ 「아무 이벤트도 안 옴」만으로 성공이라 하지 않았다 — 같은 도구의 양성 대조를 붙였다.
★ 차단 대상은 **B 에서 비가시인 A 소유 fixture** 다(같은 계정·같은 범위로 REST 는 404).

  그 표식이 보이는 자리(서버 로그 팝업)를 열지 못했다. 「전달됐다」와 「제품이 소비했다」는
  다른 사실이므로 소비는 주장하지 않는다.
- **뒤늦은 «옛 연결» 이벤트 무시**: 지시대로 네트워크 차단과 **별개**인 지연 이벤트 실행
  시험이 필요하다 — **미착수**.

### 부수 발견 — 기동이 설치본으로 노드를 다시 쓴다

배터리 노드에 심은 `dept_id` 결속이 **서버를 재기동하니 사라졌다.** `run.py` 의
`_apply_installation_settings()` 가 `data/instance.json` 으로 `organization_nodes` 를 매 기동
**다시 쓰기** 때문이다. DB 에 직접 심은 fixture 결속은 기동으로 날아간다.
★ `instance.json` 쪽에 `dept_id` 를 적어 고쳤고 재기동 후 유지를 확인했다. 절차 문서 갱신 대상.

#### ② 브라우저 «화면 표시» — 미확인으로 남긴다

작업공간을 열어 둔 채 표식을 발행했지만 **DOM 어디에도 나타나지 않았다**

(「서버 연결」은 상태 표시였고 로그 팝업을 열지 못했다).

★ 그래서 셋을 **구분해** 적는다.

| 사실 | 증거 |

## 1. 경계 보완 — 「모르면 추측하지 않는다」

### ① 번호 없는 항목에서도 입력을 지킨다

종전에는 `incoming === null || here === null` 이면 **묻지 않고 바로 화면을 내렸다.**
번호가 없다는 것은 「앱 밖」이라는 증거가 아니다 — 같은 문서에서 다른 코드가 만든 항목일
수 있고 그때 `beforeunload` 는 뜨지 않는다. 지적 그대로다.

⚠️⚠️ **그리고 내 시험이 그 동작을 초록으로 고정하고 있었다**(`assert.deepEqual(applied, [0])`).
시험이 결함을 단언한 두 번째 사례다. 그 단언을 지우고 반대로 뒤집었다.

### ② `delta === 0` 은 «모른다»는 뜻이다

`history.go(0)` 은 아무 일도 안 하는 것이 아니라 **문서를 다시 읽는다.** 되돌리려다
미저장 입력을 통째로 잃는 자리였다. 번호가 겹쳤다는 것 자체가 신뢰할 수 없다는 신호다.

⚠️ 검토가 짚은 대로 **내 대역 히스토리가 이 경계를 덮고 있었다** — 위치가 같으면 조용히
넘겼다. 이제 `go(0)` 을 `RELOAD` 로 기록하게 고쳐서, 회귀가 빨강으로 보인다.

### ③ 믿을 수 있을 때만 붙잡는다

```ts
const incoming = typeof raw === 'number' && Number.isSafeInteger(raw) ? raw : null;
const delta = incoming !== null && here !== null ? incoming - here : 0;
const trusted = delta !== 0 && Math.abs(delta) < window.history.length;
```

정수가 아니면(소수·NaN·문자) 번호로 쓰지 않는다. 칸 수가 이 문서의 히스토리보다 클 수 없다.

### ④ 믿을 수 없을 때의 **안전한 fallback**

```
잃을 것이 없으면          → 그대로 따라간다(정상 이동을 막지 않는다)
미저장 입력이 있으면      → go() 를 «부르지 않고», 화면·입력도 «건드리지 않고»,
                            어긋난 주소를 배너로 «보이게» 남긴다
```

배너는 **명시적인 선택 둘**을 준다. 둘 다 칸을 늘리지 않는다.

- 「주소가 가리키는 화면으로 이동」 → 기존 미저장 확인 UI(저장/유지/폐기)를 그대로 거친다
- 「이 화면의 주소로 되돌리기」 → **현재 칸의 주소만 바꿔 끼운다**(`replaceState`).
  새 칸을 만들지 않고 **없는 번호를 지어내지도 않는다**(기존 state 를 그대로 둔다)

★ 번호가 있는 정상 앞/뒤 취소·승인은 **그대로다**(아래 검사 ②~⑧ 보존).

### ① 취소 복원이 뒤로 한 칸만 가정함 → **번호로 방향과 칸 수를 안다**

```
취소 → window.history.go(-delta)      승인 → window.history.go(delta)
```

- **앞으로 이동 취소**가 이제 뒤로 돌아온다(종전 `go(1)` 은 «더 앞으로» 갔다).

| ③ | 「계속 작성」(취소) | 전부 그대로 (URL·번호·입력·칸) |
| ④ | **뒤로 → 「입력 유지하고 이동」** | 번호 0 · 목록 화면 · 칸 안 늘어남 |
| ⑤★ | 목록(2)에서 **앞으로** 취소 | 확인창 뜸 · **번호 1로 복귀** · URL `target=new` · 입력 그대로 |
| ⑥ | 다시 **앞으로** → 「입력 유지하고 이동」 | 번호 2 · 목록 화면 |

**⑤ 가 이번 지적의 정면이다.** 옛 `go(1)` 이면 취소가 «더 앞으로» 가서 화면과 주소가
갈라졌다. 지금은 온 방향으로 정확히 되돌아온다.

### 연속 전이 — 「복원 표시가 다음 클릭까지 남는가」

초안 주소로 들어간 뒤(문서 적재 1회) **그 뒤는 전부 같은 문서**다.

```
초안(번호0) → 닫기 → 목록(번호1, 칸+1)     ← 닫으니 URL 에서 초안이 «빠졌다»
  → 뒤로 → 초안(번호0, 칸 그대로, 편집기 내용 복원)
  → 닫기 → 목록(번호1, 칸 그대로 = «교체가 아니라 밀어 넣기»)
  → 뒤로 → **초안 주소·화면으로 돌아왔다**
```

마지막 줄이 핵심이다. 복원 표시가 남아 있었다면 그 클릭이 **교체**가 되어 초안 칸을
덮었을 것이고, 뒤로가기는 초안으로 못 돌아온다.

### ★★★ 브라우저가 잡은 새 결함 — `?target=new` 가 히스토리 칸을 **둘** 만들었다

```
고치기 전: ?space=build&target=new 로 진입 → 번호 2 · 뒤로가기가 «중간의» ?space=build 로 감
고친 뒤  : 같은 주소 → 번호 0 · 중간 칸 없음 · 만들기 화면 열림
```

원인은 **effect 로 뒤늦게 열었기 때문**이다. 첫 렌더에서는 `buildStart` 가 `false` 라
`openTarget` 이 비었고, 그 사이 URL 동기화가 **목록 주소를 새 칸으로 밀어 넣었다.**
`buildStart` 초기값을 `initialEntry.current.isNew` 로 옮겼다 — 릴리스의 `pendingRelease`
와 **같은 이유·같은 처방**이다(그래서 릴리스는 이 문제가 없었다).

⚠️ 이건 내가 이번에 만든 결함이다. `new` 를 주소에 실으면서 **첫 렌더 순서를 안 봤다.**
같은 모양을 잡는 시험을 더했고(초기값을 «실행»해서 본다), 변이로 극성도 확인했다.

## 8. 미검증 / 위험 / 필요한 결정

- **실제 브라우저 NOT_RUN.** 프런트 검사는 모의 HTTP·실제 flow/store·SSR·정적 계약이다.
  URL 재조회·뒤로/앞으로·중복 mount 는 리뷰 순서 5번(단일 진입·히스토리) 범위다.
- ⚠️ **프런트가 새 칸을 «엄격히» 요구한다.** `is_mega_project` 가 없으면 `malformed` 다.
  같은 저장소에서 함께 배포되므로 택했으나, **서버보다 프런트가 먼저 나가는 배포에서는
  프로젝트 진입이 전부 막힌다.** 관용(없으면 false)으로 바꿀지는 지시 대상이다.
- ⚠️ **관찰(고치지 않음)**: `_ID_RE` 에 **길이 상한이 없다**. 자식 id 200자도 형식상
  정상이라 404 가 된다. 부모 `project_id` 도 처음부터 같은 성질이다(프런트는 160자로 막는다).
- ⚠️ 손상된 상태 파일은 404 가 아니라 **503** 이라, 「없는 자식」과 「있는데 손상된 자식」이
  구분된다. 부모 단독 경로가 원래 그런 성질이라 계약을 맞췄을 뿐 새로 만든 것은 아니다.

- **서버 권한 변경 없음.** 판정은 전부 기존 `_authorized`·`resolve_scope(fresh=True)` 재사용.
  ★ Codex 핵심 diff 검토 대상으로 표시할 **권한 변경이 없다.**
