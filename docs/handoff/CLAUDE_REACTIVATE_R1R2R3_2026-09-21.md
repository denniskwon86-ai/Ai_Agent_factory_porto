## 지적 3건 모두 제 코드의 실제 결함이었습니다 — 수용하고 고쳤습니다

| # | 지적 | 고친 곳 | 상태 |
|---|---|---|---|
| R1 | 후보로 복원한 뒤 재개를 **다시** 부르면 `active` | `reactivate` | **완료** |
| R2 | 지문을 중단 직전이 **아닌 과거 값**으로 복원 | `_restore_point` | **완료** |
| R3 | 읽기·쓰기 사이 **경쟁** | `set_status` CAS + 트랜잭션 | **완료** |

### R1 — reactivate 는 중단 해제이지 승격 명령이 아니다

앞선 판의 「중단이 아니면 종전대로 ACTIVE」가 **같은 구멍을 다시 열었습니다.**
이제 중단 상태가 아니면 **상태·지문·대체 대상을 그대로 둔 채** 돌려주고,
`restored: False` 와 함께 **복원했다고 말하지 않습니다.** 오류 계약은 늘리지 않았습니다.

* `deprecated` 의 암묵적 경고 해제도 이 명령에서 **하지 않습니다**(명시적 상태 변경과 분리).
* 조기 반환이 검증을 건너뛰지 않도록 **행위자·릴리스 존재 확인을 앞으로** 옮겼습니다.

### R2 — 세 값은 «같은 한 행» 에서 온다

`_restore_point` 가 이제 **중단 바로 앞 이력 행 하나**에서 상태·지문·대체 대상을 통째로
읽습니다. 그 행이 그때 `program_status` 에 쓴 값이 곧 중단 시점의 현재 값이었습니다.

* **빈 값도 값**입니다 — 과거의 비어 있지 않은 값으로 채우지 않습니다.
* 중단이 **첫 기록**이면 앞 행이 없으므로 지문·대체 대상은 빈 값입니다(만들지 않습니다).
* 앞 행의 도착 상태 ≠ 중단 행의 출발 상태면 **이력이 어긋난 것**이므로 「모른다」로 답합니다.

### R3 — 읽기·판정·쓰기를 한 트랜잭션으로

`set_status` 가 `BEGIN IMMEDIATE` 로 쓰기 잠금을 먼저 잡고, **직전 상태를 그 안에서** 읽습니다
(종전에는 밖에서 `get_status` 로 읽었습니다). 새 `expected_status` CAS 를 걸면 그 사이 상태가
바뀐 경우 **아무것도 쓰지 않고 거절**합니다. `reactivate` 는 `expected_status=DISABLED` 로
부릅니다. SQLite 트랜잭션이라 **프로세스가 달라도** 유효합니다.

## ⚠️ 일반 `status` 경로 — **배포 차단으로 표시합니다** (고치지 않았습니다)

`POST /api/v1/programs/{release_id}/status` 는 관리자가 지정한 상태를 `set_status` 에 그대로
넘깁니다. 이번 R1 수정은 `reactivate` 만 막았고 **이 경로는 열려 있습니다.**

```
소비자        제품 프런트에 «없음» — programApi.ts 는 disable/deprecate/reactivate 만 감싼다
              (관리 API·도구에서만 부를 수 있다)
운영 활성화   /status 로 active 를 직접 지정하면 candidate → active 가 그대로 통과한다
승격 기록     workspace_promotion 은 별도 테이블 — 이 경로는 만들지도 보지도 않는다
```

**최소 차단안(제시만):** `set_status` 가 `CANDIDATE → ACTIVE` 전이를 **승격 근거 없이는
거절**하게 한다. 근거의 정의(승격 기록 유무? 별도 인자?)는 승인 경계에 관한 결정이라
제가 정하지 않습니다. 역할 권한을 바꾸거나 새 승격 정책을 만들지 않았습니다.

★ 기존 전사 승격 기록은 중단/복원으로 **만들지도 지우지도 않습니다.** 이전에 active 였다는
이유만으로 새 운영 승인을 발급하지 않습니다.
