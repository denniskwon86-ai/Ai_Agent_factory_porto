- 시작 기준선: `c1e0c8b42`. 관문 G2 초기자료 정합성 / 실사용자 조직 연결 선행 점검.

## 1. 앞 판단을 구체화한 사실

“배터리 부서가 없다”가 아니다. **기존 부서는 있지만 검증 공장과 다른 회사 문맥에 있다.**

| 항목 | 기존 사용자 조직 | 업무키트 설치 조직 |
|---|---|---|
| 회사 표시 | LS MnM | LS MnM |
| tenant | tenant_default | tenant-afs-demo-materials |
| 회사 노드 | node_41402723bc90 | org-laxs-mnm |
| 배터리 노드 | node_36c1c7c797e0 / 배터리소재 사업부 | plant-afs-battery-02 / 배터리소재 공장·사전검증 |
| 연결 부서 | production_battery / 배터리소재 생산 | 비어 있음 |
| 상위 조직 | 기존 LS MnM 노드 | 검증 LS MnM 노드 |

현재 tenants 이름 등록 표에는 검증 tenant의 LS MnM 1행이 있지만, organization_nodes에는 위 두 문맥이 실제로 존재한다. **표시명 일치로 같은 범위라고 단정하거나 합칠 수 없다.**

master.db의 현행 active 부서는 13개다(테스트 부서 포함). 구매·물류는 기존 회사 노드, 배터리소재 생산은 기존 배터리소재 사업부에 연결돼 있다.

활성 사용자와 조인한 역할 기록:

- 구매: manager 1건
- 물류: manager 1건
- 배터리소재 생산: manager 1건 + member 1건
- 제련공장(시연 자료): manager 2건, **둘 다 .invalid 예약 도메인 계정**

예약 도메인이 아닌 계정이라는 이유만으로 실제 권한이 검증된 것으로 보지 않는다. 이번에는 Principal/PDP를 호출하지 않았다. 반대로 제련 쪽에 ACTIVE 결속이 있다는 이유로 실사용자 접근까지 이미 된 것으로 보지도 않는다.

## 3. 권고 방향과 선택에 따른 영향

**권고: 새 시연 전용 부서를 추가하지 않고 기존 구매·물류 부서를 책임 조직으로 활용하되, 기존 사용자 조직과 업무키트가 같은 회사 문맥을 보도록 정리하는 방향을 먼저 확정한다.**

이는 “모든 테스트·시연 데이터를 단일로 유지한다”는 사용자 방향과 맞는다. 다만 현재 같은 물리 DB를 쓴다고 같은 tenant/권한 문맥인 것은 아니다.

- 기존 부서의 scope_node_id만 바꾸면 기존 사용자가 보던 자료와 권한 범위가 바뀐다.
- 반대로 업무키트 행의 tenant만 바꾸면 판·색인·기준선·계산 승인·기존 안건의 결속이 어긋날 수 있다.
- 어느 tenant를 유지할지는 이름이나 레코드 수로 고르지 않는다. 현재 프로젝트·앱·원장·안건에 대한 이행 영향 조사와 명시 실행 지시가 필요하다.
- 임시 검증 부서 추가는 기존 사용자 조직을 즉시 옮기지 않는 대안이지만, 또 다른 검증용 조직·역할을 유지하게 된다. 사용자 결정 없이 선택하지 않는다.
- 제련공장과 hq의 현재 연결도 같은 회사 문맥 정리 범위에서 점검해야 한다. 이번에 배터리만 고쳐 전체 정합성이 완성됐다고 하지 않는다.

이번 종료점은 **기존 부서를 활용하는 방향의 승인 여부**를 묻는 것이다. 실제 테넌트 병합·이관이나 부서 재배치를 승인받았다고 해석하지 않는다.

## 4. 시행일과 인증일은 업무 발생일과 다르다

`core/data_preparation/scope_index.py:write_conn()`는 소유권을 **새 데이터판의 certified_at** 시점으로 조회한다. `ownership_binding.resolve()`는 UTC의 [effective_from, effective_to) 반열 구간을 사용한다.

따라서 적용 순서는 다음과 같다.

1. 회사·부서 대응 및 실제 사용자 역할을 결정한다.
2. 같은 문맥의 책임 부서·범위·자료 5종·시행 시점·근거를 승인 절차로 확정한다.
3. 그 시행 시점 이후에 새 데이터판을 인증하고 색인을 함께 만든다.
4. 일반 담당자에게 정상 조회되는지, 권한 없는 대조 사용자에게는 보이지 않는지 확인한다.

오늘 결속을 만들고 8월의 옛 인증일로 색인만 다시 계산하면 오늘 결속이 선택되지 않을 수 있다. 이를 피하려고 소유권을 2023년 발주일까지 임의 소급하지 않는다.

FND-01 full 원본은 배터리 공장이 VIRTUAL·2024-01-01부터 유효하고 상위가 org-afs-battery-bu이다. 설치 ECM은 org-laxs-mnm 아래의 검증 공장으로 연결됐으며 유효일은 빈값이다. **원천 조직 이력과 설치 문맥은 같지 않다.** 이 차이와 2023년 계약 후보를 분리해서 검토해야 한다. 현재 자료 소유권을 부여하는 것이 과거 조직 이력까지 증명하지 않는다.

## 5. 기존 제품 경로를 사용해야 할 통제

새 승인기를 만들지 않는다. 기존 ownership API와 핵심 계약이 다음을 수행한다.

- 승인자 실재·활성, 사용자 정본 admin/data_admin 플래그와 확정 권한 교차
- 대상·근거·시행일이 포함된 승인 지문과 원장 사건 확인
- 중첩 결속 거부, 철회 사건과 부서 생존 재검증
- 승인 뒤 등록 실패 시 승인 사건 취소/보상 처리

이번에 해당 API를 호출하지 않았다. 읽은 ACTIVE 행은 권한 검사 통과의 증명이 아니다. 조직 대응을 정한 뒤 실제 주체로 검증할 때 다음 수용 기준을 쓴다.

- 담당자: 허용된 5종을 일반 권한으로 볼 수 있음
- 무관한 부서 사용자: 대상 자료 비노출
- 관리자만 보이고 일반 사용자에게 0건: 미완료
- 소유권 미지정/시행일 미도래: 미지정을 표시하고 0 영향·정상 준비로 오인하지 않음
- 기존 안건 3개의 봉인 근거 및 다른 정상 앱 접근이 보존됨

## 6. 읽기 검증·주의사항

- 저장소 서비스의 _connect/_ready/get_department 등 초기화 경로를 호출하지 않았다.
- 실제 파일은 `data/master/master.db`, `data/enterprise_context.db`, `data/data_preparation.db`다. 처음 data/master.db로 시도한 잘못된 read-only 조회는 열기 실패했고 파일을 만들지 않았다.
- SQL은 mode=ro, query_only=ON, BEGIN으로 읽었다. 사용자 식별자·비밀번호·토큰을 출력하지 않고 역할은 집계만 했다.
- 선택한 DB 3개 및 WAL/SHM 6개를 전후 비교했다. **본 DB 3개는 동일**, data_preparation의 WAL/SHM은 없음→빈 WAL/SHM 파일로 나타났다. 읽기 전용 SQLite의 보조 파일 생성 가능성을 기록하며 타 세션 탓으로 귀속하지 않는다.
- DB들 간 동시점 스냅샷, 원장 유효성, 실사용자 API·브라우저 검증은 미실행이다.
- 소스·제품 기능을 고치지 않은 결정자료 작업이므로 pytest/T3는 실행하지 않았다. 5종 행수는 부모 후보에서 독립 재집계했다.
- 기존 실행 로그 및 docs/video/ 작업은 보존하고 커밋에서 제외한다.
