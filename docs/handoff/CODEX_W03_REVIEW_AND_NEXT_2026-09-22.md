### CR-1 (차단) — 링크 정책이 저장소와 **반대**다

`core/atomic_write.py:_resolved_target()` 은 대상이 symlink·junction 이면 **따라가서** 실제
파일에 쓴다. 구현자가 「공유 저장을 링크로 거는 구성을 지원해야 한다」를 근거로 댔다.

**그 근거가 틀렸다. 이 저장소는 링크를 «거절»하는 쪽으로 이미 확립돼 있다.**

```

api/routes/factory_control.py:2448    latest_state.json  링크면 503 "연결된 상태 원문"
api/routes/factory_control.py:2631·2662                  "연결된 파일을 원본으로 인정하지 않는다"
core/studio_project_files.py:53·56 · core/studio_pause_state.py:37
core/studio_revision_requests.py:81·87 · core/studio_contract_reconcile.py:219·292
api/routes/studio_input_draft_control.py:106
```

P05.1 검토에서 **「출력 경로 junction 차단 누락」이 결함으로 지적**된 것과 같은 방향이다.

⚠️ **실제로 만들어지는 상태**: `latest_state.json` 이 링크일 때 —
쓰기는 링크를 따라가 **성공**하고, 읽기는 `factory_control.py:2448` 이 **503 으로 거절**한다.
쓰기와 읽기가 갈리는 비대칭이며, W03 이 없애려던 「한쪽에서만 열리는 자원」을 오히려 만든다.

**요구**: `_resolved_target()` 을 **차단**으로 바꾼다. 링크·junction 대상이면 쓰지 말고
식별 가능한 오류로 끊는다. 대상뿐 아니라 **상위 경로**도 본다
(`scripts/session_data_snapshot.py:70 regular()` 가 이미 그 형태다 — 재사용 검토).
시험의 `test_a_linked_target_stays_a_link` 는 **반대 방향으로 뒤집는다.**

### 미충족 잔여 — 「잘못된 판본」과 「성공 버전 소실」

구현자는 lost update 를 「지시가 다른 문제라고 했으므로 범위 밖」으로 두었다. 지시 원문
(§4-2)은 **「두 가지를 한 번에 달성했다고 쓰지 말라」**는 뜻이고 **「하나만 해도 된다」가
아니다.** acceptance 에도 「부분 파일**이나 잘못된 판본**」으로 둘 다 들어 있다.

다만 구현자가 **하지 않았음을 문서·코드 주석·probe 출력에 일관되게 명시**했으므로 과장은
없다. 이 부분은 **결함이 아니라 잔여**로 다룬다 — §4 에서 별도 단계로 뗀다.

★ 더 구체적인 잔여 하나: 지시의 **「정상 반환한 성공 버전의 소실을 허용하지 않는다」**가
`core/async_orchestrator.py:_save_latest_state` 에서 **실제로 깨진다.** Windows 교체 거절이
예외로 오는데(probe 실측 41/180) 그 함수가 `except Exception: print(...)` 로 삼킨다.
호출자는 저장된 줄 알고 진행한다. 구현자가 「동작이 바뀌므로 판단 요청」으로 남겼고,
그 판단은 **§4 에서 내린다.**

### 관측 — 원자 쓰기 구현이 저장소에 **넷** 있다

구현자가 「구현을 한 곳에 둔다」고 썼으나 통합한 것은 하나뿐이다.

```

core/config_snapshot.py:160               → 그대로 (os.replace, "반쪽 파일이 남지 않게")
```

W03.2 대상(release.json·latest_state.json) 밖이라 **이번 판정에 영향은 없다.** 다만 서술은

## 5. Codex 에게 넘길 때 함께 볼 것

1. **CR-1 의 방향이 맞는가** — 링크를 차단하는 것이 정말 이 저장소의 정책인가, 아니면
   읽기 쪽만 그런 것이고 공유 마운트 지원이 별도 계획에 있는가. 위 아홉 곳은 전부 읽기·
   검증 경로다. **쓰기 쪽 정책이 명시된 문서를 찾지 못했다.**

### Claude 다음 묶음 — 중간 검토 대기 없이 연결 구현

1. **조건부 저장→writer 배선:** 읽은 기준 revision/digest와 현재 값을 비교하고 비교부터 교체까지 같은 상호배제 구간으로 묶는다. 기존 잠금을 먼저 조사한다. `studio_project_files.operation_lock`은 `prj_` ID 제한·로컬 `data/studio_bootstrap_locks` 경로이므로 그대로 호출한다고 배포 노드 간 잠금이 되지 않는다. 서로 다른 writer가 같은 잠금 권위를 사용해야 한다. 프로세스 내부 lock이나 잠금 밖 compare+replace는 불충분하다. 충돌 시 낡은 payload를 최신 revision으로 재표기해 덮어쓰지 않는다. 정본 writer별 적용/불필요 근거를 남긴다.
2. **실패 결과→실제 소비:** 성공/실패·미확정 결과를 호출자까지 전달한다. checkpoint를 회복 원본으로 재사용한다면 실제 재조회로 확인한다. 새 거대 복구 시스템은 만들지 않는다. A 프로젝트 실패 후 B 성공이 A 실패를 지우지 않게 한다. 기존 API 상태코드를 임의 변경하지 않는다.
3. **상위 링크→같은 소비:** 명시한 저장 뿌리와 대상 사이의 모든 구성요소를 링크를 풀기 전에 검사한다. 뿌리 자체/상위 링크도 묵시적으로 신뢰하지 말고 초기 검증 대상으로 둔다. 정식 mount는 별도로 식별한다. 뿌리 정보가 없다는 이유로 즉시 부모에서 검사를 끝내지 않는다. mkdir 등 선행 쓰기도 같은 경계 안에 둔다. 실제 깊은 junction 거절과 정상 깊은 경로 양성 하나로 확인한다. OS 개발자/관리자 모드는 변경하지 않는다.
4. **후속 읽기·복구로 묶음 확인:** 두 독립 writer가 같은 기준을 읽고 경쟁→늦은 writer 충돌→두 소비자는 정상 새 판본 재조회. 중간 교체 실패는 이전 판본 보존·저장 성공으로 보이지 않음. 이어 W03.3 정본 부재→격리→동일 소유 정본 복구→disabled 결정 보존과 타 문맥 비노출을 소비한다. 관련 회귀는 끝에 한 번. 함수마다 변이·새 요청서·전제품 검증을 반복하지 않는다.
