# 테스트 증거·실패 분류 기준

> 기준일: 2026-07-26 | 목적: LLM 공급자 변동과 제품 결함을 혼동하지 않고, 같은 결과를 다른 실행자가 재검증할 수 있게 한다.

## 1. 시나리오 결과 상태

| 상태 | 의미 | 다음 행동 |
|---|---|---|
| `PASS` | 수용 기준과 최소 증거를 모두 충족 | 다음 시나리오 진행 가능 |
| `COND` | 핵심 흐름은 완료했으나 명시한 제한/외부 조건이 남음 | P2이면 책임자 승인 전 다음 Phase 금지 |
| `FAIL` | 제품·설계·테스트 자동화 결함이 재현됨 | 결함 수정 후 동일 시나리오 재실행 |
| `DEFERRED` | 쿼터/공급자/외부 환경 때문에 실행을 완료할 수 없음 | 환경 회복 뒤 같은 입력으로 재개 |
| `IN_PROGRESS` | 실행 중이며 마지막 사실 상태가 기록됨 | 재개 전 상태 API로 대조 |
| `SKIP` | 현 버전에 구현되지 않은 기능 또는 범위 밖 | 구현 전 PASS로 취급하지 않음 |

원인 태그는 하나 이상 붙인다: `SYSTEM`, `EXTERNAL`, `TEST_ENV`, `BUILD_RECOVERY`, `DATA_GROUNDING`, `SECURITY_SCOPE`, `DESIGN_GAP`.

## 2. 최소 증거 묶음

각 LLM 시나리오는 트래커의 비고 또는 연결된 결과 문서에 아래를 남긴다. 긴 원문·API 키·개인정보는 남기지 않는다.

```text
시나리오 / 프로젝트 ID / 시작·종료 시각 / 실행자
입력 아이디어와 템플릿 ID
최종 factory_mode, current_stage, current_sprint_task_id
WBS 태스크별 최종 상태와 FAILED 사유(있으면)
HOTL 단계·입력한 피드백 또는 자동승인 여부
활성 LLM 공급자, 429/504/timeout 발생 횟수와 최종 원인
필수 산출물 목록(RFP, PRD, 아키텍처, WBS, 코드, QA, 매뉴얼)
프리뷰/문서/UI Releases 확인 결과, release_id
점수(6개 항목)·최종 상태·원인 태그·다음 행동
```

API 관찰 최소 세트는 다음과 같다.

```text
GET /api/v1/factory/{project_id}/state/latest
GET /api/v1/factory/{project_id}/wbs
GET /api/v1/factory/{project_id}/feed
GET /api/v1/factory/{project_id}/hotl/check
GET /api/v1/factory/logs     # 서버 관점 오류가 필요한 경우
```

## 3. 빌드 자가복구 평가

현재 자가복구는 코드 생성 → 구문/렌더/스모크/회귀 검사 → 개발자 재작업을 최대 3회 시도하고, 한도를 넘으면 안전 상태로 롤백하고 실패 상태를 전파하는 구조다. “3회 시도” 자체가 성공 증거는 아니다.

| 확인 | 성공 판정 | 실패 판정 |
|---|---|---|
| 시도 추적 | `developer_retry_count`가 증가하고 각 실패 이유가 남음 | 카운터 초기화/무한 루프/원인 유실 |
| 회복 | 재작업 뒤 모든 하드 게이트 통과, WBS `DONE` | 실패 파일이 남거나 검사 우회 |
| 한도 초과 | 롤백·`SPRINT_FAILED`·WBS `FAILED` 또는 명확한 HOTL 상승 | UI만 계속 실행 중, 다음 태스크가 진행 |
| 후속 조치 | 실패 번들로 사용자가 수정 지시/재시도/종료 선택 가능 | 자동으로 같은 프롬프트를 무한 반복 |

향후 개선 요구로는 실패 번들(실패 파일 diff, 검사 로그, 마지막 유효 checkpoint), 원인별 복구 전략 선택, 사람 승인 재시도 버튼, 재시도 예산·쿨다운 표시가 있다. 이는 현재 테스트에서 **존재 여부가 아니라 실제 관찰 결과**로 기록한다.

## 4. 지식·제조 트랙 추가 증거

D/E/F 시나리오에서는 연결한 마스터 도메인·지식팩 이름, 인용/근거가 적용된 산출물 위치, 다른 프로젝트 정보가 섞이지 않았다는 확인을 남긴다. 현재 수리 시뮬레이션 엔진은 없으므로, 수치 정확도 검증을 통과 조건으로 주장하지 않는다. What-if는 입력 변화가 결과 비교 문서에 일관되게 반영되는지로 판정한다.

DOC/DOCX/PPT/PPTX 원본은 현 지식 업로더 지원 형식과 별개로 취급한다. 수집 전 추출·정제·출처 메타데이터 처리가 없다면 `DATA_GROUNDING` 또는 `DESIGN_GAP`으로 기록한다.
