## 1. 현재 제품 범위와 검증의 정직한 경계

⚠️ **【2026-09-08 리비전】 제품 범위가 넓어졌다.** 아래 2.0 서술은 «생성 팩토리» 부분에
대해 여전히 맞지만, 그 위에 **기업 운영 데이터 계층**이 올라왔다 — 회사·조직 컨텍스트(ECM),
업무키트와 데이터 준비도, 외부 공개자료 수집, 계산·기준선·의사결정, 보고 발간이다.
그래서 판정 대상이 하나 더 늘었다:

| 판정 대상 | PASS의 의미 | PASS가 의미하지 않는 것 |
|---|---|---|
| 기업 데이터 계층 | 계약·상태·통제가 «실제로 막고», 막힌 이유와 다음 행동이 드러난다 | 그 데이터가 사실이거나 실적 인증을 받았다는 뜻 |

★★★ 특히 **실물 데이터는 아직 `READY` 에 도달할 수 없다.** `DEMO_CERTIFIED` 가 유일한
  인증 종점이기 때문이며, 이는 결함이 아니라 **의도된 경계**다(실제 Data Owner 없이 실적
  인증을 주장하지 않는다). 시나리오 `Z-2` 가 그 경계를 정직하게 기록한다.

---

현재 제품은 FastAPI·LangGraph 기반의 **AI 산출물/프로토타입 생성 팩토리**다. Release는 산출물을 라이브러리에 게시하고 RAG 재사용을 가능하게 하며, 프런트엔드 프리뷰는 iframe에서 렌더한다. 생성된 백엔드는 스모크 테스트를 수행하지만, 고객이 즉시 쓸 수 있는 영구 운영 애플리케이션(운영 DB·배포 환경·권한 체계)까지 자동 제공하는 기능은 아직 범위 밖이다.

따라서 아래 테스트는 두 사실을 분리해 판정한다.

| 판정 대상 | PASS의 의미 | PASS가 의미하지 않는 것 |
|---|---|---|
| 팩토리 파이프라인 | 정해진 단계, HOTL, 품질 게이트, Release가 증거와 함께 완료 | 생성물이 실제 운영계에 배포·보안 승인됨 |
| 생성 산출물 | 요구사항, 문서, 코드, 프리뷰가 상호 일관되고 검토 가능한 초안 | 실제 사용자 부하·권한·운영 데이터에서 검증된 제품 |
| 제조/시뮬레이션 트랙 | 연결한 기준정보·지식팩을 근거로 일관된 분석/시나리오 문서를 생성 | 수리 최적화·물리 시뮬레이션 엔진의 계산 정확도 |

## 2. 검증 대상 개요

| 트랙 | 템플릿 | 대표 검증 | LLM 필요 |

| 마케팅·데이터 분석 | `content-marketing`, `data-analytics` | 레지스트리 기반 범용 선형 파이프라인 | 예 |
| 제조 분석 | `manufacturing-*` | 도메인 스킬·기준정보·지식 근거의 반영 | 예 |
| 경영 시뮬레이션 | `mfg_sim` | What-if 서사/비교 산출물의 정합성 | 예 |
| 메가 프로젝트 | master + 8 sub-projects | 공유 원장, 보드룸 관제, 서브 실행 | 예 |
| 플랫폼 기능 | CRUD, Export, Release, 스킬 진화, 치유, 복원 | API·UI·증거 보존 | 일부 |

`default`의 핵심 순서는 **Requirement Interviewer → RFP → PM/PRD → UI/VisionQA → Architect → PMO/WBS → Tech Lead → 개발 → Build/Review/QA/Supervisor/Manual**이다. VisionQA는 현재 조언·반려 신호를 제공하는 품질 단계이며, 운영 브라우저 E2E를 대체하지 않는다.

## 3. 실행 원칙

1. **트래커 SSOT**: 실행 현황은 `02_progress_tracker.md`에만 기록한다. 외부 실행자가 갱신 중이면 다른 작업자는 해당 파일을 수정하지 않는다.
2. **증거 우선**: PASS/COND/FAIL은 로그 한 줄이 아니라 상태 스냅샷, WBS, Release, UI 확인, 오류 로그를 근거로 한다. 형식은 `04_evidence_and_failure_taxonomy.md`를 따른다.
3. **단일 LLM 실행**: 무료/공유 쿼터에서는 파이프라인 동시 실행을 1건으로 제한한다. 구조 테스트와 문서 검토만 병렬 허용한다.
4. **HOTL의 목적 보존**: A-1 같은 무인 완주 시험은 추천안 자동 승인을 허용한다. A-10/A-11·명확성·안전성 검증에서는 사람이 의도한 피드백을 반드시 입력한다.
5. **테스트 산출물 보존**: `test_` 접두사 프로젝트와 Release는 캠페인 종료·사용자 승인 전 삭제하지 않는다.
6. **외부 장애와 제품 결함 분리**: 429/504/네트워크 단절은 즉시 “제품 실패”로 단정하지 않는다. 재시도 정책이 정상 작동했는지와 재개 가능성을 별도로 판정한다.

★★★ **P12~P16 은 P2 관문(A-1)에 걸리지 않는다.** 다른 계층이고 대부분 LLM 이 필요 없다 —
  쿼터와 무관하게 **지금 바로 시작할 수 있다.**
⚠️ 그리고 **Z-1·Z-2 를 가장 먼저 돌 것을 권한다.** 조각을 다 통과시켜도 관통이 끊겨 있으면
  사용자는 아무것도 할 수 없다. 「조각의 합 100% 가 관통 0% 일 수 있다」 —
  끊긴 곳을 먼저 알아야 나머지 순서를 정할 수 있다.

### P2 관문 판정

- `PASS`: 계획과 모든 WBS 태스크가 DONE, 필수 산출물·프리뷰·Release가 확인되고, 미해결 시스템 결함이 없다.
- `COND`: 외부 공급자 장애 등으로 한 번 이상 중단되었으나 재개 후 모든 기능 증거가 충족된 경우다. P3 진입에는 사용자/책임자의 명시 승인이 필요하다.
- `DEFERRED`: API 키·쿼터·공급자 장애로 증거가 부족한 상태다. 원인 태그를 `EXTERNAL` 또는 `TEST_ENV`로 남기며, 제품 PASS가 아니다.
- `FAIL`: 파이프라인, 상태 복원, HOTL, 빌드, Release 중 시스템 결함이 확인된 상태다. 원인 수정과 동일 시나리오 재실행 전 P3+를 진행하지 않는다.

## 8. 재개 프로토콜

1. `02_progress_tracker.md`와 최신 프로젝트 `latest_state.json`을 읽어 **실행 소유자·프로젝트·마지막 상태**를 파악한다.
2. 다른 자동 드라이버/서버가 동작 중이면 새 서버를 띄우거나 같은 프로젝트를 재시작하지 않는다.
3. `IN_PROGRESS`는 먼저 `/state/latest`, `/wbs`, `/hotl/check`, `/feed`로 사실을 확인한다. `SUSPENDED_QUOTA`·`FAILED`·무활동 스톨을 구분한다.
4. 재개 가능한 경우에만 `run_e2e_scenario.py <project_id> --resume`을 사용한다. 새 PLANNING을 시작하면 기존 산출물 아카이브가 발생할 수 있다.
5. 종료·중단 모두 증거와 원인 태그를 기록하고, 다음 Phase로 넘어갈 권한을 판정한다.

상세 실행 절차는 `03_test_execution_command.md`, 증거 양식은 `04_evidence_and_failure_taxonomy.md`를 따른다.
