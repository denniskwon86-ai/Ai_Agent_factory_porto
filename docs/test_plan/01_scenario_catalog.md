# 시나리오 카탈로그 — 전 케이스 입력 데이터 정의서

> 각 시나리오의 `초기 아이디어(initial_idea)`는 그대로 복사해 투입 가능한 실전 입력문이다.
> 프로젝트 ID 규칙: `test_<시나리오ID소문자>` (예: A-1 → `test_a1_unitconv`)
>
> 공통 판정·증거 규칙은 `04_evidence_and_failure_taxonomy.md`를 따른다. 이 카탈로그의 “검증”은 생성 결과의 사실성이나 운영 배포를 자동 보증하지 않으며, 현재 구현된 팩토리 동작과 산출물 품질을 검증한다.

## Z — 관통 시나리오  ★★★ 이것이 가장 중요하다

> **조각의 합이 100% 여도 관통이 0% 일 수 있다.** H~L 이 각각 통과해도 「사용자가 실제로
> 무엇을 할 수 있나」에는 답하지 못한다. Z 는 그 질문에만 답한다.

### Z-1 [P16] 회사 하나를 세워 보고까지 — 시연 데이터로
- **대상**: 전 트랙 관통
- **시나리오**:

        ① 회사·조직을 세운다                      (H-1)
        ② 업무키트를 고르고 부족한 데이터를 본다     (I-1 · I-2)
        ③ 부족한 계약에 외부 수집을 붙인다          (J-1)
        ④ 시연 자료를 인증해 READY 로 만든다        (I-3)
        ⑤ 계산을 돌린다                           (K-1 · K-2)
        ⑥ 결과를 보고로 낸다                       (L-1)

- **수용 기준**: 각 단계가 **다음 단계의 입력을 실제로 만들어 주는가.** 중간에 사람이
  DB 를 직접 만지거나 스크립트로 우회해야 한다면 그 지점이 **관통의 끊긴 곳**이다
- ★ 끊긴 곳을 찾는 것이 목적이다. 통과가 목적이 아니다

### Z-2 [P16] 같은 흐름을 «실물» 데이터로 — 어디서 막히는지 기록
- **시나리오**: Z-1 과 같되 시연이 아닌 실물 분류로 시도
- **예상 결과**: ④에서 막힌다 — `DEMO_CERTIFIED` 가 유일한 인증 종점이라 실물은 READY 가
  될 수 없다(I-3)
- ★★★ **이 시나리오의 PASS 는 「완주」가 아니라 「막히는 지점과 이유가 명확히 드러남」이다.**
  지금 제품이 실물 데이터로 어디까지 가는지를 **정직하게 기록**하는 것이 목적이다
- **수용 기준**: 막힌 지점에서 「무엇이 없어서 막혔는지 · 누가 무엇을 하면 풀리는지」가
  응답에 있다. 그냥 실패하면 FAIL
