## 1. 이 문서의 목적

AI Factory Studio는 기능을 많이 붙인 AI 도구가 아니라, 기업이 자기 업무·데이터·의사결정을 스스로 디지털화하고 발전시키게 하는 장기 플랫폼이다.

이 문서는 다음 질문에 같은 답을 유지하기 위해 존재한다.

- 우리는 정확히 무엇을 만드는가?
- 왜 이 기능을 먼저 만들어야 하는가?
- 무엇은 절대 타협하면 안 되는가?
- 무엇은 아직 만들지 말아야 하는가?
- AI, 데이터, 사람은 각각 어디까지 책임지는가?
- 현업 고객과 시장에 어떤 실질적 가치를 주는가?

구현 세부사항, API, 데이터 스키마, 단계별 백로그는 `LLM_MASTER_IMPLEMENTATION_SPEC_2026-07-28.md`를 따른다. 이 문서는 그보다 상위의 제품 철학과 의사결정 원칙을 정의한다.

## 2. 우리의 북극성

> **현업 사용자가 자기 회사의 실제 데이터와 업무 지식을 바탕으로, 필요한 업무 시스템을 만들고 운영하며, 전사 의사결정과 미래 시뮬레이션까지 연결할 수 있게 한다.**

궁극적으로 AI Factory Studio는 다음을 가능하게 해야 한다.

```text
현업의 의도와 문제
  → 필요한 데이터·기준·규칙의 정의
  → 안전한 현업 시스템/파일 연계
  → AI 기반 업무 앱·워크플로우·시뮬레이터 생성
  → 부서별 운영·승인·공유
  → 결과와 지식의 전사 축적
  → 실제/계획/예측/시나리오의 비교
  → 경영진의 미래 의사결정 지원
```

이 시스템이 충분히 성장했을 때, 경영자는 다음과 같은 질문을 신뢰 가능한 근거와 함께 다룰 수 있어야 한다.

- 올해 하반기와 내년·내후년의 매출, 원가, 손익, 현금흐름은 어떻게 될 가능성이 높은가?
- 환율, 원자재, 전기료, 수요, 인력, 공급망이 바뀌면 어떤 부서·제품·공장·계정에 어떤 영향이 생기는가?
- 어떤 조치를 하면 하방 위험을 줄일 수 있으며, 누가 언제 실행해야 하는가?
- 그 판단은 어떤 데이터, 가정, 산식, 승인 이력에 근거하는가?

## 3. 우리가 해결하려는 시장의 공백

기업은 이미 ERP, MES, CRM, 그룹웨어, 엑셀, BI, 데이터 레이크, 각종 파일을 갖고 있다. 문제는 시스템이 없어서가 아니라 다음이 분리되어 있다는 점이다.

| 현재의 단절 | 결과 |
|---|---|
| 현업의 문제와 IT 개발 사이 | 작은 요구도 긴 프로젝트·높은 비용으로 변환 |
| 업무 시스템과 데이터 정의 사이 | 같은 “매출”, “제품”, “재고”가 서로 다르게 해석 |
| 보고서와 실제 업무 행동 사이 | 분석은 하지만 입력·승인·조치로 이어지지 않음 |
| 부서 최적화와 전사 최적화 사이 | 각 부서의 앱과 데이터가 고립 |
| 계획과 실제 운영 사이 | 계획은 엑셀, 실적은 ERP, 전망은 개인 경험에 의존 |
| AI의 생성력과 기업 신뢰 사이 | AI는 빠르지만 권한·근거·재현성이 부족 |

AI Factory Studio는 이 단절을 단일 거대 시스템으로 갈아엎는 방식이 아니라, **현업의 작은 가치부터 생성하고 그 결과를 전사 자산으로 연결하는 방식**으로 해소한다.

## 4. 제품의 핵심 사상

### 4.1 아래에서 위로 자라는 전사 플랫폼

기존 대형 플랫폼은 전사 데이터 모델을 먼저 만들고 현업 앱을 나중에 올리는 경우가 많다. AI Factory Studio는 반대 방향도 가능해야 한다.

```text
현업의 구체적 문제
  → 부서 업무 앱 생성
  → 사용 데이터·업무 규칙·승인 이력 축적
  → MDM·카탈로그·계보·용어사전으로 승격
  → 부서 간 데이터·워크플로우 연결
  → 전사 운영 모델과 디지털트윈 형성
```

현업에는 즉시 효용을 주고, 기업에는 시간이 갈수록 재사용 가능한 지식과 의미 모델을 남긴다.

### 4.2 제조 경영 온톨로지는 공통 의미 계층이다

AI Factory Studio에서 **제조 경영 온톨로지**는 회사의 업무 개념과 관계를 사람과 시스템, AI가 같은 뜻으로 해석하도록 만드는 공통 의미 계층이다. 단순 문서 태깅이나 그래프 시각화가 아니라 다음을 명시적으로 연결한다.

```text
회사 구조 → 조직 책임 → 가치사슬 → 업무 사건 → 자원·제품·공정
           → KPI → 계산 규칙 참조 → 재무 영향 → 의사결정·실행 결과
```

각 관계에는 조직 범위, 방향, 유효기간, 버전, 출처, 신뢰도, 승인 상태를 둔다. 예를 들어 `원료 도입 지연 → 재고 가용량 감소 → 생산계획 영향 → 출하·매출 지연 → 현금흐름·손익 변화`의 경로를 설명할 수 있어야 한다.

| 구성요소 | 책임 |
|---|---|
| MDM | 품목·조직·공장·공정·거래처·계정 등 공식 업무 대상과 기준값 관리 |
| 데이터 카탈로그 | 데이터의 위치·스키마·소유자·품질·민감도·계약·사용처 관리 |
| 용어사전·Crosswalk | 현업 표현·동의어·외부 시스템 코드와 표준 개체의 대응 관리 |
| 제조 경영 온톨로지 | 개체·사건·책임·정책·KPI·영향 관계의 의미와 제약 관리 |
| Graph RAG | 권한과 근거를 지키며 온톨로지·지식 그래프의 관계를 따라 탐색 |
| 결정론적 계산 그래프 | 승인된 입력·산식·버전으로 수치 영향을 재현 가능하게 계산 |
| LLM·에이전트 | 자연어 해석, 후보 관계 제안, 설명, 문서·앱 생성 지원 |
| 디지털트윈 | 실제 상태와 가정을 온톨로지 및 계산 모델 위에서 재현·비교 |

온톨로지는 핵심 기반이지만 그 단어 자체가 차별화는 아니다. 실제 운영 데이터, 승인된 관계, 계산식, 의사결정과 효과 이력이 계속 축적될 때 기업 고유 자산이 된다. 모든 산업과 업무를 먼저 범용 모델로 만들지 않고, 첫 수직 폐루프의 검증된 관계부터 확장한다.

현재 구현의 `entity_types`, MDM, 카탈로그, 용어사전, 계보, Crosswalk는 온톨로지의 기반 자산이다. **통합 관계 저장·버전·범위·근거 질의와 관리 런타임은 아직 완성되지 않았으므로, 현재 제품을 완성형 온톨로지 플랫폼으로 표현하지 않는다.**

### 4.3 생성보다 신뢰가 우선

AI가 화면과 코드를 빨리 만드는 것은 출발점일 뿐이다. 기업이 비용을 지불하는 이유는 “생성된 결과가 실제로 써도 되는가”에 있다.

따라서 생성 결과는 다음을 동반해야 한다.

- 요구사항과 의도
- 데이터 원천과 정의
- 권한과 승인 조건
- 테스트와 품질 결과
- 운영·장애 대응 방법
- 변경 이력과 영향 범위
- 사람의 최종 확인

### 4.4 AI는 보조자, 데이터와 규칙은 진실의 원천

| 영역 | 최종 권한 |
|---|---|
| 요구사항 이해·초안·설명·추천 | AI 에이전트 + 사용자 확인 |
| 기준정보·용어·데이터 품질 | 데이터 오너 + 규칙 엔진 |
| 숫자 계산·시뮬레이션 결과 | 버전 관리된 결정론적 계산 엔진 |
| 권한·외부 시스템 쓰기 | 서버 정책 + 승인자 |
| 경영 가정·최종 의사결정 | 책임 있는 인간 사용자 |

LLM이 “그럴듯한” 답을 낸다는 이유만으로 실제값, 권한, 승인, 경영 숫자를 확정하면 안 된다.

### 4.5 모든 중요한 결정은 다시 설명 가능해야 한다

Solution Blueprint와 Decision Ledger는 부가 기능이 아니라 제품의 핵심이다.

```text
왜 이 기능이 만들어졌는가?
왜 이 수치를 계획에 사용했는가?
왜 이 앱에 이 데이터 접근 권한이 있는가?
왜 이 시나리오가 이 손익 결과를 만들었는가?
```

이 질문에 데이터·가정·산식·근거·승인 이력으로 답할 수 있어야 한다.

## 5. 제품이 제공해야 할 일곱 가지 가치

### 5.1 현업 주도 업무 시스템 생성

사용자는 개발 언어가 아니라 자기 업무 언어로 필요한 기능을 설명한다. 시스템은 상담·요구사항 정제·기획·설계·구현·검토·릴리스 과정을 지원한다.

### 5.2 전사 지식과 데이터의 축적

각 부서가 만든 앱, 문서, 데이터 정의, 규칙, 테스트, 개선 이력은 개인 산출물로 소멸하지 않고 전사 지식으로 연결된다.

### 5.3 부서별 운영과 전사 통합

부서에는 자기 업무에 맞는 안전한 작업공간이 필요하고, 경영진에게는 부서 경계를 넘는 통합 관점이 필요하다. 둘은 같은 의미 모델과 권한 체계 위에서 연결되어야 한다.

### 5.4 실제 업무를 반영한 시뮬레이션

시뮬레이션은 보기 좋은 차트가 아니라 실제 업무 제약, 데이터, 가정, 산식을 반영해야 한다. 결과는 재현 가능하고 Backtest 가능해야 한다.

### 5.5 자비스형 전역 슈퍼바이저

슈퍼바이저는 단순 Task ID 기반 챗봇이 아니다. 권한 범위 내에서 제품 전체의 프로젝트, 데이터 결손, 비용, 위험, 시나리오, 승인 상태를 이해하고 사용자를 안내해야 한다.

### 5.6 안전한 외부 연계

외부 시스템을 대체하는 것이 아니라 기존 진실 원천을 존중하며 연결한다. 기본값은 읽기 전용이고, Shadow Mode로 검증한 뒤에만 제한적 쓰기를 허용한다.

거래처·관세사·포워더·운송사 등 외부 참여자는 고객사가 이미 운영하는 공급사 포털·물류/통관 시스템·협력사 웹 등 외부 협업 시스템을 계속 사용한다. AI Factory Studio를 외부에 개방하거나 같은 입력 화면을 중복 개발하지 않는다. 기존 시스템이 신원·입력·원본 업무 사건을 책임하고, 우리는 승인된 MCP/API/DB View/파일 계약으로 필요한 데이터만 받아 의미·계산·의사결정에 연결한다. LPL은 이 원칙을 적용하는 LS 환경의 Reference Profile일 뿐 제품 공통 기능이 아니다.

### 5.7 비용 대비 품질의 최적점

경쟁력은 가장 비싼 모델을 가장 많이 쓰는 데 있지 않다. 최소 비용으로 승인 가능한 품질을 안정적으로 내는 데 있다.

## 6. 제품의 고유한 가치 제안

AI Factory Studio는 다음 어느 하나로만 정의되지 않는다.

- 단순 노코드 플랫폼이 아니다.
- 단순 RAG 챗봇이 아니다.
- 단순 코드 생성기나 에이전트 프레임워크가 아니다.
- 기존 ERP/MES를 즉시 대체하려는 제품이 아니다.
- 단순 경영 대시보드가 아니다.
- LLM이 숫자를 예측해 주는 서비스가 아니다.

우리의 정의는 다음과 같다.

> **기업의 실제 데이터와 업무 의미를 기반으로, 현업이 필요한 운영 앱과 의사결정 모델을 생성하고, 그 결과를 전사 지식·통제·시뮬레이션 체계로 축적하는 AI-native Enterprise Operating Platform**

이 제품의 본질은 자동화가 아니라 **경영**이다. 자동화·에이전트·앱 생성은 데이터를 더 정확하고 빠르게 모으기 위한 수단이고, 최종 목적은 경영자가 회사의 실제 상태·미래 전망·대안·결정·실행 효과를 통제하는 것이다. 모든 업무와 모든 사용자를 제품 안으로 흡수하는 것이 아니라, 기존 시스템의 진실 원천을 존중하면서 경영에 필요한 의미와 영향 경로를 통합한다.

이 제품의 방어력은 특정 LLM 모델이나 프롬프트가 아니라 다음 자산의 축적에서 나온다.

```text
기업별 제조 경영 온톨로지(경영 의미 모델)
+ 기준정보와 용어사전
+ 데이터 카탈로그·계약·계보
+ 승인된 업무 템플릿과 에이전트 스킬
+ Decision Ledger
+ 실제 운영 결과와 사용자 피드백
+ 시뮬레이션 모델과 Backtest 이력
```

## 7. 데이터와 외부환경에 대한 원칙

### 7.1 데이터는 네 종류를 섞지 않는다

| 데이터 구분 | 의미 |
|---|---|
| Actual | 실제 발생·확정된 내부/외부 데이터 |
| Plan | 회사가 승인한 계획 기준값 |
| Forecast | 외부 기관 또는 모델의 전망값 |
| Scenario | 사용자가 의도적으로 바꾼 가정값 |

같은 “환율 1,380원”이라도 실제값인지, 전망인지, 경영계획 가정인지, 위험 시나리오인지 반드시 구분한다.

### 7.2 외부환경은 빠름보다 검증을 우선한다

경영계획과 중장기 의사결정에서 기본 입력값은 1~2일 늦더라도 출처·발표일·수정 이력·라이선스가 분명한 데이터여야 한다.

| 등급 | 역할 |
|---|---|
| Gold | 공식·검증·확정 데이터. 기준 시나리오와 공식 보고에 사용 |
| Silver | 잠정 통계·전망·승인된 유료 데이터. 전망/위험 시나리오에 사용 |
| Bronze | 뉴스·RSS·웹 수집 사건 후보. 경보와 검토 요청에만 사용 |

범용 크롤러는 만들지 않는다. 승인 원천 등록부를 통해 공식 API, 공식 파일, RSS·공시, 계약된 제공자, 허용된 웹 원천 순으로 제한한다.

### 7.3 외부지표는 내부 영향 경로를 가져야 한다

환율, 원자재 가격, 전기료, 금리, 수요지수, 임금 상승률은 그 자체로 경영 의사결정이 되지 않는다.

```text
외부지표
→ 내부 동인
→ 제품/공장/사업부 영향
→ 원가·매출·재고·납기
→ 손익·현금흐름
→ 가능한 조치와 책임자
```

이 관계는 승인된 Driver Mapping과 결정론적 계산 엔진으로 관리한다.

## 8. 제품 성장의 순서

모든 것을 동시에 만들지 않는다. 다음 순서는 제품 철학의 일부다.

```text
P0. 생성 공장 안정화
M0. 업무·데이터 설계 상담 + Solution Blueprint
M1. MDM·카탈로그·용어·품질·계보·외부지표 기반
M2. 권한·데이터 계약·안전한 읽기 연계·Shadow Mode
M3. 증빙형 부서 업무 앱과 공유·운영
M4. 경영계획–실적–외부환경 시뮬레이션 파일럿
M5. 전사 자비스·부서 간 통합·개인화
```

### 8.1 첫 파일럿의 원칙

첫 번째 실제 검증 대상은 **경영계획–실적–외부환경 시나리오 관리**다.

이 파일럿은 조직·계정·제품·원가센터·실적·계획·승인·외부지표·시뮬레이션·경영진 보고를 하나의 좁은 범위에서 검증할 수 있다.

성공의 기준은 기능 수가 아니다.

- 경영관리팀이 실제 데이터로 계획을 수립·승인하는가?
- 계획과 실적의 차이를 설명할 수 있는가?
- 외부 변수 변화의 손익 영향을 재현할 수 있는가?
- 기존 엑셀 방식보다 의사결정 속도·정확성·추적성이 개선되는가?

## 9. 절대 피해야 할 함정

### 9.1 기능 나열형 플랫폼

에이전트, RAG, Graph RAG, MCP, 카탈로그, MDM, 시뮬레이션, 대시보드를 나열한다고 제품이 되지 않는다. 각 기능은 하나의 실제 사용자 흐름 안에서 연결되어야 한다.

### 9.2 범용 플랫폼을 너무 일찍 만들기

첫 번째 고객도 없는 상태에서 범용 ERP, 범용 MES, 범용 데이터 플랫폼, 범용 디지털트윈을 동시에 만들지 않는다.

### 9.3 AI에게 진실을 맡기기

LLM이 판단한 데이터 매칭, 숫자, 권한, 규제 해석, 외부 사건을 승인 없이 확정하면 안 된다.

### 9.4 데이터 없이 시뮬레이션을 약속하기

실제 데이터, 명시된 가정, 검증된 산식, 버전이 없는 결과는 시뮬레이션이 아니라 설명 가능한 추정일 뿐이다.

### 9.5 외부 시스템을 너무 빨리 쓰기

읽기 → 검증 → Shadow Mode → 승인 → 제한적 쓰기의 순서를 지킨다.

### 9.6 비용보다 모델 이름에 집착하기

좋은 모델 하나가 제품을 만들지 않는다. 작업 분할, 데이터 문맥, 테스트, 캐시, 승인 구조가 품질을 만든다.

## 10. 팀 협업 헌장

### 10.1 공통 역할

| 참여자 | 기본 역할 |
|---|---|
| 제품 오너 | 문제 정의, 우선순위, 실제 업무 가치·승인 기준 결정 |
| 도메인 전문가 | 업무 규칙, 데이터 의미, 예외, 실제 운영 검증 |
| Codex | 소스 분석, 설계·구현·테스트·문서화, 기술적 리스크 명시 |
| Claude Code | 장시간 구현·테스트·재현·수정 작업 협업 |
| Gemini Antigravity | 별도 관점의 구현·분석·검증 협업 |
| 이후 참여자/LLM | 본 문서와 구현 명세를 읽고 동일 원칙 아래 작업 |

어떤 도구나 LLM도 제품 오너의 업무 의도와 데이터 오너의 승인보다 우선하지 않는다.

### 10.2 협업 방식

1. 작업 전: As-Is, 목표, 영향 범위, 승인 필요 여부를 확인한다.
2. 작업 중: 추측을 구현 사실처럼 말하지 않고, 불확실성·리스크·선택지를 명시한다.
3. 작업 후: 변경 파일, 검증 결과, 미검증 항목, 다음 작업을 한국어로 남긴다.
4. 인수인계: `AI_HANDOFF.md`, 최신 handoff, 구현 명세, 이 Product Bible을 최신화한다.
5. 충돌 시: 기능 속도보다 데이터 신뢰·사용자 가치·운영 안전을 우선한다.

### 10.3 의사결정 우선순위

```text
실제 사용자 가치
  > 데이터 신뢰와 운영 안전
  > 재현성과 유지보수성
  > 비용 대비 품질
  > 기능 범위와 시각적 화려함
```

## 11. 시장에서 성공했다고 판단할 기준

다음은 단순 가입자 수나 데모 완성도가 아니라 실제 제품 가치를 판단하는 기준이다.

### 현업 가치

- 현업 사용자가 개발자 도움 없이 업무 문제를 구조화하고 프로젝트를 시작한다.
- 생성 앱이 실제 업무 입력·검토·승인·예외 처리에 사용된다.
- 기존 엑셀·메일·수작업 조정 시간이 줄어든다.

### 데이터 신뢰

- 주요 KPI와 데이터셋에 소유자·정의·원천·갱신일·품질 상태가 있다.
- 실제/계획/전망/시나리오가 섞이지 않는다.
- 중요한 결과를 같은 입력과 버전으로 재현할 수 있다.

### 경영 의사결정

- 경영진이 “무슨 일이 일어났는가”뿐 아니라 “왜, 무엇을 바꾸면, 누가 실행할 것인가”를 확인한다.
- 외부환경 변화에 대한 시나리오를 실제 데이터 기준으로 실행한다.
- 과거 시나리오와 실제 결과를 비교해 모델과 가정을 개선한다.

### 경제성

- 승인된 결과물 1건당 비용이 통제된다.
- 고성능 모델은 필요한 작업에만 사용된다.
- 축적된 템플릿·지식·데이터 모델로 다음 프로젝트의 비용과 시간이 감소한다.

## 12. 마지막 선언

AI Factory Studio의 목표는 “팔란티어를 복제하는 것”이 아니다.

우리의 목표는 더 생성형이고, 더 점진적이며, 현업 사용자가 직접 참여할 수 있는 방식으로 다음을 실현하는 것이다.

> **기업이 자신의 업무와 데이터를 스스로 이해하고, 필요한 시스템을 만들고, 운영 결과를 학습하며, 미래의 선택을 더 신뢰성 있게 검증하도록 돕는 것.**

기능 하나를 추가할 때마다 다음 질문을 한다.

```text
이 기능이 현업의 실제 문제를 더 빨리 해결하는가?
이 기능이 전사 지식·데이터·의미 모델을 더 신뢰성 있게 축적하는가?
이 기능이 운영 안전성과 재현성을 높이는가?
이 기능이 미래 시뮬레이션과 의사결정으로 이어질 수 있는가?
```

네 질문 중 어느 것도 만족하지 못한다면, 지금 만들지 않는다.
