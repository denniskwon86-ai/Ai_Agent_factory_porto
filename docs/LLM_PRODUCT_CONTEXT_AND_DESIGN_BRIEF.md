## 1. 가장 먼저 이해할 한 문장

**AI Factory Studio는 현업 사용자의 업무 의도를, 회사의 데이터·지식·정책을 근거로 실제 사용할 수 있는 소프트웨어로 만들고, 그 결과를 다시 전사 지식과 경영 시뮬레이션의 기반으로 축적하려는 AI 업무시스템 팩토리다.**

이는 단순 AI 코딩 도구, 챗봇, 문서 생성기가 아니다. 최종적으로는 회사가 수주·구매·생산·품질·물류·판매·회계의 운영 사실과 미래 가정을 바꾸어 보고, 손익·현금·납기·재고·품질 영향을 추적 가능한 방식으로 검증하는 **경영 디지털트윈**을 지향한다.

## 2. 사용자가 확정한 제품 목표: 7개 기능과 다음 단계

| 번호 | 목표 기능 | 설명 |
|---|---|---|
| 1 | 현업 SW 생성기 | 현업 사용자가 자연어와 짧은 선택만으로 필요한 업무 SW를 만들고 사용할 수 있어야 한다. 생성물은 코드만이 아니라 업무 명세, 화면, 데이터 계약, 권한, 테스트, 운영 정보까지 포함한다. |
| 2 | 전사 지식·데이터 허브 | 현업 데이터와 생성 앱의 지식이 사일로로 끝나지 않고, 동의어·유사어·관계·출처·품질을 가진 전사 자산으로 축적·검색·재가공되어야 한다. |
| 3 | 시뮬레이터 생성·실행 | 부서 단위와 전사 단위의 운영 시뮬레이터를 생성하고, 실제값·예측값·가정값을 구분해 실행해야 한다. |
| 4 | AI 에이전트 공장 | AI가 에이전트·스킬·워크플로·템플릿을 추천·구성하고, 목적별 생산 파이프라인을 관리해야 한다. |
| 5 | 자비스형 슈퍼바이저 | 특정 Task ID에 종속되지 않고 프로젝트·앱·데이터·연계·비용·시뮬레이션 전반의 상태를 이해·설명·제안·제어하는 전역 AI 비서여야 한다. |
| 6 | 조직·권한·부서 작업공간 | 부서별 업무 영역과 권한을 분리하고, 부서가 만든 기능을 안전하게 공유·재사용·게시해야 한다. |
| 7 | 전사 통합 업무 시스템 | 부서 앱들을 MES/ERP처럼 순차·동시 업무 흐름으로 연결하고, 경영진이 전사 실적·예측·시나리오를 관리할 수 있어야 한다. |
| 다음 | 개인화 | 권한 경계 안에서 역할·선호·업무 문맥에 맞춘 개인화 보조를 검토한다. 권한/데이터 경계가 먼저다. |

### 궁극적 경영 질문

다음과 같은 질문에 LLM의 그럴듯한 답이 아니라, 데이터·가정·계산 모델·시점·신뢰도를 함께 가진 답을 제공해야 한다.

- 올해 하반기·내년·후년의 매출, 손익, 현금, 납기, 재고는 어떻게 되는가?
- 수요, 판가, 환율, 전기료, 원재료비, 인력, 외주, 수율, 가동률을 바꾸면 어떤 부서와 KPI가 어떻게 변하는가?
- 어떤 조치안이 더 낫고, 그 판단의 근거와 한계는 무엇인가?

## 3. 제품 철학과 절대 원칙

### 3.1 현업 사용자는 개발자가 아니다

사용자에게 긴 프롬프트, 데이터 모델, 에이전트 구성, 코드 리뷰를 요구하면 안 된다. 이상적인 흐름은 다음이다.

1. 사용자가 업무 목적을 자연어로 말한다.
2. 시스템이 2~4개의 **선택형** 질문으로 대상·KPI·범위·우선순위를 확인한다.
3. 시스템은 기존 템플릿·앱·데이터·지식을 재사용 후보로 제시한다.
4. 사용자는 설계 미리보기와 데이터·권한·예상 비용을 승인한다.
5. AI 생산 공장이 생성·검증한다.
6. 사용자는 샌드박스/UAT 후 부서 또는 전사에 게시한다.
7. 운영 피드백은 다음 생성과 지식 정제에 반영된다.

### 3.2 생성 앱은 새 사일로가 되어서는 안 된다

생성 앱이 각자 임의 DB를 만들고 독립 운영되면 목표 2·6·7은 실패한다. 장기적으로 생성 앱은 다음 공통 계약을 써야 한다.

- 앱 ID, 소유 부서, 버전, 배포·롤백 정보
- 데이터 계약: 생산자·소비자·스키마·SLA·변경 승인
- 공용 읽기/쓰기 API와 이벤트 계약
- 권한, 감사, 상관관계 ID, `as-of` 시점
- 재사용·포크·영향 분석 가능한 계보

### 3.3 LLM은 계산의 진실 원천이 아니다

LLM은 요구사항 정제, 설계, 문서·표준 탐색, 코드·테스트 초안, 설명, 이상 징후 요약, 대안 제안에 강하다. 그러나 재고·BOM·능력·수율·리드타임·원가·손익·현금흐름 계산은 결정론적 규칙/최적화/시뮬레이션 엔진이 책임져야 한다.

**동일 입력에는 동일 결과가 나와야 하며**, 모든 시뮬레이션 결과는 입력 스냅샷·가정·계산 모델·버전·실행 시점·신뢰도를 기록해야 한다.

### 3.4 Actual / Forecast / Scenario를 섞지 않는다

- `Actual`: 원천에서 수집된 확정/발생 사실
- `Forecast`: 모델이 추정한 미래값과 오차·신뢰구간
- `Scenario`: 사용자가 바꾼 가정 및 승인·적용 기간

시나리오는 실제값을 덮어쓰지 않는다. 세 종류의 데이터 혼합은 경영 디지털트윈 신뢰를 무너뜨리는 치명적 오류다.

### 3.5 최저 모델 단가가 아니라 승인 결과당 비용을 최적화한다

이 제품의 차별점은 '가장 싼 모델'이 아니다. **사람이 승인하고 추적 가능한 결과 1건당 총비용**을 최소화하는 것이다.

1. 규칙·검색·캐시·검증으로 LLM 호출을 제거한다.
2. 정형 추출, 분류, 짧은 인터뷰, 요약, 국소 수정은 저/중비용 모델을 쓴다.
3. 복잡한 설계·멀티파일 코드·고위험 검토만 상위 모델로 승격한다.
4. 독립 품질 게이트와 사람 승인을 둔다.
5. 모델·단계별 비용/토큰/지연, 첫 통과율, 재작업률, 승인 산출물당 비용을 기록한다.

## 4. 현재 코드가 실제로 구현한 것

### 4.1 현재 정체성: AI 소프트웨어 생산 공장

현재 제품의 강점은 **AI 기반 SW 생성·검토·통제 파이프라인**이다.

- FastAPI + LangGraph 백엔드, React/Vite 프런트엔드
- 요구사항 정제(선택형 Clarification) → RFP → 기획/PRD → UI 설계/VisionQA → 아키텍처 → WBS → 개발 → 리뷰 → QA → 매뉴얼
- HOTL(Human-on-the-loop) 승인·수정·재개
- SSE 기반 타임라인과 프로젝트별 상태 관리
- 템플릿·에이전트 레지스트리·스킬 진화·품질 게이트·실패 복구 구조
- 지식팩 RAG, 경량 MDM(M1), Crosswalk(M2), 읽기 중심 MCP 데이터 브로커(M3), 텔레메트리·추적성·벤치마크

현재 프런트엔드의 대표 구조는 `WorkflowStrip` + `ControlPanel` + `TimelinePanel` + `PreviewPanel`의 작업공간이다. 지식허브, 마스터데이터, Crosswalk, 텔레메트리는 별도 패널로 제공된다. 이것이 제품 UX의 출발점이며, 임의의 좌측 메뉴형 포털로 바꾸어 상상하면 안 된다.

### 4.2 구현된 데이터 기반의 위치

| 영역 | 현재 상태 | 주의 |
|---|---|---|
| M1 기준정보 | 경량 SQLite 저장소, UI/API, 컨텍스트 주입 존재 | 전사 MDM의 일부이며 완성형 MDM이 아니다. |
| M2 Crosswalk | 외부 스키마/필드 매핑 초안과 사용자 확인 흐름 | 실제 대규모 연계·운영 계약은 다음 단계다. |
| M3 MCP 브로커 | 읽기 중심, 온디맨드 조회 + TTL 캐시 | MCP는 연계 프로토콜이지 전체 데이터 전략의 대체물이 아니다. |
| 지식 허브/RAG | 지식팩 등록·프로젝트 연결·근거 주입 | 카탈로그·계보·정책·수명주기까지 완성된 것은 아니다. |
| 추적성 | 요구사항-산출물 그래프와 영향 분석 | 전사 데이터 계보/운영 계보 전체와는 다르다. |
| 제조 시뮬레이션 템플릿 | 존재 | 결정론적 운영/재무 시뮬레이션과 백테스트는 미구현이다. |

### 4.3 현재 미구현 또는 설계 단계인 것

다음은 목표이며, 현재 제품이 이미 제공한다고 주장하면 안 된다.

- 생성 앱의 지속 런타임, 운영 배포, 공통 업무 API, 공용 쓰기 저장소
- 실제 조직 SSO와 백엔드 강제 권한 집행
- 완성형 데이터 카탈로그(자산/오너/품질/계보/계약/사용 현황)
- 전사 데이터 품질·계보·영향 분석
- MES/ERP급 부서 간 쓰기 워크플로와 인박스
- 실제 운영·재무 계산 엔진, 백테스트, 예측 신뢰구간
- 전사 통합 디지털트윈
- 전역 문맥을 가진 자비스형 슈퍼바이저의 완성형 UX/도구 권한 모델

## 5. MDM, 데이터 카탈로그, 제조 경영 온톨로지, Graph RAG의 정확한 관계

이 네 가지를 서로 대체하는 것으로 표현하면 안 된다. 문서에서 사용해 온 `경영 의미 모델`의 기술적 정식 명칭은 **제조 경영 온톨로지(Manufacturing Management Ontology)**이며, 사용자에게는 **기업 경영 의미지도**로 설명한다.

```text
MDM
  공식 업무 대상과 기준값: 품목, 설비, 공정, 거래처, 조직, 계정
        ↓
데이터 카탈로그
  자산의 위치와 의미: DB/테이블/API/파일/문서/모델/대시보드,
  오너, 스키마, 용어, 민감도, 최신성, 품질, 사용처
        ↓
품질·계보·권한·데이터 계약
  믿을 수 있는가, 어디서 왔는가, 누가 어떤 목적으로 쓸 수 있는가
        ↓
제조 경영 온톨로지 + 지식 그래프
  회사·조직·업무 사건·공정·자원·KPI·정책·재무 영향의 의미와 관계,
  관계의 범위·유효기간·버전·출처·승인 상태
        ↓
Graph RAG / RAG
  관계를 활용한 근거 탐색과 영향 경로 확장
        ↓
결정론적 계산 그래프
  승인된 입력·산식·버전으로 수치 영향 계산
        ↓
생성 앱 · 전역 AI 비서 · 시뮬레이터 · 경영 의사결정
```

- **MDM**: 무엇이 공식 업무 대상인가.
- **데이터 카탈로그**: 어디에 어떤 자산이 있고, 의미·오너·품질·계약은 무엇인가.
- **제조 경영 온톨로지**: 공식 개체와 업무 사건이 어떤 의미·책임·제약·영향 관계를 갖는가. 온톨로지 스키마와 그에 따른 지식 그래프 인스턴스를 함께 관리한다.
- **Graph RAG**: 품목-공정-설비-원가-KPI처럼 관계가 깊은 지식을 탐색·확장하는 방법이다. 온톨로지, 카탈로그, MDM을 대체하지 않는다.
- **결정론적 계산 그래프**: 온톨로지로 발견한 관계 중 승인된 산식만 계산한다. Graph RAG와 LLM이 경영 수치를 직접 확정하지 않는다.
- **MCP**: 외부 시스템과 연결하는 인터페이스/프로토콜이다. 표준·권한·품질·계보의 대체물이 아니다.

현재의 `entity_types`, MDM, 카탈로그, 용어사전, 계보, Crosswalk는 온톨로지 기반 자산이지만 통합 온톨로지 런타임은 아직 목표 상태다. 다른 LLM은 이 기반 구현을 완성형 온톨로지로 과장하거나, 반대로 온톨로지가 전혀 없는 것으로 재구현해서는 안 된다.

## 6. 목표 아키텍처: 두 개의 Twin과 하나의 공통 기반

### 운영 Twin

`수주/수요 → 생산계획 → 자재/구매 → 생산/품질 → 출하/매출`

운영 용량, 재고, BOM, 수율, 불량, 리드타임, 납기, 가동률을 다룬다.

### 재무 Twin

`매출 → 원가 → 판관비 → 손익 → 현금흐름`

수요, 판가, 원재료, 환율, 에너지, 인력, 외주, CAPEX를 재무 영향으로 연결한다.

### 공통 기반

두 Twin은 MDM, 카탈로그, 데이터 계약, 권한, Actual/Forecast/Scenario, 이벤트·계보, 앱 런타임을 공유한다. 처음부터 ERP 전체를 재현하지 말고 다음 폐쇄형 가치 흐름 하나를 Pilot으로 완성한다.

`수주/수요 → 생산계획 → 자재·구매 → 생산·품질 → 출하·매출 → 원가·손익`

---

## 7. 슈퍼바이저의 올바른 정의

슈퍼바이저는 '특정 Task ID의 재개 피드백을 넣는 채팅창'이 아니다. 자비스형 전역 보조자여야 한다.

### 알아야 할 문맥

- 현재 사용자·조직·권한
- 프로젝트/스프린트/게이트/실패/재작업 상태
- 생성 앱·배포·버전·데이터 계약
- MDM·카탈로그·지식팩·외부 연계 상태
- 시뮬레이션 입력·가정·결과·신뢰도
- LLM 비용·쿼터·성능·리스크

### 할 수 있어야 할 일

- 상태와 원인을 근거와 함께 설명한다.
- 대안을 비교해 제안한다.
- 권한과 정책 안에서 중지·재개·검증·승인요청·알림을 수행한다.
- 불가역 조치, 운영 배포, 고비용 재시도는 사람에게 승격한다.

### 안전장치

권한별 컨텍스트, 도구 화이트리스트, 비용 예산, 사람 승인, 감사 로그, 롤백 정보가 필수다.

## 8. 현재 가장 중요한 우선순위

### P0 — 생산 공장 신뢰성 증명

새 기능보다 먼저 A-1 E2E 완주 증거를 얻어야 한다. 현재 수정 사항이 있어도 새 환경에서의 깨끗한 완주 증거가 없으면 '생성 공장'의 사업 주장을 키우면 안 된다.

최근 결함·테스트 맥락은 다음 문서를 우선 읽는다.

1. `docs/handoff_2026-07-27_b_fix14_and_next.md`
2. `docs/handoff_2026-07-27_a1_completion.md`
3. `docs/test_plan/02_progress_tracker.md`

특히 코드 생성이 약한 폴백 모델로 붕괴하면 구문 오류, 출력 상한, 장시간 지연이 연쇄 발생한다. 품질/비용 정책은 로그와 텔레메트리로 증명해야 하며, 모델·출력 계약·컨텍스트 크기를 함께 다뤄야 한다.

### P1 — 하나의 가치 흐름을 명세로 고정

제조 품질 예외 또는 수주→손익 흐름 중 하나를 정해 다음을 먼저 정의한다.

- 사용자, 업무 단계, 입력·출력, 의사결정, 예외
- 핵심 KPI와 계산식
- Actual/Forecast/Scenario 데이터 계약
- 데이터 오너, 품질 규칙, 갱신 주기
- 승인/권한/감사 규칙
- Pilot 수용 기준: 시간 단축, 재작업 감소, 데이터 재사용, 의사결정 개선

### P2 — 데이터·권한·앱 런타임의 공통 기반

조직 권한, 카탈로그, 공용 앱 런타임, 공통 쓰기 저장소, 이벤트/워크플로는 함께 설계해야 한다. 순서는 `docs/design_backbone_system_platform.md`와 `docs/design_org_permission_enterprise.md`를 따른다.

### P3 — Twin MVP와 Graph RAG

P1/P2의 실제 데이터와 계약이 확보된 뒤 운영·재무 Twin을 붙인다. Graph RAG는 관계 기반 근거 탐색/영향 분석을 강화하지만, 숫자를 계산하는 엔진이 아니다.

## 9. 다른 LLM이 작업할 때의 행동 규칙

1. **항상 한국어로 소통한다.** 사용자에게 보이는 설명, 로그성 메시지, 문서, 프롬프트를 포함한다. 코드 식별자/표준 약어는 예외다.
2. 먼저 현재 코드와 최신 인수인계 문서를 읽고, 설계 문서를 구현 현황으로 오해하지 않는다.
3. '목표 상태'와 '현재 구현'을 표나 문장으로 명확히 분리한다.
4. 새로운 대형 기능을 제안/구현하기 전 P0 완주 증거와 선행 게이트를 확인한다.
5. UI를 제안할 때는 현재 `Private AI Cockpit`의 프로젝트 생성 및 3분할 작업공간을 출발점으로 삼는다. 실제 캡처 없이 가상의 완성 제품 화면을 현재 구현처럼 제시하지 않는다.
6. 슈퍼바이저를 Task ID 전용 채팅으로 축소하지 않는다.
7. MDM, 카탈로그, Graph RAG, MCP를 같은 것으로 합치지 않는다.
8. LLM이 만든 계산값을 경영 수치의 진실로 쓰지 않는다.
9. 비용 절감 때문에 코드·아키텍처·운영 배포 품질을 낮추지 않는다. 저비용화는 캐시, 결정론적 검증, 재사용, 모델 승격 정책으로 달성한다.
10. 권한은 프런트엔드 표시가 아니라 백엔드 데이터/도구/검색 경로에서 강제해야 한다.
11. 실제 데이터·승인·운영 배포 관련 기능은 fail-open이 아니라 fail-loud, 감사 가능, 롤백 가능하게 설계한다.

## 11. 인수인계용 결론

이 프로젝트의 현재 위치는 다음 한 문장으로 요약한다.

> **AI Factory Studio는 AI 기반 소프트웨어 생산 공장으로서 상당한 구현을 갖췄지만, 아직 전사 운영 플랫폼이나 경영 디지털트윈은 아니다. 다음 승부는 기능을 더 많이 붙이는 것이 아니라, 생성 공장의 완주 신뢰성을 증명하고 하나의 실제 업무 가치 흐름을 데이터·권한·앱 런타임·결정론적 시뮬레이션까지 폐쇄형으로 연결하는 데 있다.**

이 원칙을 지키면, 장기 비전은 과장 없이도 강해진다. 지키지 않으면 모델 데모·문서·가상 UI만 많은 시스템이 된다.
