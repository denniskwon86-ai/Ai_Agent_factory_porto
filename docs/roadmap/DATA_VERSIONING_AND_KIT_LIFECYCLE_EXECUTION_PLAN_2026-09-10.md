부수적으로 Excel 템플릿 35 개도 삭제됐다가 재생성됐는데, 재계산에 필요한 LibreOffice 가

### 2.1 그래서 진짜 문제는 「CSV 냐 DB 냐」가 아니다

**확정된 것을 확정된 채로 두는 장치가 어느 층에도 없다.**

| 층 | 덮어쓰기를 막는가 |
|---|---|
| 파일 | ✗ 누구나 쓴다 |
| 생성기 | ✗ 재실행하면 같은 경로에 덮어쓴다 |
| DB 등록부 | ✗ `upsert` 가 내용으로 덮는다 (사실 4) |
| git | △ 이력은 남지만 **실수를 막지는 못한다** |

DB 로 옮기는 것은 **질의·동시성·참조무결성**을 얻는 일이고, 판본 불변성은 **별도로
설계해야 얻는다.** 둘을 한 문장으로 묶으면 「DB 로 옮겼으니 안전하다」는 오해가 남는다.

## 3. 목적과 전체 흐름

### L0 — 목적

**AX 의사결정 플랫폼의 산업 커버리지를 정하고, 대상별 업무키트를 만들어 적용한다.**
판본 관리는 그 자체가 목적이 아니라, 3·4 단계에서 같은 사고가 반복되는 것을 막는 수단이다.

### L1 — 전체 흐름

| 단계 | 내용 | 상태 |
|---|---|---|
| 1 | **분류** — 어떤 사업들이 있나 | 거의 완료. 모수 21,613 · 인스턴스 20,478 · 셀 101 · 오판정 약 3% |
| 2 | **대상 선정** — 어디에 키트를 만드나 | 1 차 확정. 비철 제련 11 개사 30.6 조 (D-47) |
| 3 | **키트 제작** — 무엇을 담나 | **막힘.** 도메인 검토 대기 + 판본 체계 없음 |
| 4 | **적용** — 실제 회사에 붙인다 | 미착수 |

3 단계가 두 가지로 막혀 있다. **도메인 검토**(제련 드라이버가 맞는가)는 사람이 답할
일이고, **판본 체계**는 이 계획이 다룬다.

## 4. 단계별 계획

### P1. 확정 판본을 불변으로 만든다 — 최우선

사고 재발을 막는 최소 조치다. P2 이후를 안 하더라도 이것만은 있어야 한다.

| | 작업 | 산출물 |
|---|---|---|
| P1-1 | 생성기가 **이미 있는 판본 디렉터리에 쓰기를 거부**하게 한다. `--force` 를 줘야만 덮어쓴다 | `generate_sample_company_starter_kit.py` |
| P1-2 | `manifest.json` 의 `status` 가 `VALIDATED_*`·`APPROVED_*` 면 **거부 대상**으로 판정 | 같은 파일 |
| P1-3 | 판본 디렉터리에 `.frozen` 표식과 `fingerprint.json`(파일별 sha256)을 남긴다 | 판본별 1 개 |
| P1-4 | `validate_*` 에 **지문 대조**를 추가 — 파일이 바뀌었으면 검증 실패 | `validate_sample_company_starter_kit.py` |

### P2. 생성기가 판본을 여럿 만들 수 있게 한다

1.1.0 을 내기 위한 전제다. 지금은 1.0.0 을 재현할 수 없게 되므로 1.1.0 을 낼 수 없다.

| | 작업 | 비고 |
|---|---|---|
| P2-1 | `KIT_VERSION` 을 **인자**로 받는다 (`--version 1.1.0`) | 기본값은 생략 불가로 두어 실수를 막는다 |
| P2-2 | 판본별 차이(드라이버·프로파일·필드)를 **데이터로 분리** — 코드 분기가 아니라 `kit_defs/{version}.py` 또는 JSON | 판본이 늘어도 생성기는 하나 |
| P2-3 | 1.0.0 을 새 구조로 재생성해 **기존 파일과 지문이 같은지** 확인 | 같지 않으면 P2 가 틀린 것이다 |
| P2-4 | 1.1.0 생성 — 제련 드라이버 5 · `industry_code` C2421 · 시나리오 4 · 데이터셋 필드 | 도메인 검토 통과분만 |

### P3. 등록·검증을 DB 로 옮긴다

질의·동시성·이력을 얻는다. **P1 을 대신하지 않는다**(사실 4).

| | 작업 | 비고 |
|---|---|---|
| P3-1 | `data_preparation.db` 를 생성하고 1.0.0 을 등록 | 이미 있는 `register_all` 을 쓴다 |
| P3-2 | `upsert_kit_version` 에 **불변 판본 보호**를 넣는다 — 상태가 `APPROVED`·`ACTIVE` 인 판본의 지문이 달라지면 `StateConflict` | 사실 4 를 고치는 자리 |
| P3-3 | 판본 목록·상태·지문을 조회하는 화면 또는 CLI | 「지금 무엇이 ACTIVE 인가」가 한눈에 |

### P4. 분류 데이터에 판본을 준다

모수 21,613 건이 「전체 대상 산정」의 근거인데 지금은 덮어쓰기만 된다.

| | 작업 | 비고 |
|---|---|---|
| P4-1 | 파이프라인 산출물에 **스냅샷 판본**을 붙인다 — `samples/{yyyy-mm-dd}/` 또는 DB 테이블 | 어느 쪽인지는 P4-2 로 정한다 |
| P4-2 | **CSV 유지 vs DB 이관 결정.** 판단 근거: 질의 빈도 · 동시 접근 · 다른 모듈이 읽는가 | 지금은 사람이 CSV 를 열어 보는 용도가 크다 |
| P4-3 | 롱리스트를 **판본과 함께** 내보낸다 — 「2026-09-10 판 제련 11 개사」 | 나중에 「그때 왜 이 명단이었나」에 답할 수 있어야 한다 |

## 5. 순서와 이유

```
P1 (불변화)  →  P2 (판본 분리)  →  P2-4 (1.1.0 생성)
                                        ↑
                              도메인 검토 통과가 전제
P3 (DB 등록) 는 P1 뒤 언제든 · P4 (분류 판본) 는 독립
```

- **P1 이 먼저인 이유**: P2 를 하려면 생성기를 고쳐야 하는데, 보호 장치 없이 고치면
  또 1.0.0 을 건드린다.
- **P2-4 가 도메인 검토 뒤인 이유**: 드라이버가 틀리면 1.1.0 을 다시 내야 하고,
  그러면 판본이 의미를 잃는다.
- **P3 를 나중에 두는 이유**: DB 등록은 사고를 막지 못한다(사실 4). 급한 것은 P1 이다.

## 6. 이번 계획에 포함하지 않는 것

- PostgreSQL 전환 (기존 계획서에서 이미 완료선 밖으로 둔 항목)
- 실제 회사 데이터 적재 — 롱리스트는 **영업 대상**이지 데이터 원천이 아니다
- Excel 재계산 파이프라인 복구 (LibreOffice 의존) — 필요할 때 별도로 다룬다
- 제련 업무 내용의 정합성 — 도메인 검토 사안이지 이 계획의 범위가 아니다
