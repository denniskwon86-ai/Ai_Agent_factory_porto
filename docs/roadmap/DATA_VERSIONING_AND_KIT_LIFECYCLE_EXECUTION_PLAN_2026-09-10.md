### 2.1 그래서 진짜 문제는 「CSV 냐 DB 냐」가 아니다

**확정된 것을 확정된 채로 두는 장치가 어느 층에도 없다.**

| 층 | 덮어쓰기를 막는가 |
|---|---|
| 파일 | ✗ 누구나 쓴다 |
| 생성기 | ✗ 재실행하면 같은 경로에 덮어쓴다 |
| DB 등록부 | ✗ `upsert` 가 내용으로 덮는다 (사실 4) |
| git | △ 이력은 남지만 **실수를 막지는 못한다** |

DB 로 옮기는 것은 **질의·동시성·참조무결성**을 얻는 일이고, 판본 불변성은 **별도로
설계해야 얻는다.** 둘을 한 문장으로 묶으면 「DB 로 옮겼으니 안전하다」는 오해가 남는다.

## 4. 단계별 계획

### P1. 확정 판본을 불변으로 만든다 — 최우선

사고 재발을 막는 최소 조치다. P2 이후를 안 하더라도 이것만은 있어야 한다.

| | 작업 | 상태 |
|---|---|---|
| P1-1 | 생성기가 **이미 있는 판본 디렉터리에 쓰기를 거부**. `--force` 를 줘야 덮어쓴다 | ✅ `build()` 앞에 `kit_freeze.guard()` |
| P1-2 | `manifest.status` 가 `VALIDATED_*`·`APPROVED_*`·`CERTIFIED_*`·`RELEASED_*` 면 거부 | ✅ 표식을 깜빡해도 막히는 이중 안전장치 |
| P1-3 | `.frozen` 표식과 `fingerprint.json`(파일별 sha256) | ✅ `scripts/freeze_starter_kit.py` |
| P1-4 | `validate_*` 에 지문 대조 | ✅ **맨 앞에서** 대조한다 — 검증기가 뒤에서 manifest·보고서를 쓰므로 |

### P1 결과 (2026-09-10)

- `core/data_preparation/kit_freeze.py` 신설 · `scripts/freeze_starter_kit.py` 신설
- **1.0.0 동결 완료** — 175 개 파일 지문, `reason: 검증 PASS 406건`
- **사고 재현 시험 통과** — 생성기를 그냥 돌리면 `FrozenKitError` + 종료코드 1,
  `generated_at` 은 `2026-08-11` 그대로, 지문 대조 PASS
- 검증 406/406 PASS(지문 대조 1 건 추가) · 시험 14 건 신설 · 키트 시험 95 건 통과

**동결 판본에서는 검증기가 보고서·manifest 를 쓰지 않는다.** `validated_at` 한 줄만
바뀌어도 지문이 달라져, 검증을 돌릴 때마다 그 판본이 「변경됨」이 되기 때문이다.
확정 판본의 재검증은 **대조가 목적**이지 기록 갱신이 아니다.

### P2. 생성기가 판본을 여럿 만들 수 있게 한다

1.1.0 을 내기 위한 전제다. 지금은 1.0.0 을 재현할 수 없게 되므로 1.1.0 을 낼 수 없다.

| | 작업 | 상태 |
|---|---|---|
| P2-1 | `KIT_VERSION` 을 **인자**로 (`--version`) · `--out` 으로 다른 경로에 생성 | ✅ `use_version()` |
| P2-2 | 판본별 차이를 **데이터로 분리** | ✅ `scripts/kit_defs/` — **오버레이** 방식 |
| P2-3 | 1.0.0 을 새 구조로 재생성해 **지문이 같은지** 확인 | ✅ **데이터 137 개 전부 일치** |
| P2-4 | 1.1.0 생성 — 제련 드라이버 5 · `C2421` · 시나리오 4 · 데이터셋 필드 | ⏸ **도메인 검토 대기** |

### P2 결과 (2026-09-10)

**왜 「완전 분리」가 아니라 「오버레이」인가.** 1.0.0 은 동결 판본이라 새 구조로
재생성했을 때 지문이 한 글자도 달라지면 안 된다. 1,300 줄 생성기에서 정의를 전부
뽑아내면 그 과정에서 순서·기본값이 미묘하게 달라지고 지문이 그것을 잡는다. 그래서
**기본 정의는 생성기에 두고 판본별 「차이」만 얹는다** — 1.0.0 의 오버레이는 비어
있으므로 결과가 같다. 판본이 셋 이상으로 늘어 「기본이 무엇인지」가 흐려지면 그때
완전 분리로 옮긴다.

**왜 JSON 이 아니라 파이썬인가.** 이 정의는 사람이 손으로 고치고, **왜 그런지가 값보다
중요하다.** 「제련사는 금속 가격으로 벌지 않는다」 같은 설명이 JSON 에서는 살지 못한다.

**P2-3 대조 결과** — 원본 175 · 재생성 137. 차이는 전부 설명된다.

| 차이 | 이유 |
|---|---|
| Excel 36 개 | 별도 스크립트 산출물 — 생성기가 만들지 않는다 |
| `validations/*.json` 2 개 | 검증기 산출물 |
| `manifest.json` | `generated_at`·`status`·`validation`·`excel_templates` — 생성 시각과 나중 단계가 채우는 값 |
| **데이터 파일 137 개** | **한 글자도 다르지 않다** |

로더가 막는 것 셋 — 없는 판본(오타로 새 판본이 생기는 것) · `OVERLAY` 누락 ·
**판본 불일치**(복사해서 만들 때 `version` 을 안 고치는 실수). 시험 12 건으로 고정했고,
그중 하나가 재생성 대조 자체다.

### P3. 등록부의 불변 판본 보호

**⚠️ P3-1 의 전제가 틀렸다.** 착수해 보니 「키트」가 두 종류이고 등록 경로가 다르다.

| | 무엇 | 경로 | 등록부에 들어가나 |
|---|---|---|---|
| 운영 템플릿 Profile | 조직에 적용할 데이터 계약 | `docs/data-kits/*.kit.json` (현재 1 개) | **예** — `register_all` 대상 |
| Starter Package | 샘플 회사·합성 데이터·앱·보고서 묶음 | `starter_kits/{id}/{version}/` | **아니오** — `starter_package_catalog` 은 읽기 전용 |

「운영 등록과 분리한다」는 의도된 설계다(`kit_registry.starter_package_catalog` 주석).
그래서 **우리가 동결한 1.0.0 은 `register_all` 로 등록할 수 없다** — P3-1 은 성립하지 않는다.

| | 작업 | 상태 |
|---|---|---|
| P3-1 | ~~`data_preparation.db` 생성하고 1.0.0 등록~~ | ❌ **불가** — Starter Package 는 등록부 대상이 아니다 |
| P3-2 | `upsert_kit_version` 에 불변 판본 보호 | ✅ `frozen` 열 + `StateConflict` |
| P3-3 | 판본 상태·지문을 드러낸다 | ✅ 카탈로그에 `frozen`·`integrity` · CLI 는 P1 의 `--list` |

### P3 결과 (2026-09-10)

**등록부 보호(P3-2)는 지금 당장 쓰이지 않지만 넣어 둔다.** `docs/data-kits` 의 Profile 도
확정되면 동결해야 하고, 나중에 Starter Package 를 등록부에 넣기로 하면 그때 필요하다.
막는 경우 넷을 시험으로 고정했다 — 미동결은 덮어쓰고 · 같은 지문이면 멱등이고 ·
**동결 판본의 지문이 달라지면 `StateConflict`** 이고 · **`frozen=False` 로 재등록해도
풀리지 않는다**(풀린다면 보호가 통째로 무력해진다).

**카탈로그가 동결 상태를 드러낸다(P3-3).** 화면에 「확정」이라고만 쓰고 대조 결과를
숨기면 파일이 바뀐 판본을 확정된 것으로 보여 주게 된다. 그래서 셋을 함께 낸다 —
`frozen` · `fingerprint_ledger` · `integrity`(`PASS`/`FAIL`/**`UNVERIFIED`**).
대장이 없으면 「검사하지 않았다」이지 「통과했다」가 아니다.

```
KIT-MFG-NONFERROUS-PROCUREMENT 1.0.0  AVAILABLE_FOR_DEMO  frozen=True   integrity=PASS
KIT-MFG-BATTERY-CHEMICAL-...   1.0.0  PREPARING           frozen=False  integrity=UNVERIFIED
```

**남은 결정** — Starter Package 를 등록부에 넣을 것인가. 넣으면 판본·지문·상태가 한
곳에서 관리되지만, 「운영 템플릿과 체험 패키지를 섞지 않는다」는 기존 설계와 충돌한다.

## 5. 순서와 이유

```
P1 (불변화)  →  P2 (판본 분리)  →  P2-4 (1.1.0 생성)
                                        ↑
                              도메인 검토 통과가 전제
P3 (DB 등록) 는 P1 뒤 언제든 · P4 (분류 판본) 는 독립
```

- **P1 이 먼저인 이유**: P2 를 하려면 생성기를 고쳐야 하는데, 보호 장치 없이 고치면
  또 1.0.0 을 건드린다.
- **P2-4 가 도메인 검토 뒤인 이유**: 드라이버가 틀리면 1.1.0 을 다시 내야 하고,
  그러면 판본이 의미를 잃는다.
- **P3 를 나중에 두는 이유**: DB 등록은 사고를 막지 못한다(사실 4). 급한 것은 P1 이다.

- 제련 업무 내용의 정합성 — 도메인 검토 사안이지 이 계획의 범위가 아니다

## 7. 승인이 필요한 것

1. **P1~P4 의 범위와 순서**가 맞는지.
2. **P4-2**: 분류 데이터를 CSV 로 둘지 DB 로 옮길지. 지금 판단 재료는
   — 읽는 주체가 대부분 사람(엑셀·아티팩트)이고, 다른 모듈이 아직 읽지 않으며,
   파이프라인이 6 단계 스크립트로 되어 있어 이관 비용이 작지 않다.
3. **P2-2 의 형태**: 판본별 차이를 파이썬 모듈로 둘지 JSON 으로 둘지.
