## 1. 고친 네 가지

1. **완료점을 작게:** 53목표를 실행/인수 단계139개로 구체화했다. 기존 완료18개는 보존했고, 남은121개 단계는 기능·API·DB·실환경 결과를 확인할 수 있는 출구를 가진다. 139개로 제품 범위를 늘린 것이 아니다.
2. **중간 즉시 가산:** 자기 단계의 선행조건·증거·검토가 충족되면 상위 목표가 미완료여도 그 단계의 점수를 즉시 인정한다. 상위 전체 종료까지 기다리지 않는다.
3. **큰 일의 배점 보정:** 남은3500점은 기존 잔여시간 범위의 중간값에 비례해5점 단위로 배분했다. 예컨대 P04(필수 저장소PG)는100→395점, C02(artifact/CI)는100→55점이다. 현재 추정 작업량에 대한 관리 배점이지 객관적 생산성/품질 수치는 아니다. 실제 오래 걸렸다고 배점을 늘리지 않는다.
4. **의존성 분리:** 상위 목표의 선행조건을 모든 하위 단계에 걸지 않는다. 예컨대 P03.1 명시 설치명령/기동DDL 분리는 PG 실서버 수용 전 수행 가능하고, C04.1 읽기 UI는 C03 전체가 아니라 C03.1 실제 조회API가 연결되면 진행 가능하다.

개시 인정1800/5300점 = **34.0%**. 기존 완료18목표×100점을 보존했다. 계획 변경으로 진척이 늘어난 것은 없다. 현재는 위 최신 수용/계산기 결과를 따른다. 5300은 관리 점수이며5300개 작업이 아니다.
목표 종결18/53은 별도 보조값이고, **이제 전체 진척은 종료 목표 수가 아니라 수용된 중간 단계 점수로 계산한다.**

## 3. 작업 크기·증거·보고 규칙

### 사용자 최신 지시 반영: 후속 소비 단계가 앞 단계를 검증한다

**2026-09-21 보완:** 단계마다 별도 검증 묶음/변이/독립 검토 대기를 끼워 넣지 않는다. 기본 순서는 **만들기 → 다음 기능이 같은 산출물을 실제로 사용 → 연결된 업무 흐름 끝에서 잔여 위험·회귀 확인**이다. 다음 소비 실행의 증거를 앞 단계 수용에도 재사용한다. 같은 검사를 이름만 바꿔 두 번 하지 않는다.

| 작업 흐름 | 다음 단계에서 앞 단계를 확인하는 실제 행동 | 별도로 남길 확인 |
|---|---|---|
| P03 설치 → 로그인·문맥 → 티켓·재시작 | 설치 CLI가 만든 DB에 제품 store로 로그인/문맥 조회; 발급 세션으로 티켓 소비; 재시작 후 같은 자료 조회 | 미설치 자동 DDL/다른 DB fallback 차단은 첫 사용 전; 동시성·권한 거절은 해당 소비 흐름에서 한 번 |
| C02 manifest → Linux 패키지 → 원격 CI | 같은 manifest로 패키지를 만들고, 원격 CI가 그 digest/출처를 재검증 | 비밀/금지 파일 포함 차단은 외부 업로드 전 |
| D05 상태 읽기 → 서명 제출·재조회 → 거절·반려 | 다음 단계 제출 결과가 같은 읽기 화면에 반영되는지 확인 | 권한/실제 인증 상태 변경 경계는 쓰기 전에 확인 |
| C03 API → C04 관리 화면 → 배포 실행 흐름 | 화면이 실제 API를 소비하고 후속 배포가 그 계획/상태를 사용 | 승인·중복 실행·실환경 쓰기 차단은 실행 전에 확인 |
| P04 저장소 이관 → 해당 업무 소비 → 횡단 재시작 | 옮긴 저장소를 업무 API가 바로 읽고 쓰며 결과를 재사용 | 자료 대사·원본 보호는 이관 적용 전후, 횡단 회귀는 묶음 끝 |

- **단계 경계는 검증 대기열이 아니다.** 선행 기능이 다음 기능을 구현할 만큼 준비되면 로컬 후속 구현을 계속한다. 원장의 prerequisites는 점수 수용 순서이며, 안전한 구현까지 독립 리뷰 완료를 기다리라는 뜻이 아니다. 외부승인/운영 위험 경계는 예외다.
- 기본 편성은 연속된 **2~3개 구현 단계당 연결 시나리오 1개 + 묶음 끝 집중 회귀 1회**다. 여러 시간짜리 검증만을 위한 단계를 추가하지 않는다. 실패한 부분만 다시 실행한다.
- 자연스러운 성공 경로가 입증하지 못하는 권한 거절·자료 무결성·중복 실행·복구는 그 경계를 실제 사용하는 시점에 집중 확인한다. 실패가 있어도 성공처럼 진행하는 것은 허용하지 않는다.
- 구현 중 나온 실제 실행 결과만으로 자기 출구를 만족하면 그때 바로 검토·가산한다. 후속 단계에서 증거가 생기면 충족된 앞 단계부터 함께 반영한다. 최종 묶음까지 무조건 가산을 미루지 않는다. 증거가 없는 코드는 구현 완료/수용 대기로 구분한다.
- 외부 PG/원격 CI가 없으면 다음 소비자의 로컬 실행 가능한 부분을 앞당긴다(예: 명시 설치→관리 store 최초 조회). 이것은 앞 구현의 좁은 출구만 확인하며 실제 PG/원격 실행의 수용을 대체하지 않는다.
- 독립 검토는 구현과 병행하거나 묶음 끝에 집중하며, 민감 데이터/권한/운영 적용 전 필수 검토만 차단 게이트로 둔다. 각 소단계마다 새 검토 문서·검토 대기를 요구하지 않는다.

- 단계는 **집중 작업1~3시간을 목표**로 한다. 4시간을 넘을 것으로 보이면 착수 전에 실제 산출물 경계에서 더 나누고 해당 단계 배점 합계를 그대로 유지한다. 작업하고 난 뒤 점수를 얻으려고 임의로 분할하지 않는다.
- 매20~30분에는 무엇을 만들고 있는지, 실제 결과/화면, 남은 작업과 예상 시간을 보고한다. 보고 자체·시간 경과·시험 건수는 점수가 아니다.
- 결과 증거는 구현 중 실행과 후속 소비 흐름에서 확보한다. 이미 확인한 정상/거절을 각 단계에서 반복하지 않는다. **수용 조건 충족 + 적정 검토 → accepted 기록 → 계산 → PROGRESS/사용자 보고**는 가능한 즉시 수행한다.
- 전체 회귀/실환경/사용자 인수는 정해진 묶음 끝·운영 출구에서 수행하고, 무관한 전역 시험을 기다리느라 이미 수용된 국소 단계를 묶어두지 않는다.
- 단, 실자료·권한·생성·배포 등 명시된 출구가 실제 환경을 요구하면 mock으로 대체하지 않는다. 가동 위험을 가리기 위해 점수를 앞당기지 않는다.
- 완료된 부분이 회귀하면 영향 단계의 점수만 회수한다. 영향을 받지 않은 구현 결과까지 전부0으로 만들지 않는다. 최종 보안/실사용 관문이 실패하면 운영 개시는 차단한다.
- 전체53목표가 모두 닫히고 U01~U03 인수 및 차단P0/P1 해소가 있어야100%다. 중간 점수를 주는 것이 최종 출구를 완화하는 것은 아니다.

## 4. 실행 큐와 인계

- Codex 큐: C02.1 → D05.1 → 가능한 C02.2 → D05.2/3. 환경이 없다는 이유로 두 큐를 함께 정지하지 않는다. 이후 C03→C04의 실제 API/화면 단위로 연결한다.
- Claude 큐: P03.1 → 승인/환경 확보 후 P03.2/3 → P04의 저장소별 실제 경로. 별도 자원을 맡는 W01~W03도 완료된 선행 단위에 맞춰 진행한다.
- P04는13개 저장소 경로와 최종 횡단 수용으로 나눴다. 저장소 하나가 실제 PG에서 동작하면 그 단계의25~30점을 즉시 인정한다.13개 전체 이관까지 기다리지 않는다.
- L04는 기존7앱 각각과 최종 앱간 업무 수용으로 나눴다. 착수 시 기존app_id 목록을 고정하고, 앱 하나의 실제 데이터/권한/입출력 연결이 끝나면 즉시 인정한다. 더 쉬운 앱으로 교체하거나 목록 조사만으로 완료하지 않는다.
- 새 Claude 지시 수신/착수는 아직 확인하지 않았다. 원장/계획은 공유 인계 경로이며 전달/실행 완료로 표현하지 않는다.
- 정책/실자료/과금/외부환경 승인 상태는 단계 원장의 approval_ids에만 적용한다. unrelated 로컬 구현의 전역 잠금으로 만들지 않는다.
