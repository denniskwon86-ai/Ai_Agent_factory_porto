동시사용은 로그인/조회/입력/SSE 혼합 업무다. 동일 인원이 모두 동시에 LLM 제작하는 부하는 별도다. 「50명 이상」을 무제한 보장으로 해석하지 않는다. CPU·메모리·DB lock/pool·작업대기·데이터량·네트워크로 승격 판단하며 등록 사용자수만으로 자동 증설하지 않는다.

## 2. 무중단의 정의와 기존안 교체

기본 목표: **일상 코드 배포로 사용자 업무를 멈추거나 재로그인시키지 않고, 접수된 쓰기/제작 작업을 잃거나 중복 실행하지 않는다.** 짧은 SSE 재연결은 자동 복원하되 이벤트 누락/중복 표시를 방지한다. TCP가 영원히 끊기지 않는다는 뜻도, 모든 인프라 장애에서100% 가용하다는 약속도 아니다.

직전 NCP_OPERATIONAL_TRIAL_CICD 문서의 「단일 App 전체 쓰기 차단→재기동」은 일상 배포 기본안에서 제외한다. 이를 무중단이라고 이름만 바꾸지 않는다. 아래 선행 작업이 끝나기 전 무중단 지원을 선언하지 않는다.

- **초기 SQLite→PostgreSQL 전환:** trial 업무 개시 전 이관을 완료하는 것이 기본. 기존 로컬 업무도 계속 써야 한다면 무승인 쓰기동결은 하지 않는다. 온라인 동기화/최종전환 설계를 추가하거나 별도 전환창을 사용자에게 승인받는다.
- 파괴적 schema 변경·대규모 데이터 정정·DB 엔진 업그레이드·재해복구는 일상 코드 배포와 구분한다. 무중단 검증이 안 되면 배포를 보류하고 예외 승인을 받는다.
- DB HA가 모든 장애에서 연결 단절0을 보장하지 않는다. 실패한 트랜잭션을 맹목적으로 재실행하지 않고 원요청 ID/영수증으로 확인한다.

## 3. 배포 시스템과 업무 시스템 분리

구성은 「GitHub/CI → 배포 관리 서버 → 각 환경의 제한된 배포 에이전트」와 「사용자 → LB → App Blue/Green → DB/작업 실행기/파일 저장소」로 나눈다.

### 관리 영역 — 별도 배포 서버

- 업무 App과 다른 VM/계정/보안규칙. 1단계2vCPU/8GB 후보. 배포 상태·승인·릴리스 카탈로그·건강도만 관리하며 실업무 원문을 보관하지 않는다.
- 배포 서버 장애 때 **업무 서비스는 기존 버전으로 계속 운영**, 신규 배포만 보류한다. 업무 요청 경로에 배포 서버를 끼워 넣지 않는다.
- 관리 원장은 별도 DB/역할로 분리. 처음에는 관리형 클러스터 내 논리DB를 사용할 수 있으나 업무 테이블 권한은 없다. 백업·재구성 가능해야 한다.
- CI 빌드/임의 PR 코드를 배포 서버에서 실행하지 않는다. Codex 작업기도 분리된 일회성 환경이며 배포키를 공유하지 않는다.
- 초기에는 GitHub Actions/Environments와 작은 배포 서비스·승인된 스크립트/조회 화면을 조합한다. Kubernetes·자체 CI 엔진·범용 플러그인 플랫폼을 첫 배포 선행 조건으로 만들지 않는다.

### 업무 영역

- **1단계부터 LB + App2대**, 각각 목표10명 전체를 감당하는지 단일 노드 부하 검증. 평상시 Blue 유지/Green 대기 또는 검증된 active-active, 전환 중 두 버전 동시존재.
- 별도 Worker1대부터 시작하되 작업별 버전 고정/완료까지 기존 프로세스 유지. worker 장애 내성과 배포 무중단은 구분. 여유 용량이 없으면 새 worker를 추가하고 드레인한다.
- 사설 Cloud DB for PostgreSQL HA2노드 권고. 실제 선택가능 SKU/리전·HA 구성을 견적에서 재확인한다. 업무 데이터 볼륨·백업·파일 저장은 release 디렉터리와 분리한다.
- 2단계App2×4vCPU/16GB, Worker2×4vCPU/16GB 후보. 3단계App3×4vCPU/16GB, Worker3×8vCPU/32GB 후보. 어디까지나 산정용 사양이며 부하검증 전 처리량 보장 아님.
- staging은 별도 환경. 작은 상시/예약기동 구성을 쓰되 배포 직전에는 구/신버전 동시가동 검증. trial 원자료·비밀 자동 복제 금지.

## 4. 무중단을 막는 현행 코드와 구현 순서

정적 확인: core/auth.py의 세션/일회용 SSE 티켓은 **SQLite 테이블**에 있다. 모두 메모리라는 주장은 틀리다. core/broadcaster.py의 clients/asyncio.Queue·내부 리스너는 프로세스 메모리, core/async_orchestrator.py의 active_tasks는 asyncio.Task 사전이다. 이것을 둔 채 앱2대만 띄우면 실행/이벤트가 갈라질 수 있다.

1. 세션·티켓·영수증·필수 업무 정본을 공용 PostgreSQL로 이관. 토큰 일회소비/유효기간/취소를 원자 처리하고 서버가 바뀌어도 같은 권한 판정.
2. API와 실행기 분리. PostgreSQL 작업큐/lease/heartbeat/fencing 및 client_request_id 멱등성 사용. 장애 재할당은 실제 실행/외부효과 상태를 대조하며 exactly-once라고 약속하지 않는다. 외부LLM 응답 유실은 UNKNOWN을 보존해 중복 과금을 방지한다.
3. SSE 이벤트는 DB outbox/내구 이벤트 ID에서 읽고 조직 필터를 재검증한다. LISTEN/NOTIFY 등은 깨우기일 뿐 원본/재생 저장소로 쓰지 않는다. Last-Event-ID/커서 재생·중복 제거·권한 회수·보존범위 밖 snapshot 재동기화. 내부 리스너 중복 실행도 잠근다.
4. 공유 파일은 객체저장/권한 있는 저장서비스로 이동. JSON 작업상태 동시쓰기 경계와 DB/파일 manifest 정합성을 먼저 정한다. NAS를 붙이는 것만으로 파일원자성·업무 트랜잭션 문제가 해결되지 않는다.
5. frontend 해시 assets/이전 chunk 보존, 이전 UI와 새API의 호환창, worker payload/checkpoint 판 호환을 명시한다. 배포로 열린 입력 양식을 강제 새로고침하지 않는다.
6. App 및 worker가 둘 이상 떠도 기동seed·scheduler·감사 이벤트가 중복되지 않아야 한다. migration은 배포 단계 단일 소유자만, 앱기동의 DDL/업무자료 갱신 제거.

## 5. Apollo에서 가져올 원칙

Apollo는 환경의 실제 버전/설정/상태 보고, 제약을 충족한 변경 계획, release channel과 건강도 기반 승격/회수를 결합한다. 고정 target state만 맞추는 제품이라고 단순화하지 않는다. [공식 동작 설명](https://www.palantir.com/docs/apollo/core/how-apollo-works).

우리 적용(설계 제안):

| 참조 원칙 | 최소 구현 |
|---|---|
| 환경/실제 상태 | staging·trial, 배포SHA/digest·schema·worker판·현재 트래픽·최종heartbeat |
| 릴리스 채널 | candidate → staging-verified → trial-canary → trial-stable |
| 제약 기반 계획 | 승인·검사·DB호환·여유용량·활성작업·백업조건 만족 전 대기 |
| 건강도 기반 승격 | API/권한/DB/작업/SSE/업무 probe를 종합, 응답없음은 UNKNOWN |
| 점진 전환/회수 | 승인된 시험 cohort부터 확장, 회수는 트래픽/호환코드 기준 |
| 환경 에이전트 | 인증된 제한 plan ID/digest만 수행, 결과/진행상태 보고 |

Apollo 문서도 건강도 신호가 없으면 liveness/시간 기준 판정만 남는 한계를 설명한다. 우리도 「프로세스가 떠 있다」를 업무건강으로 판정하지 않는다. [승격 파이프라인](https://www.palantir.com/docs/apollo/managing-release-channels/configure-promotion-pipeline).

Apollo 제품 도입/라이선스 구매 계획이 아니며 동일 수준 제품을 새로 구현하겠다는 약속도 아니다. 초기 범위는 환경2개·릴리스1계열·승인·블루그린·조회/감사다. 여러 고객 설치환경/폐쇄망은 후속이다.

배포계획 상태: REQUESTED→VALIDATED→APPROVAL_PENDING→PREPARING→CANARY→PROMOTING→DRAINING→SUCCEEDED. 실패시 BLOCKED/FAILED/ROLLBACK_PENDING/ROLLED_BACK/RECOVERY_REQUIRED 구분. 프로세스 중단/응답 유실 시 UNKNOWN에서 실제환경 재조회, 자동 재실행 금지. environment별 잠금·plan 원키·lease·감사와 취소가능 단계 정의.

## 6. 무중단 배포 절차/수용 기준

1. 보호된 ref에서 불변 release 생성, 단위·계약·보안·이관호환 검사. staging에서 동일 artifact 수용. 실제 GitHub 승인기능 요금제/권한 확인은 기존 CI/CD 문서대로.
2. DB는 **expand 먼저**: nullable/default의 영향과 lock timeout 검증, 오래 걸리는 backfill은 별도. 구/신 앱이 모두 읽고 쓸 수 있어야 한다. 같은 배포에서 구 컬럼 삭제 금지.
3. Green 기동, 준비상태/DB schema범위/권한·SSE/작업큐·정적asset 확인. 필요시 추가 슬롯 확보. Blue는 계속 서비스.
4. 운영 승인 후 선택된 시험계정/cohort에만 Green. NCP LB의 실제 가중치/라우팅 기능을 확인하고 불가하면 승인된 ingress 계층으로 cohort routing; 지원을 지어내지 않는다. 쓰기 shadow 복제 금지.
5. 단계별 health·최소요청수·관찰시간을 만족하면 확대. 1단계10명이면 퍼센트만 믿지 않고 지정계정+합성 probe로 판단. 예시5→25→100%는 정책 초안이지 필수 고정수치가 아니다.
6. Blue는 신규 요청에서 제외하고 기존 HTTP/SSE/worker를 드레인. SSE는 새티켓으로 재연결·이벤트 재생, 진행작업은 기존 worker가 완료/검증된 checkpoint 인계. 임의 timeout kill 금지.
7. 안정화 뒤 이전판은 복귀창 동안 보존. DB contract/삭제는 이후 별도 승인 release. 관리서버 중단/네트워크 단절이면 새작업을 시작하지 않고 현재 업무는 유지.

초기 수용 목표(검증 대상, SLA 아님): 목표 동시부하에서 배포기인 사용자5xx/로그인 유실/쓰기 유실/명령 중복0; DB migration lock이 요청timeout을 넘지 않음; 일반API p95≤1.5초; SSE는 네트워크 정상 시5초 내 재연결·미반영 이벤트0; 전환 전후 접수된 장기작업 완료/중단 판정 일치. 저트래픽이라 오류가0인 것만으로 통과하지 않는다.

rollback: DB N/N-1 호환이면 트래픽을 Blue로 복귀. 비호환/데이터손상은 자동 snapshot 덮어쓰기 금지, 해당 쓰기 격리·원장보존·복구 절차. 배포1회=DB무조건downgrade가 아니다. 실패Green·권한누락·health미보고·DBlock·worker진행·SSE구연결·배포서버장애를 사전 리허설한다.

## 7. 배포 후 Codex 수정 흐름

**운영 서버에 Codex를 붙여 원본 파일을 고치는 방식은 사용하지 않는다.**

사용자/운영자 수정 요청 → 자료 정제/권한 확인 → 현재 운영 release SHA를 기준으로 격리 작업 → Codex 패치·검사 → PR → 독립 검토 → 기존CI/staging → 승인형 무중단배포 → 해당 요청에 결과 연결.

- 초기 입구는 운영관리의 「수정 요청」/GitHub Issue 또는 로컬 Codex 작업. 일반 사용자는 요청만, 관리자/담당자가 코드변경 작업을 승인한다. 업무자료 공유·제출 승인을 코드실행 권한으로 확대하지 않는다.
- 요청 봉투: 문제·기대결과·재현절차·운영버전·대상환경/프로그램·허용파일·금지영역·수용시험·비용/시간한도. 로그/stack은 비밀·개인정보 제거. 운영DB/원자료를 자동 모델입력으로 보내지 않는다.
- **플랫폼 소스** 수정은 저장소 PR, **생성된 업무앱** 수정은 해당 앱/버전/소유자에 결속된 소스 패키지 및 candidate 새판으로 분기. 플랫폼 전체와 사용자앱을 같은 권한으로 수정하지 않는다. 기존 승인/승격 경계를 통과해야 한다.
- 공식 Codex GitHub Action/비대화형 실행을 기반으로 초기 연동한다. 공식 예제의 패치 생성 job과 PR 쓰기 job 분리 방식을 채택: Codex 실행은 repo read+격리 workspace write, 별도 job만 제한된 PR 생성 권한. [GitHub Action](https://developers.openai.com/codex/github-action), [비대화형 패치→PR](https://developers.openai.com/codex/noninteractive).
- 개인 로그인 토큰을 공유 서버에 복사하지 않는다. 자동화용 인증/한도/사용료를 별도 관리한다. 전체 job에 모델 API키를 노출하지 않으며 공식 안전 실행 전략·승인된 사용자 trigger·제한 네트워크를 적용한다. 공식 OpenAI Docs 확인 결과를 반영한 설계이며 아직 연동 구현/실행하지 않았다.
- Issue/로그/PR 본문은 신뢰되지 않은 입력이다. 저장소안의 명령도 임의 실행/배포권한 요청으로 승격하지 않는다. Codex는 운영SSH·DB·NCP관리키·자동merge·배포승인권한0. build/test는 별도 fresh sandbox에서 재확인하고 정책/검사 삭제·workflow 변경은 독립 승인.
- 동시변경이면 운영 SHA/PR base/배포상태를 재확인하고 stale 결과 자동 반영 금지. 오류 발생→무제한 자동수정 루프 금지, 예산/횟수 초과면 사람에게 인계.
- 단계1은 사람 요청·사람 검토, 단계2부터 반복 장애의 패치 제안 자동화 검토. 자동 배포 승인은 별개. 이 기능은 유료Codex 호출 승인도 포함하지 않는다.

## 9. 추진 순서와 완료 증거

새로운 일반UI 확장은 뒤로 미룬다. Claude가 이미 수행한 릴리스 권한/재개 보완은 최신 인계에서 확인해 중복 작업하지 않는다.

1. **다음30~45분 묶음:** 최신보안 마감 상태 인용 + DB-0에 auth/영수증/작업/SSE/파일경계 포함 + 실제 GitHub 보호기능 확인 + 계산기 품목 견적표. 비과금 읽기/설계만.
2. DB-1/2와 무중단 기반을 한 묶음의 수직 경로로 구현: 세션/명령1종/작업/이벤트→두 App→한 worker 경로. 관련계약/이관 대사와 노드교체 동안 기존작업 보존을 검증. 정확 구현기간은 DB지도 후 산정.
3. 별도 배포서비스 최소버전/immutable빌드/staging 블루그린/코드복귀. 관리서버 장애 시 업무영향0 검증.
4. Codex 요청→격리패치→PR만 우선 연결(승인된 소스·합성자료). 모델 실행 비용/계정은 별도 승인.
5. 목표부하에서 세션·SSE·쓰기·진행작업을 유지한 배포 리허설 성공 후 1단계 trial 오픈. 2/3단계는 해당 부하/실자료/비용/복구 Gate로 승격.

기존 DB12~20인일/웹4~5인일은 과거 추정이다. 이번 무중단·배포분리 추가범위가 들어갔으므로 며칠 내 완료로 재사용하지 않는다. 사용자에게 다음30~45분 산출물과 전체 critical path를 분리 보고한다. 전체21/40은 마지막 인정치 유지, 무중단/이관/배포 완료로 가산하지 않는다.

확정된 사용자 수를 다시 묻지 않는다. 아직 필요한 결정은 예산 권고 승인, 3단계50초과 보장상한(검증 단계에서), 실제 반입자료/보존·복구요구·도메인/관리자·자동화 계정이다. 자원 생성·과금·실자료 전송·커밋/푸시를 이번 계획 작성에 포함하지 않는다.

## 10. 소스/확인 범위

OpenAI 공식 문서를 먼저 확인한 뒤 Codex 연동을 설계했다. API키를 PR빌드와 공유하지 않는 패치/PR 작업분리 방향에 반영했다. Apollo는 위2개 공식문서의 운영원칙만 참고했다. 현행 소스는 부분 정적검토이며 다중노드/부하/DB실행은 미실행이다.
추가 경계: [NCP DB 사전조건](https://guide.ncloud-docs.com/docs/en/clouddbforpostgresql-spec), [GitHub 배포환경 제약](https://docs.github.com/en/actions/how-tos/deploy/configure-and-manage-deployments/manage-environments). NCP일반 요금표에는 여러 세대/상품이 섞여 있으므로 실제 장바구니 견적이 배정예산을 넘으면 구매 전 다시 보고한다.
