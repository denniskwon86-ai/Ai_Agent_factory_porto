# NCP 운영 트라이얼·DB 이관·CI/CD 실행안

> **후속 사용자 결정 2026-09-20:** 규모는30/동시10 →100/동시30 →200/동시50+, 별도 배포 시스템과 무중단 기본으로 변경. 최신 정본은 [무중단·Codex·예산 계획](NCP_ZERO_DOWNTIME_DELIVERY_AND_CODEX_2026-09-20.md). 아래 단일App 전체쓰기차단/재기동은 일상배포 기본안에서 대체되며, 보안·자료분리·승인·복구 원칙은 유지한다. 사용자규모 재질문 금지.

작성: Codex · 2026-09-20 KST.
사용자 확정: 기존 계획의 NCP 클라우드, 일부 실제 업무자료를 포함한 운영 트라이얼. CI/CD 방안까지 준비한다.
상태: 실행 설계. 클라우드 자원 생성/구매·실자료 업로드·운영 배포는 미실행. 기존 시연 계획을 전면 폐기하지 않고 아래 차이를 우선 적용한다.

## 1. 기존 계획에서 달라지는 경계

- 합성자료만의 demo가 아니다. 실자료를 쓰는 trial은 제한된 실제 운영으로 취급한다. 현재 전체21/40 인정치와 배포 준비도를 혼동하지 않는다.
- 시연 Reset, seed 덮어쓰기, 매 기동 조직/계정 재생성, 시연 종료 후 VM 삭제를 **trial에서는 실행하지 않는다**. 기동 초기화가 업무자료를 변경하는지 첫 배포 차단 항목에 넣는다.
- 사용자 승인 자료만 이전한다. 기존 Git 평문 테스트자료 공유 승인을 새 실제 업무자료 공개 승인으로 확장하지 않는다.
- 운영 중요도에 따라 DB 분리/복구를 설계한다. 기존 저비용 단일VM SQLite 시연 구성이나 앱+DB 동거 제한파일럿을 아무 검토 없이 실자료 trial에 적용하지 않는다.
- 기존 DB-0~7 순서를 유지한다. DB 분류/접근계층 준비는 UI 전체 수용 완료와 독립적으로 진행한다.

## 2. 기본 구성안 / 비용 집행 전 확인

권고 구성은 한국 리전 NCP VPC의 App VM + **사설 접근 Cloud DB for PostgreSQL** + 비공개 파일/백업 저장소다. 앱은 기존 systemd/Caddy 방향을 재사용하고 첫 전환은 단일 Uvicorn worker를 유지한다. DB 교체가 메모리 기반 SSE/작업 상태 외부화를 뜻하지 않는다.

App의 HTTPS 진입 외 관리 접속은 VPN/승인된 관리자 경로로 제한한다. DB 공인 접근 금지, App 및 별도 승인 이관 경로만 허용한다. DB 계정은 앱 DML·스키마 이관 DDL·백업/복구 역할을 분리하고 앱에 관리자 권한을 주지 않는다. 비밀값은 서버측 제한된 비밀 저장소/파일로 주입하며 CI 산출물에 넣지 않는다.

관리형 PostgreSQL의 VPC 제공·자동 백업 및 신규 서버 복원은 공식 문서에 근거한다. 가용성/사양/백업 보관/RPO/RTO와 월 비용은 견적 및 복구 실측 후 승인한다. HA가 백업을 대신하지 않는다. [NCP 개요](https://guide.ncloud-docs.com/docs/clouddbforpostgresql-overview), [생성/접속 절차](https://guide.ncloud-docs.com/docs/clouddbforpostgresql-procedure).

관리형 DB 비용이 예산 밖이면 별도 사설 DB VM을 비교하되 자동 선택하지 않는다. 그 경우 PostgreSQL 패치·WAL/PITR·백업·복구 운영 책임까지 명시한다. NCP 과거 계획의 금액을 현재 견적으로 재사용하지 않는다.

## 3. 환경·자료 경계

| 환경 | 자료 | 목적/접근 |
|---|---|---|
| 개발/PR CI | 합성 fixture | 코드 검사. 실제 DB·LLM 키·서버 배포 권한 없음 |
| staging | 합성자료 기본, 별도 승인된 비식별 자료만 예외 | 이관/복구·로그인·권한·SSE·재기동 검증 |
| trial | 반입 승인된 실제 업무자료 및 구별된 시험자료 | 초대된 실명 계정/최소 조직 권한, 변경·열람 감사 |

staging과 trial은 별도 DB·계정·스토리지·비밀값·도메인을 사용한다. staging 프로세스/runner가 trial DB 자격증명을 가지지 않게 한다. 시험환경을 위해 trial DB를 자동 복제하지 않는다.

반입표 필수: 자료 소유자/승인자·회사/부서·기간·개인/민감정보 여부·허용 사용자·보관/삭제 조건·모델 제공자 전송 허용 여부. **클라우드 반입 승인과 외부 LLM 전송 승인은 별개**다. 코드 생성/로그/프롬프트/RAG에 실자료가 섞이는 경로도 통제한다. 실제 자료 목록 승인 전에는 파일을 업로드하지 않는다.

초기계정·테스트 토큰·개발 신뢰헤더 비활성, 기본비밀번호 금지. 관리자 MFA와 초대/회수 절차 확인. 로그는 토큰/원문/개인정보를 기본 제거하고 감사에는 필요한 최소 식별 정보만 둔다. 생성 앱의 네트워크/비밀 접근도 본 앱과 분리한다.

## 4. CI/CD 기본 흐름

`PR → CI 통과·코드 검토 → 보호된 통합 ref → 불변 산출물 생성 → staging 배포/수용 → 사람 승인 → 동일 산출물 trial 배포 → 상태 관측`

현재 checkout에 .github 디렉터리는 없다. 기존 CI가 설정됐다고 보고하지 않는다. 실제 원격 설정/요금제는 아직 확인하지 않았다. 아래 파일은 **Claude 구현 대상 제안**이며 생성 완료가 아니다.

### CI: .github/workflows/ci.yml

- PR의 타입/프런트 build/영향 범위 서버·프런트 검사, 기존 격리 시험 러너 사용. 전체 pytest를 무조건 운영 checkout에서 실행하지 않는다.
- 필수 보안 계약은 변경 범위에 상관없이 검사: 조직/프로젝트 격리, 릴리스 읽기, 미확정 재실행 차단, 상태/승격 경계. DB 변경은 PostgreSQL/기존 저장소 계약·빈DB 설치·이관 대사 검사 추가.
- secret 탐지·의존 취약점 검사와 배포 산출물 허용목록 검사. 기존 실패/부채를 skip으로 숨기지 말고 baseline과 신규 실패를 분리한다. 필수검사 실패는 병합/배포 차단.
- PR 작업은 최소 read 권한과 비밀값0. 신뢰되지 않은 PR 코드를 배포권한 runner에서 실행하지 않는다. Actions는 검토된 전체 commit SHA로 고정한다. [GitHub 보안 지침](https://docs.github.com/en/actions/reference/security/secure-use).
- 테스트/배포 자동 과정에서 유료LLM은 기본0. 승인을 받은 별도 작업만 예외.

### 불변 빌드: .github/workflows/release.yml

- 실제 통합 브랜치/ref는 사용자 저장소 운영 방식 확인 후 정한다. dev/main 이름을 임의로 가정하거나 브랜치를 생성하지 않는다.
- PR 산출물을 그대로 승격하지 않고 검토·병합된 정확한 SHA에서 Linux용 산출물을 만든다. 의존성 잠금·런타임 버전을 고정한다. 서버에서 git pull·npm install로 다른 결과물을 다시 만들지 않는다.
- 현행 systemd 방향에 맞춘 버전별 release 패키지(백엔드/잠긴 의존성 설치 묶음·frontend/dist·이관/배포 스크립트) 사용. 컨테이너 전환을 필수 선행 과제로 추가하지 않는다.
- manifest: commit SHA, 빌드ID, 내용 digest, 의존성 목록/SBOM, 스키마 판과 지원 범위, 검사 보고, 배포 스크립트 판. 재실행으로 같은 버전을 덮어쓰지 않는다.
- 소스 전체를 tar/zip하지 않고 허용목록으로 패키징한다. data/, projects/, library/, 사용자로그, .env, data_sync, output, 보호문서, fixture와 비밀값은 제외. 실자료가 CI artifact/log/cache에 섞이지 않는지 검사한다.

### staging: .github/workflows/deploy-staging.yml

- 검증된 release digest만 배포. staging DB에서 migration/하위호환과 복구 시험.
- HTTPS, 로그인/만료, 조직 음성대조, 대표읽기/쓰기, Preview, SSE/재연결, 재기동 영속성 확인.
- 합성 전용 계정으로 쓰기검사하고 실제자료 Reset 금지. 결과·manifest·DB판을 배포 기록에 결속한다.
- staging에서 통과한 **같은 digest**만 trial 후보가 된다. 후보 이후 코드가 바뀌면 다시 후보 절차를 밟는다.

### trial: .github/workflows/deploy-trial.yml

- 초기에는 **승인형 CD**. staging 성공만으로 trial 자동 반영하지 않는다. 승인자·변경범위·DB 영향·백업/복구 준비·중단창을 기록한다.
- GitHub Environment required reviewers·자기승인 금지·배포 ref 제한을 기본안으로 하되, 비공개 저장소/요금제에서 실제 지원되는지 확인한다. 지원이 안 되면 무인배포를 켜지 않고 권한 있는 운영자가 승인기록을 확인한 뒤 제한된 배포 명령으로 같은 artifact를 배포한다. workflow_dispatch 버튼만으로 독립 승인과 같다고 하지 않는다. [GitHub 환경/요금제 조건](https://docs.github.com/en/actions/how-tos/deploy/configure-and-manage-deployments/manage-environments).
- 실행 중인 migration/deploy를 새 커밋 때문에 취소하지 않는다. 환경별 단일 배포 잠금과 DB migration 잠금을 사용한다. 겹친 요청은 대기/거절한다.
- 모든 앱/백그라운드 쓰기 경로를 차단하고 실행 작업·SSE 연결을 유예 종료/재연결 처리한다. 강제종료가 작업 취소 증거라고 말하지 않는다.
- 백업 성공·복구 준비 확인 → 별도 역할로 migration 한 번 → 권한 제한 release 디렉터리 설치 → 원자적 현재 코드 전환 → 서비스 재기동 → 읽기 중심 smoke → 사용자 쓰기 재개. 실제 데이터 검사용 변경은 별도 승인된 시험계정/대상만.
- 성공은 프로세스 시작이 아닌 로그인·DB schema·핵심 조회·권한 음성대조·SSE·최근 오류 확인으로 판단한다. 배포자/승인자·시간·SHA/digest·schema·backup ID·결과 기록.

## 5. runner·배포 권한

GitHub-hosted CI에는 trial 네트워크/비밀 접근0. CD는 별도 제한된 배포 runner/운영 경로를 사용한다. **앱/DB 서버 자체에 PR을 실행하는 self-hosted runner를 설치하지 않는다.**

기본 자동화안은 NCP의 별도 배포 runner에서 신뢰된 배포 workflow만 실행하고, 사설망의 제한 deploy 계정으로 승인된 digest 설치/상태 확인만 수행하는 방식이다. DB 자격증명은 PR/빌드로 전달하지 않는다. runner는 일반 개발 셸이나 root 권한을 공유하지 않는다. 일회성 실행/정리·workflow/ref 제한과 비용을 구현 전에 확인한다. 구현이 준비 안 되면 초기 수동 승인 배포를 유지한다.

NCP와 GitHub 간 OIDC 지원/권한 결속을 확인하지 않았으므로 가능하다고 가정하지 않는다. 지원 검증 시 단기 자격증명을 우선하고, 고정키가 필요한 대안은 최소권한·회전·철수 절차를 갖춰 별도 승인한다. SSH host key 검증을 끄거나 인터넷 전체에 관리 포트를 열지 않는다.

## 6. DB 변경과 복구 규칙

- 초기 SQLite→PostgreSQL은 사본 전체 리허설 후 쓰기동결/최종이관. 업무 DB뿐 아니라 파일/산출물·원장·영수증 결속을 대사한다. 기본 데이터 reset/seed 금지.
- 후속 schema는 expand→호환 코드 전환→안정화→contract. 삭제/열 축소/대량 backfill은 자동 일상배포에 끼워 넣지 않는다. 장시간이관은 별도 유지보수 작업.
- 코드 복귀는 DB가 이전 코드와 호환되고 데이터 의미가 바뀌지 않았음을 확인한 경우만 가능. 새 쓰기가 생긴 뒤 DB백업을 자동 덮어써서 롤백하지 않는다.
- 호환성 불명/파괴적 migration 실패: 쓰기 차단 유지, 현재 DB 보존, 별도 복구 인스턴스에서 대사, 사용자 승인 후 재개. schema downgrade를 무조건 자동 실행하지 않는다.
- DB와 projects/library/첨부자료를 같은 복구 기준점으로 기록한다. 일일백업만으로 요구 복구 수준이 충족된다고 가정하지 않는다. RPO/RTO·보관일수는 사용자와 확정하고 실제 복구시간/복원시점으로 검증한다.
- NCP 자체 백업 복원과 Object Storage 내보내기는 별개다. 공식 문서는 **Object Storage에 보낸 백업을 Cloud DB 서비스에서 직접 복원하는 기능은 현재 제공하지 않는다**고 명시한다. 보관 성공을 복구 성공이라 하지 말고 실제 지원 경로로 신규DB 복구를 시험한다. 버킷을 공개하는 우회는 금지한다. [NCP 백업/복구](https://guide.ncloud-docs.com/docs/clouddbforpostgresql-backup).

## 7. 첫 배포 Go/No-Go

| 항목 | 통과 증거 |
|---|---|
| 범위/자료 | 사용자수·동시작업·기간·자료 반입표/소유자 승인, 외부LLM 전송 경계 |
| 보안 | 릴리스 권한 누락/고아자료/상태불명 payload 및 candidate 활성화 경계 해결, 실제 권한 음성대조 |
| DB/파일 | 사본 이관 대사 차이0 또는 승인된 설명, 기동/재기동이 자료를 덮지 않음 |
| 복구 | 별도환경 복원 성공, RPO/RTO 측정, 새쓰기 보존/롤백 중단 조건 |
| CI/CD | PR 실패 차단, 동일 artifact 승격, 승인 우회 차단, 배포 잠금, 실패 리허설 |
| 운영 | 비용 상한/알림·디스크/오류/DB연결/SSE 관측·연락 담당·중단창 |

## 8. Claude 다음 묶음과 미확정 사항

1. 앞선 DB-0/1 준비와 보안 마감은 계속한다. 시연 전용 명령이 trial에 실행될 가능성을 차단 목록에 추가한다.
2. **첫30~45분**: 원격 저장소 공개범위/Actions 요금제·보호규칙 확인(읽기 전용), 기존 격리 테스트 명령/Linux 의존성 확인, artifact 허용목록·workflow/deploy 스크립트 파일 계획. 이미 조사한 항목 반복 금지.
3. **후속60~90분 추정**: 로컬 CI/workflow·배포 스크립트 초안과 합성 dry-run. 클라우드 생성/runner 등록/Secrets 설정/실제 업로드 없이 가능한 범위만. 완성시간 약속이 아니며 깨끗한 Linux 검증이 안 되면 미검증으로 보고한다.
4. 이 단계 산출물이 운영 배포 완료는 아니다. DB 접근계층 변경 규모가 확인되면 DB 이관·CI/CD·서버 셋업을 별도 소요시간으로 재산정한다.

사용자 확인 필요: 초기 사용자/동시사용 규모, 인프라 월예산 상한(LLM 별도), 사용할 도메인/관리자, 허용 중단시간·데이터 손실 허용량, 반입 자료 목록. 상세가 미정이어도 비과금 로컬 설계/CI 초안은 진행 가능하다.

문서 작성/공식문서 확인은 Codex, 실제 코드·검증 수행은 Claude. 공유 문서 수신/착수 미확인. 실제 배포·과금·자료이전·커밋/푸시 없음. 과거 시연 종료 자동삭제 절차는 trial에 적용하지 않는다.
