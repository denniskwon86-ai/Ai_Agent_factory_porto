## 1. 로드맵 운영 원칙

### 1.1 최우선 목표

첫 목표는 기능 수를 늘리는 것이 아니라 다음 수직 폐루프를 실제 데이터로 완주하는 것이다.

> 원료 구매·도입계획 → 물류 입력 협업 → 재고·생산·현금·손익 시뮬레이션 → 의사결정 요청·승인 → 실행 배포 → 실제 효과 측정

### 1.2 관문 방식

각 단계는 코드가 존재한다는 이유로 완료되지 않는다. 다음 네 조건을 모두 충족해야 다음 단계로 승격한다.

1. 사용자 여정이 처음부터 끝까지 동작한다.
2. 권한·감사·실패 시나리오가 검증된다.
3. 결과의 데이터·규칙·모델 계보가 남는다.
4. 시간·비용·품질 지표가 측정된다.

### 1.3 구현 상태 용어

| 상태 | 정의 |
|---|---|
| 설계 | 데이터 모델·API·상태 전이·화면·검수 기준이 합의됨 |
| 구현 | 코드와 단위 테스트가 존재함 |
| 통합 | 실제 인접 기능과 연결되어 계약 테스트를 통과함 |
| 파일럿 검증 | 대표 현업 데이터와 사용자 여정으로 효과를 측정함 |
| 제품화 | 배포·보안·운영·지원 기준을 충족함 |

### 1.4 우선순위

- **P0**: 수직 폐루프 또는 보안·데이터 신뢰를 막는 작업
- **P1**: 파일럿 가치와 운영성을 크게 높이는 작업
- **P2**: 확장성과 편의성을 높이지만 첫 증명에 필수는 아닌 작업
- **보류**: 첫 폐루프 검증 전에는 착수하지 않는 작업

## 2. 현재 기준선

### 2.1 구현된 강한 기반

- LangGraph 기반 다중 에이전트 SW 생성 파이프라인
- RFP 명확화, HOTL 승인, WBS, 코드 생성, 검토, QA, 릴리스
- 로컬 품질 게이트와 실패·재작업·자가복구 구조
- 회사·조직 계층과 REAL/VIRTUAL/COMPETITOR 컨텍스트
- MDM, 데이터 카탈로그, 용어사전, 데이터 계보, 계약, 크로스워크
- 외부지표 저장·품질·시나리오 연결 기반
- 경영계획, 기준선, 가정, 결과 비교의 초기 구조
- 조직 범위 강제, 404 은폐, 감사·의사결정 원장 기반
- 다중 LLM 공급자, 폴백, 호출 텔레메트리의 초기 구조
- 승인된 UI North Star와 기능별 프로토타입
- CL-0 App-in-App Manifest와 자체 인증 정적 검사

### 2.2 아직 닫히지 않은 핵심 고리

- 실제 SSO/사용자 생명주기와 엔터프라이즈 권한
- 생성 앱의 Host Runtime API와 실행 샌드박스
- 사용자별·조직별 실시간 이벤트 격리
- 앱 전달·수락·앱 주머니의 실제 제품 코드
- 제조 경영 의미 모델의 통합 질의 런타임
- 확정 계산식과 실제 데이터로 검증한 경영 시뮬레이션
- 의사결정 요청·회의·실행 업무·효과 측정 폐루프
- Jarvis의 전역 근거 질의와 승인된 실행
- 운영 DB·마이그레이션·관측성·백업·복구·배포
- 현업 파일럿의 ROI 및 예측 오차 증명

### 2.3 즉시 주의할 구조 부채

- 여러 도메인 SQLite 저장소가 분산되어 트랜잭션·마이그레이션·운영성이 약하다.
- 프론트엔드는 다수 전역 boolean과 오버레이에 의존해 URL·권한·복귀 동작이 불명확하다.
- SSE는 전역 클라이언트에 방송되며 사용자·조직 필터가 없다.
- 개발용 UserSwitcher는 인증이 아니다.
- 현재 의미 계층은 여러 저장소의 조합이며 통합 그래프 질의와 정책 평가가 약하다.
- 정적 코드 검사는 생성 앱의 실제 런타임 권한을 강제하지 못한다.

## 3. 전체 단계 지도

| 단계 | 목표 | 핵심 관문 |
|---|---|---|
| G0 | 기준선 고정과 충돌 방지 | 현행 상태·테스트·소유자·결정 기록 |
| G1 | 플랫폼 안전 기반 강화 | 앱이 호스트 권한 밖에서 실행 불가 |

| G3 | 운영 App Factory 완성 | 생성→릴리스→전달→수락→실행이 권한 안에서 완주 |
| G4 | 경영 Twin MVP 완성 | 실제/기준/시나리오 수치가 재현 가능하게 계산 |
| G5 | 의사결정·실행·효과 폐루프 완성 | 결정 전후가 업무와 성과로 연결 |
| G6 | Jarvis와 실행 패브릭 | 근거 질의와 승인된 행동을 전역에서 수행 |
| G7 | 엔터프라이즈 제품화 | SSO·RLS·배포·관측·DR·SLA 충족 |
| G8 | 파일럿·ROI 검증 | 사용자와 실제 데이터로 가치 증명 |
| G9 | 전사·그룹 확장 | 도메인·회사·가상기업 확장 규칙 검증 |

G1~G5가 첫 제품 완성선이다. G6~G7은 상용 운영 완성선이며, G8은 시장 가치 증명선이다.

### 3.1 권고 일정 범위

아래는 **2주 Sprint, 핵심 의사결정자와 현업 데이터 담당자가 지연 없이 참여한다는 가정**의 계획 범위다. AI 작업 속도와 별개로 보안 검토, 실제 데이터 보정, 사용자 검증에는 사람이 필요하므로 확정 납기로 사용하지 않는다.

| Release | Sprint 범위 | 목표 | 출구 조건 |
|---|---:|---|---|
| R0 Safe Foundation | S0~S2 | G0, CL-0.5, SSE 격리, Runtime 계약 | 생성 앱과 이벤트의 권한 경계 증명 |
| R1 Vertical Data | S2~S5 | G2 원료 구매 의미 모델·MVA 부트스트랩 | CERTIFIED Snapshot의 의미·계보 질의 |
| R2 Operational Apps | S4~S8 | G3 생성·전달·수락·앱 주머니 | 구매→물류 앱 협업 완주 |
| R3 Twin MVP | S6~S11 | G4 계산 그래프·Replay·백테스트 | 생산·현금·손익 재현과 오차 설명 |
| R4 Decision Loop | S9~S14 | G5 회의·결정·실행·효과·내부 보고 | 결정 전후 폐루프 완주 |
| R5 Enterprise Beta | S12~S20 | G6·G7 Jarvis·SSO·운영·배포 | 통제된 내부 Beta 운영 |
| R6 Proof & Scale | S18~S26 | G8 파일럿·ROI·2차 조직 복제 | 효과 증명과 포크 없는 확장 |
| R7 Group Expansion | S24 이후 | G9 인접 업무·그룹·가상기업 | 반복 가능한 산업 패키지 |

현업 데이터가 준비되지 않거나 보안 승인이 지연되면 R1 이후 일정은 즉시 재산정한다. 반대로 문서·샘플 데이터로 API를 빨리 만들었다는 이유로 R3~R6 관문을 생략하지 않는다.

## 4. G0 — 기준선 고정과 작업 통제

### 목표

여러 팀원이 동일 작업트리에서 작업하는 상황에서 구현 상태, 책임 범위, 인터페이스 변경을 잃지 않도록 한다.

### 작업

| ID | 우선 | 작업 | 산출물 |
|---|---:|---|---|
| G0-01 | P0 | 현재 테스트 수, 주요 E2E, DB, Router, 화면의 기준선 스냅샷 | 기준선 보고서 |
| G0-02 | P0 | `TEAM_BOARD` 진행 항목에 작성자·이유·영향·다음 담당을 의무화 | 최신 팀 보드 |
| G0-03 | P0 | 구현·설계·전략 가설을 문서에서 명시적으로 구분 | 문서 상태 태그 |
| G0-04 | P0 | CL-0~CL-5와 본 로드맵의 의존성 매핑 | 작업 패키지 매트릭스 |
| G0-05 | P1 | API·DB·권한·이벤트 변경 계약 목록 관리 | 인터페이스 변경대장 |
| G0-06 | P1 | 테스트 데이터와 실제/가상/경쟁사 데이터 표시 규칙 | 데이터 분류 규약 |

### 완료 정의

- 현재 HEAD와 검증된 테스트 명령이 인수인계 문서에 있다.
- 각 활성 작업에 단일 책임자와 교차검토 대상이 표시된다.
- 다른 작업자의 미커밋 파일을 덮지 않고 패키지 단위로 통합할 수 있다.
- 기능 상태를 문서만 보고 구현/부분/설계로 오판하지 않는다.

### 현재 판정

부분 충족. 팀 보드는 성숙했지만 오래된 완료·검토 항목이 누적되어 최신 우선순위가 흐려질 수 있다. 주기적 아카이브가 필요하다.

> **A-1 관문 정정:** 과거 기간계 설계의 `G0 = A-1 완주`는 `test_a1_v11`의 6개 태스크 DONE·QA PASS·수용검수 PASS·게시로 2026-07-27 이미 해제되었다(`AI_HANDOFF.md:317-331`). 본 로드맵의 G0는 작업 기준선과 통합 통제이며 A-1 재수행을 뜻하지 않는다. CL-0.5·Runtime 변경 후 A-1은 회귀 카나리로 다시 실행할 수 있지만, 현재의 다음 제품 관문은 G1 안전 경계와 G2 실제 데이터 부트스트랩이다.

상세 Adapter·Query Contract·Snapshot·증분 사건 설계는 [`design_external_engagement_system_integration.md`](../design_external_engagement_system_integration.md)를 따르고, LPL 특이사항은 [`design_lpl_readonly_integration.md`](../design_lpl_readonly_integration.md)에 Profile로만 둔다.

연계 우선순위:

1. 고객사 기존 시스템의 공식 API 또는 MCP Server
2. 승인된 DB Read Replica/View
3. 정기 파일 Export와 checksum
4. 화면 자동화는 API·Export가 모두 불가능한 경우에만 별도 위험 승인

현재 `MCPAdapter.fetch()`는 단일 객체 조회에 적합하고 목록·증분 사건에 부족하다. 원료 도입에는 다음 계약 확장이 필요하다.

```python
query(system_id, entity, filters, fields, cursor, limit)
changes_since(system_id, entity, updated_after, cursor, limit)
```

반환값에는 `items`, `next_cursor`, `source_as_of`, `source_version`이 포함되어야 한다. 페이지별 재시도와 중복 수신에도 동일 사건을 한 번만 반영하도록 `(system_id, source_event_id, source_version)` 멱등키를 사용한다.

### 완료 정의

- 릴리스 부적격 앱은 Preview 외 운영 실행·전달·수락이 불가능하다.
- 생성 앱이 플랫폼을 우회해 사용자 계정·토큰·DB를 관리할 수 없다.
- 다른 조직·사용자의 이벤트와 데이터 존재 여부가 노출되지 않는다.
- 외부 참여자용 AI Factory Studio 계정·화면·앱이 존재하지 않는다.
- 외부 원천에서 읽는 범위가 승인 Query Contract를 넘지 않고 내부 조직 권한보다 넓어지지 않는다.
- 권한 해석 실패는 모두 차단되며 감사로그가 남는다.
- 위협 모델과 침투·회귀 테스트가 통과한다.

### 필수 시험

- 권한 없는 앱/사용자/조직/릴리스 조합의 테이블 기반 부정 테스트
- Manifest 축소 후 기존 capability 호출 시 차단
- 토큰 재사용·만료·위변조·다른 앱 사용 차단
- SSE 다중 사용자 동시 연결 격리
- Query Contract 밖 엔터티·필드·무필터 전건 조회 차단
- 중복·순서 역전·정정·취소 원천 사건의 멱등·버전 처리
- 원천 장애 시 오래된 값을 최신값처럼 사용하지 않고 `as_of/stale` 표시
- 정적 검사 우회 시도와 런타임 차단의 이중 검증

## 6. G2 — 첫 업무 도메인의 의미·데이터 기반

### 목표

### G2-A. 업무·의미 모델

최소 엔터티:

- 조직: 법인, 사업부, 사업장, 공장, 부서

| ID | 예상 | 작업 | 출구 조건 |

- `source_count/sum`, `loaded_count/sum`, `variance`, `tolerance`
- `owner_user_id`, `certified_by/at`, `lineage_id`

#### 외부 협업 시스템 최초 데이터 계약 후보

실제 엔터티·필드명은 고객사 원천 스키마 확인 후 확정하고, 아래 업무 의미를 Query Contract로 매핑한다. LS 환경에서는 LPL Profile이 이 매핑을 제공한다.

| 논리 계약 | 최소 업무 의미 | 필수 조회 조건 |
|---|---|---|
| `partner_submission` | 거래처 제출 상태·수정 시각 | 회사·거래/발주 식별자 |
| `shipment_milestone` | 선적·출항·도착 예정/실적 | 선적 또는 발주 식별자 |
| `customs_clearance` | 신고·검사·통관 상태와 일자 | 수입/선적 식별자 |
| `transport_milestone` | 배차·픽업·이동·도착 상태 | 운송 또는 선적 식별자 |

원천 시스템의 사용자 개인정보 전체를 가져오지 않는다. 시뮬레이션과 업무 연결에 필요한 파트너 코드, 원천 사건, 상태, 업무 일자, 참조키만 최소 수집하며 민감 필드는 Query Contract에서 제외한다.

#### 원칙

- 직접 쓰기나 전량 복제보다 파일·API·DB Read Replica의 최소 Snapshot을 우선한다.
- 자격증명은 Secret 참조로 관리하고 추출 로그·프롬프트에 노출하지 않는다.
- 원천 대사 실패 데이터는 앱과 Twin의 공식 Actual로 사용하지 않는다.
- 데이터가 부족해도 시스템은 가능한 범위, 신뢰도, 막힌 결과, 필요한 다음 작업을 제시한다.

### 완료 정의

- “이 원료의 도입 지연이 어느 공장의 어떤 생산계획과 현금흐름에 영향을 주는가?”에 근거 경로로 답한다.
- 동일 질문이 회사·사업부 권한에 따라 다른 범위로 안전하게 계산된다.
- 업무 앱과 시뮬레이션이 같은 엔터티 ID, 단위, 버전을 사용한다.
- 자연어 검색 결과마다 출처·기준시점·신뢰도·조직 범위를 표시한다.
- 최소 한 개 실제 문서·파일·운영 데이터 Snapshot이 RAW→표준화→대사→CERTIFIED→결과까지 추적된다.
- 원천 건수·핵심 수량·금액의 대사 차이가 허용 오차 안에 있고 미매핑·격리 건을 별도로 설명한다.

## 7. G3 — 운영 App Factory와 협업 완성

### 목표

현업 사용자가 생성한 앱이 플랫폼 계약 안에서 릴리스되고, 필요한 사용자에게 전달·수락되어 실제 데이터를 입력·조회할 수 있게 한다.

### Claude Code CL 작업과의 정렬

| 기존 패키지 | 본 로드맵 위치 | 선행 조건 |
|---|---|---|
| CL-0 App-in-App Manifest | G1-A | CL-0.5 보강 후 완료 선언 |
| CL-1 앱 전달·수락 | G3-A | G1 사용자별 SSE·Host Runtime 최소 계약 |
| CL-2 의사결정 회의 | G5-A | G4 시뮬레이션 결과 계약 |
| CL-3 보고서 발간 | G5-C | 공개 등급·승인·스냅샷 |
| CL-4/5 UI 통합 | G3/G5 | API·권한·상태 전이 통합 후 |

### G3-A. 앱 자산과 전달

| ID | 우선 | 작업 |
|---|---:|---|
| G3-A01 | P0 | App, Release, Manifest, Assignment, Acceptance 모델 확정 |
| G3-A02 | P0 | 개인 전달과 조직 공유를 별개 상태 전이로 구현 |
| G3-A03 | P0 | 전달 대상 권한·회사 범위·앱 capability 사전 검증 |
| G3-A04 | P0 | 수락은 앱 사용권만 부여하고 데이터 권한은 확대하지 않음 |
| G3-A05 | P0 | 앱 주머니 등록·거절·철회·만료·업데이트 승인 |
| G3-A06 | P0 | 사용자별 SSE/알림과 멱등 처리 |
| G3-A07 | P1 | 생성 앱이 Host Runtime을 통해 표준화된 외부 원천 데이터만 조회 |
| G3-A08 | P1 | 앱 화면에 원천 시스템·기준시점·stale·정정 상태 표시 |
| G3-A09 | P1 | 조직 템플릿 승격과 관리자 승인 |

### G3-B. 생성·릴리스 품질

- 요구사항 명확화 질문과 데이터 준비도 확인
- 회사·업종·업무 프로필 기반 에이전트팩 추천
- Host Runtime SDK를 코드 생성 기본 템플릿으로 강제
- 자체 인증·로컬 사용자 저장소·직접 DB 접근 생성 금지
- API 계약, UI 접근성, 테스트, 보안, 회귀, 렌더, 실행 smoke gate
- 빌드 3회 실패 후 무한 재시도 대신 실패 패키지 생성:
  - 실패 단계와 원인 분류
  - 세 번의 수정 diff와 동일 실패 여부
  - 마지막 정상 상태
  - 사용자 선택: 강한 모델 재시도 / 범위 축소 / 전문가 인계 / 보류
- 릴리스 승인과 롤백

### G3-C. 제품 UI

- `/factory`: 요구 입력, 전체 workflow, WBS, 현재 작업, 사용자 결정, Jarvis, 실행 기록
- `/apps`: 내 앱 주머니, 전달받음, 조직 공유, 버전·권한·상태
- `/agents`: 에이전트·워크플로우·비용·품질 관리
- 전역 AppShell: 회사 컨텍스트, 알림, Jarvis, 설정, 관리자
- URL 기반 라우팅과 페이지별 권한 가드
- 화면에 실제 API 상태만 표시하고 데모 값 제거

### 완료 정의

- 구매 담당자가 앱을 생성·릴리스하고 물류 담당자에게 전달한다.
- 물류 담당자가 수락해 자신의 앱 주머니에서 실행하고 데이터를 입력한다.
- 거래처·관세사·포워더·운송사는 고객사의 기존 외부 협업 시스템에서 업무 데이터를 입력하고 AI Factory Studio에 접속하지 않는다.
- 생성 앱은 원천 시스템 자격증명을 갖지 않고 Host Runtime과 승인된 Query Contract를 통해 필요한 표준 데이터만 읽는다.
- 원천 버전·기준시점·정정 상태가 화면과 계산 계보에 표시된다.
- 앱은 별도 로그인 없이 현재 회사·사용자 컨텍스트를 상속한다.
- 허용되지 않은 데이터·행동은 서버에서 차단된다.
- 앱 업데이트 시 권한·Manifest 변경을 재승인한다.
- 릴리스 실패는 이유와 다음 행동이 사용자에게 명확히 보인다.

## 8. G4 — 경영 디지털트윈 MVP

### 목표

실제값, 기준선, 가정, 외부지표를 분리하고 생산·재고·현금·손익 영향을 재현 가능하게 계산한다.

### G4-A. 계산 계약

모든 계산 모델은 다음을 가져야 한다.

- model_id, version, owner, status
- input schema와 단위
- output schema와 단위
- formula 또는 실행 코드 fingerprint
- effective_from/to
- baseline_id, assumption_set_id
- source observations와 공개 시점
- 조직·기간·통화 범위
- 검증 데이터셋과 허용 오차

### G4-B. 첫 계산 그래프

```text
도입 예정량·일정·가격
 + 환율·운임
 → 원료 입고량·매입·현금 유출
 + 기초재고·소요량·수율·생산능력
 → 가용재고·생산량·부족 위험
 + 판매계획·제품가격
 → 매출·원가·재고자산·운전자본·손익
```

### G4-C. 시나리오 기능

- 기준/낙관/비관 및 사용자 정의 시나리오
- 단일 변수와 복합 변수 변화
- 외부지표 충격과 지연 전파
- 민감도, 기여도, 임계점
- 결과 범위와 불확실성
- 시나리오 비교와 설명
- REAL 기준선 복제 VIRTUAL 기업 실험
- COMPETITOR 정보는 공개 근거와 추정치를 분리

### G4-D. 백테스트

- 과거 특정 시점에 당시 공개된 데이터만 사용
- 개정된 외부지표는 빈티지별 저장
- 예측과 실제 실적 비교
- 오차를 입력 데이터, 가정, 모델, 실행 편차로 분해
- 모델 버전별 정확도와 안정성 비교

### 완료 정의

- 같은 입력·모델 버전에서 계산 결과가 동일하다.
- 모든 결과에서 입력→수식→출력 계보를 조회할 수 있다.
- 과거 기간 한 개 이상을 백테스트하고 오차 원인을 설명한다.
- 환율·원료가격·운임·전기료 변화가 생산·현금·손익에 미치는 경로를 표시한다.
- LLM을 끄고도 핵심 숫자 계산이 완주한다.

## 9. G5 — 의사결정·실행·효과 측정 폐루프

### 목표

시뮬레이션 결과를 실제 조직 의사결정과 실행으로 연결하고, 약속한 효과와 실제 효과를 비교한다.

### G5-A. 의사결정 Case

필수 데이터:

- 결정 제목·업무·조직·긴급도
- 기준선과 문제 정의
- 선택 대안과 미선택 대안
- 핵심 가정과 신뢰도
- 재무·운영·리스크 영향
- 영향받는 조직과 협의 상태
- 요청 결정, 결정권자, 기한
- 근거 스냅샷과 시뮬레이션 fingerprint

세 관점 검토서는 원본 데이터를 공유하되 표현과 강조만 달리한다.

1. 요청자: 왜 지금 결정이 필요한가
2. 결정권자: 무엇을 선택하면 어떤 결과와 위험이 있는가
3. 영향부서: 자신의 업무·자원·KPI가 어떻게 바뀌는가

### G5-B. 회의·승인·실행

- 회의 요청, 참석자, 안건, 자료 스냅샷
- 승인/조건부 승인/반려/보류와 사유
- 이해충돌·대리 승인·위임 규칙
- 결정 결과를 실행 업무, 담당자, 기한, KPI로 변환
- 실행 상태, 증빙, 예외, 재승인
- 외부 시스템 쓰기는 명시적 승인과 멱등키 사용

### G5-C. 보고서 발간

- 내부 경영 보고서와 외부 보고서를 분리
- 확정값·시나리오·추정·AI 서술의 시각적 구분
- 원천·기준시점·승인자·버전·공개등급 표시
- 외부 발간은 미리보기→법무/홍보/권한 승인→고정 스냅샷
- 발간 후 정정·철회·새 버전 이력

### G5-D. 효과 측정

- 결정 시점에 성공 KPI, 목표값, 측정 기간을 약속
- 실제 실행 데이터와 결과 KPI 연결
- 예상/실제 차이와 원인 분해
- 재사용 가능한 규칙·플레이북·스킬 후보 생성
- 자동 학습 반영 금지; 근거와 승인 후 승격

### 완료 정의

- 시뮬레이션 결과에서 의사결정 요청이 생성된다.
- 승인 결과가 적절한 사용자에게 실행 업무로 배포된다.
- 결과가 실제 실적과 연결되어 예상 효과 대비 달성률이 계산된다.
- 누가 어떤 근거로 무엇을 결정하고 실행했는지 한 화면에서 추적된다.
- 보고서의 모든 중요 수치가 원천·계산·승인 스냅샷으로 추적된다.

## 10. G6 — Jarvis와 안전한 실행 패브릭

### 목표

Jarvis가 Target Task ID에 종속된 채팅이 아니라, 사용자의 권한 범위에서 회사 전체 상태를 이해하고 질문·조언·제어를 수행하는 전역 AI 비서가 되게 한다.

### 능력 단계

| 단계 | 능력 | 승인 원칙 |
|---|---|---|
| J0 | 현재 화면·프로젝트 설명 | 자동 |
| J1 | 전사 데이터·문서·결정 근거 질의 | 읽기 권한 내 자동 |
| J2 | 시나리오·앱·회의 초안 생성 | 사용자 확인 |
| J3 | 내부 업무·알림·앱 전달 실행 | 명시 승인·감사 |
| J4 | 외부 시스템 쓰기·대외 발간 | 다중 승인·정책·증빙 |

### 핵심 작업

- 전역 컨텍스트: 회사, 조직, 사용자 역할, 현재 화면, 최근 결정
- 근거 라우터: MDM, 카탈로그, 의미 모델, 운영 데이터, 문서, 텔레메트리
- 질문 분류: 설명, 데이터 조회, 진단, 추천, 초안, 실행
- 답변에 출처, 기준시점, 범위, 확정/추정 상태 표시
- 도구 레지스트리와 capability 정책
- 실행 전 계획·영향·권한·비용 미리보기
- 사용자 승인과 멱등 실행
- 실행 결과 검증과 되돌림 가능성 표시
- 대화 기억은 권한·보존기간·삭제 정책을 준수

### 완료 정의

- Task ID 없이 “현재 우리 회사에서 지연 중인 주요 의사결정은?”에 답한다.
- 답변은 사용자의 조직 범위와 근거를 명시한다.
- “원료가격 10% 상승 시나리오를 만들고 검토회의 초안을 준비해줘”를 승인 전까지 수행한다.
- 외부 쓰기는 승인 없이 실행되지 않으며 결과 증빙이 남는다.

## 11. G7 — 엔터프라이즈 제품화

### 목표

로컬 개발 시스템을 기업이 설치·운영·감사할 수 있는 제품으로 전환한다.

### G7-A. 인증·권한

- OIDC/SAML SSO
- SCIM 또는 사용자·그룹 동기화
- 역할+속성+조직 범위 정책
- 서비스 계정·앱 계정·위임
- Postgres RLS 또는 동등한 데이터 계층 강제
- 관리자 break-glass와 강화 감사

### G7-B. 데이터 플랫폼

- 운영 DB를 Postgres 중심으로 통합 또는 명확히 분리
- Alembic 등 버전 마이그레이션
- 트랜잭션 경계와 outbox/event 처리
- Object Storage에 문서·산출물·스냅샷 저장
- 검색/벡터/그래프 저장소는 용도와 정합성 책임 분리
- 암호화, 키 관리, Secret Vault
- 보존·파기·법적 보존 정책

### G7-C. 운영성

- 구조화 로그, metric, trace, LLM telemetry 통합
- SLO: API, 생성 스프린트, 시뮬레이션, 알림
- 큐·백그라운드 작업·재시도·DLQ
- 백업·복구·재해복구 훈련
- 다중 워커, 리소스 제한, 작업 취소
- 취약점·의존성·SBOM·서명된 릴리스
- 온프레미스·Private Cloud 배포 패키지

### G7-D. 프론트엔드 제품화

- AppShell과 URL 라우팅
- 회사 CI·상징색·접근성·반응형 기준
- 페이지별 오류·로딩·빈 상태·권한 상태
- 고밀도 화면의 1280/1440 검증
- 사용자 행동 분석과 기능 사용성 계측

### 완료 정의

- 두 개 이상 조직을 동시에 운용해도 데이터·이벤트가 격리된다.
- 배포와 DB 마이그레이션을 자동화하고 롤백할 수 있다.
- 장애 시 복구 목표를 실제 훈련으로 검증한다.
- 보안 위협 모델·침투 테스트의 P0/P1 취약점이 없다.
- 감사자가 사용자→결정→데이터→실행 이력을 재현한다.

## 12. G8 — 파일럿과 ROI 검증

### 목표

내부 데모가 아니라 실제 사용자·업무 주기·데이터로 제품 가치와 위험을 측정한다.

### 파일럿 구성

- Sponsor: 의사결정과 데이터 접근을 승인할 임원 또는 책임자
- Product Owner: 구매/경영관리 업무 책임자
- 참여: 구매, 물류, 생산, 재무, IT, 보안
- 범위: 1개 법인, 1개 사업부, 1~2개 원료군, 제한된 기간
- 비교: 기존 Excel/메일/회의 방식과 병행 Shadow Mode

### 3단계 검증

1. **Replay**: 과거 데이터로 결과 재현과 오차 검증
2. **Shadow**: 실제 업무와 병행하되 운영계 쓰기 금지
3. **Controlled Live**: 승인된 일부 입력·배포·결정만 실제 사용

### 성공 지표

| 축 | 지표 |
|---|---|
| 시간 | 계획 취합, 보고서 작성, 결정 리드타임 감소 |
| 품질 | 데이터 오류, 누락, 재작업, 예측 오차 |
| 실행 | 승인 후 업무 배포율, 기한 준수, 증빙 연결률 |
| 신뢰 | 근거 조회율, 사용자 수정량, 감사 재현 성공률 |
| 경제성 | LLM·인프라·운영 비용 대비 절감 시간·효과 |
| 채택 | 주간 활성 사용자, 반복 사용, 자발적 앱 생성 |

### 중단 또는 재설계 조건

- 같은 결과를 반복 계산할 수 없다.
- 데이터 정합성 문제의 소유자와 보정 경로가 없다.
- 사용자가 결과보다 기존 Excel을 계속 진실 원천으로 사용한다.
- 권한·감사 우회가 발견된다.
- LLM 비용과 장애율이 업무 절감 효과를 지속적으로 초과한다.
- 의사결정권자가 결과 근거를 이해하거나 신뢰하지 못한다.

중단은 실패가 아니라 범위·데이터·계산·UX를 조정하는 관문이다.

## 13. G9 — 전사·그룹·가상기업 확장

### 목표

첫 파일럿의 검증된 의미 모델과 폐루프를 다른 업무·회사로 복제하되, 고객별 SI로 붕괴하지 않게 한다.

### 확장 순서

1. 원료 구매·물류 인접 업무
2. 생산계획·품질·재고
3. 판매·수주·수익성
4. 재무·손익·현금흐름
5. 전사 통합 경영계획
6. 그룹사 Roll-up과 내부거래
7. VIRTUAL 신사업·증설·공장 시나리오
8. COMPETITOR 공개정보 비교

### 제품화 규칙

- 80%는 산업 공통 프로필·템플릿·계약으로 재사용한다.
- 고객 특화 20%는 설정·확장팩·커넥터로 격리한다.
- 핵심 제품 코드는 고객별 분기하지 않는다.
- 확장팩은 버전, 의존성, 권한, 데이터 계약, 테스트를 가진다.
- 가상기업은 운영계 권한 승급 통로가 아니며 별도 Sandbox에서 동작한다.

### 완료 정의

- 첫 법인의 구성을 두 번째 법인에 코드 포크 없이 적용한다.
- 회사 구조·업종 프로필을 선택하면 관련 마스터·프로세스·에이전트팩·KPI 후보가 제안된다.
- 그룹 집계에서 통화·내부거래·지분·기간 기준이 명시된다.
- REAL/VIRTUAL/COMPETITOR 데이터가 화면·API·계산에서 혼동되지 않는다.

## 14. 병렬 작업 트랙

순차 관문을 지키되 모든 작업을 직렬화하지 않는다.

| 트랙 | 주 작업 | 병렬 가능 범위 | 통합 관문 |
|---|---|---|---|
| Platform | 인증, 권한, Runtime, SSE, 배포 | G1부터 지속 | G1/G7 |
| Data/Semantic | MDM, 카탈로그, 의미 모델, 데이터 키트 | G1과 병렬 | G2 |
| App Factory | 생성, 릴리스, 전달, 앱 주머니 | G1 계약 후 | G3 |
| Twin | 계산식, 시나리오, 백테스트 | G2 데이터 계약과 병렬 | G4 |
| Decision | Case, 회의, 실행, 효과, 보고서 | G4 결과 계약 후 | G5 |
| Jarvis | 근거 질의, 도구, 승인 실행 | 읽기 기능은 G2부터 | G6 |
| UX | AppShell, Factory, Apps, Twin, Decision | API 계약 후 샘플→구현 | 각 단계 |
| QA/FinOps | E2E, 보안, 비용·품질 평가 | 전 단계 지속 | 모든 관문 |

팀 역할은 강점 중심으로 배치하되 고정하지 않는다. 구현자는 자체검토 후 넘기고, 권한·데이터 모델·핵심 API·재무 계산은 필요할 때 독립 교차검토한다. 교차검토는 작업을 멈추는 상시 승인 절차가 아니라 통합 전 위험 관문이다.

### 14.1 권고 주담당과 교차검토

| 영역 | 주담당 권고 | 교차검토·지원 |
|---|---|---|
| 제품 방향·현업 우선순위·조직 협의 | Supervisor | 전 팀 |
| 핵심 백엔드·데이터 모델·E2E·복구 | Claude Code | Codex/Antigravity 위험별 검토 |
| 제품 전략·UI/UX·사용자 여정·문서 정합성 | Codex | Claude Code 구현 가능성 검토 |
| 공신력 외부 데이터·산업 기준·출처 검증 | Antigravity | Supervisor 도메인 판단, Claude 연계 |
| 권한·보안·재무 계산·외부 발간 | 해당 구현자 | 최소 한 명 독립 검토 후 통합 |

이는 배타적 역할표가 아니다. 결과 품질이 낮거나 위험이 크면 다른 팀원이 같은 문제를 독립적으로 다시 풀고 비교한다. 단, 동일인이 구현과 독립 승인을 동시에 기록하지 않는다. 자체검토는 언제나 허용하며, 독립 검토는 통합·배포 관문에서만 요구한다.

## 16. 검증 체계

### 16.1 테스트 피라미드

- 단위: 상태 전이, 정책, 계산식, 파서
- 계약: API schema, event, Manifest, 데이터 계약
- 통합: DB·권한·Runtime·Ledger 원자성
- E2E: 역할별 사용자 여정과 실패 복구
- 보안: 위협 모델 기반 부정·우회 테스트
- 데이터: 품질·계보·유효기간·단위·환산
- 모델: 고정 평가셋의 품질·비용·지연 회귀
- 운영: 백업·복구·부하·장시간·한도 소진

### 16.2 골든 시나리오

- 회사·조직 설정
- 원료 구매 앱 생성
- 릴리스 부적격 차단과 수정
- 물류 사용자 전달·수락
- 실제 입력과 조직 격리
- 시뮬레이션과 결과 계보
- 의사결정 요청·승인·실행
- 보고서 생성·내부 발간
- 효과 측정·지식 후보 생성
- Jarvis 근거 질의

### 16.3 실패 복구 검증

빌드 또는 자가복구 3회 실패 후 프로세스가 무한 대기하거나 종료 상태 없이 멈추면 안 된다.

필수 후속 상태:

```text
AUTO_REPAIR_EXHAUSTED
  ├─ 강한 모델로 1회 제한 재시도
  ├─ 실패 파일만 범위 축소 재생성
  ├─ 마지막 정상 릴리스로 롤백
  ├─ 전문가 검토 패키지 생성
  └─ 작업 보류 및 재개 가능한 체크포인트
```

전문가 검토 패키지는 오류, 로그, 생성 diff, 세 번의 시도, 사용 모델, 토큰·비용, 관련 요구사항, 마지막 정상 상태를 포함한다.

- 개발 경위, 기여자, 회사 자원 사용 범위 기록

- 상표·도메인·저작권·특허 가능성 검토
- 라이선스와 오픈소스 의존성 정리

- 제품 라이선스
- 초기 셋업·데이터 온보딩

## 18. 최종 완성 판정표

다음 질문에 모두 “예”라고 답할 때 1차 제품 완성으로 판정한다.

### 데이터와 의미

- 회사·조직·업무·KPI·재무 영향이 하나의 의미 경로로 연결되는가?
- 결과의 원천·시점·단위·버전·품질을 추적할 수 있는가?

### App Factory

- 현업이 만든 앱이 회사 인증·권한·감사를 자동 상속하는가?
- 앱 전달·수락이 데이터 권한을 우회하지 않는가?

### Twin

- 핵심 숫자가 결정론적으로 재현되는가?
- 과거 데이터 백테스트와 실제 실적 대사가 가능한가?

### 결정과 실행

- 결정 근거, 승인, 실행, 효과가 하나의 이력으로 연결되는가?
- 예상과 실제 차이의 원인을 설명할 수 있는가?

### Jarvis

- Task ID 없이 권한 범위의 전사 질문에 근거로 답하는가?
- 실행은 영향 미리보기와 승인 뒤에만 이루어지는가?

### 운영과 경제성

- SSO·격리·감사·백업·복구·배포가 검증되는가?
- 업무 가치 대비 LLM·인프라·운영 비용이 측정되고 개선되는가?

### 시장 가치

- 한 현업 업무에서 반복 사용과 측정 가능한 효과가 있는가?
- 두 번째 조직에 제품 코어 포크 없이 확장할 수 있는가?
