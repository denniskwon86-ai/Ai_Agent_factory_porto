## 1. 결론

개발·감사 방식을 개선하면 **같은 결함을 여러 번 고치고 전체 회귀를 반복하는 낭비는 약 25~35% 줄일 수 있다.** 그러나 계산 모델, 화면 종단, PostgreSQL 이전, 운영성처럼 아직 만들지 않은 제품 기능까지 없어지는 것은 아니다.

현재 상태를 시험 개수나 코드 줄 수가 아니라 **실제 사용자 여정의 완료 증거**로 환산하면 다음과 같다.

| 완성선 | 의미 | 현재 준비도 | 남은 순수 작업량 | 예상 달력 기간 |
|---|---|---:|---:|---:|
| **M0 대외 시연판** | 도메인에서 12분 표준 시연을 3회 재현 | **55~60%** | **9~14인일** | 2~3주 |
| **M1 통제 시험운영** | 최대 10명, PostgreSQL, 백업·복구 | **30~35%** | M0 이후 **16~27인일** | 추가 3~5주 |
| **M2 부서 파일럿** | 평시 30명·최대 50명, 앱/DB 분리·작업 큐 | **20~25%** | M1 이후 **20~35인일** | 추가 5~8주 |
| **M3 상용 운영판** | 기업 설치·보안·감사·복구·운영 기준 충족 | **15~20%** | M2 이후 **45~75인일** | 추가 10~16주 |

`인일`은 한 명이 AI 코딩 도구를 사용해 구현·회귀·문서화를 수행하는 순수 작업일이다. 사용자 승인, 서버 계정 발급, DNS 전파, 실제 사용자 일정, 보안 검토 대기는 별도다. 추정 오차는 현재 기준 ±30%다.

따라서 **지금부터 상용 운영판까지 남은 전체 갭은 약 90~150인일**이다. 다만 지금 필요한 목표는 M3가 아니라 M0이며, M0 이후에는 실제 사용자 증거를 보고 M1·M2의 범위를 조정한다.

## 2. “100% 구현 완료”를 네 단계로 나누는 이유

하나의 100%만 쓰면 다음 네 상태가 섞인다.

1. 코드와 단위 시험이 존재한다.
2. 실제 제품 API와 화면에서 호출된다.
3. 여러 사용자가 데이터를 넣어도 복구 가능하게 운영된다.
4. 기업이 보안·감사·SLA를 근거로 구매할 수 있다.

이 문서는 완료를 다음처럼 정의한다.

### M0 — Demonstrable MVP

합성 데이터로 핵심 가치가 실제 화면에서 끝까지 이어지고, 공개 도메인 시연을 안전하게 수행할 수 있다. 운영 고객 데이터와 24×7 SLA는 범위가 아니다.

### M1 — Controlled Trial, 최대 10명

초대된 최대 10명이 제한된 업무 키트를 사용한다. PostgreSQL, 일일 백업·복구, 사용자·조직 격리, 재시도 안전성이 필요하다. 중요 실적과 개인정보는 아직 넣지 않는다.

### M2 — Department Pilot, 평시 30명·최대 50명

한 부서 또는 한 법인의 실제 업무 주기를 Shadow Mode로 수행한다. 앱/DB 분리, 작업 큐, 부분 실패 복구, 관리형 DB 또는 동등한 운영 장치, 실제 데이터 연결이 필요하다.

### M3 — Commercial/Enterprise Ready

SSO·SCIM·RLS, HA, DR, 보안시험, 감사 재생, 배포·마이그레이션 롤백, 지원·운영 문서까지 갖춘다. 이는 “기능이 많다”가 아니라 “고객 데이터와 업무를 맡길 수 있다”는 완성선이다.

G8의 시장 적합성·ROI 증명은 M3 이후가 아니라 M1부터 병행하지만, 제품 구현률에는 섞지 않는다.

## 3. 현재 기준선 — 있는 것과 실제로 도는 것

### 3.1 강한 기반

- Host Runtime proof, manifest·계약·물질화 지문 봉인과 410 프레임 폐기
- 신규 PDP 강제와 롤백 스위치, shadow 관측, 관리 API
- 데이터셋 릴리스 결속, 스키마 판, 소유권 결속, 승인·재승인·철회 API
- Decision Ledger의 대상 결속 승인·철회 검증
- 데이터 키트 의미 분류와 이중 입력 방지
- 실제 Dataset Resolver와 5노드·4간선 온톨로지 경로
- 경로 근거를 G5에 전달하고 계산 없는 숫자를 차단하는 기반
- 대규모 회귀와 운영 DB 불변식 검사

### 3.2 아직 실제 완료가 아닌 핵심

- 계산 능력 4종은 등록돼 있지만 전부 실행 불가이며, MVP 계산 모델 3종은 0/3이다.
- 계산 결과를 G5 안건·브리핑에 봉인하는 B2가 없다.
- 승인된 온톨로지 계약 설치는 `DESIGN_ONLY` 상태로 HOLD다.
- 조직 문맥의 실제 시연 데이터 결속과 화면 종단 증거가 부족하다.
- 제품 UI에서 회사 선택부터 보고서까지 완주한 최신 브라우저 증거가 없다.
- Demo Reset·Readiness·3회 연속 재현 증거가 완성되지 않았다.
- 도메인·TLS·NCP 배포는 계획만 있고 실행되지 않았다.
- PostgreSQL 이전은 방향과 일부 마이그레이션 원칙만 있으며 본전환은 시작하지 않았다.

### 3.3 현재 수치의 해석

```text
코드 자산 완성도          ███████░░░  약 72%
M0 실제 사용자 여정       ██████░░░░  약 55~60%
웹 도메인 시연 준비       ████░░░░░░  약 40~45%
M1 최대 10명 운영 준비    ███░░░░░░░  약 30~35%
M2 30~50명 파일럿 준비    ██░░░░░░░░  약 20~25%
M3 상용 운영 준비         ██░░░░░░░░  약 15~20%
```

코드 자산과 사용자 여정의 차이는 **배선·화면·운영 증거**다. 백엔드 모듈이 존재해도 제품이 호출하지 않거나 사용자가 다음 단계로 갈 수 없으면 구현 완료로 세지 않는다.

## 5. M0 — 대외 시연판 갭 해소 계획

### 목표

처음 보는 사람이 도메인에 접속해 다음 흐름을 보고, 발표자가 같은 결과를 세 번 연속 재현한다.

```text
회사·조직 선택
  → Javis 준비도와 업무 키트 선택
  → 현업 데이터·앱 실행
  → 구매 지연 영향 경로
  → 결정론적 수치 시뮬레이션
  → 의사결정 안건과 검토
  → 경영 브리핑·HTML 보고서
```

### M0 작업 묶음

| 순서 | 작업 | 예상 | 완료 증거 |
|---:|---|---:|---|
| M0-0 | 범위 동결·계산 의미 3건 승인 | 0.5~1일 | 승인 결정과 변경 불가 계산 계약 |
| M0-1 | 5b 계산 모델 3종 구현 | 2~3일 | 동일 입력 3회 동일, 부호·단위·Snapshot 확인 |
| M0-2 | B2 계산 결과→G5 봉인 | 1~1.5일 | request/result 지문, 경로·계산 결속 불일치 거부 |
| M0-3 | 조직·데이터 시연 결속 마감 | 1~1.5일 | 상위 조직 허용, 단일 공장 교차·타 조직 거부 |
| M0-4 | 제품 화면 폐루프 | 2~3일 | 회사 선택부터 HTML 보고서까지 개발자 도구 없이 완주 |
| M0-5 | Reset·Readiness·오류 상태 | 0.5~1일 | 원클릭 초기화, 실패와 0건 구분, 재시도 안내 |
| M0-6 | NCP 도메인 배포 | 4~5일 | Linux 재현, TLS, 초대 계정, 외부 백업·복구 |
| M0-7 | 3회 리허설·발표 패키지 | 1일 | Gate A~E와 12분/3분 시연 기록 |

M0-1~5와 WEB-0~3은 일부 병렬 가능하다. 핵심 기능 기준선이 동결된 뒤 WEB-4~5를 수행한다. 병렬을 반영한 임계경로는 9~14인일, 달력 2~3주다.

### M0에서 즉시 막는 결함

- 인증·테넌트·조직 범위 우회
- 시연 계정·비밀·보호 데이터 노출
- 정상 시나리오 중단·무한 로딩·빈 화면
- 데이터 손실 또는 Reset 불가
- 핵심 계산·보고서 미완성 또는 재현 불가
- 계산 불가가 0 또는 영향 없음으로 표시됨
- 도메인·TLS·CORS·백업 실패

그 밖의 운영성 결함은 M1~M3 부채로 등록하고 M0 완료를 되돌리지 않는다.

### M0 출구 조건

- Gate A~E 모두 통과
- 실제 브라우저 1280×720, 1440×900 확인
- 표준 시나리오 3회 연속 성공
- 외부 LLM 장애 중에도 저장된 계산·결정 결과 재현
- 신규 서버에서 문서만으로 배포 및 Reset 가능
- 시연 종료 후 백업 해시 확인과 서버 삭제 절차 존재

## 6. M1 — 최대 10명 통제 시험운영 갭

M0와 M1의 가장 큰 차이는 **“보여 줄 수 있다”에서 “사람이 데이터를 넣어도 되돌릴 수 있다”**로 바뀌는 것이다.

### 필수 작업

1. **PostgreSQL 1단계 이전**
   - DB-0 저장소·정본·트랜잭션 지도
   - DB-1 직접 `sqlite3` 접근계층 분리
   - DB-2 PostgreSQL DDL·Alembic·제약·트리거
   - DB-3 일관 사본 이관과 행수·내용 지문 대사
   - DB-5 전환·SQLite 복귀 각각 1회 실증

2. **승인 API M1 보정 두 건**
   - tenant/entity/scope가 다른 dangling approval 차단과 원장 strict read
   - 같은 요청 재전송 시 승인 사건이 중복되지 않는 idempotency key

3. **최대 10명 운영 안전**
   - 동시 세션 3~5명, 시험 부하 1→3→5→10
   - DB pool 5 + overflow 5 기준 확인
   - 일일 외부 백업과 빈 서버 복구 1회
   - 서버·DB 비밀 분리, 관리자 계정과 시연 계정 분리

4. **기본 업무 키트**
   - 기존 시스템과 이중 입력을 요구하지 않는 키트 2~3종
   - 파일 Snapshot 또는 AFS_NATIVE 입력 중 하나를 명시
   - 기존 실적은 읽고, 현업 보완·시나리오·결정만 AFS에 기록
   - Source Binding과 Zero Duplicate Entry Gate를 화면에 표시

5. **사용자 운영**
   - 초대·비활성화·역할 변경·퇴사 계정 차단
   - 사용자 가이드, 관리자 운영 카드, 장애 신고 양식

| 묶음 | 예상 |
|---|---:|
| PostgreSQL 핵심 경로 이전 | 12~20인일 |
| API·idempotency·격리 보정 | 2~3인일 |
| 백업·복구·부하·모니터링 | 2~3인일 |
| 업무 키트·사용자 운영 보정 | 2~4인일 |
| 중복 가능 작업 반영 후 합계 | **16~27인일** |

### M1 출구 조건

- 최대 10명 계정으로 1주 시험운영
- 동시 5명 정상 시나리오에서 데이터 정합성 오류 0
- PostgreSQL 백업에서 새 인스턴스 복구 1회
- 타 사용자·타 조직·타 앱 데이터 접근 부정 시나리오 통과
- 중복 요청이 승인·결정·쓰기 행을 늘리지 않음
- 업무 키트 사용자가 같은 내용을 기존 시스템과 AFS에 두 번 입력하지 않음

---

## 7. M2 — 평시 30명·최대 50명 부서 파일럿 갭

M1과 M2의 차이는 사용자 숫자만이 아니다. 장시간 AI·계산 작업과 여러 사용자의 쓰기를 웹 프로세스 하나가 직접 감당하지 않게 만들어야 한다.

### 필수 작업

- App VM과 PostgreSQL 분리, DB 사설망 구성
- 평시 동시 10명·최대 15명, 시험 부하 5→10→15→30
- 생성·계산 작업 큐, 취소·재시도·DLQ
- 프로세스 메모리의 SSE·작업 상태 외부화
- 관리형 PostgreSQL 또는 동등한 PITR·모니터링
- 부분 실패 상태와 보상·재처리 운영 화면
- 원장·감사 조회 pagination과 장기 조회 성능
- 부서 관리자 위임, 데이터 소유자 승인·재승인 운영
- 업무 키트 4~6종, 선택적 ERP/EAI 연결
- 실제 데이터는 원천 시스템을 대체하지 않고 Snapshot·Source Binding으로 읽음
- AFS는 보완 입력, 시나리오, 승인, 결정, 효과 측정의 정본이 됨

### M2 예상 작업량

| 묶음 | 예상 |
|---|---:|
| 앱/DB 분리·작업 큐·상태 외부화 | 7~12인일 |
| 관리형 DB·PITR·관측·부하 | 4~7인일 |
| 실패 복구·운영 화면·감사 조회 | 4~7인일 |
| 실제 데이터 연결·업무 키트 확대 | 5~9인일 |
| 합계 | **20~35인일** |

### M2 출구 조건

- 평시 30명·최대 50명 계정, 목표 동시 15명에서 정상 업무 수행
- 앱 프로세스 재시작 중 실행 중 작업의 상태가 사라지지 않음
- 작업 재시도·취소·DLQ 복구 실증
- DB 장애·네트워크 단절·외부 LLM 실패의 사용자 상태가 구분됨
- 파일럿 한 업무 주기의 기준선→시나리오→결정→실적 대사가 완료됨
- 기존 업무 시스템 이중 입력 증가가 파일럿 KPI 허용범위 이내

## 8. M3 — 상용 운영판 갭

### 필수 작업군

1. **기업 인증·권한**: OIDC/SAML, SCIM, 서비스 계정, 위임, break-glass, Postgres RLS.
2. **운영 데이터 플랫폼**: 관리형 PostgreSQL HA, online migration, outbox, Object Storage, 암호화·KMS, 보존·파기.
3. **운영성**: 구조화 로그·metric·trace, SLO, 다중 worker, 리소스 제한, DR 훈련.
4. **보안 공급망**: 위협 모델, SAST/DAST, 의존성·SBOM, 서명된 릴리스, P0/P1 침투시험 0.
5. **제품 UX**: 접근성, 반응형, 관리자 콘솔, 사용성 분석, 일관된 오류·로딩·권한 상태.
6. **납품·지원**: 설치/업그레이드/롤백, 운영 매뉴얼, SLA, 지원 절차, 교육·온보딩.
7. **도메인 확장 통제**: 업무 키트 생명주기와 계약 호환성, 추가 온톨로지 namespace, 모델 승인·폐지.

### M3 예상 작업량

**45~75인일**. 고객 보안 심사, 실제 IdP 연동, DR 일정과 침투시험 대기는 별도다.

### M3 출구 조건

- 두 조직 이상 동시 운영에서 데이터·이벤트 격리
- 자동 배포·DB 마이그레이션·롤백 실증
- RPO/RTO를 명시하고 복구 훈련으로 입증
- 위협 모델과 침투시험 P0/P1 0
- 감사자가 사용자→데이터→모델→결정→실행 이력을 재생
- 운영 담당자가 개발자 개입 없이 백업·복구·계정·장애를 처리

## 9. 임계경로와 선후 의존성

```text
계산 의미 승인
  → 5b 계산 모델
    → B2 결과 봉인
      → G5 안건·브리핑
        → 제품 화면 폐루프
          → Gate A~E
            → NCP 도메인 배포·3회 리허설             [M0]

M0 기준선 동결
  → SQLite 자산 지도·접근계층 분리
    → PostgreSQL 이식·대사·복구
      → 최대 10명 부하·백업·업무 키트              [M1]

M1 사용 증거
  → 앱/DB 분리·작업 큐
    → 30~50명 운영·실제 Source Binding
      → 부서 파일럿·실적 대사                      [M2]

M2 운영 증거
  → SSO/SCIM/RLS·HA·DR·보안시험·지원 체계           [M3]
```

FND 조직 결속과 UI는 계산 모델 구현과 병렬로 진행할 수 있다. WEB-1 패키징 초안도 기능 개발과 병렬 가능하다. PostgreSQL 데이터 이관은 M0 스키마가 동결된 뒤 시작한다.

## 10. 개선된 개발·감사 운영 규칙

### 10.1 작업 단위

- Claude Code: 합의된 WBS 한 묶음의 구현·집중 회귀·T2.
- Codex: 설계 진입 감사 1회, 묶음 완료 감사 1회, 문서·Gate 대조.
- 사용자: 의미 계약, 범위, 승인, 상용 위험 수용 결정.

같은 결함의 수정→재감사 반복은 최대 1회다. 남은 결함은 위험등급과 목표 단계로 등록한다.

### 10.2 결함 분류

| 분류 | 처리 |
|---|---|
| NOW | 현재 단계의 정상 흐름·보안·데이터·핵심 가치 차단. 즉시 수정 |
| M1 | 최대 10명 운영 전 필수 |
| M2 | 30~50명 파일럿 전 필수 |
| M3 | 상용 운영 전 필수 |

하위 단계 결함이 아니면 현재 완료 판정을 취소하지 않는다. 단, 인증 우회·교차 테넌트·데이터 손실·거짓 숫자는 언제나 NOW다.

### 10.3 검증 예산

- T1: 변경 파일, 편집 중 반복.
- T2: 영향 모듈, 묶음 완료 전.
- T3: 하루 또는 Release Candidate당 1회.
- 변이 검사: 인증·테넌트·승인·금액·계산 결속·데이터 손실 분기만.
- 모든 화면에 브라우저 회귀를 요구하지 않고, 표준 사용자 여정과 위험 경계만 종단 검증.

### 10.4 진척 계산

시험 개수와 코드 줄 수는 진척률에 넣지 않는다. 각 항목은 다음 네 증거로 센다.

```text
설계 확정 20% + 제품 배선 30% + 실제 종단 30% + 운영/복구 증거 20%
```

M0 기능은 운영/복구 비중을 WEB Gate로 충족한다. 제품 배선 없이 단위 시험만 있으면 최대 20%다.

## 11. 갭 등록부 운영

각 미완료 항목은 아래 필드를 갖는다.

| 필드 | 설명 |
|---|---|
| `gap_id` | 예: `M0-CALC-01` |
| 사용자 영향 | 사용자가 못 하는 일 또는 잘못 믿게 되는 일 |
| 현재 증거 | 코드·시험·실측 중 무엇이 있는가 |
| 목표 단계 | NOW/M1/M2/M3 |
| 선행 조건 | 승인·데이터·다른 구현 |
| 완료 증거 | API·화면·부하·복구·보안 중 필요한 것 |
| 담당 | 구현·감사·승인 |
| 추정 | 인일과 불확실성 |
| 상태 | READY/BLOCKED/IN_PROGRESS/DONE/DEFERRED |

최소 주 2회 갱신하고, “완료”는 커밋이 아니라 완료 증거 링크가 있을 때만 쓴다.

## 13. 일정 방어선과 범위 절단 규칙

M0 일정이 밀릴 때 다음 순서로 자른다.

1. 자유형 앱 생성 대신 승인 템플릿 1종만 시연한다.
2. 실제 Connector 대신 인증된 파일 Snapshot을 사용한다.
3. 자연어 자유질의 대신 고정 Intent 3개를 사용한다.
4. 보고서 양식은 HTML 경영 브리핑 1종만 유지한다.
5. 추가 UI 미화와 범용 관리 기능은 M1로 넘긴다.

다음은 자르지 않는다.

- 사용자·조직·앱 격리
- 데이터 역할과 합성 표시
- 계산 재현성과 경로·수치 결속
- 계산 불가/0건/장애의 구분
- Reset·Readiness·백업
- 도메인 TLS와 비밀 제거

## 15. 최종 판단

개선된 개발 방식은 완성선을 낮추는 것이 아니라 **현재 단계에 필요 없는 완벽주의를 뒤로 보내는 장치**다. M0에서는 핵심 가치와 치명적 경계만 100%로 만들고, M1에서는 10명 운영, M2에서는 50명 파일럿, M3에서는 기업 운영의 100%를 요구한다.

가장 중요한 다음 순서는 다음과 같다.

```text
1. 계산 의미 승인
2. 5b 계산 모델 3종
3. B2 결과 봉인과 G5 연결
4. 조직 결속·제품 화면 폐루프
5. Reset·Readiness·3회 리허설
6. NCP 도메인 배포
7. M1 PostgreSQL·최대 10명 시험운영
```

이 순서를 지키면 “안전 기반은 많은데 보여 줄 숫자가 없는 시스템”에서 먼저 벗어나고, 이후에 실제 사용자가 데이터를 맡길 수 있는 제품으로 단계적으로 승격할 수 있다.
