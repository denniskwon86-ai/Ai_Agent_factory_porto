## 1. 목표와 완료 정의

로컬 PC가 아니라 인터넷에 연결된 서버에서 AI Factory Studio를 실행하고, 초대받은 사람이
`https://demo.<보유도메인>`으로 접속해 표준 시연을 완주할 수 있게 한다.

완료는 단순히 첫 화면이 열리는 것이 아니다. 아래 조건을 전부 만족해야 한다.

1. HTTPS 도메인으로 로그인부터 보고서까지 완주한다.
2. 서버 재시작 후에도 SQLite DB, 생성 프로젝트, 시연 상태가 보존된다.
3. SSE, App Preview, Host Runtime Bridge가 역방향 프록시 뒤에서도 동작한다.
4. 운영·개발 데이터가 아니라 승인된 `DEMO/SYNTHETIC` 자료만 올라간다.
5. 시연 전 상태로 되돌리는 Reset과 배포 전 상태로 되돌리는 Restore를 각각 한 번 실증한다.
6. 표준 시나리오를 서로 다른 브라우저 세션에서 3회 연속 성공한다.
7. 월 고정비와 LLM 변동비에 상한을 둔다.

이 단계는 G7 상용 제품화를 대신하지 않는다. 고가용성, 다중 인스턴스, 무중단 DB 이전,
정식 DR/SLA는 후속 G7 범위다.

## 2. 현재 코드에서 확인한 배포 제약

| 사실 | 배포에 미치는 영향 |
|---|---|
| FastAPI 백엔드와 Vite/React 프런트가 별도 프로세스 | 정적 프런트 제공과 `/api`, SSE 프록시가 필요하다. |
| `core/paths.py`가 코드 파일 위치를 기준으로 `data/`, `projects/`를 정함 | 배포 릴리스마다 영속 디렉터리를 정확히 연결해야 한다. 임시 파일시스템 PaaS에 그대로 올리면 안 된다. |
| 다수 SQLite DB와 JSONL·프로젝트 파일을 사용 | 영속 디스크가 필수이며 백엔드는 **1개 프로세스/1개 인스턴스**로 제한한다. |
| EventSource 기반 SSE 사용 | 프록시 버퍼링·응답 시간제한·접속표 로그 노출을 확인해야 한다. |
| 프런트 API 기본값이 `127.0.0.1:8080` | 웹 빌드 시 실제 HTTPS 주소를 주입하거나 같은-origin 기준으로 정리해야 한다. |
| 런타임 의존성 목록이 `docs/requirements.txt`에 있고 잠금본이 없음 | 깨끗한 Linux 설치가 재현되는 배포 의존성 정본이 필요하다. |
| 앱 기동 시 그래프와 일부 기준정보를 준비 | 무료 서비스의 긴 cold start는 시연 위험이다. |
| RAG·임베딩 라이브러리까지 포함 | 0.5~1 GB RAM 무료 컨테이너는 부적합하다. 4 GB를 최소, 8 GB를 안전선으로 본다. |

따라서 무료 서버리스, 무료 Render Web Service, 정적 호스팅 단독 구성은 기본안에서 제외한다.
Render 무료 서비스는 유휴 시 내려가고 로컬 SQLite 파일을 재시작·재배포 때 잃는다.

## 3. 권장 아키텍처

```text
초대 사용자
    │ HTTPS
    ▼
보유 도메인 DNS
  · 기존 등록기관 DNS 또는 Ncloud Global DNS
  · A 레코드 → NCP 공인 IP
    │
    ▼
NAVER Cloud Platform 한국 리전 · 단일 Linux VM
  Caddy :443
    ├─ /                 → frontend/dist 정적 파일
    ├─ /api/*            → Uvicorn 127.0.0.1:8080
    └─ SSE 경로          → Uvicorn, buffering off

  systemd: afs-demo.service
    └─ uvicorn main:app --host 127.0.0.1 --port 8080 --workers 1

  영속 영역
    ├─ /var/lib/afs-demo/data
    ├─ /var/lib/afs-demo/projects
    ├─ /var/lib/afs-demo/output
    └─ /var/backups/afs-demo
```

### 왜 한 대인가

- 현재 저장소는 SQLite와 로컬 파일을 함께 사용한다.
- 여러 인스턴스로 나누면 DB 잠금, SSE 메모리 상태, 생성 프로젝트 파일이 갈라진다.
- 시연 부하는 작으므로 분산보다 **단일 노드의 결정론과 복구 가능성**이 중요하다.
- 프런트와 API를 같은 도메인에 두면 CORS·세션·SSE 문제가 줄어든다.

### 왜 Caddy인가

시연 배포에서 필요한 것은 정적 파일 제공, HTTPS, 역방향 프록시다. 복잡한 오케스트레이션보다
설정이 작은 단일 프록시가 적합하다. Caddy가 Let's Encrypt 인증서를 자동 갱신하게 하면
유료 Load Balancer나 별도 인증서 상품 없이 HTTPS를 제공할 수 있다.

### 제한 사용자 운영 — 1단계 최대 10명, 2단계 평시 30명·최대 50명

사용자 수는 **등록·활성 사용자 수**이고 전원이 동시에 생성 작업을 한다는 뜻은 아니다. 용량 계획은
동시 세션과 동시 쓰기를 별도로 둔다.

| 구분 | 1단계 | 2단계 |
|---|---:|---:|
| 사용자 | 최대 10명 | 평시 30명·최대 50명 |
| 목표 동시 세션 | 3~5명 | 평시 10명·최대 15명 |
| 동시 쓰기 | 1~2건 | 3~5건 |
| SSE 연결 | 최대 8개 | 평시 20개·최대 30개 |
| 동시 AI 생성·계산 | 1~2개 | 3~5개, 초과 요청은 큐에서 대기 |

50명이 동시에 생성·계산하는 부하는 2단계 보증 범위가 아니다. 그 요구가 생기면 별도 부하 등급과
3단계 확장 설계를 연다.

#### 1단계 — 최대 10명, 비용 최소화

```text
NCP Standard-g2 2 vCPU / 8 GB / 50 GB · 공인 IP 1개
  ├─ Caddy + frontend/dist
  ├─ FastAPI/Uvicorn 1 worker + Chroma
  └─ PostgreSQL · 별도 데이터 볼륨
       └─ 일 1회 암호화 백업을 VM 밖에 보관
```

실사용자가 데이터를 쓰므로 SQLite 대신 PostgreSQL로 시작하지만, 최대 10명 동안은 비용을 줄이기
위해 앱과 DB를 한 VM에 둔다. DB 데이터는 OS·코드와 다른 볼륨에 두고 백업은 같은 VM에만 남기지
않는다. 동일 실패영역을 허용하는 **제한 파일럿 구성**이므로 실제 개인정보·중요 실적의 정식 운영에는
쓰지 않는다.

월 비용은 VM 88,000원 + 공인 IP 4,032원 + 데이터/백업 볼륨이다(VAT 별도). VAT와 소량의
스토리지를 포함한 **인프라 상한은 월 12만원**, LLM API는 별도다.

#### 2단계 — 평시 30명, 최대 50명

```text
NCP App VM · Standard-g2 4 vCPU / 16 GB · 공인 IP 1개
  Caddy + frontend/dist + FastAPI + Chroma
  │ VPC 사설망
  ├─ NCP DB VM · Standard-g2 2 vCPU / 8 GB · 공인 IP 없음
  │    PostgreSQL + 데이터/백업 볼륨
  └─ 작업 실행기
       초기에는 App VM의 별도 프로세스
       부하 기준 초과 시 High CPU-g2 2 vCPU / 4 GB VM으로 분리
```

2단계부터 앱과 DB를 분리한다. App VM은 월 176,000원, DB VM은 월 88,000원, 공인 IP는
월 4,032원으로 **기본 컴퓨팅 합계 약 26.8만원 + 스토리지, VAT 별도**다. 기본 인프라 상한은
월 35만원, 실행기 VM까지 분리할 때는 월 45만원으로 둔다. 실제 업무자료·개인정보·복구 SLA가
붙으면 이 예산보다 관리형 **NCP Cloud DB for PostgreSQL**을 우선하며, 자동 백업·시점 복원·
페일오버를 포함한 금액을 계산기에서 별도 확정한다.

현재 SSE·일부 런타임 상태가 프로세스 메모리에 있으므로 PostgreSQL을 붙였다는 이유만으로 다중
Uvicorn worker를 켜지 않는다. 2단계 전에 작업 상태 외부화와 대기열을 구현한다. 첫 구현은
PostgreSQL 작업 테이블과 `FOR UPDATE SKIP LOCKED` 방식으로 시작해 운영 대상을 늘리지 않고,
재시도·지연 작업·처리량이 이를 넘을 때 국내 관리형 메시지 큐를 검토한다.

#### 단계별 승격 Gate

| 관문 | 1단계 → 2단계 | 2단계 → 3단계 |
|---|---|---|
| 사용자 | 10명 초과 또는 동시 5명 지속 | 50명 초과 또는 동시 15명 지속 |
| DB | pool 5, overflow 5; 일 백업·복구 실증 | 관리형 PostgreSQL, PITR·장애 복구 실증 |
| AI 작업 | 동시 2개, 초과는 명시적 대기 | 독립 실행기·취소·재시도·DLQ |
| 데이터 | 관계형 2 GB, 문서·벡터 5 GB 이하 | 관계형 10 GB 또는 문서·벡터 30 GB 초과 시 저장소 재산정 |
| 성능 | 일반 API p95 1.5초, 검색 p95 3초 | 같은 목표 + 평시 부하 CPU 70%·RAM 75% 이하 |
| 안전 | 합성/승인 자료, 단일 VM 복구 | 실제 자료 투입 전 VPC 사설 DB·PITR·권한·감사 Gate |

부하 시험은 1단계에서 1→3→5→10 동시 세션, 2단계에서 5→10→15→30 동시 세션 순서로 한다.
각 단계의 목표 동시 수에서 성능 기준을 만족해야 하고, 다음 단계 시험 부하에서는 느려져도 데이터
손상·중복 실행·권한 누설·SSE 혼선 없이 대기하거나 명시적으로 거부해야 한다.

## 5. 추가 단계 — WEB-DEMO

기존 기능 MVP의 마지막에 아래 단계를 추가한다.

### WEB-0 배포 기준선 동결

완료 조건:

- 시연 커밋 SHA와 데이터 키트 지문을 기록한다.
- 전체 회귀, 프런트 빌드, 운영 불변식이 초록이다.
- SQLite 사용처·파일·소유 모듈·테이블·마이그레이션 판을 목록화해 이후 PostgreSQL 이관의
  기준선을 함께 봉인한다. 시연에서 SQLite를 쓴다는 결정이 상용 저장소 결정으로 굳지 않게 한다.
- `data/`, `.env`, 원장 아카이브, 테스트 오염 백업을 배포 대상에서 제외한다.
- 배포 대상은 깨끗한 Git 산출물과 승인된 합성 시드의 **허용목록**으로 만든다.

### WEB-1 Linux 재현 패키징

구현 항목:

- 런타임 의존성 정본(`requirements.txt` 또는 lock)을 저장소 루트에 둔다.
- Ubuntu clean install에서 Python venv 설치를 검증한다.
- `npm ci && npm run build`를 재현한다.
- 프런트 API 주소를 배포 도메인 또는 same-origin으로 단일화한다.
- `deploy/`에 systemd, Caddy, 설치·업데이트·점검 스크립트를 둔다.

완료 조건: 빈 Linux VM에서 문서에 없는 수동 조작 없이 `/api/v1/health`와 첫 화면이 열린다.

### WEB-2 영속 저장소와 복구

구현 항목:

- 릴리스 코드와 `data/`, `projects/`, `output/`을 분리한다.
- 배포 전 SQLite online backup과 프로젝트 파일 아카이브를 만든다.
- 백업 manifest에 코드 SHA, DB 지문, 데이터 키트 지문, 생성시각을 기록한다.
- 코드 롤백은 **그 코드와 짝인 데이터 백업**으로만 수행한다.

완료 조건:

1. 서버 재시작 뒤 로그인·프로젝트·원장이 유지된다.
2. 배포 전 백업으로 별도 복구 디렉터리를 만들고 시연 질문 한 건을 재실행한다.

### WEB-3 도메인·TLS·접근통제

구현 항목:

- `demo.<보유도메인>` DNS를 연결한다.
- NCP ACG는 80/443만 공개하고 SSH는 관리자 IP로 제한한다.
- 불특정 공개를 피해야 하는 시연은 Caddy `basic_auth`를 1차 관문으로 두고 제품 로그인을
  2차 관문으로 쓴다. 참석자별 식별이 필요하면 Cloudflare Access 무료 계층을 선택적으로 붙인다.
- Uvicorn 8080은 loopback에만 바인딩한다.
- `CORS_ALLOWED_ORIGINS=https://demo.<도메인>`만 허용한다.
- `AFS_DEV_TRUST_HEADER=0`, 기본 비밀번호 금지, 실제 API 키는 서버 secret 파일에만 둔다.
- FastAPI 문서와 관리용 진단 경로는 Access 뒤에 두거나 시연 모드에서 끈다.

완료 조건: 허용되지 않은 이메일, 직접 IP, 잘못된 Origin, 기본 비밀번호 접근이 모두 거부된다.

### WEB-4 서버 배포와 네트워크 카나리

필수 카나리:

1. HTTPS·인증서·리디렉션
2. 로그인·로그아웃·세션 만료
3. SSE 연결·재연결·중복 연결 없음
4. App Preview·Host Runtime Proof·읽기/쓰기 대조군
5. Demo Reset 후 기준선 지문 복구
6. 서버 재시작 후 데이터 보존
7. LLM 장애 시 결정론적 계산·기존 브리핑 재현
8. 브라우저 콘솔 secret·ticket·stack trace 노출 없음

### WEB-5 도메인 종단 리허설

완료 조건:

- 1280×720, 1440×900에서 표준 시나리오 3회 성공
- 서로 다른 두 네트워크에서 접속 성공
- 참석자 계정으로 권한 밖 조직·데이터 비노출
- P95 API 응답, SSE 안정성, 메모리·디스크 사용량을 기록
- 발표자용 장애 대응표를 준비

시연 승인 기준:

```text
기능 Gate A~E 통과
AND WEB-0~5 통과
AND 시연 24시간 전 코드·DB 스키마 동결
```

### WEB-6 시연 종료와 비용 차단

- 참석자 계정·Caddy 1차 인증·선택적 Access 정책·API 키를 폐기 또는 회전한다.
- 최종 백업을 내려받아 해시를 확인한다.
- Cloud VM을 **중지하지 말고 삭제**해 과금을 끝낸다.
- DNS 레코드를 제거하거나 maintenance 페이지로 돌린다.
- 실제 로그와 비용을 시연 회고에 기록한다.

## 9. 시연 DB와 상용 DB의 분리 계획

SQLite는 이번 단일 VM·단일 프로세스·합성 데이터 시연을 빠르고 값싸게 여는 **임시 실행
저장소**다. 상용 운영의 목표 저장소가 아니다. 현재 코드에는 SQLite 직접 사용 파일이 31개이고,
`data/`에는 아카이브를 제외해도 다수의 관계형 DB가 분산되어 있다. 그대로 사용자를 늘리면 다음
문제가 생긴다.

- 다중 워커·다중 서버의 일관된 쓰기와 잠금 제어가 어렵다.
- 여러 DB를 가로지르는 업무 트랜잭션·outbox·감사 정합성이 약하다.
- 테넌트 격리를 애플리케이션 판정에만 의존하게 되고 Postgres RLS 같은 DB 계층 방어가 없다.
- 스키마 버전, 온라인 마이그레이션, 시점 복원, 운영 모니터링을 한 방식으로 관리하기 어렵다.

### 환경별 원칙

| 환경 | 저장소 | 허용 조건 |
|---|---|---|
| 이번 도메인 시연 | 단일 VM의 SQLite | 합성 데이터·초대 사용자·백엔드 1 worker·백업/복구 실증 |
| 1단계 최대 10명 | 단일 VM PostgreSQL | 합성/승인 자료·VM 외부 백업·복구 실증, 중요 실적·개인정보 제외 |
| 2단계 평시 30명·최대 50명 | 앱/DB 분리 PostgreSQL | 사설 DB·작업 대기열·부하 Gate 통과 |
| 상용 운영 | 국내 리전 관리형 PostgreSQL | 자동 백업·시점 복원·감사·모니터링·마이그레이션 롤백 필수 |

상용 기본 후보는 **NAVER Cloud DB for PostgreSQL**이다. 자동 백업, 시점 복원, 모니터링,
자동 페일오버를 제공해 같은 NCP VPC 안에서 애플리케이션 VM과 사설 연결할 수 있다. 다만 관리형
DB는 VM 한 대보다 비용이 커지므로 3~7일 합성 시연에는 만들지 않는다. 파일럿 견적 시
KakaoCloud PostgreSQL과 NHN Cloud PostgreSQL을 같은 사양·스토리지·백업·고가용성 조건으로
다시 비교한다.

### G7-DB — PostgreSQL 이전 별도 단계

| 단계 | 내용 | 완료 증거 |
|---|---|---|
| DB-0 자산 분류 | DB·테이블·소유 모듈·트랜잭션 경계·보존기간 분류 | 누락 없는 저장소 지도와 데이터 정본 표 |
| DB-1 접근계층 분리 | 라우트·서비스의 직접 `sqlite3` 의존 제거, DSN·트랜잭션 인터페이스 통일 | SQLite/PostgreSQL 계약 테스트 동시 통과 |
| DB-2 스키마·마이그레이션 | PostgreSQL DDL, Alembic 판, 제약·인덱스·트리거 이식 | 빈 DB 전진 설치와 이전 판 롤백 실증 |
| DB-3 데이터 이관 | 일관된 SQLite 사본에서 ETL, PK/FK·행수·내용 지문 대조 | 도메인별 대사 보고서 100% |
| DB-4 병행 검증 | 동일 입력을 두 저장소에 재생해 판정·조회·감사 결과 비교 | 설명되지 않은 차이 0 |
| DB-5 전환·복구 | 짧은 쓰기 동결 후 최종 증분 이관, DSN 전환, 복구 연습 | 전환과 SQLite 복귀를 각각 1회 실증 |
| DB-6 운영 안전 | 백업·PITR·pool·slow query·용량·RLS/권한·비밀 관리 | 장애 훈련과 관측 대시보드 |
| DB-7 폐기 판정 | 보존기간 뒤 SQLite 쓰기 경로 제거, 필요한 원본은 읽기 전용 보관 | 제품 코드의 업무 SQLite 쓰기 0 |

첫 전환에서 애플리케이션 이중 쓰기는 쓰지 않는다. 두 저장소 중 하나만 성공하는 상태가 생기면
정합성을 복구하기 더 어렵다. 먼저 읽기 재생·대조를 하고, 짧은 쓰기 동결과 최종 증분 이관으로
전환한다. 캐시(`llm_cache`, `mcp_cache`)와 Chroma 저장소는 업무 정본과 분리해 별도 생명주기로
관리하며, 관계형 DB를 무조건 한 스키마에 합치지 않는다.

초기 추정 작업량은 **12~20인일**이다. 현재 31개 코드 파일의 직접 SQLite 의존과 분산된
저장소를 실제로 걷어내야 하므로 단순 덤프·복원 작업이 아니다. DB-0·DB-1은 기능 개발과 병렬로
시작할 수 있지만, DB-3 이후는 시연 기준선과 핵심 스키마가 동결된 뒤 수행한다.

## 10. 진척도 반영 규칙

WEB-DEMO는 기능 완성률을 부풀리지 않고 별도 축으로 센다.

```text
기능 MVP 진척       기존 Gate A~E
웹 배포 진척        WEB-0~6
상용 DB 진척        G7-DB DB-0~7
도메인 시연 준비도  두 축의 교집합
```

현재 시작점:

```text
기능 MVP            ███████░░░  약 72%
WEB-DEMO            █░░░░░░░░░  약 10%  (health·CORS·Vite build 기반만 존재)
G7-DB               █░░░░░░░░░  약 10%  (방향·일부 마이그레이션만, PostgreSQL 이식 미착수)
도메인 시연 종합     ██████░░░░  약 65%
```

웹 배포가 끝나도 기능 Gate C의 계산 모델과 조직 격리가 미완이면 대외 시연은 승인하지 않는다.
반대로 기능이 끝나도 WEB-5를 통과하지 않으면 “로컬에서만 되는 제품”이므로 역시 승인하지 않는다.
