# 향후 과제 — 외부 백엔드를 가진 앱도 호스팅할 것인가 (2026-08-26 보류)

> 상태: **보류(기록만).** 이번에는 반대 방향(기획에게 현재 제약을 알려 주기)으로 갔다.
> 결정자: Supervisor. 결정 근거는 아래 「왜 지금 하지 않는가」.

## 1. 무엇이 문제였나 — 실측

`live-walk-02` 를 실제 LLM 으로 끝까지 돌리다 나왔다. Architect 가 이렇게 설계했다:

```
백엔드 API 서버 … 경량 백엔드 프레임워크(예: Spring Boot)를 사용하여 구현합니다.
프론트엔드가 백엔드 API 서버에 데이터를 요청하고, 응답받은 데이터를 화면에 표시합니다.
```

공장은 그대로 만들었다 — `InboundApplication.java`, `RawMaterialInboundRepository.java`,
`schema.sql`. 그리고 프론트 렌더 검증이 「App 루트를 찾지 못했습니다」로 **8회 반려**한 뒤
`FAILED_REVIEW` 로 끝났다. **앱이 한 줄도 나오지 않았다.**

이유는 런타임 계약이 그 구조를 금지하기 때문이다(`core/app_runtime_contract.py`):

| 능력 | 판정 | 코드에 적힌 이유 |
|---|---|---|
| `server.custom_logic` | PROHIBITED | 임의 FastAPI 생성 금지 |
| `api.direct_call` | PROHIBITED | 증명 경계를 우회한다 |
| `auth.local_login` / `auth.local_session` | PROHIBITED | 회사 권한 체계 밖에서 인증하게 된다 |
| `storage.local_db` | PROHIBITED | 판정이 두 곳이 된다 |
| `network.external_api` | HOST_SERVICE_REQUIRED | CSP `connect-src 'none'` — Host 가 중개한다 |

즉 **앱은 호스트 안에서 도는 단일 화면**이고, 데이터는 `window.afs.data` 로만 온다.

## 2. 두 갈래

### ① 기획에게 현재 제약을 알려 준다 — **이번에 한 것**

`core/app_runtime_brief.py` 가 위 닫힌 목록을 읽어 고지문을 렌더링하고, Architect ·
UIDesigner · Master_PM 프롬프트에 붙인다. 계약 프로필이 꺼진 레거시 프로젝트에는
빈 문자열이라 종전과 같이 동작한다. 회귀: `tests/test_planning_knows_runtime_contract.py`.

### ② 플랫폼이 외부 백엔드 앱도 호스팅한다 — **이 문서의 과제**

앱이 자기 서버(Spring Boot·FastAPI 등)를 갖고, 호스트는 그것을 배포·중개한다.

## 3. 왜 지금 하지 않는가

②는 「기능 추가」가 아니라 **증명 경계를 다시 여는 일**이다. 최소한 다음이 함께 움직인다.

1. **CSP** — 지금 `connect-src 'none'` 이다. 앱이 자기 서버를 부르려면 이 값이 열려야 하고,
   그 순간 「앱이 어디로든 나갈 수 있다」와의 경계를 새로 정의해야 한다.
2. **권한 판정 위치** — `auth.local_*` 를 금지한 이유가 「권한 판정이 두 곳이 된다」이다.
   외부 백엔드는 자기 권한 판정을 갖는다. 회사 권한 체계와 어떻게 하나로 유지할 것인가.
3. **데이터 이중 입력** — `ENTERPRISE_READ` 는 「원천을 직접 호출하지 않고 화면에서 다시
   입력받지도 않는다」를 전제한다. 외부 백엔드가 ERP 를 직접 붙으면 이 전제가 깨진다.
4. **계약·지문·승인** — 지금 계약은 «데이터셋 + 능력»으로 지문을 만든다. 서버가 생기면
   «엔드포인트·배포 대상·비밀」이 계약 대상에 들어와야 하고, 재승인 규칙이 달라진다.
5. **배포·수명** — 호스트는 지금 앱을 프레임 수명 안에서만 돌린다(`job.background` 가
   `NOT_YET_SUPPORTED` 인 이유). 서버는 상시 프로세스다 — 누가 띄우고 누가 끄는가.
6. **검증 하네스** — `frontend/scripts/render_check.mjs` 는 React 루트를 렌더해 본다.
   서버형 앱에는 이 검증이 성립하지 않으므로 다른 게이트가 필요하다.

★ 즉 ②는 **한 층의 변경이 아니라 여섯 층의 재설계**다. 지금 판단할 근거(실제로 그런 앱
  수요가 얼마나 되는가)가 없고, ①로 완주가 되는지를 먼저 봐야 한다.

## 4. 다시 꺼낼 조건

다음 중 하나라도 참이면 이 문서를 다시 연다.

- 사용자가 「기존 사내 서버와 붙는 앱」을 반복해서 요구한다.
- ① 을 적용한 뒤에도 기획이 서버 구조를 계속 만들어 낸다(= 요구 자체가 그 모양이다).
- 호스트가 중개하는 방식(`network.external_api` 를 Host 가 대신 호출)으로는 못 푸는
  사례가 실제로 나온다.

## 5. 함께 남은 것 (이번에 안 고침)

- **`pending_decisions` 를 결정할 화면·API 가 0곳이다.** 계약 컴파일러가 「사용자 결정이
  필요한 요구」를 만들어 내지만 읽는 곳이 없다(전수 확인). 미지원 능력이 남으면 사람이
  그것을 결정할 방법이 없어 막다른 길이 된다. `capability` 닫힌 목록을 스킬에 실어
  발생 자체는 줄였지만, 발생하면 여전히 막힌다.
- **`LIBRARY` 태스크에도 프론트 렌더 검증을 강제한다.** 화면을 만들 의무가 없는 태스크가
  「App 루트가 없다」로 반려된다. ① 적용 후 재확인 필요.
