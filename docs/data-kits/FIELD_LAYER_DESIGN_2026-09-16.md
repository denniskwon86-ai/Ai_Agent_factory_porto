# 필드 계층 설계 — 업태·셀에 따라 필드를 붙이는 자리

- 기준일: 2026-09-16
- 전제: [확산 적용 준비도 분석](DIFFUSION_READINESS_ANALYSIS_2026-09-16.md) 2.3 의 결정
  — **필드는 그것이 의미를 갖는 층에만 붙인다. 제조업에만 필요한 것을 서비스업·
  유통업 분류에까지 동일하게 적용하지 않는다.**
- 상태: **설계안.** 구현 전이고, 5 장의 결정이 나야 짤 수 있다.

---

## 1. 지금 구조가 어떤가 — 그리고 왜 자리가 없나

### 1.1 ★ 필드를 선언하는 곳이 아예 없다

`make_contract()` 를 열어 보면 이렇다.

```python
headers = []
for row in rows:                    # ← 만들어진 데이터에서
    for key in row:
        if key not in headers:
            headers.append(key)     # ← 헤더를 뽑는다
```

**계약은 데이터에서 파생된다.** `DATASETS` 에 있는 것은 `name` · `keys` · `deps`
뿐이고 **필드 목록이 없다.**

| 있는 것 | 무엇 |
|---|---|
| `DATASETS[ds]["keys"]` | 업무 키 (계약의 `business_keys`) |
| `DATASETS[ds]["deps"]` | 선행 데이터셋 |
| `REQUIRED_DATASET_FIELDS[ds]` | 필수로 올릴 필드 이름 (지금 `MDM-07` 한 곳) |
| **필드 목록** | **없다** |

그래서 **필드를 더한다 = 값을 만든다**이다. 선언만으로는 열이 생기지 않고, 값을
만들면 계약은 저절로 따라온다.

### 1.2 값은 데이터셋별 생성 함수가 만든다

`generate_materials` · `generate_contracts` · `generate_plans_batches_events` …
20 여 개가 각자 행을 만들고, `generate_profile()` 이 모아 `{dataset_id: rows}` 를
돌려준다.

즉 **필드를 계층으로 나누려면 이 함수들 안으로 들어가거나, 함수 밖에서 덧붙이거나**
둘 중 하나다.

### 1.3 키트는 산업 좌표를 하나 갖는다

```
manifest.industry_codes = ["C24"]      # 1차 금속
manifest.company_profile_id = "AFS-DEMO-MATERIALS-GROUP"
```

회사 프로파일은 6 개이고 **각자 다른 산업**이지만(제련 C2412 · 기초화학 C2013 …),
**데이터셋은 키트 좌표 하나를 따른다.** 프로파일은 시나리오 맥락이지 데이터 스키마가
아니다.

## 2. 설계 — 생성 뒤에 덧붙이는 **확장 층**

생성 함수 20 여 개를 고치지 않는다. 고치면 계층 조건이 함수마다 흩어지고, 그 순간
「어느 산업에 무엇이 붙는가」를 한눈에 볼 수 없게 된다.

대신 **생성이 끝난 뒤 좌표에 맞는 확장만 얹는다.**

```
generate_profile()  →  {dataset_id: rows}
                            ↓
                   apply_extensions(rows, coord)     ← 여기가 새 자리
                            ↓
                     make_contract()  (계약은 따라온다)
```

### 2.1 확장 하나의 모양

```python
@dataclass(frozen=True)
class FieldExtension:
    scope: str                     # 어느 층에 붙나 — 3 장
    dataset_id: str                # 어느 데이터셋에
    field: str                     # 어떤 이름으로
    compute: Callable              # (row, ctx) -> 값
    required: bool = False         # 계약에서 필수로 올릴지
    why: str = ""                  # ★ 왜 이 산업에만 있는가 — 비우지 말 것
```

`why` 를 필수로 두는 이유는 판본 정의(`kit_defs/__init__.py`)와 같다 — **값보다
왜 그런지가 중요하고, 그것이 없으면 반년 뒤에 아무도 못 고친다.**

### 2.2 적용

```python
def apply_extensions(data, coord, ctx):
    for ext in EXTENSIONS:
        if not matches(coord, ext.scope):
            continue
        for row in data[ext.dataset_id]:
            row[ext.field] = ext.compute(row, ctx)
```

- 행에 열이 생기므로 **계약은 자동으로 따라온다**(1.1)
- `required=True` 인 것은 `REQUIRED_DATASET_FIELDS` 에 합류시킨다
- 좌표가 안 맞으면 **아무 일도 일어나지 않는다** — 서비스업 키트에
  `tc_usd_per_dmt` 가 생기지 않는다

## 3. 층 표기 — 어디까지 내려가나

분류가 이미 계층이므로 그 표기를 그대로 쓴다.

| 표기 | 뜻 | 예 |
|---|---|---|
| `ALL` | 모든 키트 | 지금의 35 종 359 필드 |
| `A:제조` | A 대분류 | `standard_yield` · `scrap_quantity` |
| `A:소재제조` | A 세분류 | 연속공정·장치산업 공통이 있다면 |
| `B:금속` | B1 주업종 | |
| `B:금속>비철금속` | B1 2 단 (품목) | |
| `B:금속>비철금속>제련·정련` | B1 3 단 (공정) | `tc_usd_per_dmt` · `recovery_rate_by_metal` |

매칭은 **접두 일치**다. 좌표가 `B:금속>비철금속>제련·정련` 이면
`B:금속` · `B:금속>비철금속` 확장도 함께 적용된다.

**원칙(2.3): 필드는 의미를 갖는 가장 넓은 층에 붙이고 그보다 좁게 내리지 않는다.**
`standard_yield` 를 `B:금속>...>제련·정련` 에 두면 화학·전자 키트를 만들 때 같은
것을 또 만들게 된다.

### 3.1 ⚠️ 좌표를 어디서 얻나 — 분류 엔진을 부르지 않는다

`industry_codes=["C24"]` 를 `ksic_rules.classify()` 에 넣으면 A·B 축이 바로
나온다. **그런데 그렇게 하지 않는다.**

분류 엔진에는 「⚠️ 검토 중인 미확정 설계다. 현재 시스템에 연결·연계하지 않는다」가
붙어 있고, 생성기가 그것을 import 하면 **연계가 된다.**

그래서 **좌표를 키트 정의에 적는다.**

```python
# scripts/kit_defs/v1_2_0.py 또는 생성기 상단
KIT_SECTOR = "B:금속>비철금속>제련·정련"
KIT_SECTOR_A = "A:소재제조"
```

분류 엔진이 판정한 결과를 사람이 옮겨 적는 것이고, 그것은 연계가 아니라 **전사**다.
어긋날 위험이 있으므로 **판정 근거(KSIC)를 함께 적고**, 분류 판본이 바뀌면 사람이
확인한다.

## 4. ★ 가장 어려운 부분 — 확장은 기존 값과 **정합해야** 한다

필드를 덧붙이는 것 자체는 쉽다. 문제는 그 값이 **이미 있는 값과 모순되지 않는가**다.

### 4.1 실제로 생길 모순

| 새 필드 | 기존 값 | 무엇이 어긋나나 |
|---|---|---|
| `MFG-02.recovery_rate_by_metal` | `actual_yield` · `input_quantity` · `output_quantity` | 회수율과 수율이 따로 놀면 **둘 다 못 믿는다** |
| `MDM-01.metal_content_pct` | `MDM-05` BOM 의 `quantity_per_output` | 정광 1 톤에 든 금속이 BOM 배합과 맞지 않게 된다 |
| `PRC-01.tc_usd_per_dmt` | `benchmark_price` · `premium_rate` · `price_formula` | 제련수수료를 넣었는데 가격식이 그대로면 **매출이 두 번 계산된다** |
| `SLS-01.byproduct_flag` | `FIN-01` 원가·`FIN-03` 손익 | 부산물 매출을 갈라 놓고 손익에 반영하지 않으면 합이 안 맞는다 |

★ **`PRC-01` 이 가장 위험하다.** 제련 초안이 「제련사는 금속 가격으로 벌지 않는다」고
했는데, 필드만 더하고 `price_formula` 를 그대로 두면 **금속 가격으로 버는 구조 위에
제련수수료가 얹힌다.** 그것은 어느 제련소의 손익도 아니다.

### 4.2 그래서 확장은 셋 중 하나다

| 종류 | 무엇 | 위험 |
|---|---|---|
| **추가** | 없던 열을 더한다 (`shutdown_type`) | 낮다 |
| **파생** | 기존 값에서 계산한다 (`recovery = f(input, output, grade)`) | 중간 — 원본이 바뀌면 따라 바뀌어야 한다 |
| **대체** | 기존 계산을 **바꾼다** (`price_formula`) | **높다 — 생성 함수를 고쳐야 한다** |

**「대체」는 확장 층으로 못 한다.** 그건 그 산업의 생성기가 필요하다는 뜻이고,
설계상 별개 문제다. 확장 층은 **추가와 파생만** 받는다.

### 4.3 정합성은 검증기가 잡아야 한다

`validate_sample_company_starter_kit.py` 가 406 건을 검사하는데, **새 필드에 대한
검사는 자동으로 생기지 않는다.** 확장에 검사식을 함께 두는 것이 맞다.

```python
FieldExtension(
    scope="B:금속>비철금속>제련·정련",
    dataset_id="MFG-02",
    field="recovery_rate_by_metal",
    compute=...,
    check=lambda rows: all(0 < f(r) <= 1 for r in rows),   # ← 이것
    why="정광에 든 금속 중 실제로 뽑아낸 비율. 생산 수율(actual_yield)과 다르다",
)
```

## 5. 결정이 필요한 것

| | 물음 | 왜 지금 정해야 하나 |
|---|---|---|
| ① | **어느 층까지 지원할 것인가** — A 대분류만 · A 세분류까지 · B 3 단까지 | 층이 깊을수록 매칭·시험이 늘어난다. 제련 필드 17 개는 B 3 단이 필요하다 |
| ② | **「대체」 확장을 어떻게 할 것인가**(4.2) — 산업별 생성 함수를 둘지, 그때 가서 볼지 | `PRC-01` 가격식이 여기 걸린다. 제련을 제대로 하려면 피할 수 없다 |
| ③ | **좌표를 어디에 적을 것인가**(3.1) — 생성기 상단 · 판본 정의 · manifest | 판본마다 다를 수 있으면 판본 정의가 맞다 |
| ④ | **기존 359 필드를 `ALL` 로 둘 것인가** | 그중 제조 전용(`standard_yield` 등)이 섞여 있다. 지금 가르지 않으면 서비스업 키트를 만들 때 한꺼번에 해야 한다 |

### 5.1 ④의 규모를 재 보면

★ ④가 조용한 함정이다. 지금 35 종은 **이미 제조업을 전제**하는데 `ALL` 로 두면
「전 업태 공통」이라고 선언하는 셈이 된다. 얼마나 되는지 세 보면 이렇다.

| 업무키트 | 종 | 필드 | 붙어야 할 층(추정) |
|---|---|---|---|
| FOUNDATION | 11 | 103 | **섞여 있다** — `MDM-05`(BOM) · `MDM-06`(Routing) 23 필드는 제조 전용 |
| BK-01 구매 | 2 | 27 | 물건을 사는 업태 |
| BK-02 물류 | 5 | 47 | **국제 조달 전제** |
| BK-03 재고 | 2 | 21 | 물리 재고 전제 |
| BK-04 생산 | 3 | 33 | **`A:제조`** |
| BK-05 품질 | 2 | 23 | `QLT-01` 12 는 물성 전제 · `KNW-01` 11 은 전 업태 |
| BK-06 판매 | 1 | 13 | 전 업태 |
| BK-07 원가 | 3 | 30 | **전 업태** |
| BK-08 시나리오 | 6 | 62 | **전 업태** (내용은 산업별) |
| **합** | **35** | **359** | |

전제별로 다시 묶으면

| 전제 | 필드 | 비중 |
|---|---|---|
| 물성 변환 (BOM · Routing · 생산 · 품질) | **68** | 19% |
| 국제 물류 (LOG 5 종 + `MDM-08`) | **56** | 16% |
| 물리 재고 (`INV` 2 종 + `MDM-04`) | 28 | 8% |
| 나머지 (조직·거래처·회계·시나리오 등) | 207 | 58% |

**359 중 152 개(42%)가 「제조·물류·재고가 있는 회사」를 전제한다.** 서비스업 키트를
만들려면 이 152 개의 소속을 정해야 하고, 지금 `ALL` 로 선언해 두면 그때 한꺼번에
다시 봐야 한다.

⚠️ 위 「붙어야 할 층」은 **데이터셋 단위 추정**이다. 실제로는 한 데이터셋 안에서도
필드마다 층이 다를 수 있다(`MDM-01` 의 `material_id` 는 전 업태, `grade` 는
물성이 있는 업태). **필드 단위로 가르는 일은 별도 작업**이고, 지금 결정할 것은
「그 일을 지금 할지 나중에 할지」다.

## 6. 구현 순서 (결정 후)

1. `FieldExtension` 자료형과 `matches()` — 층 매칭만. 시험으로 고정
2. `apply_extensions()` 를 `generate_profile()` 뒤에 끼운다. **확장이 없으면
   아무것도 바뀌지 않아야 한다** — 1.1.0 재생성 지문이 그대로여야 한다
3. 제련 확장 17 개 중 **「추가」·「파생」만** 먼저 (4.2). `PRC-01` 은 ②가 정해진 뒤
4. 검사식을 검증기에 연결
5. 새 판본(1.2.0)으로 낸다 — 확장이 들어가면 1.1.0 과 데이터가 달라진다

⚠️ 2 번의 「확장이 없으면 그대로」가 합격 조건이다. 이것이 깨지면 기존 판본을
재현할 수 없게 되고, 그 문제는 이미 1.0.0 에서 한 번 겪었다.
