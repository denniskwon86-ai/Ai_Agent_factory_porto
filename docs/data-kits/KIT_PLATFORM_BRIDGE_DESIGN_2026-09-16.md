# 키트 → 플랫폼 이음매 설계 — 우리가 준 것이 현업에게 닿게

- 기준일: 2026-09-16
- 전제: [확산 적용 준비도 분석](DIFFUSION_READINESS_ANALYSIS_2026-09-16.md) 2.0 의 결정
  — **산업 분야의 가능한 최대한은 우리가, 회사 특성·경영방침은 현업이.**
- 문제: 그 경계의 **오른쪽은 구현돼 있는데 왼쪽이 들어갈 문이 없다**(분석 2.6)
- 상태: **설계안 + 검증 완료.** 7 장의 결정이 나야 짤 수 있다.
- 검증: 2026-09-16 에 임시 DB 로 실제 변환을 돌렸다(6 장). **소스는 고치지 않았다.**

---

## 0. 한 줄

**키트는 동인을 심고 계수는 비운다.** 비워 둔 자리가 경고로 드러나고, 그 경고가
현업의 할 일 목록이 된다.

⚠️ **검증에서 조용한 결함 둘이 나왔다**(6 장). 설계에 반영했다.

- **시나리오 변화량의 단위가 100 배 어긋난다** — 키트는 `0.1`(비율), 플랫폼은
  `10`(퍼센트 수). 그대로 넘기면 **오류 없이 100 배 작게** 계산된다
- **동인 이름이 업무 언어가 아니다** — `AR_AP_TIMING` · `ETA_DELAY_DAYS` 가 그대로
  들어간다. 플랫폼이 동인을 두는 이유 자체가 「업무 언어」인데 그것이 깨진다

## 1. 이음매는 하나가 아니라 셋이다

키트가 주는 것 중 플랫폼의 계획 체계로 가야 하는 것이 셋이다. **순서가 있다** —
계정이 없으면 동인이 붙을 데가 없고, 동인이 없으면 시나리오가 설 수 없다.

| | 키트 | 플랫폼 | 지금 |
|---|---|---|---|
| ① | `MDM-07` 계정·원가센터 | `plan_accounts` | 연결 없음 |
| ② | `SIM-01` 드라이버 | `plan_drivers` | 연결 없음 |
| ③ | `SIM-02` 시나리오 | 계획 가정 | 연결 없음 |
| — | (없음) | `driver_impacts` 파급 계수 | **현업 몫** — 여기는 비운다 |

## 2. 실측 — 무엇이 이미 맞고 무엇이 안 맞나

### 2.1 ★ 계정 코드가 이미 같다

| | |
|---|---|
| 키트 `MDM-07` | `4000 제품매출` · `5000 재료비` |
| 플랫폼 시험 | `upsert_account("4000", "매출", "REVENUE")` · `("5000", "원가", "COGS")` |

**같은 코드 체계다.** 우연으로 보기 어렵고, 양쪽이 같은 설계를 보고 만들어진 것으로
보인다. 이음매의 가장 어려운 부분(코드 대응)이 이미 풀려 있다.

#### 분류만 옮기면 된다

| 키트 `pnl_line` | 건 | 플랫폼 `category` |
|---|---|---|
| `REVENUE` | 1 | `REVENUE` |
| `COGS` | 4 | `COGS` |
| `OPEX` | 21 | `SGA` |
| `BALANCE_SHEET` | 4 | **없다** — 플랫폼은 손익·현금흐름만 받는다 |

`sign` 은 키트에 없지만 `account_type` 에서 나온다 — `REVENUE`→`+1`, `EXPENSE`→`−1`.

⚠️ **30 개 중 26 개만 넘어간다.** 현금·매출채권·재고자산·매입채무는 재무상태표
계정이라 `PL_CATEGORIES`·`CF_CATEGORIES` 어디에도 없다. 버리는 것이 맞는지, 아니면
현금흐름(`WORKING_CAPITAL`)으로 보내는지는 7 장에서 정한다.

### 2.2 동인은 모양이 다르다

| 키트 `SIM-01` | 플랫폼 `plan_drivers` | 대응 |
|---|---|---|
| `driver_id` (`DRV-FX`) | `driver_code` | ✅ 그대로 |
| `input_metric` (`USD_KRW`) | `name` · `unit` | △ 사람이 읽을 이름으로 |
| `output_metric` (`PURCHASE_COST`) | — | ✗ **지표명이지 계정이 아니다** |
| `formula_definition` (`PURCHASE_USD*USD_KRW`) | — | ✗ 받는 자리가 없다 |
| `lag_period_months` | — | ✗ 〃 |
| — | `category` (volume·price·cost·fx…) | ✗ 키트에 없다 |
| — | **`elasticity`** | ✗ **키트에 없다 — 있어서도 안 된다(3 장)** |
| — | **`rationale`·`source`** | ✗ 〃 |

★ **`formula` 와 `elasticity` 는 서로 다른 것이다.** `PURCHASE_USD × USD_KRW` 는
**계산식**이고, 「환율 1% 오르면 재료비 0.6% 오른다」는 **민감도**다. 전자에서 후자가
자동으로 나오지 않는다 — 구매액 중 외화 비중이 얼마인지는 **그 회사만 안다.**

### 2.3 시나리오는 모양이 맞다

키트 `SIM-02` 는 `(driver_id, change_value, change_unit, impact_metrics)` 이고,
플랫폼은 `expand_driver_assumption(driver_code, pct_change)` 다. **동인 + 변화율**로
같은 모양이다.

    SCN-01  환율 10% 상승   DRV-FX  0.1  %   → PURCHASE_COST, CASH, GROSS_MARGIN

`impact_metrics` 는 **지표명**이라 계정으로 바로 못 간다. 다만 그럴 필요가 없다 —
실제 파급은 현업이 등록한 `driver_impacts` 가 정한다. 키트의 `impact_metrics` 는
**「무엇에 영향이 간다」는 업무 설명**으로 남는다.

## 3. ★ 핵심 결정 — 키트는 동인을 심고 **계수는 비운다**

### 3.1 왜 비우나

플랫폼의 설계 사상이 이것을 요구한다.

> 파급 계수는 **사람이 등록하고 승인한다.** LLM 이나 자동 회귀로 만들면 **그럴듯한
> 가짜 인과**가 생기고, 그것은 경영 보고서에 「환율 때문에 원가가 이만큼 오릅니다」로
> 인쇄된다. — `core/planning_drivers.py`

키트가 `elasticity=0.6` 을 심으면 그것이 정확히 **그럴듯한 가짜 인과**다. 어느
제련소의 숫자도 아니고, `rationale` 에 적을 것이 없다. 그리고 한 번 들어가면 현업은
그것을 **검증된 값으로 착각한다.**

경계(분석 2.0)로도 같은 답이 나온다 — 「환율이 구매원가를 움직인다」는 **업무 사실**이고
우리 몫, 「우리 회사는 0.6」은 **회사 사실**이고 현업 몫이다.

### 3.2 비워 두면 어떻게 되나 — 경고가 할 일이 된다

```python
# expand_driver_assumption()
if not impacts:
    return [], [f"동인 '{driver_code}' 에 등록된 파급 계수가 없습니다 — "
                f"이 가정은 어떤 계정에도 적용되지 않습니다."]
```

**이미 이렇게 설계돼 있다.** 매핑이 없으면 조용히 무시하지 않고 경고를 낸다.

그러면 키트를 받은 현업이 보는 것은 이렇다.

    동인 12 개가 등록돼 있습니다.
    ⚠️ DRV-FX · DRV-COMMODITY · … 에 파급 계수가 없습니다.

★ 이것이 **「우리 회사는 얼마인가」를 채우라는 할 일 목록**이다. 빈칸이 결함이 아니라
**설계된 빈칸**이고, 그 자리에 현업의 도메인이 쌓인다.

### 3.3 그럼 키트가 아는 것은 어디에 남기나

계수는 못 심어도 **「무엇이 무엇을 움직이는가」는 알고 있다.** 그것을 버리면 키트를
심는 의미가 없다.

`plan_drivers` 에 받을 자리가 있다.

| 열 | 키트가 넣을 것 |
|---|---|
| `name` | 「환율(USD/KRW)」 — 업무 언어 |
| `unit` | `KRW/USD` |
| `category` | `fx` · `price` · `cost` · `volume` … |
| `external_code` | 외부 지표 연결(표시용) |
| **`note`** | **`output_metric` · `formula` · 영향 계정 후보** |

`note` 에 「구매원가에 파급된다(일반적으로 재료비 5000). 계산식
`PURCHASE_USD × USD_KRW`」를 적으면, 현업이 계수를 등록할 때 **어느 계정에 붙일지
바로 안다.** 이것이 「적응이 빠르다」의 실체다.

⚠️ `note` 는 자유 텍스트라 기계가 못 읽는다. 구조를 갖춘 자리가 필요하면
스키마 변경이고, 그것은 플랫폼 쪽(다른 세션) 소관이다 — 7 장 ③.

## 4. 설계 — 세 갈래

### 4.1 ① 계정 — `MDM-07` → `plan_accounts`

```python
_PNL_TO_CATEGORY = {"REVENUE": "REVENUE", "COGS": "COGS", "OPEX": "SGA"}

def seed_accounts(rows):
    for r in rows:
        cat = _PNL_TO_CATEGORY.get(r["pnl_line"])
        if cat is None:
            continue              # BALANCE_SHEET — 7장 ①에서 정한다
        sign = 1 if r["account_type"] == "REVENUE" else -1
        store.upsert_account(r["account_id"], r["account_name"], cat, sign)
```

⚠️ **건너뛴 것을 세어 보고한다.** 30 개 중 4 개가 빠지는데 조용히 빠지면 나중에
「왜 재고자산이 없지」가 된다.

### 4.2 ② 동인 — `SIM-01` → `plan_drivers`

```python
def seed_drivers(rows):
    existing = {d["driver_code"] for d in drivers.list_drivers()}
    skipped = []
    for r in rows:
        if r["driver_id"] in existing:
            skipped.append(r["driver_id"])   # ★ 덮어쓰지 않는다 (5.1)
            continue
        drivers.register_driver(
            driver_code=r["driver_id"],
            name=_readable(r["input_metric"]),          # USD_KRW → 환율(USD/KRW)
            unit=r["output_unit"],
            category=_category_of(r["driver_id"]),      # fx · cost · volume …
            external_code="",                           # 외부 지표 연결은 별도 판단
            note=_note(r),                              # output_metric · formula · 계정 후보
        )
        # ★ driver_impacts 는 만들지 않는다 (3장)
    return skipped      # 건너뛴 것을 **보고한다** — 조용히 지나가면 안 된다
```

### 4.3 ③ 시나리오 — `SIM-02`

시나리오는 **계수가 채워진 뒤에만 의미가 있다.** 그래서 키트가 심는 것은 실행 가능한
시나리오가 아니라 **초안**이다.

| 무엇 | 어디 |
|---|---|
| 「환율 10% 상승」이라는 **질문** | 키트가 준다 |
| 그때 손익이 얼마 변하나 | 현업이 계수를 채운 뒤 플랫폼이 계산한다 |

즉 ③은 ②가 되고 현업이 계수를 채운 다음에 붙는다. **먼저 만들면 전부 「적용되지
않음」으로 나온다.**

### 4.4 어디에 구현하나

`scripts/seed_starter_data.py` 가 키트를 런타임에 심는 자리다. 거기에 붙인다.

⚠️ 그 스크립트에는 이미 알려진 결함이 있다 — **빈 설치본을 전제하지 않는다**
(2026-09-11 인계 4-(3)). 이음매를 붙이기 전에 그것이 고쳐졌는지 확인해야 한다.

## 5. 위험

### 5.1 ★ 키트를 두 번 심으면 승인된 동인의 설명이 조용히 바뀐다

`register_driver` 를 열어 보니 이렇다.

```sql
INSERT INTO plan_drivers(...) VALUES(...)
ON CONFLICT(driver_code) DO UPDATE SET
  name=excluded.name, unit=excluded.unit, category=excluded.category,
  external_code=excluded.external_code, note=excluded.note
```

**덮어쓴다.** 그리고 승인 판본 검사가 **없다.**

| | 키트를 다시 심으면 |
|---|---|
| `driver_impacts` (현업이 채운 계수) | 별개 표라 **살아남는다** ✅ |
| 동인의 `name` · `note` · `category` | **덮어써진다** ⚠️ |
| 승인된 판본이 있어도 | **막지 않는다** ⚠️ |

계수가 지워지지 않는 것은 다행이지만, **승인된 동인의 설명이 바뀌는 것**은 위험하다.
현업이 「환율(USD/KRW) — 재료비에 파급」을 보고 계수 0.6 을 등록·승인했는데, 키트
갱신으로 `note` 가 「환율 — 재료비·운반비에 파급」이 되면 **그 0.6 이 무엇에 대한
숫자였는지 흐려진다.**

★ Codex 갈래가 `remove_impact()` 에는 이 보호를 넣었다 —

> 승인된 계수를 밑에서 갈아치우면 「우리가 승인한 그 숫자」가 무엇이었는지 아무도
> 답할 수 없다. 먼저 `revoke()` 로 철회하고 고친다.

**같은 논리가 `register_driver` 에는 없다.** 이것이 의도인지 아직 손대지 않은
것인지는 모른다 — 확인한 것은 코드에 검사가 없다는 사실뿐이다.

→ 이음매는 **이미 있는 동인을 건드리지 않아야** 한다. 심기 전에 `list_drivers()` 로
확인하고, 있으면 **건너뛰고 그 사실을 보고**한다. 덮어쓰기를 고를 수 있게 하더라도
기본은 「건드리지 않음」이어야 한다.

### 5.2 키트를 갱신하면

1.1.0 을 심은 회사에 1.2.0 이 나오면? 동인이 늘어나는 것은 괜찮지만, 이름이나
`note` 가 바뀌면 현업이 붙여 둔 계수의 전제가 달라진다. **판본 간 이행**은 이 설계의
범위 밖이고 별도로 다뤄야 한다.

### 5.3 지표명과 계정의 거리

`output_metric` 이 `PURCHASE_COST` 인데 계정은 `5000 재료비`다. 「구매원가」와
「재료비」가 같은 것인지는 **회사마다 다르다.** `note` 에 후보를 적어 주는 것까지가
우리 몫이고, 확정은 현업이 한다 — 그것이 경계다.

## 6. ★ 검증 — 계산이 아니라 실제로 돌려 봤다

이 문서의 숫자는 처음에 전부 **계산**이었다. 이 세션에서 이미 같은 함정을 겪었으므로
(「35 종 중 6 종」이 초안의 계획치였고 실제로는 일부가 이미 있는 것과 겹쳤다),
임시 DB 에 실제로 변환해 넣어 봤다. **저장소 소스는 고치지 않았다.**

### 6.1 맞은 것

| 검증 | 결과 |
|---|---|
| ① 계정 30 건 중 26 건 적재 | ✅ **계산과 일치.** 실패 0 · 건너뜀 4(재무상태표) |
| `account_id` 유일성 | ✅ 30 건 전부 유일 — 원가센터별 중복을 걱정했으나 없었다 |
| ③ 계수를 비우면 경고 | ✅ 「파급 계수가 없습니다 — 이 가정은 어떤 계정에도 적용되지 않습니다」 |
| ⑤ 두 번 심으면 | ✅ `note` 는 덮어써지고 **계수는 살아남는다**(5.1 그대로) |

### 6.2 ★★★ 단위가 100 배 어긋난다

| | |
|---|---|
| 키트 `SIM-02` | `SCN-01 환율 10% 상승` · `change_value=0.1` · `change_unit=%` |
| 플랫폼 | `expand_driver_assumption(code, pct_change)` → `value = pct_change × elasticity` |

**키트는 비율(0.1)로 적고 플랫폼은 퍼센트 수(10)를 받는다.** 탄력도 0.6 을 넣고
두 해석을 비교하면

    pct_change=0.1   → 재료비 +0.06%      ← 키트 값을 그대로 넘기면 이것
    pct_change=10.0  → 재료비 +6.00%      ← 「환율 10% 상승」의 실제 의미

★ **오류가 나지 않는다.** 실행되고 숫자만 100 배 작다. 「환율이 10% 올랐는데 원가가
0.06% 밖에 안 오르네」를 이상하다고 느끼지 못하면 그대로 경영 보고서로 간다.

→ 이음매는 `change_unit` 을 보고 **반드시 환산**해야 한다. `%` 면 ×100, `DAY` 같은
절대 단위는 애초에 `pct_change` 로 넘길 수 없다(SCN-04 「선적 14 일 지연」).

⚠️ `DAY`·절대량 시나리오를 어떻게 다룰지는 이 설계의 범위를 넘는다 — 플랫폼의
`expand_driver_assumption` 이 **퍼센트만** 받기 때문이다. 7 장 ⑤로 넘긴다.

### 6.3 ★ 동인 이름이 업무 언어가 아니다

`input_metric` 을 그대로 `name` 에 넣으면 이렇게 된다.

    DRV-CASH       name=AR_AP_TIMING        unit=KRW
    DRV-DELAY      name=ETA_DELAY_DAYS      unit=TON     ← 단위도 틀렸다
    DRV-COMMODITY  name=COMMODITY_PRICE     unit=USD/TON

플랫폼이 동인을 1 급으로 두는 이유가 **「가정이 업무 언어가 된다」**인데
(`판매량 +10%` 는 읽히지만 `4000 계정 pct +10` 은 안 읽힌다), `AR_AP_TIMING` 은
`4000 계정` 과 다를 바 없다. **이음매가 그 이유를 깨뜨린다.**

그리고 `unit` 을 `output_unit` 에서 가져오면 **입력의 단위가 아니라 출력의 단위**가
들어간다 — `DRV-DELAY`(지연 일수)의 단위가 `TON` 이 된 까닭이다.

→ 이음매에 **이름·단위 대응표**가 필요하다. 설계 4.2 의 `_readable()` 이 그 자리인데,
**그 표를 누가 만드는지가 빠져 있었다.** 12 개뿐이므로 사람이 한 번 적으면 되고,
그것 자체가 「산업 최대한을 반영한다」의 일부다.

| 키트 | 이름 | 단위 |
|---|---|---|
| `DRV-FX` | 환율(USD/KRW) | `KRW/USD` |
| `DRV-DELAY` | 선적 지연 일수 | `DAY` |
| `DRV-CASH` | 매출채권·매입채무 회수 시점 | `DAY` |
| … | (12 개 전부 사람이 적는다) | |

## 7. 결정이 필요한 것

| | 물음 | 왜 |
|---|---|---|
| ① | **재무상태표 계정 4 개를 어떻게 할 것인가** — 버릴지, `WORKING_CAPITAL` 로 보낼지 | 현금·매출채권·재고·매입채무다. 운전자본 시나리오를 쓰려면 필요하다 |
| ② | **`note` 로 충분한가** — 아니면 「영향 계정 후보」를 구조화할 자리가 필요한가 | 자유 텍스트는 기계가 못 읽는다. 구조화하면 플랫폼 스키마 변경이다 |
| ③ | **누가 구현하나** — 이음매는 키트 쪽인가 플랫폼 쪽인가 | `seed_starter_data.py` 는 공용이고, `plan_drivers` 는 다른 세션 영역이다 |
| ④ | **`formula`·`lag_period_months` 를 버릴 것인가** | 플랫폼에 받을 자리가 없다. `note` 로 남기면 사람만 읽는다 |
| ⑤ | **절대 단위 시나리오를 어떻게 다룰 것인가**(6.2) | `expand_driver_assumption` 이 **퍼센트만** 받는데 `SCN-04 선적 14 일 지연`·`SCN-08 정기보수 연장` 은 일수다. 퍼센트로 바꿀 수 없다 |
| ⑥ | **동인 이름·단위 대응표를 누가 적나**(6.3) | 12 개뿐이라 사람이 한 번 적으면 되고, **그것 자체가 「산업 최대한 반영」의 일부**다 |

★ ③이 먼저다. 이 설계는 **양쪽에 걸쳐 있고**, 어느 쪽이 맡는지에 따라 ①②④의 답이
달라진다.
