# 업무키트를 플랫폼 안에서 어떻게 확산하고 늘리나

- 기준일: 2026-09-17
- 물음: **새 산업·새 회사의 업무키트를 플랫폼에 어떻게 추가하나**
- ⚠️ 검토 제안이다. 플랫폼 코드는 아직 고치지 않았다
- 이 문서의 「실측」은 전부 코드·데이터에서 직접 확인한 것이다

---

## 0. 결론부터

**경로는 이미 거의 다 깔려 있다. 끊긴 곳이 두 군데다.**

    사업 정의 ─→ 생성기 ─→ Starter Kit ─┬─→ 【끊김 ①】 ─→ 등록부 ─→ 조직 적용
    (30줄)              (35종+앱7)      │
                                        └─→ profile_from_manifest()  ← 있는데 시연 전용

| | 무엇 | 크기 |
|---|---|---|
| **1단계** | 생성기가 낸 키트를 **정식 등록 경로**에 올린다 | **작다 — 먼저** |
| **2단계** | 키트를 **사업 단위로** 낸다 (제련만 / 전지소재만) | **중간 — 핵심** |
| 3단계 | 회사공통 13 종을 갈라 **기반 키트 + 산업 키트**로 | 크다 — 2 단계 결과를 보고 |
| 4단계 | 분류 셀 → 키트 후보를 잇는다 | 중간 — 3 단계와 함께 |

★ **하지 말 것**: `POST /kits` 로 아무나 키트를 올리게 하는 것. 이유는 5 장.

---

## 1. 실측 — 지금 어떻게 돌아가나

### 1.1 「업무키트」는 두 가지를 가리킨다

이 구분을 놓치면 이야기가 어긋난다. `kit_registry.py` 머리말이 이미 경고한다.

| | **Profile** (`docs/data-kits/*.kit.json`) | **Starter Kit** (`starter_kits/`) |
|---|---|---|
| 무엇 | **업무키트 정의** — 요구 데이터 + 산출물 | **샘플 데이터** — 가상회사의 실제 CSV |
| 담은 것 | 데이터셋 9 종(필드 수준) · 산출물 4 | 데이터셋 35 종 · 127,752 행 · 앱 7 |
| 쓰임 | 조직에 적용하는 **운영 템플릿** | 체험·시연 |
| 개수 | **1 개** (`afs_materials_procurement_v1`) | 2 개 |
| 만드는 법 | **사람이 손으로 쓴다** | 생성기 |

⚠️ 지금까지 이 세션이 다듬은 것은 **오른쪽**이다. 사용자가 확산을 물을 때의
「업무키트」는 **왼쪽**이다.

### 1.2 등록 경로가 둘인데 하나만 정식이다

    ㉮ docs/data-kits/*.kit.json ─ discover() ─ register_all() ─→ 등록부
       └ GET /kits 가 호출할 때마다 멱등 등록                    현재 1 개

    ㉯ starter_kits/…/manifest.json ─ profile_from_manifest() ─→ upsert_kit_version()
       └ **core/demo_vertical_slice.py 에서만 부른다** (시연 수직 경로 전용)

★ **㉯ 는 이미 잘 돈다.** 1.2.0 manifest 로 실제로 돌려 봤다.

    datasets 35 종 · outputs 7 개
    datasets[0] = {dataset_contract_key: 'FND-01', label: '기업·조직 계층',
                   required: True, keys: ['node_id'], deps: []}
    outputs[0]  = {output: 'APP-01', label: '원료 도입계획·추적',
                   requires: ['EXT-01','EXT-02',…,'PRC-02']}

즉 **앱 청사진이 산출물이 되고, 그 앱이 요구하는 데이터셋이 그대로 따라온다.**

### 1.3 조직 적용은 이미 실제 운영을 전제로 한다

    POST /instances          키트 × 테넌트 × 조직범위 × entity_mode
      → POST /instances/{id}/bindings      데이터셋별 바인딩
      → POST /bindings/{id}/snapshots      실제 데이터 업로드
      → POST /ownership/approve            소유권 승인

| | |
|---|---|
| `KIT_MODES` | `DEMO/SYNTHETIC` · **`REAL`** |
| `ENTITY_MODES` | `REAL` · `VIRTUAL` · `COMPETITOR_REFERENCE` · `SYNTHETIC_TEST` |
| 권한 | `require_caps(PROJECT_CREATE)` · 조직범위 가시성 검사 · 감사 로그 |

★ **실측: `kit_instances` 에 `(kit_id, tenant, scope)` 유일 제약이 없다.**
  한 조직이 **키트를 여럿 물 수 있다.** 2 단계 제안이 여기에 기댄다.

## 2. 병목 — 무엇이 확산을 막나

| | 병목 | 실측 근거 |
|---|---|---|
| **①** | **생성기가 낸 키트가 정식 키트가 되지 못한다** | `profile_from_manifest()` 를 `demo_vertical_slice` 만 부른다. `discover()` 는 `docs/data-kits/*.kit.json` 만 훑는다 |
| **②** | **키트가 회사 단위로 한 덩어리다** | 사업 정의는 갈랐는데(`--business`) **등록은 안 갈렸다.** 고려아연에 주면 전지소재 35 종이 함께 간다 |
| ③ | 키트 정의를 손으로 쓴다 | `afs_materials_procurement_v1.kit.json` 은 데이터셋 9 종을 **필드 수준까지** 사람이 적은 것이다. 새 산업마다 반복할 수 없다 |
| ④ | 키트 추가에 배포가 필요하다 | API 에 `GET /kits` 는 있고 **`POST` 가 없다** |

⚠️ ①과 ②가 실제 병목이다. ③은 ①이 풀리면 대부분 사라지고, ④는 **지금 풀 문제가
아니다**(5 장).

---

## 3. 제안

### 3.1 【1단계】 생성기가 낸 키트를 정식 경로에 올린다 — 작다

`profile_from_manifest()` 를 시연 밖으로 꺼내고, `discover()` 가 `starter_kits/` 도
보게 한다.

**막는 것은 두 칸뿐이다.** 변환 결과에 `load_profile()` 이 요구하는 `name`·`mode` 가
없다(manifest 에 그 이름이 없다). 대응은 셋 중 하나다.

| | 어떻게 | 판단 |
|---|---|---|
| ⓐ manifest 에 `name`·`mode` 를 넣는다 | 생성기 두 줄 · 판본을 새로 내야 한다 | △ |
| **ⓑ 변환이 채운다** | `name ← company_name`, `mode ← data_class` 매핑 | **✅ 추천 — 판본을 안 건드린다** |
| ⓒ 등록 시 인자로 준다 | `demo_vertical_slice` 가 지금 하는 방식 | △ 호출부마다 반복된다 |

⚠️ ⓑ에서 **지어내지 않는다.** `data_class: SYNTHETIC` → `DEMO/SYNTHETIC`,
  실 데이터 키트가 나오면 그때 `REAL` 을 매핑한다. 모르는 값은 거부한다 —
  `profile_from_manifest` 머리말의 규칙(「옮기지 못한 것을 지어내지 않는다」)과 같다.

### 3.2 【2단계】 ★ 키트를 사업 단위로 낸다 — 핵심

**이것이 확산의 본체다.** 이번에 사업 정의를 갈라 냈으므로 이미 뽑을 수 있다.

    python scripts/generate_sample_company_starter_kit.py --business smelting_nonferrous
    → 전지소재 흔적 0 · 123,817 행 (실측)

그러면 키트가 셋이 된다.

| 키트 | 담는 사업 | 줄 수 있는 회사 |
|---|---|---|
| `KIT-SMELTING-NONFERROUS` | 제련·정련 | **고려아연 · 영풍 · LS MnM** … 롱리스트 11 개사 |
| `KIT-BATTERY-MATERIALS` | 전지소재 | **켐코 · 에코프로머티리얼즈** … |
| `KIT-MFG-NONFERROUS-PROCUREMENT` | 둘 다 | LS MnM 형(두 사업을 한 법인에서) |

★ 세 번째가 남는 이유: **한 조직이 키트를 여럿 물 수 있으므로**(1.3) 사실 제련 +
  전지소재를 각각 붙이면 된다. 그런데 **두 사업이 한 법인 안에서 물류·재고를
  주고받는 경우**(제련 부산물 황산 → 전지소재 원료)는 그것이 한 키트여야 한다.
  ⚠️ 지금 데이터에는 그 연결이 **없다**(황산은 `BP-H2SO4`, 원료는 `RM-H2SO4` 로
  별개 품목이다) — 그러니 지금 당장은 셋째 키트에 근거가 약하다. **먼저 둘로 내고,
  사업 간 연결을 데이터로 만든 뒤에 셋째를 판단한다.**

### 3.3 【3단계】 회사공통을 갈라낸다 — 크다, 나중

35 종의 갈래는 이미 세어 두었다(`business_defs/__init__.py` 머리말).

| 부류 | 종 | |
|---|---|---|
| 사업별 | **20** | 품목 · 위치 · BOM · 공정 · 구매 · 물류 · 재고 · 생산 · 품질 · 판매 · 원가 |
| 회사공통 | 13 | 사용자 · 달력 · 공급사 · 고객 · 계정 · 무역조건 · 외부지표 · 동인 · 결정 · 문서 |
| 혼재 | 2 | 조직 · 회계 |

기반 키트(13) + 산업 키트(20)로 나누면 **새 산업 추가 비용이 20 종으로 준다.**

⚠️ 다만 전제가 있다 — 플랫폼이 **키트 합성**을 어떻게 다루는지 확인해야 한다.
  인스턴스를 여럿 만들 수는 있지만(1.3), 「기반 + 산업」이 **하나의 업무 화면**으로
  보여야 하는지는 화면 쪽 이야기다. **2 단계를 내고 실제 쓰임을 본 뒤에 정한다.**

### 3.4 【4단계】 분류에서 키트로 잇는다

manifest 에 **`industry_codes: ['C24']` 가 이미 있다.** 분류 엔진이 낸 셀과 이을 자리다.

    A축 업태 × B축 업종 3단(공정·형태)  ─→  키트 후보
    소재제조 × 금속 > 비철금속 > 제련·정련  ─→  KIT-SMELTING-NONFERROUS

`business_defs` 는 이미 그 좌표를 들고 있다(`sector = "B:금속>비철금속>제련·정련"`).
**키트와 분류를 잇는 열이 양쪽에 다 있는데 이어 놓지 않았을 뿐이다.**

## 4. 그래서 새 산업 키트 하나를 늘리는 데 무엇이 드나

1·2 단계를 마친 뒤의 모습이다.

| 단계 | 무엇 | 크기 | 누가 |
|---|---|---|---|
| ① | 사업 정의 `business_defs/<code>.py` | **30 줄** (실측: 제련 29 · 전지소재 31) | 우리 |
| ② | 생성 → 검증 → 봉인 | 명령 3 개 | 우리 |
| ③ | 등록 | 자동(1 단계가 풀리면) | — |
| ④ | 조직 적용 | `POST /instances` | 현업 |
| ⑤ | 산업 특성(드라이버·등급 값) | — | **도메인 검토** |

★ ⑤가 실제 비용이다. 코드는 30 줄이지만 **그 산업을 아는 사람의 답**이 필요하다.
  이것은 줄일 수 없고, 줄이려 하면 「인접하니 비슷하겠지」가 되어 특성이 죽는다.

---

## 5. 하지 말 것 — `POST /kits`

키트를 API 로 올리게 하면 확산이 빨라 보인다. 그러나 **지금은 아니다.**

| | 왜 |
|---|---|
| 키트는 **우리가 주는 전문성**이다 | 현업이 플랫폼에서 쌓는 것은 **세부 도메인**이지 키트 정의가 아니다. 이 경계가 우리 제공 가치의 정의다 |
| 검증이 붙어 있다 | 생성 → 검증 420 건 → 봉인 → 지문. 업로드 경로는 이 사슬을 우회한다 |
| 아직 한 번도 안 늘려 봤다 | 키트가 **1 개**다. 늘리는 구조를 시험하기 전에 문을 먼저 여는 셈이다 |

대신 **키트 만드는 도구**를 우리 안에서 좋게 한다(1·2 단계).

## 6. 결정이 필요한 것

| | 물음 | 추천 |
|---|---|---|
| ① | 1 단계 변환 방식 — ⓐ/ⓑ/ⓒ (3.1) | **ⓑ** (판본을 안 건드린다) |
| ② | 2 단계에서 **몇 개로 낼 것인가** (3.2) | **둘** (제련 · 전지소재). 셋째는 사업 간 연결이 데이터에 생긴 뒤 |
| ③ | 기존 `afs_materials_procurement_v1` (9 종) 을 어떻게 하나 | **남긴다.** 35 종 키트와 목적이 다르다(최소 수직 경로). 다만 **둘이 같은 목록에 뜨면 혼란**이므로 화면 구분이 필요하다 |
| ④ | 3 단계(기반+산업 분리)를 할 것인가 | **2 단계 뒤에 판단.** 지금 정하면 쓰임을 모른 채 구조를 만든다 |

⚠️ ③이 실제로 막힐 수 있는 자리다. 지금 `GET /kits` 는 `docs/data-kits/*.kit.json`
  만 보는데, 1 단계로 `starter_kits/` 가 더해지면 **성격이 다른 둘이 한 목록**에 뜬다.
