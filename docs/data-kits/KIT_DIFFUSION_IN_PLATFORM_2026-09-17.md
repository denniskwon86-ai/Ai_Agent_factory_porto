# 업무키트를 플랫폼 안에서 어떻게 확산하고 늘리나

- 기준일: 2026-09-17
- 물음: **새 산업·새 회사의 업무키트를 플랫폼에 어떻게 추가하나**
- ⚠️ 검토 제안이다. 플랫폼 코드는 아직 고치지 않았다
- 이 문서의 「실측」은 전부 코드·데이터에서 직접 확인한 것이다

---

## 0. 결론부터

**경로는 이미 거의 다 깔려 있다. 끊긴 곳이 두 군데다.**

    사업 정의 ─→ 생성기 ─→ Starter Kit ─┬─→ 【끊김 ①】 ─→ 등록부 ─→ 조직 적용
    (30줄)              (35종+앱7)      │
                                        └─→ profile_from_manifest()  ← 있는데 시연 전용

| | 무엇 | 크기 |
|---|---|---|
| **1단계** | 생성기가 낸 키트를 **정식 등록 경로**에 올린다 | **작다 — 먼저** |
| **2단계** | 키트를 **사업 단위로** 낸다 (제련만 / 전지소재만) | **중간 — 핵심** |
| 3단계 | 회사공통 13 종을 갈라 **기반 키트 + 산업 키트**로 | 크다 — 2 단계 결과를 보고 |
| 4단계 | 분류 셀 → 키트 후보를 잇는다 | 중간 — 3 단계와 함께 |

★ **하지 말 것**: `POST /kits` 로 아무나 키트를 올리게 하는 것. 이유는 5 장.

## 1. 실측 — 지금 어떻게 돌아가나

### 1.1 「업무키트」는 두 가지를 가리킨다

이 구분을 놓치면 이야기가 어긋난다. `kit_registry.py` 머리말이 이미 경고한다.

| | **Profile** (`docs/data-kits/*.kit.json`) | **Starter Kit** (`starter_kits/`) |
|---|---|---|
| 무엇 | **업무키트 정의** — 요구 데이터 + 산출물 | **샘플 데이터** — 가상회사의 실제 CSV |
| 담은 것 | 데이터셋 9 종(필드 수준) · 산출물 4 | 데이터셋 35 종 · 127,752 행 · 앱 7 |
| 쓰임 | 조직에 적용하는 **운영 템플릿** | 체험·시연 |
| 개수 | **1 개** (`afs_materials_procurement_v1`) | 2 개 |
| 만드는 법 | **사람이 손으로 쓴다** | 생성기 |

⚠️ 지금까지 이 세션이 다듬은 것은 **오른쪽**이다. 사용자가 확산을 물을 때의
「업무키트」는 **왼쪽**이다.

### 1.2 등록 경로가 둘인데 하나만 정식이다

    ㉮ docs/data-kits/*.kit.json ─ discover() ─ register_all() ─→ 등록부
       └ GET /kits 가 호출할 때마다 멱등 등록                    현재 1 개

    ㉯ starter_kits/…/manifest.json ─ profile_from_manifest() ─→ upsert_kit_version()
       └ **core/demo_vertical_slice.py 에서만 부른다** (시연 수직 경로 전용)

★ **㉯ 는 이미 잘 돈다.** 1.2.0 manifest 로 실제로 돌려 봤다.

    datasets 35 종 · outputs 7 개
    datasets[0] = {dataset_contract_key: 'FND-01', label: '기업·조직 계층',
                   required: True, keys: ['node_id'], deps: []}
    outputs[0]  = {output: 'APP-01', label: '원료 도입계획·추적',
                   requires: ['EXT-01','EXT-02',…,'PRC-02']}

즉 **앱 청사진이 산출물이 되고, 그 앱이 요구하는 데이터셋이 그대로 따라온다.**

### 1.3 조직 적용은 이미 실제 운영을 전제로 한다

    POST /instances          키트 × 테넌트 × 조직범위 × entity_mode
      → POST /instances/{id}/bindings      데이터셋별 바인딩
      → POST /bindings/{id}/snapshots      실제 데이터 업로드
      → POST /ownership/approve            소유권 승인

| | |
|---|---|
| `KIT_MODES` | `DEMO/SYNTHETIC` · **`REAL`** |
| `ENTITY_MODES` | `REAL` · `VIRTUAL` · `COMPETITOR_REFERENCE` · `SYNTHETIC_TEST` |
| 권한 | `require_caps(PROJECT_CREATE)` · 조직범위 가시성 검사 · 감사 로그 |

★ **실측: `kit_instances` 에 `(kit_id, tenant, scope)` 유일 제약이 없다.**
  한 조직이 **키트를 여럿 물 수 있다.** 2 단계 제안이 여기에 기댄다.

## 2. 병목 — 무엇이 확산을 막나

| | 병목 | 실측 근거 |
|---|---|---|
| **①** | **생성기가 낸 키트가 정식 키트가 되지 못한다** | `profile_from_manifest()` 를 `demo_vertical_slice` 만 부른다. `discover()` 는 `docs/data-kits/*.kit.json` 만 훑는다 |
| **②** | **키트가 회사 단위로 한 덩어리다** | 사업 정의는 갈랐는데(`--business`) **등록은 안 갈렸다.** 고려아연에 주면 전지소재 35 종이 함께 간다 |
| ③ | 키트 정의를 손으로 쓴다 | `afs_materials_procurement_v1.kit.json` 은 데이터셋 9 종을 **필드 수준까지** 사람이 적은 것이다. 새 산업마다 반복할 수 없다 |
| ④ | 키트 추가에 배포가 필요하다 | API 에 `GET /kits` 는 있고 **`POST` 가 없다** |

⚠️ ①과 ②가 실제 병목이다. ③은 ①이 풀리면 대부분 사라지고, ④는 **지금 풀 문제가
아니다**(5 장).

---

## 3. 제안

### 3.1 【1단계】 생성기가 낸 키트를 정식 경로에 올린다 — 작다

`profile_from_manifest()` 를 시연 밖으로 꺼내고, `discover()` 가 `starter_kits/` 도
보게 한다.

**막는 것은 두 칸뿐이다.** 변환 결과에 `load_profile()` 이 요구하는 `name`·`mode` 가
없다(manifest 에 그 이름이 없다). 대응은 셋 중 하나다.

| | 어떻게 | 판단 |
|---|---|---|
| ⓐ manifest 에 `name`·`mode` 를 넣는다 | 생성기 두 줄 · 판본을 새로 내야 한다 | △ |
| **ⓑ 변환이 채운다** | `name ← company_name`, `mode ← data_class` 매핑 | **✅ 추천 — 판본을 안 건드린다** |
| ⓒ 등록 시 인자로 준다 | `demo_vertical_slice` 가 지금 하는 방식 | △ 호출부마다 반복된다 |

⚠️ ⓑ에서 **지어내지 않는다.** `data_class: SYNTHETIC` → `DEMO/SYNTHETIC`,
  실 데이터 키트가 나오면 그때 `REAL` 을 매핑한다. 모르는 값은 거부한다 —
  `profile_from_manifest` 머리말의 규칙(「옮기지 못한 것을 지어내지 않는다」)과 같다.

### 3.2 【2단계】 ★ 키트를 사업 단위로 낸다 — 핵심

**이것이 확산의 본체다.** 이번에 사업 정의를 갈라 냈으므로 이미 뽑을 수 있다.

    python scripts/generate_sample_company_starter_kit.py --business smelting_nonferrous
    → 전지소재 흔적 0 · 123,817 행 (실측)

그러면 키트가 셋이 된다.

| 키트 | 담는 사업 | 줄 수 있는 회사 |
|---|---|---|
| `KIT-SMELTING-NONFERROUS` | 제련·정련 | **고려아연 · 영풍 · LS MnM** … 롱리스트 11 개사 |
| `KIT-BATTERY-MATERIALS` | 전지소재 | **켐코 · 에코프로머티리얼즈** … |
| `KIT-MFG-NONFERROUS-PROCUREMENT` | 둘 다 | LS MnM 형(두 사업을 한 법인에서) |

★ 세 번째가 남는 이유: **한 조직이 키트를 여럿 물 수 있으므로**(1.3) 사실 제련 +
  전지소재를 각각 붙이면 된다. 그런데 **두 사업이 한 법인 안에서 물류·재고를
  주고받는 경우**(제련 부산물 황산 → 전지소재 원료)는 그것이 한 키트여야 한다.
  ⚠️ 지금 데이터에는 그 연결이 **없다**(황산은 `BP-H2SO4`, 원료는 `RM-H2SO4` 로
  별개 품목이다) — 그러니 지금 당장은 셋째 키트에 근거가 약하다. **먼저 둘로 내고,
  사업 간 연결을 데이터로 만든 뒤에 셋째를 판단한다.**

### 3.3 【3단계】 회사공통을 갈라낸다 — 크다, 나중

35 종의 갈래는 이미 세어 두었다(`business_defs/__init__.py` 머리말).

| 부류 | 종 | |
|---|---|---|
| 사업별 | **20** | 품목 · 위치 · BOM · 공정 · 구매 · 물류 · 재고 · 생산 · 품질 · 판매 · 원가 |
| 회사공통 | 13 | 사용자 · 달력 · 공급사 · 고객 · 계정 · 무역조건 · 외부지표 · 동인 · 결정 · 문서 |
| 혼재 | 2 | 조직 · 회계 |

기반 키트(13) + 산업 키트(20)로 나누면 **새 산업 추가 비용이 20 종으로 준다.**

⚠️ 다만 전제가 있다 — 플랫폼이 **키트 합성**을 어떻게 다루는지 확인해야 한다.
  인스턴스를 여럿 만들 수는 있지만(1.3), 「기반 + 산업」이 **하나의 업무 화면**으로
  보여야 하는지는 화면 쪽 이야기다. **2 단계를 내고 실제 쓰임을 본 뒤에 정한다.**

### 3.4 【4단계】 분류에서 키트로 잇는다

manifest 에 **`industry_codes: ['C24']` 가 이미 있다.** 분류 엔진이 낸 셀과 이을 자리다.

    A축 업태 × B축 업종 3단(공정·형태)  ─→  키트 후보
    소재제조 × 금속 > 비철금속 > 제련·정련  ─→  KIT-SMELTING-NONFERROUS

`business_defs` 는 이미 그 좌표를 들고 있다(`sector = "B:금속>비철금속>제련·정련"`).
**키트와 분류를 잇는 열이 양쪽에 다 있는데 이어 놓지 않았을 뿐이다.**

## 4. 그래서 새 산업 키트 하나를 늘리는 데 무엇이 드나

1·2 단계를 마친 뒤의 모습이다.

| 단계 | 무엇 | 크기 | 누가 |
|---|---|---|---|
| ① | 사업 정의 `business_defs/<code>.py` | **30 줄** (실측: 제련 29 · 전지소재 31) | 우리 |
| ② | 생성 → 검증 → 봉인 | 명령 3 개 | 우리 |
| ③ | 등록 | 자동(1 단계가 풀리면) | — |
| ④ | 조직 적용 | `POST /instances` | 현업 |
| ⑤ | 산업 특성(드라이버·등급 값) | — | **도메인 검토** |

★ ⑤가 실제 비용이다. 코드는 30 줄이지만 **그 산업을 아는 사람의 답**이 필요하다.
  이것은 줄일 수 없고, 줄이려 하면 「인접하니 비슷하겠지」가 되어 특성이 죽는다.

## 5. 하지 말 것 — `POST /kits`

키트를 API 로 올리게 하면 확산이 빨라 보인다. 그러나 **지금은 아니다.**

| | 왜 |
|---|---|
| 키트는 **우리가 주는 전문성**이다 | 현업이 플랫폼에서 쌓는 것은 **세부 도메인**이지 키트 정의가 아니다. 이 경계가 우리 제공 가치의 정의다 |
| 검증이 붙어 있다 | 생성 → 검증 420 건 → 봉인 → 지문. 업로드 경로는 이 사슬을 우회한다 |
| 아직 한 번도 안 늘려 봤다 | 키트가 **1 개**다. 늘리는 구조를 시험하기 전에 문을 먼저 여는 셈이다 |

대신 **키트 만드는 도구**를 우리 안에서 좋게 한다(1·2 단계).

## 6. 결정이 필요한 것

| | 물음 | 추천 |
|---|---|---|
| ① | 1 단계 변환 방식 — ⓐ/ⓑ/ⓒ (3.1) | **ⓑ** (판본을 안 건드린다) |
| ② | 2 단계에서 **몇 개로 낼 것인가** (3.2) | **둘** (제련 · 전지소재). 셋째는 사업 간 연결이 데이터에 생긴 뒤 |
| ③ | 기존 `afs_materials_procurement_v1` (9 종) 을 어떻게 하나 | **남긴다.** 35 종 키트와 목적이 다르다(최소 수직 경로). 다만 **둘이 같은 목록에 뜨면 혼란**이므로 화면 구분이 필요하다 |
| ④ | 3 단계(기반+산업 분리)를 할 것인가 | **2 단계 뒤에 판단.** 지금 정하면 쓰임을 모른 채 구조를 만든다 |

⚠️ ③이 실제로 막힐 수 있는 자리다. 지금 `GET /kits` 는 `docs/data-kits/*.kit.json`
  만 보는데, 1 단계로 `starter_kits/` 가 더해지면 **성격이 다른 둘이 한 목록**에 뜬다.

## 7. ★ 그런데 **줄 물건**이 없다 — 무엇을 미리 만들어 두나

⚠️ 6 장까지는 **배관** 이야기다. 정작 「넣어 줄 것」은 지금 **리스트뿐**이다.
  요청이 올 때마다 새로 만들어 주는 방식은 **같은 내용을 두 번 줄 수 없다** —
  이 저장소가 이미 그렇게 실패했다(1.0.0 을 재생성할 수 없게 됐다).

### 7.1 실측 — 키트 하나는 두 부분이고, 성격이 정반대다

| | **정의** | **샘플 데이터** |
|---|---|---|
| 무엇 | 계약 35 · 앱 청사진 7 · 회사 프로파일 · 시나리오 · manifest | `samples/{quick,full}` CSV |
| 크기 | **432 KB** | **35 MB** (quick 3.4 · full 32) |
| 몫 | 1.2 % | **98.8 %** |
| 고객이 실제로 쓰나 | **그렇다** — 자기 데이터를 이 계약에 맞춘다 | 체험·시연에만 |
| 언제 필요한가 | **쓸 때** (도입 후 내내) | **팔 때** (영업·시연) |

    키트 하나 전체 35 MB · 압축 4.6 MB · 생성 7 초 (실측)
    저장소 `.git` 는 이미 660 MB · `starter_kits/` 작업트리 119 MB

★ **미리 만들어 둬야 하는 것은 「정의」다.** 산업 20 개를 준비해도 **8.6 MB** 다.
  샘플 데이터까지 다 쌓으면 700 MB(압축 92 MB)가 되고, 판본마다 또 쌓인다.

### 7.2 「플랫폼 안에 생성기」는 하지 않는다

| | 왜 |
|---|---|
| **이 저장소가 그 길에서 이미 실패했다** | 1.0.0 은 **재생성되지 않는다.** 로직이 바뀌어 오버레이로 되돌릴 수 없었고, 그래서 「파일과 지문이 판본을 보증한다」로 결론 났다([[v1_0_0]]·[[v1_1_0]]). 런타임 생성은 「생성기 = 정본」으로 되돌아가는 것이다 |
| 생성기는 **개발 도구**다 | `business_defs` · 검증 420 건 · 봉인 스크립트 · 지문 대장이 한 벌로 딸려 온다. 런타임에 둘 물건이 아니다 |
| **「동일한 내용」이 깨진다** | 고객 환경마다 생성기 판이 엇갈리면, 같은 키트를 요청해도 다른 것이 나온다 — 막으려는 바로 그 일이다 |

### 7.3 제안 — **키트 선반** 세 층

    ① 사업 정의   scripts/business_defs/<code>.py        ~1 KB   git · 전부
    ② 키트 정의   starter_kits/<KIT>/<ver>/ (samples 제외) 432 KB  git · **전부 미리**
    ③ 샘플 데이터 starter_kits/<KIT>/<ver>/samples/        35 MB   **선별 보관**

| 층 | 언제 만드나 | 어디 두나 | 왜 |
|---|---|---|---|
| ① | 대상이 정해질 때 | 저장소 | 30 줄. 이것이 키트의 씨앗이다 |
| ② | **①이 생기는 즉시 전부** | 저장소 · **플랫폼 상주** | 작다(20 개 = 8.6 MB). 고객이 실제로 쓰는 것 |
| ③ | **팔 대상이 생길 때** | 저장소(압축) 또는 아티팩트 | 크다. 체험에만 쓴다 |

★ **③의 규칙 하나**: **고객에게 준 판본은 반드시 보관한다.** 안 준 것은 지문만 남기고
  필요할 때 재생성해 지문으로 대조한다 — 재생성이 실패하면 그 판본은 「재생성 불가」로
  드러나고, 그것이 바로 보관해야 한다는 신호다.

### 7.4 지금 선반에 실제로 무엇이 있나 — 정직하게

| | 사업 정의 ① | 키트 정의 ② | 샘플 ③ | 도메인 검토 |
|---|---|---|---|---|
| 제련·정련 | ✅ | ✅ (1.2.0 안에) | ✅ | ⏳ 드라이버 5 · 등급 값 |
| 전지소재 | ✅ | ⚠️ **안 뽑아 뒀다** | ⚠️ 뽑을 수 있음 | ⏳ 램프업 |
| 전선·케이블 | ✗ | ✗ | ✗ | ⏳ 드라이버 4 · `ORDER:PROJECT` |
| 나머지 37 셀 | ✗ | ✗ | ✗ | ✗ |

⚠️ **제련·전지소재가 한 키트에 섞여 있다.** 사업 정의는 갈랐지만 키트로는 **따로 낸
  적이 없다**(3.2). 선반에 올린다는 것은 **각각을 실제로 뽑아 봉인해 둔다**는 뜻이다.

### 7.5 ★ 실제 제약은 용량도 시간도 아니다

    사업 정의 30 줄  ·  생성 7 초  ·  정의 432 KB

**늘리는 비용이 이미 낮다.** 막고 있는 것은 **그 산업을 아는 사람의 답**이다 —
드라이버, 등급 체계의 실제 값, 공정 순서, 램프업 수치. 이것은 줄일 수 없고,
줄이려 하면 「인접하니 비슷하겠지」가 되어 특성이 죽는다(확산 분석 2.5 의 원칙).

★ 그러므로 선반을 채우는 속도는 **도메인 검토가 정한다.** 구조를 먼저 만들어 두면,
  답이 하나 올 때마다 **기계적으로** 한 칸이 찬다.

### 7.6 순서

| | 무엇 | 크기 | 왜 먼저인가 |
|---|---|---|---|
| **1** | **전지소재를 따로 뽑아 봉인한다** | 명령 3 개 | 선반이 실제로 도는지 **두 번째 칸으로 확인**한다. 지금은 한 칸뿐이라 구조를 시험한 적이 없다 |
| **2** | 키트 정의만 뽑는 경로 (`--profile-only`) | 작다 | ②를 ③ 없이 낼 수 있어야 「정의는 전부, 샘플은 선별」이 성립한다 |
| **3** | 선반 카탈로그 | 작다 | 무엇이 있고 어느 분류 좌표인지. `industry_codes` · `sector` 가 이미 양쪽에 있다(3.4) |
| 4 | 등록 경로 잇기 (1 단계) | 작다 | 선반이 차야 이을 것이 생긴다 |

⚠️ **1 번을 건너뛰고 구조부터 만들지 않는다.** 키트가 하나인 채로 선반·카탈로그를
  설계하면, 두 번째를 넣을 때 맞지 않는 것이 뒤늦게 드러난다.

### 7.7 ★ 7.6 의 1 번을 실제로 해 봤다 — 막혔다

전지소재만 뽑아 manifest 를 열었다.

    full_rows          131,740              ← 데이터는 전지소재만, 제대로 나온다
    kit_id             KIT-MFG-NONFERROUS-PROCUREMENT   ← **비철 조달 키트**
    industry_codes     ['C24']              ← 1 차 금속. 황산니켈이 아니다
    company_name       AFS 데모소재그룹      ← 그룹 이름 그대로
    primary_use_case   원료 구매·도입계획에서…  ← 제련 서술

★ **사업은 갈랐는데 「키트의 정체성」은 안 갈렸다.** 데이터는 전지소재인데 이름표가
  전부 제련이다. 이대로 선반에 올리면 **켐코에 「비철 조달 키트」를 주는 셈**이다.

데이터셋 계약키(`MDM-01` …)는 사업과 무관하므로 **앱 7 개는 그대로 돈다.** 막힌 것은
이름표뿐인데, 그 이름표가 **고객이 키트를 고르는 근거**다.

#### 무엇을 더해야 하나

사업 정의가 키트 정체성을 들어야 한다.

    class BatteryMaterials(BusinessDef):
        code    = "battery_materials"
        kit_id  = "KIT-MFG-BATTERY-MATERIALS"     # ← 없다
        use_case = "…"                             # ← 없다
        ksic    = (…)                              # ← 없다 (아래 ⚠️)

⚠️ **`ksic` 는 사업 정의에 고정할 수 없다.** 이미 확인한 바다 — 같은 황산니켈 제조라도
  **켐코(별도 법인)는 `C2820`, LS MnM(사업부)은 모법인을 따라 `C24`** 로 간다
  (`LSMNM_BATTERY_NEWBIZ_REVIEW` 1 장). **법인 구조가 정하는 것**이지 사업이 정하는
  것이 아니다. 그러니 `industry_codes` 는 **키트가 아니라 적용 대상(회사)** 쪽 값이고,
  키트에는 **우리 분류 좌표**(`sector`)를 싣는 것이 맞다 — `business_defs` 가 이미 갖고
  있다(`"B:전자·정밀>전지·전원부품>전지소재"`).

#### 조합일 때는 누가 정하나

| 사업 | kit_id |
|---|---|
| 하나 | 그 사업의 `kit_id` |
| 여럿 | **명시해야 한다** (`--kit-id`). 「제련+전지소재」에 자동으로 붙일 옳은 이름이 없다 |

★ 이것이 7.6 에서 **1 번을 먼저 하라**고 한 이유다. 구조부터 만들었다면 두 번째 칸을
  넣을 때 이 이름표 문제가 뒤늦게 드러났을 것이다.

### 7.8 그래서 순서를 고친다

| | 무엇 | 크기 |
|---|---|---|
| **1** | **사업 정의에 키트 정체성**(`kit_id` · `use_case`)을 더하고, `--kit-id` 로 조합을 명시 | 작다 — 사업 정의 2 줄 · 생성기 몇 줄 |
| 2 | 전지소재를 **따로 뽑아 봉인** → 선반 두 번째 칸 | 명령 3 개 |
| 3 | 키트 정의만 뽑는 경로 (`--profile-only`) | 작다 |
| 4 | 선반 카탈로그 (`sector` 좌표 포함) | 작다 |
| 5 | 등록 경로 잇기 (3.1) | 작다 |

⚠️ `industry_codes`(KSIC)는 **키트에서 뺀다.** 지금 manifest 에 `['C24']` 가 박혀 있는데
  그것은 **AFS 데모 회사의 코드**이지 키트의 속성이 아니다. 분류와 잇는 열은 `sector` 다.

## 8. 플랫폼 **밖에 별도 시스템**으로 분리하는 안

### 8.1 앞서 반대한 셋 중 무엇이 풀리나

| | 7.2 의 반대 이유 | 별도 시스템이면 |
|---|---|---|
| ① | 이 저장소가 재생성 보증에서 실패했다(1.0.0) | **안 풀린다.** 별도 시스템이라도 **「요청 시 생성」이면 똑같다.** **보관**해야 풀린다 |
| ② | 생성기는 개발 도구다 | **풀린다** — 플랫폼 런타임에서 빠진다 |
| ③ | 환경마다 생성기 판이 엇갈린다 | **풀린다** — 한 곳에서 만들어 배급한다 |

★ 즉 **「별도 시스템이냐」가 아니라 「보관해서 배급하느냐」가 문제를 푼다.** 생성을
  어디서 하느냐는 그다음이다. 이 구분을 놓치면 별도 시스템을 세워 놓고 거기서
  **요청 시 생성**하게 되어, 막으려던 재현 문제를 그대로 안고 간다.

### 8.2 그런데 배포 형태를 보니 필요가 실재한다 — 실측

    /opt/afs/app     ← 릴리스 코드. update.sh 가 `git pull` 로 갈아 끼운다
    /opt/afs/data    ← data/ · projects/ · output/ (남는다)

    kit_registry.KITS_DIRNAME     = "docs/data-kits"      ← 상수
    kit_registry.kits_dir()       = PROJECT_ROOT + 위     ← 환경변수 없음
    STARTER_PACKAGES_DIRNAME      = "starter_kits"        ← 상수

**키트가 `app` 쪽에 있다.** 즉 **코드 릴리스에 묶여 있다.**

| | 지금 | 산업 20 개가 되면 |
|---|---|---|
| 모든 고객 서버가 받는 키트 | 119 MB | **700 MB** (압축 92 MB) |
| 제련만 쓰는 고객이 받는 것 | 전지소재까지 | 전선·화학·식품까지 전부 |
| `git pull` 한 번 | — | 판본마다 누적 |

★ **고객사 설치형이라 이 문제가 실재한다.** SaaS 한 벌이면 저장 위치 문제였겠지만,
  설치가 늘 때마다 같은 짐이 복제된다.

### 8.3 그러므로 이름을 바꿔야 한다 — **「생성기 시스템」이 아니라 「키트 저장소」**

| | 생성 | 배급 |
|---|---|---|
| 언제 도나 | **사업 정의가 바뀔 때만** | 고객이 늘 때마다 · 판본이 나올 때마다 |
| 비용 | **7 초** | 카탈로그 · 보관 · 선별 · 이력 |
| 누가 | **CI** (검증 420 건 · 봉인까지 한 사슬) | 저장소 시스템 |

**생성은 문제가 아니다.** 7 초짜리 배치이고 이미 자동이다. 실제로 필요한 것은 넷이다.

    ① 무엇이 있나            카탈로그 (분류 좌표 · 판본 · 지문)
    ② 같은 것을 다시 줄 수 있나  봉인된 꾸러미 보관
    ③ 이 고객에게 무엇을 주나    **선별** 배급
    ④ 누구에게 무엇을 줬나      이력

★ ③이 핵심이다. 지금은 **선별이 없다** — 저장소에 있으면 전부 간다.

### 8.4 지금 만들 것인가 — **아직 아니다**

| | |
|---|---|
| 키트 수 | **2 개**(사실상 1 조합). 늘리는 구조를 **한 번도 시험하지 않았다** |
| 따라오는 것 | 시스템 하나를 더 세우면 인증·권한·백업·가용성·버전 정책이 딸려 온다 |
| 되돌리기 | 일찍 세우면 키트가 5 개 될 때 구조가 안 맞는 것이 드러난다(7.7 에서 이미 겪었다) |

**임계를 정해 두는 편이 낫다.**

| 언제 | 무엇 |
|---|---|
| 지금 (키트 1~2) | **8.5 의 한 줄만** |
| 키트 5 개 **또는** 고객 설치 3 곳 | 배급 **스크립트** — 봉인 꾸러미(zip 4.6 MB)를 골라 내려받아 푸는 수준 |
| 키트 10 개+ **또는** 고객 여럿 | **키트 저장소 시스템** — 카탈로그 API · 이력 · 서명 |

### 8.5 ★ 지금 해 둘 하나 — 키트를 코드에서 떼어낼 수 있게

**경로를 설정으로 뺀다.** 그것뿐이다.

    kits_dir()  ← PROJECT_ROOT 고정          지금
                ← 환경변수(없으면 지금 그대로)  바꾼 뒤

| | |
|---|---|
| 지금 | 기본값이 같으므로 **아무것도 달라지지 않는다** |
| 나중 | 키트를 `/opt/afs/data/kits/` 로 옮기면 **코드 배포와 분리된다** |
| 그다음 | 배급 시스템이 생기면 **설정 한 줄로 갈아 끼운다** |
| 덤 | 고객사마다 **다른 키트 조합**을 둘 수 있다 |

★ `discover(directory="")` 는 **이미 인자를 받는다.** 기본값만 환경변수로 바꾸면 되고,
  `STARTER_PACKAGES_DIRNAME` 쪽도 같다. 크기가 작다.

### 8.6 정리 — 무엇을 하고 무엇을 미루나

| | 무엇 | 언제 |
|---|---|---|
| ✅ | 사업 정의에 **키트 정체성**(7.8 의 1) | 지금 |
| ✅ | 전지소재를 따로 뽑아 **선반 두 번째 칸** | 지금 |
| ✅ | **키트 경로를 설정으로** (8.5) | 지금 — 작고, 나중 선택지를 전부 연다 |
| ⏸ | 배급 스크립트 | 키트 5 개 또는 설치 3 곳 |
| ⏸ | 키트 저장소 시스템 | 키트 10 개+ 또는 고객 여럿 |
| ✗ | 플랫폼 안 생성기 | **하지 않는다** (7.2) |
| ✗ | 별도 시스템에서 **요청 시 생성** | **하지 않는다** — 8.1 의 ①이 그대로 남는다 |

⚠️ 마지막 줄을 특히 조심한다. 별도 시스템을 세우기로 하면 「거기서 만들어 주면
  되지」로 가기 쉬운데, 그러면 **「언제든 동일한 내용」이 다시 깨진다.** 별도
  시스템은 **만드는 곳이 아니라 보관·배급하는 곳**이다.
