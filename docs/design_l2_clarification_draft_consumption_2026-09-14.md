## 1. 지금 상태 — 확인된 사실만

| 항목 | 확인 방법 | 결과 |
|---|---|---|
| 명확화 초안은 저장·조회·폐기가 된다 | `studio_input_drafts.Target.kind` | `CLARIFICATION` 지원 |
| 명확화 초안은 **닫히지 않는다** | `studio_input_draft_control._receipt()` | `CONSUME_UNSUPPORTED` 로 거절 |
| 화면은 조합된 한 문자열을 제출한다 | `StudioDecisionPanel.tsx:252` | `serializeClarifyAnswers(...)` 결과를 `feedback` 으로 보냄 |
| 초안은 구조를 유지한 채 저장된다 | `studio_input_drafts.Content` | `text` 와 `selections` 를 따로 보관 |
| 서버는 질문 원문을 갖고 있다 | `studio_input_draft_control.py:278` | `current_state["clarification_questions"]` 로 이미 선택값을 검증한다 |
| 화면 질문 = 서버 질문이 보증된다 | `verifyHotlQuestions` · `validate_selections` | 양쪽이 `questions_digest` 로 대조된다 |

### 조합 규칙 (`frontend/src/factory/clarifyAnswers.ts`)

    [요구 확인 인터뷰 답변]
    1. {질문}
    → 선택: {label} ({description})        ← description 이 있을 때만 괄호
    → 선택 없음 (전문가 추천안대로 진행)      ← 고른 것이 없을 때
    ...
    (빈 줄)
    [추가 의견]
    {메모}                                  ← 메모가 있을 때만

조합에 필요한 재료(`question`, `options[].label`, `options[].description`)는 **전부 서버에
있다**. 즉 서버가 같은 문자열을 만드는 것은 기술적으로 가능하다.

### 그래서 무엇이 문제인가

초안(구조)과 제출물(문자열)의 모양이 다르다. 서버가 「이 초안이 이 제출을 만들었다」를
확인하려면 **조합 규칙을 알아야** 한다. 지금은 화면만 안다.

★ 클라이언트가 보낸 「이 초안을 냈다」를 그대로 믿는 길은 막혀 있다 —
`studio_input_drafts.verify_decision_submission` 머리말: 「HTTP submitted=true 는 증거가
아니다」.

## 2. 갈래

### 갈래 A — 서버가 저장 초안에서 조합해 대조한다

제출 시 `input_draft` 참조로 서버가 **자기 저장소의 초안**을 읽고, 서버가 가진 질문으로
조합한 뒤 제출 본문과 비교한다. 클라이언트가 `selections` 를 다시 보내지 않는다.

- 변경: `core/` 에 조합 함수 신규(약 30줄), `studio_hotl_submissions` 의 대상 제한 해제와
  검증 분기, `_receipt()` 분기, `consume_supported` 확장, 시험.
- 제출 DTO·화면 제출 경로는 **바뀌지 않는다**. 이미 만든 결속 구조를 그대로 쓴다.
- 대가: **표시 문구가 화면과 서버 두 곳에 생긴다.** 한쪽만 고치는 날 정상 제출이 대조
  실패로 닫힌다. 이 저장소가 반복해 경계한 「같은 판정을 두 곳에 두면 조용히 어긋난다」다.
- 완화: 같은 입력에 대한 **고정 예제(golden)** 를 서버 시험과 프런트 계약 시험 양쪽에 두고
  각자 그 값과 비교한다. 어긋나면 한쪽이 즉시 빨강이 된다. 실제 상호 호출은 아니다.

### 갈래 B — 화면이 `selections` 를 함께 보내고 서버가 본문을 만든다

제출 DTO 에 `selections` 를 받고 **서버가 `feedback` 을 생성**한다. 화면의 조합은 미리보기
전용이 된다.

- 변경: A 의 전부 + `HOTLResumeRequest` 확장 + 화면 제출 경로 변경 + 기존 호출 호환 처리.
- 이점: 제출 본문의 **생성 주체가 서버 하나**가 된다. 대조가 아니라 생성이므로 어긋날 여지가
  구조적으로 없다.
- 대가: 변경 범위가 가장 크다. 미리보기와 실제 제출물이 다를 수 있어(화면 조합 = 미리보기)
  그 차이를 사용자에게 어떻게 보일지 별도 결정이 필요하다.

### 갈래 C — 초안에 조합 결과를 함께 저장하고 그것과 대조한다

초안 저장 시 화면이 조합 문자열도 함께 넣는다. 제출 시 서버는 **자기 저장소의 그 값**과
제출 본문을 비교한다. 서버는 조합하지 않는다.

- 변경: `Content` 모델에 필드 추가, 저장 시 화면 변경, 검증 분기, 시험. A 보다 작다.
- 이점: 표시 문구가 화면 한 곳에 남는다.
- 대가: 서버는 「그 문자열이 `selections` 를 정확히 반영하는가」를 **모른다.** 다만 초안
  소비가 막으려는 것(남의 초안을 닫기·내지 않은 초안 닫기·다른 내용을 내고 초안만 닫기)은
  모두 막는다 — 비교 대상이 둘 다 서버가 가진 값이기 때문이다.
- ⚠️ 「서버가 독립적으로 확인한다」는 기존 원칙에서 한 걸음 물러선다. 저장 시점의 클라이언트
  값을 신뢰 기준으로 삼는다.

### 갈래 D — 명확화는 소비 대상이 아니라고 못 박는다

현 동작을 유지하고, 화면이 「이 입력은 제출 뒤 자동으로 닫히지 않는다」를 표시한다.
사용자는 명시적으로 폐기한다.

- 변경: 화면 문구와 `consume_supported` 주변 문서화, 시험 1~2건. 가장 작다.
- 근거가 될 수 있는 관점: 명확화의 본체는 **선택값**이고 제출 문자열은 그 파생물이다. 「낸
  것과 저장한 것이 같은가」를 파생물로 판정하는 것 자체가 어색할 수 있다.
- 대가: 사용자는 답변을 제출한 뒤에도 초안을 손으로 정리해야 한다. 일반 HOTL·수정 요청·결정
  의견과 동작이 달라 「왜 이것만」이라는 물음이 남는다.

## 4. 권고

**A 를 권고한다.** 이미 만든 결속 구조(요청 번호·제출 기록·소비 CAS)를 그대로 쓰고 제출
경로를 건드리지 않으면서, 서버가 독립적으로 확인한다는 원칙을 지킨다.

유일한 대가인 표시 문구 이중화는 고정 예제로 잠글 수 있다. 다만 **그 잠금이 실제로 어긋남을
잡는지는 구현 전 미확인**이다 — 양쪽 시험이 같은 예제를 쓰는지 사람이 지켜야 하고, 예제
자체를 한쪽만 고치면 잡히지 않는다. 이 한계를 인정하고 갈 것인지가 결정의 핵심이다.

C 는 변경이 작고 문구 이중화도 없어 실용적이다. 「서버가 독립 확인한다」를 어디까지 요구할
것인가에 따라 갈린다. 그 기준은 제품 오너의 판단 영역이다.

## 5. 결정이 필요한 것

1. 네 갈래 중 어느 것인가.
2. A 를 고를 경우, 고정 예제 잠금으로 충분한가 아니면 더 강한 보증이 필요한가.
3. D 를 고를 경우, 화면에 무엇이라고 표시할 것인가.

결정 후 A 기준 예상은 서버 구현·시험 60~90분, 화면 표시·계약 시험 30~40분이다.
C 는 그보다 짧고 B 는 길다. **착수 전 재산정한다.**
