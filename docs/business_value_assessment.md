# 사업 가치 평가 — AI 업무시스템 팩토리

> **작성일**: 2026-07-26 · **기준 커밋**: `2981f67cb`
> **전제**: 현재 구현분 + `docs/design_org_permission_enterprise.md`(Phase 0~13) + `docs/design_backbone_system_platform.md`(①~⑤)의 **설계가 전부 구현되었다고 가정**한 평가.
> **관점**: 이 프로그램을 전혀 모르는 제3자.
> **성격**: 사내 판단용 냉정한 평가서. 홍보 문구가 아니다.

---

## 1. 이 프로그램이 무엇인가 (세 문장)

업무 담당자가 **한국어로 "이런 게 필요하다"고 말하면**, 여러 AI 에이전트가 요구정의서 → 기획서 → 설계 → 코드 → 검수 순서로 **업무용 소프트웨어나 제조 시뮬레이션을 만들어낸다.**

일반 AI 코딩 도구와 다른 점은, 만들 때 **그 회사의 실제 기준정보**(자재코드·설비 스펙·KPI 산식)와 **사내 문서**를 근거로 삼고, 단계마다 **사람의 승인**을 거친다는 것이다.

완성본은 **부서별 게시판에 올라가고**, 권한 있는 사람만 쓰며, 그 안의 데이터는 **전사 공통 표준으로 정리되어 부서 경계 없이 합쳐진다.**

## 2. 전부 구현됐다고 가정한 전체 그림

| 계층 | 무엇을 하나 |
|---|---|
| **생성** | SW 생성 + 시뮬레이터 생성·시뮬레이션 두 축. 요구 인터뷰 → RFP → PRD → UI → 아키텍처 → WBS → 개발 → 리뷰 → QA → 수용검수 → 매뉴얼 |
| **그라운딩** | 기준정보(M1) 결정론 주입 · 지식허브 RAG · 외부 시스템 실측(M3) · 추적성(REQ↔FR↔파일) |
| **거버넌스** | 계층 조직도 · 부서 권한(상속) · 경영진/시스템관리자/**DA** 3축 분리 · 단계별 HOTL 승인 |
| **중복 방지** | 아이디어 시점 + **PRD 시점 유사도 판정** → 포크·증분 수정 유도 · 계보 추적 |
| **데이터 표준** | 게시 시 스키마 카탈로그 등재 → 표준 자동 매핑 → DA 승인으로 표준 편입 → 전사 정합화 배치 |
| **전사 활용** | 부서 경계 없는 검색 · 부서 결과 롤업·불일치 대조 · 전사 단일 시뮬레이션 · 경영진 Go/No-Go 하달 |
| **기간계(로드맵)** | 앱 간 읽기 연계 → 작업지시 인박스 → 공용 쓰기 저장소 → 워크플로 엔진 |

한 문장으로: **"회사의 데이터·조직·표준에 묶인 사내 업무 시스템 공장."**

## 3. 시장에서 어디에 서 있나

이 제품은 다섯 카테고리를 **동시에 조금씩** 건드린다. 그것이 차별점이자 최대 위험이다.

| 카테고리 | 대표 | 상대 위치 |
|---|---|---|
| AI 코드 생성 | Cursor · Devin · Lovable · v0 · Replit Agent | **정면 승부 시 승산 없음** — 자본·속도·모델 접근성이 다르다 |
| 로우코드/노코드 | OutSystems · Mendix · PowerApps | 유사 목적, 다른 방식(작성 대신 생성). 거버넌스 성숙도는 저쪽이 압도 |
| ERP/MES | SAP · 더존 · 영림원 · Nexplant | 로드맵상 지향점이나 **현재는 같은 리그가 아님** |
| 디지털 트윈/시뮬 | AnyLogic · Plant Simulation · FlexSim | **수치 엔진이 없어** 현재는 정성 추론 수준 |
| 데이터 카탈로그/거버넌스 | Collibra · Alation · DataHub | 설계 방향은 맞으나 실물이 얕음 |

**냉정한 판단**: 개별 카테고리에서 1등 제품과 붙으면 전부 진다.

## 4. 진짜 차별점은 무엇인가

### ★ 차별점은 "AI"가 아니라 "회사 컨텍스트"다

외부 AI 도구가 **구조적으로 할 수 없는 것**이 이 제품의 자리다.

| 외부 AI 도구가 못 하는 것 | 이유 |
|---|---|
| 우리 회사 자재코드 `RM-MHP-001`, 설비 `EQ-FLASH-01`(자용로)을 안다 | 회사 기준정보를 모른다. 알려주려면 **데이터를 밖으로 내보내야 한다** |
| 만든 앱을 구매팀 게시판에 올리고 권한을 건다 | 조직·권한 개념이 없다 |
| 만든 앱의 필드명이 전사 표준을 따르게 한다 | 회사 표준을 모른다 |
| 3년 전 만든 앱과 겹치는지 판정한다 | 회사 자산 이력이 없다 |
| 감사 대응용 추적성(요구→구현→파일)을 남긴다 | 요구 추적 개념이 없다 |

즉 **"AI가 앱을 만든다"는 이미 레드오션이지만, "회사 데이터 표준을 강제하면서 앱을 만든다"는 아직 비어 있다.**

### 실질 차별 자산 5개 (우선순위 순)

1. **결정론적 그라운딩** — 기준정보를 LLM 0콜로 주입. 모델을 바꿔도 자재코드·KPI 산식은 안 흔들린다. **모델 불가지성의 실체**
2. **생성 → 게시 → 표준 정합화 폐쇄 루프** — 만든 앱의 스키마가 자동으로 전사 카탈로그에 등재되고 표준에 매핑된다. **경쟁 제품에 없는 설계**
3. **HOTL 거버넌스** — "AI가 만든 걸 어떻게 믿나"에 대한 답. 규제·감사가 있는 제조 대기업에서 결정적
4. **중복 생성 방지(PRD 유사도 + 포크)** — 사내 앱이 수백 개로 늘 때 유일한 방어선
5. **SW와 시뮬레이션이 같은 기준정보를 공유** — 시뮬 결과를 기준정보로 승격하는 폐쇄 루프 구상

### 차별점이 **아닌** 것 (착각하면 위험)

- **코드 품질** — 범용 모델을 쓰는 한 Cursor/Devin보다 나을 이유가 없다
- **생성 속도** — 다단계 HOTL 때문에 오히려 느리다. 의도된 트레이드오프
- **"AI 에이전트 여러 개"** — 이제 흔하다. 개수는 가치가 아니다

- 진단은 "외부 API 환경 요인"이나, `docs/session_log_2026-07-25.md` §E-2의 **쿨다운 가설**(유료 제공사가 무료와 함께 30분 배제)도 아직 배제되지 않았다

### 5-5. 종합 판정

**"PoC조차 안 됐다"는 부정확하다.** 정확히는:

> **기획 파이프라인(전체의 약 60~70%)은 만점에 가까운 점수로 실증됐고, 실행 구간의 마지막 한 걸음이 남았다.**

## 6. 사업 가치가 성립하는 시나리오 3가지

### A. 자사 내부 DX 플랫폼 (가장 현실적)

제조 대기업 DX 조직이 사내 업무 자동화 수요를 흡수.

- **가치**: 소규모 사내 앱(구매 요청 관리, 설비 점검 체크리스트, 원료 입고 대장)을 외주 SI 대신 사내 생성
- **정량 근거**: 이런 앱 1건 외주 시 통상 수천만 원 + 2~4개월
- **장점**: 고객 확보 불필요, 실패해도 학습 자산
- **전제**: §7 R1(앱 런타임)

### B. 도메인 특화 SaaS (해자가 가장 깊음)

배터리소재·비철제련 등 **특정 업종의 기준정보·표준·시뮬 모델을 미리 채워** 판매.

- **해자**: 도메인 지식팩과 기준정보 사전이 곧 진입 장벽. 범용 AI 도구가 절대 못 따라오는 지점
- **이미 자산이 있다** — `docs/reference/`의 스마트공장 참조모델·KS X 9101·ISO22400·전사 교육자료, `data/master`의 골든레코드 36건
- **가장 차별적이지만 가장 오래 걸린다**

### C. 컨설팅 번들 (수익화가 가장 빠름)

스마트공장 ISP·컨설팅에 얹어 **"설계서로 끝나지 않고 실제 앱까지"** 를 판다.

- 컨설팅의 고질병(보고서만 남고 실행 안 됨)을 정면 공략
- 기존 매출에 얹는 구조라 신규 고객 확보 부담이 적다
- **전제**: §7 R1

## 7. 냉정한 리스크

### R1. ★ 생성된 앱이 실제로 돌지 않는다 (최대 리스크)

프론트는 iframe 미리보기, **백엔드는 부팅 검사 후 폐기**(`tools/backend_smoke_run.py`), 앱 DB는 생성된 적 없음. 현재는 **"데모 생성기"** 이지 업무 시스템 생성기가 아니다.

**시나리오 A·C가 전부 여기에 걸린다.** 5-1의 성공률 개선은 "파이프라인이 도는가"를 증명했지 "쓸 수 있는 물건이 나오는가"를 증명하지 못했다.

### R2. 마지막 한 걸음이 아직 안 넘어갔다

기획은 실증됐으나 **실행 산출물이 라이브러리에 게시된 사례가 0건**이다. 5-5의 "60~70%"는 낙관적으로 읽으면 안 된다 — 남은 30%가 **가치의 전부**다(사람이 쓰는 건 기획서가 아니라 앱이다).

### R3. 시뮬레이션에 수치 엔진이 없다

"몬테카를로"는 프롬프트 지시어일 뿐 전부 LLM 추론(`nodes/universal.py:102`). **디지털 트윈이라 부르기엔 근거가 약하다.** 대외 커뮤니케이션에서 과장하면 신뢰를 잃는다.

### R4. 표준 사전이 3건뿐

데이터 표준이 핵심 차별점인데 실물이 거의 없다. **코드가 아니라 데이터 작업이라 리드타임이 길다.**

### R5. 범위가 너무 넓다

5개 카테고리를 동시 추격 중이고 설계는 Phase 0~13 + 기간계 ①~⑤. **리소스가 분산되면 어느 것도 경쟁력이 안 된다.**

### R6. 책임 소재

AI가 만든 시스템이 제조 현장에서 잘못 계산하면 안전·품질·납기에 직결. HOTL이 완화책이지만 **법적·계약적 책임 구조가 설계에 없다.**

### R7. 유지보수 폭발

앱이 수백 개로 늘면 누가 유지하나. **스키마 진화·데이터 마이그레이션 미해결**(기간계 설계서에도 공백으로 명시).

### R8. 외부 LLM 의존

07-26 실패 5건이 외부 API 504였다. **품질·가용성·가격이 전부 외부 통제 밖**이다. 다중 폴백이 완화책이나 근본 해결은 아니다.

## 9. 결론

### 한 줄 평가

> **설계는 시장의 빈 자리를 정확히 겨눴고, 파이프라인이 원리적으로 작동한다는 것도 방금 증명됐다. 남은 것은 "쓸 수 있는 물건"이 실제로 나오는가 하나다.**

### 포지셔닝 권고

**"AI가 앱을 만들어 줍니다"로 말하지 말 것.** 그 순간 Cursor·Devin과 비교당하고 진다.

**"우리 회사 데이터 표준을 지키는 앱만 만들어집니다"로 말할 것.** 이건 아무도 안 하고 있고, 외부 도구가 구조적으로 못 한다.

### 우선순위 (사업 관점)

### 경영진에게 한 장으로 설명한다면

- **강점**: 외부 AI 도구가 구조적으로 접근 못 하는 "회사 컨텍스트"를 자산화. 설계 깊이가 상당하고 기존 자산 재사용률이 높다. **파이프라인 작동은 실측으로 증명됨**(성공률 87%, 리드타임 19분, 무인 통과)

- **판단 시점**: 실행 구간 완주 1건. 그것이 나오면 시나리오 A를 즉시 검증할 수 있고, 안 나오면 이 평가의 긍정 항목 대부분이 가설로 남는다
