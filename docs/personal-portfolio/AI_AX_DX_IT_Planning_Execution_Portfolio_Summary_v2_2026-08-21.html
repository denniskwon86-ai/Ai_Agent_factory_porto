현업의 문제를 제품 과제로 정리하고,
실제로 운영할 수 있는 구조까지 설계합니다.

저는 제조 현장에서 생기는 업무와 데이터 문제를 제품의 언어로 정리하고, 현업·IT·보안·경영진이 함께 검토할 수 있는 실행안으로 만드는 일에 집중해 왔습니다. AI를 적용하는 것 자체보다, 누가 왜 써야 하는지, 어떤 데이터와 규칙을 믿을 것인지, 운영 과정에서 무엇을 통제해야 하는지를 먼저 봅니다.

현재 공개 가능한 대표 작업은 현업이 필요한 업무 도구를 만들고, 그 과정에서 생기는 데이터를 경영 시뮬레이션과 의사결정에 연결하는 제조기업용 AI 제품 프로젝트입니다. 특정 회사의 데이터나 내부 자료를 사용하지 않고 합성 시나리오로 설계·구현·검증하고 있습니다.

현업 AX와 경영관리 AX를 따로 만들지 않는 제품

현업이 필요한 업무 앱과 시뮬레이터를 만들고, 그 결과를 전사 기준의 데이터·관계·계산·의사결정 흐름으로 연결하는 제조기업용 AI 제품을 설계하고 있습니다.

출발한 문제

  • 업무 변화 때마다 엑셀과 별도 개발이 늘어납니다.
  • 새 시스템은 기존 ERP·MES와 이중 입력을 만들기 쉽습니다.
  • 부서가 만든 데이터는 전사 경영 기준과 연결되기 어렵습니다.
  • AI가 만든 설명과 회사가 책임지는 숫자의 경계가 모호합니다.

제가 맡은 범위

  • 제품 문제 정의와 첫 수직 업무 시나리오 선정
  • 기능 구조, 데이터 흐름, 권한·감사 원칙 설계
  • 화면과 사용자 흐름, 단계별 구현 우선순위 정리
  • AI 기반 개발 작업의 분할·검토·통합·회귀 관리
핵심 판단기능보다 먼저 정한 제품 원칙
기존 데이터 재입력 금지

ERP·MES 등 기존 시스템의 공식 사실을 새 화면에 다시 입력하지 않습니다. 현업 앱은 기존 시스템에 없는 보충 사실이나 새로운 업무 결과를 만드는 데 집중합니다.

현업의 추가 업무가 되면 사용률이 떨어지고, 같은 사실의 정본이 두 개가 되기 때문입니다.

AI와 계산의 역할 분리

온톨로지는 관계와 영향 경로를 찾고, 계산 그래프는 수치를 계산하며, LLM은 결과를 설명하도록 역할을 나눴습니다.

경영 수치를 문장 생성 모델의 추정에 맡기지 않기 위해서입니다.

사용자 제작 앱도 통제

현업이 만든 앱이 조직 범위, 데이터 계약, 권한, 감사 정책을 Host에서 상속하도록 설계했습니다.

빠른 업무 개선이 섀도 IT와 데이터 유출로 이어지지 않게 하기 위해서입니다.

기본 업무 키트

사용자가 빈 화면에서 시작하지 않도록 구매·물류·재고·생산·판매 등 제조 업무의 기본 데이터와 흐름을 준비합니다.

현업 참여가 충분하지 않아도 첫 업무가 돌아가야 하며, 필요할 때만 확장할 수 있어야 하기 때문입니다.

복잡한 과제를 작게 나누되, 마지막에는 하나의 제품으로 맞춥니다.

아래 내용은 일반적인 역량 표현 대신, 대표 프로젝트에서 실제로 다룬 문제와 조치를 요약한 것입니다.

01

현업 앱의 데이터 접근 범위

사용자가 만든 앱이 다른 조직이나 다른 앱의 데이터에 접근할 수 있는 경로를 점검하고, 서버 판정·단기 증명·브라우저 브리지를 같은 계약으로 묶었습니다.

검증: 허용·거부 양쪽 카나리, 다른 앱 식별자 주입, 만료·세션·조직 범위 부정 시나리오.

02

시험 데이터와 경영 결과의 혼입

개발 과정의 샌드박스 자료가 승격·공유·경영 집계에 섞이는 문제를 찾아 격리하고, 시험 자료가 실제 실적이나 인증 데이터로 취급되지 않도록 상태와 경계를 분리했습니다.

검증: 과거 오염 감사, 삭제 없는 격리, 재실행 멱등성, 운영 데이터 불변식 검사.

03

AI가 계산한 것처럼 보이는 숫자

질문을 이해하는 기능과 숫자를 계산하는 기능을 분리했습니다. 데이터 판, 기준시점, 계산식, 결과 지문이 맞지 않으면 답을 만들지 않는 방향으로 계약을 설계했습니다.

검증: 기준선·스냅샷·계산 결과 지문, 관계 승인과 유효기간, 실패 시 0이나 빈 결과로 접지 않는 규칙.

04

초록이지만 믿을 수 없는 테스트

시험이 운영 DB를 읽거나 쓰고도 통과하는 문제를 발견해 테스트 경로를 분리했습니다. 이후에는 회귀 전후의 운영 파일·행·내용 지문을 비교해 검사 자체가 운영 데이터를 바꾸지 않았는지 확인합니다.

검증: 깨끗한 작업공간 재실행, 고의 변이, WAL·SHM 감시, 운영 원장 오염 사고의 포렌식 보관.

05

현업 참여가 낮을 때의 제품 공백

현업이 충분한 데이터를 만들지 못하면 경영 기능도 약해지는 구조를 약점으로 보고, 기존 시스템의 공식 데이터와 기본 업무 키트를 함께 사용하는 방향으로 제품 계획을 보완했습니다.

원칙: 공식 실적은 기존 시스템에서 읽고, 현업은 중복 입력 없이 부족한 사실만 보충하며, 출처와 인증 수준을 구분.

저는 문제를 숨기지 않는 것을 실행력의 일부로 봅니다. 실패나 재작업도 원인, 영향 범위, 보정 방법과 함께 기록해야 다음 사람이 같은 실수를 반복하지 않습니다.
