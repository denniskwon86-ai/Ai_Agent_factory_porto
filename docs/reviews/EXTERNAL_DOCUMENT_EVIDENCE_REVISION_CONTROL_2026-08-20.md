# AI Factory Studio 대내외 문서 증거·개정 통제 기준

작성일: 2026-08-20  
목적: 제품 구현의 실제 상태와 제품소개서·사업제안서·마스터플랜의 주장을 일치시키고,
측정하지 않은 효과나 구현 대기 기능이 완성 기능처럼 배포되는 일을 막는다.

문서 전체 포트폴리오와 정본·파생 관계는
`docs/governance/DOCUMENT_PORTFOLIO_AND_SOURCES_OF_TRUTH_2026-08-20.md`를 따른다.

---

## 1. 운영 원칙

1. **제품 구현을 우선한다.** 문서는 구현을 앞질러 완료를 선언하지 않는다.
2. **설계·구현·검증·실증을 구분한다.** 네 상태는 서로 대체할 수 없다.
3. **합성 데이터와 실제 실적을 구분한다.** `DEMO_CERTIFIED` 결과는 제품 동작 증거이지
   실제 고객 효과나 예측 정확도 증거가 아니다.
4. **LLM·온톨로지·계산 그래프의 역할을 섞지 않는다.** 온톨로지는 의미와 영향 경로,
   계산 그래프는 수치, LLM은 탐색 보조와 설명을 담당한다.
5. **ROI는 기준선과 사후 측정이 있을 때만 결과로 쓴다.** 그전에는 가설·측정 항목·목표로 표시한다.
6. **화면은 촬영 시점과 상태를 표시한다.** 실제 화면, 승인 목표 화면, 구현 대기 화면을 구분한다.
7. **원천 문서·레거시 데이터 접근성도 사실대로 쓴다.** 접근·대사·승인되지 않은 자료를
   이미 통합된 기업 지식이나 공식 실적으로 표현하지 않는다.

## 2. 상태 표기 정본

| 상태 | 외부 문서 표기 | 의미 | 허용되는 주장 |
|---|---|---|---|
| `CURRENT_VERIFIED` | CURRENT PRODUCT · VERIFIED | 제품 배선과 회귀가 있으며 재현 절차가 존재 | 현재 사용할 수 있는 기능 |
| `CURRENT_LIMITED` | CURRENT PRODUCT · LIMITED | 구현됐지만 범위·데이터·운영 조건이 제한됨 | 제한 조건을 함께 쓴 현재 기능 |
| `APPROVED_TARGET` | APPROVED TARGET | 제품 범위와 UX가 승인됐지만 구현·검증이 덜 됨 | 목표와 구현 계획 |
| `DESIGNED_PENDING` | DESIGNED · IMPLEMENTATION PENDING | 상세 설계만 존재 | 설계 의도, 구현 예정 |
| `DEMO_PROVEN` | DEMO PROVEN · SYNTHETIC | 합성 데이터로 종단 동작을 검증 | 제품 동작·재현성 |
| `PILOT_MEASURED` | PILOT MEASURED | 실제 사용자·업무 기준선과 사후값을 측정 | 실측 효과·ROI |
| `NOT_SUPPORTED` | NOT CURRENTLY SUPPORTED | 지원하지 않거나 의도적으로 막음 | 지원 대기 또는 비대상 설명 |

`DEMO_PROVEN`을 `PILOT_MEASURED`로 번역하지 않는다. `CURRENT_VERIFIED`도 고객 가치가
증명됐다는 뜻이 아니다.

## 3. 현재 제품 주장 기준선

아래 표는 대외 문서 개정의 출발점이다. 완료 판정은 코드·회귀·불변식·종단 증거가
함께 있을 때만 갱신한다.

| 제품 주장 | 현재 문서 판정 | 필요한 증거·잔여사항 |
|---|---|---|
| 현업 생성 앱이 Host 인증·권한·데이터 계약을 상속 | `CURRENT_LIMITED` | Host Runtime/PDP 배선은 구현됨. 생성기 전체 연동과 실제 사용 종단은 잔여 |
| 현업 생성 데이터가 전사 경영 데이터로 환류 | `CURRENT_LIMITED` | App Data Plane·Dataset Contract는 구현 중. 공식 실적 전환은 Source Binding·대사·Data Owner 인증 필요 |
| 제조 경영 온톨로지가 영향 경로를 찾음 | `DESIGNED_PENDING`에서 단계별 갱신 | 런타임·승인 기반·`ResolveContext`는 구현. Dataset 범위 색인·Resolver·계약 설치·화면 종단은 잔여 |
| 계산 결과가 재현 가능하고 LLM이 숫자를 만들지 않음 | `CURRENT_LIMITED` | 기존 Planning/Calc Bridge 존재. 온톨로지 `CALC.*` 실행 어댑터와 과거 백테스트는 잔여 |
| 분석이 회의·결정·발간·브리핑으로 이어짐 | `CURRENT_LIMITED` | Decision Package 기반 존재. 온톨로지 경로 어댑터·발간 종단 증거 보강 필요 |
| 실행 후 실제 효과를 측정해 다음 계획에 반영 | `APPROVED_TARGET` | 실제 실적 연결·달성률·효과 측정과 파일럿 기준선 필요 |
| 레거시·문서·외부지표가 통합됨 | `CURRENT_LIMITED` | 연결 계약별로 표기. `docs/reference`는 현재 68건 중 17건 지원, 50건 AIP/IRM 암호화, 1건 변환 필요 |
| 실제 고객 ROI·의사결정 시간 단축 | `NOT YET MEASURED` | 90일 파일럿 전에는 수치 결과 주장 금지 |

## 4. 개정 대상과 순서

### 4.1 1순위 — 제품 및 기능소개서 v3

정본 후보: `docs/product-feature-guide-v2/`

개정 목표:

- 최신 실제 화면으로 교체하고 화면별 촬영 시점·제품 상태를 표시한다.
- 첫 수직 폐루프를 `PRC-02 → LOG-02 → INV-01 → MFG-01 → SLS-01`로 구체화한다.
- 합성 인증판과 실제 실적의 차이를 설명한다.
- 온톨로지 경로·G4 계산·G5 결정 패키지의 역할과 실제 연결 상태를 표시한다.
- 기존 시스템을 대체하는 범위와 보완하는 범위를 분리한다.
- 업무키트를 초기 진입점으로 전면 배치하고 이중 입력 방지 구조를 설명한다.
- 현재/목표/구현 대기 상태 배지를 모든 핵심 주장에 적용한다.

### 4.2 2순위 — 공식 파일럿·제품화 제안서

정본 후보: `docs/business-model/enterprise-business-proposal.html`

개정 목표:

- “전사 플랫폼 도입”보다 “첫 의사결정 폐루프 검증”을 구매 단위로 제안한다.
- 90일 범위, 역할, 데이터 준비, 보안, 중단 조건과 확산 조건을 명시한다.
- EAI 전면 구축이 아니라 파일/Snapshot/승인된 Read 연결부터 시작하는 비용 통제안을 제시한다.
- 업무키트가 기존 시스템의 중복 입력을 만들지 않는 원칙과 Zero Duplicate Entry Gate를 설명한다.
- 비용·효과는 확정값 대신 산정식, 측정 방법, 상·중·하 시나리오로 제시한다.
- 고객이 물을 보안·대사·책임·운영·총소유비용 질문에 답한다.

### 4.3 3순위 — 100일 사업 실행 마스터플랜

정본 후보: `docs/business-model/three-path-field-success-master-roadmap.html`

개정 목표:

- 제품 완성 관문과 사업 검증 관문을 별도 트랙으로 분리한다.
- 3주 시연 MVP의 실제 Gate와 90일 파일럿의 Gate를 연결한다.
- 내부 확산·외부 사업화·제품 리더 경로의 공통 증거와 분기 조건을 명시한다.
- 각 시점의 산출물, 책임자, 필요 권한, 중단 조건과 되돌림 계획을 넣는다.
- 문서·데이터·온톨로지·계산·결정·성과의 증거 사슬을 WBS에 연결한다.

### 4.4 4순위 — 제품 브로셔

정본 후보: `docs/product-brochure/`

브로셔는 위 세 문서의 정본 메시지가 안정된 뒤 압축 개정한다. 새로운 기능 주장을
브로셔에서 먼저 만들지 않는다. 브로셔의 역할은 제품의 핵심 가치와 검증 가능한 차별점을
짧게 전달하는 것이다.

## 5. Claude Code 진행 보고 감사 기준

각 완료 보고는 다음 순서로 검토한다.

### 5.1 사실성

- 보고한 파일·라우트·DB 표·상태·필드가 실제로 존재하는가
- “연결됨”이 단순 모듈 존재인지 실제 호출 배선인지
- 테스트 수가 깨끗한 checkout에서도 재현되는가
- 운영 DB·원장·프로젝트 폴더에 시험 부산물이 생기지 않았는가

### 5.2 통제

- 인증·tenant·조직·entity mode·자원 범위가 모두 판정되는가
- 장애와 미존재가 같은 응답으로 접혀 운영 장애를 숨기지 않는가
- 권한 없는 자원의 존재·개수·사유가 새지 않는가
- 승인 철회·버전 변경·유효기간 종료가 실행 중 세션에도 반영되는가

### 5.3 증거

- 대조군과 부정 시나리오가 있는가
- 변이 검사가 실제 결함을 잡는가
- 전체 회귀와 운영 불변식 전후 비교가 있는가
- 합성 데이터·운영 데이터·실제 고객 효과를 구분했는가

### 5.4 통합과 잔여사항

- 다른 멤버의 미커밋 파일을 섞지 않았는가
- 커밋이 원자적인가
- `origin` 보존 정책을 지켰는가
- 남은 작업의 의존성·차단 조건·전체 진척도를 표시했는가

## 6. 문서별 필수 증거 표

| 주장 | 기능소개서 | 제안서 | 마스터플랜 | 필요한 실제 증거 |
|---|:---:|:---:|:---:|---|
| 현업 앱 생성·실행 | ● | ● | ● | 생성→Preview→Host Runtime 종단 |
| 업무키트 기반 시작 | ● | ● | ● | Kit Instance·Source Binding·Snapshot |
| 이중 입력 방지 | ● | ● | ● | 출처 결정표·Zero Duplicate Entry Gate 회귀 |
| 온톨로지 영향 경로 | ● | ● | ● | 승인 관계·근거·as_of·조직 범위 질의 |
| 결정론적 수치 계산 | ● | ● | ● | 계산식 판·기준선·입력·결과 지문 |
| 회의·결정·발간 | ● | ● | ● | 경로·계산 결과 ID를 가진 Decision Package |
| 실제 효과·ROI | 상태만 | 측정계획 | Gate | 파일럿 전후 기준선과 실제값 |
| 보안·감사 | 통제 요약 | 책임·조건 | Gate | 인증·격리·철회·원장·불변식 회귀 |

## 7. 개정 산출물 완료 조건

각 문서는 다음을 모두 만족해야 배포 후보가 된다.

```text
□ 구현 상태 배지와 실제 코드 상태 일치
□ 합성·목표·실측 수치 구분
□ 최신 제품 화면 사용
□ 온톨로지·계산·LLM 역할 분리
□ 업무키트·이중 입력 방지 설명
□ Legacy 보완/대체/비대상 범위 명시
□ 보안·권한·감사·대사 절차 명시
□ ROI를 측정 전 확정값으로 주장하지 않음
□ HTML 브라우저와 PDF 출력 모두 시각 검증
□ 문서의 날짜·버전·근거 커밋 기록
```

## 8. 현재 작업 순서

```text
구현 보고 상시 감사                 진행
G2 첫 수직 폐루프 증거 축적          진행
기능소개서 v3 주장·화면 갱신         대기 — 핵심 종단 안정 후
공식 파일럿·제품화 제안서 개정        대기 — 기능소개서 정본 후
100일 마스터플랜 개정                대기 — 구현 Gate 재산정 후
제품 브로셔 개정                     마지막 압축 단계
```

이 문서는 제품 완료를 선언하는 문서가 아니라, 문서가 제품보다 앞서 달리지 않도록 하는
개정 통제 기준이다.
