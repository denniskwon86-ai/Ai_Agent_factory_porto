# 업무키트 L2 표준 프로세스 셋업 상세 설계

> 작성: Codex · 2026-09-12 · 상태: 상세 설계안 / 제품 코드 미구현
>
> 사용자 확정 방향: 업무키트 제공 시 L2 표준 프로세스까지 셋업하며, 현업이 변경할 수 있어야 한다.
>
> 상세 정책·식별자·API는 이 방향을 구현하기 위한 제안이다. 운영 승인이나 데이터 사용 승인을 대신하지 않는다.
>
> 진척 기준: 전체 21/40=52.5%, 로컬 18/28=64% 유지. 업무키트 D02는 2/4 유지하며 설계 보강을 중복 가산하지 않는다.

## 1. 결정 요약과 범위

업무키트는 데이터 목록과 앱 청사진뿐 아니라 **수정 가능한 L1/L2 업무지도**를 제공한다. 회사는 빈 화면에서 업무를 분류하는 대신 추천 골격을 확인하고 필요한 부분을 고친다. 앱은 각 업무에서 생성하거나 기존 시스템과 연결한다.

핵심 결정:

1. L1은 메가 프로세스, L2는 목적·입력·결과·책임을 설명할 수 있는 하위 업무다. 이 문서의 레벨은 제품 내부 정의이며 외부 표준의 레벨 번호와 동일하다고 주장하지 않는다.
2. 키트의 표준 원본은 불변·버전 관리하고, 회사 구성은 별도 승인판으로 저장한다. 표준 변경이 회사 구성을 덮어쓰지 않는다.
3. 기존 ECM `process_profile`을 회사 업무지도의 정본으로 확장한다. 키트별 독립 업무지도 DB를 추가하지 않는다.
4. 프로세스와 앱은 다대다다. 업무 노드 설치는 앱 생성·실적 인증·권한 부여·외부 시스템 쓰기를 실행하지 않는다.
5. 같은 업무는 한 번 정의하고, 다른 L1에서는 바로가기로 보여준다. 화면상의 계층은 업무 실행 순서나 조직 권한 계층이 아니다.
6. L2를 변경할 수 있지만 데이터 정의·정책·공식 승인 통제를 임의로 약화할 수는 없다.
7. L2가 없는 상태에서도 자유 요청으로 요구사항 초안을 시작할 수 있다. 공식 연결·릴리스 전에는 대상 업무와 정책을 확정한다.

### 1.1 로드맵 정렬

- 권고 착수 **4번** 데이터 키트와 **7번** 최소 의미 관계의 설계 보강, **10번** Factory/UI 연결 계약에 해당한다.
- 주 관문은 **G2-A/B/C**, 소비 접점은 **G3-B/C**다. 첫 원료 구매 폐루프의 업무와 데이터·앱을 명시적으로 연결한다.
- 모든 산업의 프로세스 완성을 지금 추진하는 것은 아니다. 첫 키트의 상세 설계는 사용자의 이번 명시 지시에 따른다.
- 구현 완료 판정은 G2/G3 연결·현업 검증 이후에 한다. 이번 문서 작성으로 기존 G2-D 인증·실사용 잔여 항목이 완료되지는 않는다.

### 1.2 이번 설계에 포함 / 제외

| 포함 | 제외 |
|---|---|
| L1/L2 템플릿, 회사별 편집·승인, 키트 설치 및 업데이트 | 전체 산업의 표준 프로세스 사전 |
| 프로세스↔데이터 요구↔앱 청사진↔실제 앱 연결 | 모든 L2의 완성된 ERP 화면 |
| 이력·복구·동시 편집·권한·구버전 호환 | 범용 BPMN 실행 엔진, 자동 발주·지급 |
| L3 확장을 위한 참조 경계 | L3 이하 세부 절차의 일괄 선행 구축 |

## 2. 현행 구조와 재사용 판단

이 절은 소스 확인 결과이며, 나머지 절의 새 기능은 설계 제안이다.

| 현행 자산 | 확인한 동작 | 설계에서의 사용 / 보완 |
|---|---|---|
| `core/data_preparation/business_kits.py` | FOUNDATION + BK-01~08, 데이터 접두사 기반 업무 분류 | 키트 식별자 보존. 접두사 분류는 데이터의 주 분류이지 프로세스 정의가 아님 |
| `kit_registry.py` | 운영 프로필과 합성 Starter Package 카탈로그 구분, 판본·지문 관리 | 두 경로에서 동일 프로세스 팩을 참조·검증. 합성 패키지 설치를 운영 셋업과 혼동하지 않음 |

| `CompanySetupPanel.tsx` | 회사/조직별 업무 구성 편집→초안→승인 | L2 확장·변경 영향·차이 검토를 이 진입점에 통합 |

| `profile_resolver.py` | 승인 프로필 상속, 일반 리스트는 교체 병합 | 프로세스 v2에 일반 리스트 병합을 적용하지 않음 |

주의: 현재 flat `nodes` 편집기는 v2 필드를 모른다. 모델에 필드만 추가하면 옛 편집기의 저장이 L2·바로가기·앱 연결을 지울 수 있다. **서버 쓰기 차단과 소비자 전환이 스키마 추가보다 먼저 또는 동시에 필요하다.**

## 3. 사용자 관점의 구조

| 단위 | 예시 | 책임 |
|---|---|---|
| Starter Package | 비철금속 제조 체험 패키지 | 여러 업무키트·샘플·앱·보고서 묶음 |
| Business Kit | BK-01 구매·원료 도입관리 | 관련 업무 템플릿과 데이터·앱 후보 제공 |
| L1 메가 프로세스 | 원료구매 | 업무를 탐색하는 상위 영역 |
| L2 하위 업무 | 구매계획, 원료계약, 주문발주 | 목적·범위·입출력·책임·도구 연결 |
| 세부 절차 / 앱 | 발주 예외 확인 앱, 계약 검토 절차 | 현업이 생성·연계·운영하는 실행 도구 |

Business Kit와 L1은 초기 화면에서는 대체로 대응하지만 ID를 합치지 않는다. 하나의 키트가 여러 L1을 제공하거나 여러 키트가 같은 공통 프로세스를 참조할 수 있다. FOUNDATION은 공통 기반팩이며 L1 업무로 세지 않는다.

### 3.1 원료구매의 기본 표시 구성

| 표시 순서 | L2 카드 | 정본 위치 | 기본 상태 |
|---:|---|---|---|
| 1 | 구매계획 | BK-01 / 원료구매 | 사용 후보 |
| 2 | 공급사 선정·평가 | BK-01 / 원료구매 | 선택 업무; 미선택 시 숨김 |
| 3 | 원료계약 | BK-01 / 원료구매 | 사용 후보 |
| 4 | 주문발주·납기관리 | BK-01 / 원료구매 | 사용 후보 |
| 5 | 선적·도착 추적 | BK-02 / 국제물류 | 연결 업무 바로가기 |
| 6 | 원료입고 | BK-03 / 재고·수급 | 연결 업무 바로가기 |
| 7 | 매입·정산 | BK-07 / 원가·현금 | 연결 업무 바로가기 |

바로가기에도 `연결 업무 · 담당 영역: 재고·수급`처럼 출처를 표시한다. 실제 카드의 상태·담당자·도구는 정본에서 읽는다. 원료입고를 여기서 열어 수정해도 동일한 프로세스가 수정되며, 원료구매 편집 권한만으로 재고 업무를 바꿀 수는 없다.

연결 대상 키트가 없으면 `관련 키트 미설치`로 표시하고 설치/기존 업무 연결을 제안한다. 미설치 업무를 몰래 생성하거나 대상 데이터의 존재를 가정하지 않는다.

### 3.2 L2 분할 기준

- 독립적인 업무 목적과 결과물이 있는가?
- 책임자 또는 검토 역할을 설명할 수 있는가?
- 인접 업무와 주고받는 정보를 설명할 수 있는가?
- 하나 또는 여러 앱/기존 시스템으로 지원할 수 있는가?

버튼·화면·DB 테이블·담당자 한 명을 L2 하나로 취급하지 않는다. `계약서 작성→검토→승인`은 원료계약의 세부 절차이며 처음부터 별도 L2로 강제하지 않는다. 구매계획과 계약의 진행은 반복·병렬일 수 있으므로 카드 순서를 실행 순서로 강제하지 않는다.

## 4. 초기 L2 표준 후보 카탈로그

아래는 현재 비철금속 키트의 **8개 L1 / 29개 정본 L2 설계 후보**다. 바로가기는 29개에 중복 가산하지 않는다. 표준 원본으로 출하하기 전 도메인 책임자 검수를 거친다. 외부 표준을 그대로 복제하거나 인증받은 모델이라는 뜻이 아니다.

`연결 후보`는 계약/청사진이 존재한다는 뜻이지 실행 가능하다는 뜻이 아니다. `상세 계약 보완`은 관련 데이터가 있어도 해당 업무의 입력·결과·판정 계약이 충분하지 않음을 뜻한다.

### 4.1 원료구매 핵심 업무의 상세 정의

| L2 | 시작 조건 / 주요 입력 | 결과 / 연결 대상 | 책임 역할 후보 | 앱 연결 후보 |
|---|---|---|---|---|
| 구매계획 | 계획 주기 또는 부족 위험; 생산 소요·가용재고·기발주·리드타임 | 기간/품목별 조달계획 후보와 검토 근거 → 계약·발주 | 구매계획 담당 / 구매 책임자 | APP-01, APP-03; 전용 계획 저장은 추가 계약 필요 |
| 공급사 선정·평가 | 신규 소싱·재평가; 공급사 기준·견적·평가기준 | 선정/유지/제외 후보와 근거 → 계약 | 구매 담당 / 선정 책임자 | APP-05는 관련 근거; 평가 앱 완성으로 간주 금지 |
| 원료계약 | 공급사·수요 범위 확정; 품목·수량·가격 기준·기간·거래조건 | 계약·가격조건·유효기간 → 발주·원가 | 구매 담당 / 계약 승인권자 | APP-01, APP-04 |
| 주문발주·납기관리 | 계약 또는 허용된 구매 근거; 수량·납기·도착지 | 발주 및 변경 이력·납기 예외 → 선적·입고 | 구매 담당 / 발주 승인권자 | APP-01, APP-05; 운영계 발주 쓰기 별도 |
| 원료입고(연결) | 도착·검사 자료·발주 참조 | 인수/입고/검사/가용 상태를 구분한 결과 → 재고·생산·정산 | 창고 담당 / 입고 책임자 | APP-02, APP-03 |
| 매입·정산(연결) | 계약·발주·입고·청구 참조 | 매입/채무/정산 상태 → 현금흐름 | 재무 담당 / 재무 승인권자 | APP-04 |

역할 후보는 안내이며 실제 사용자·조직에 자동 배정하지 않는다. 납품·입고·검사합격·가용재고·지급은 서로 다른 사건이며 이름이 비슷하다고 같은 완료 상태로 합치지 않는다.

## 5. 패키지 계약

### 5.1 배치와 버전

새 Starter 판본 후보 `1.1.0`에 `processes/l2-process-pack.json`을 추가하고 manifest가 참조한다. 기존 `1.0.0` 파일·등록 지문·설치 인스턴스는 변경하지 않는다. 실제 배포 판번은 릴리스 시 확정한다.

운영 `docs/data-kits/*.kit.json`에도 동일한 프로세스 팩 참조 형식을 사용한다. 경로가 다르더라도 내용을 재작성한 두 정본을 만들지 않고 하나의 승인 아티팩트와 digest로 공급한다. Starter의 회사·샘플 데이터 정보는 운영 프로세스 템플릿에 섞지 않는다.

manifest 확장 제안:

```json
{
  "process_pack": {
    "pack_id": "afs.manufacturing.materials-processes",
    "version": "1.0.0",
    "schema_version": 1,
    "path": "processes/l2-process-pack.json",
    "sha256": "<배포 시 계산하는 원문 SHA-256>",
    "requires_process_profile_schema": 2,
    "setup_policy": "INCLUDED_REVIEW_REQUIRED"
  }
}
```

예시는 필드 계약이며 현재 읽을 수 있는 배포 파일이 아니다. 검증기는 경로 탈출·외부 URL·지원하지 않는 schema·누락 파일·digest 불일치·미정의 부모/참조를 거절한다. 프로세스 팩을 선언한 키트는 팩 해석 실패 시 데이터만 설치하고 성공으로 처리하지 않는다.

### 5.2 ProcessTemplate 필수 항목

| 항목 | 의미 / 규칙 |
|---|---|
| `template_key`, `template_revision` | 공급자 namespace 안의 안정 식별자와 개정. 표시명에서 생성하지 않음 |
| `level`, `parent_template_key` | L1/L2; L1 부모 없음, L2 정본 부모 하나 |
| `business_kit_id`, `label`, `description` | 공급 키트·기본 표시명·범위 |
| `purpose`, `trigger`, `input_roles`, `output_roles` | 무엇을 받고 무엇을 남기는 업무인지 설명 |
| `suggested_responsible_roles` | 직무 후보; 계정·권한 부여 아님 |
| `default_selected`, `applicability_tags` | 기본 사용 후보·국내/수입 등 명시 선택 조건 |
| `data_requirements` | 논리 정보 요구 + 실제 dataset 계약 후보 + 필수 조건 |
| `suggested_blueprint_refs` | `(kit_id, kit_version, app_id)` 후보; 앱 생성 명령 아님 |
| `relations`, `shortcut_refs` | 정보 전달·관련 업무와 다른 L1에서의 표시 참조 |
| `source_refs`, `review_status` | 저작 근거·도메인 검토 상태; 외부 모델이면 별도 사용조건 확인 |

필수 정보에 대응하는 데이터 계약이 없으면 `unresolved_requirement`로 남긴다. 예를 들어 구매계획 저장 계약이 없는 것을 PRC-02(발주)로 대신 채우지 않는다. 계약의 존재, 데이터 연결, 인증, 실사용 가능 여부는 각각 별도다.

### 5.3 설치 당시 원본의 불변 보존

현행 `DataPreparationStore.upsert_kit_version()`은 같은 `(kit_id, version)`의 profile과 fingerprint를 갱신할 수 있다. 앱 경로의 `_kit_profile_or_503()`도 현재 등록부를 조회한다. **현재 버전 문자열만으로는 설치 당시 표준이 고정되지 않는다.**

- v2 팩과 연결에 사용한 manifest/profile 원문을 digest 기반 불변 아티팩트로 보존한다. 등록부는 검색 인덱스이며 실행 기준선이 아니다.
- 새 v2 등록은 동일 ID/판번의 동일 digest만 멱등 허용한다. 다른 digest는 `IMMUTABLE_VERSION_CONFLICT`로 거절하고 새 판번을 요구한다. 레거시 갱신 경로를 검토 없이 일괄 변경하지 않는다.
- 설치 참조에 kit ID/판번뿐 아니라 kit artifact digest와 process pack digest를 기록하고 정확한 원문을 읽는다.
- 팩·데이터 요구·앱 blueprint의 정확한 구성요소 참조를 bundle digest로 검증한다. 다른 판 조합은 §9.2의 명시적 호환성 검증 없이는 허용하지 않는다. 등록부가 바뀌어도 설치판을 최신판으로 대체하지 않는다.
- 최초 설치 원본과 마지막 수용 표준 원본을 모두 보존한다. 3-way 비교 B인 마지막 수용 표준을 찾지 못하면 업데이트를 차단한다. 현재 등록부를 B로 대체하지 않는다.
- 기존 인스턴스의 원문과 지문이 불일치하면 이관 보류로 표시한다. 기존 instance fingerprint를 일괄 전진시키지 않는다.

## 6. 회사별 데이터 모델

### 6.1 정본과 식별자

회사 업무 구성은 ECM `enterprise_profiles`의 `profile_kind=process_profile`, `payload.schema_version=2`인 **불변 승인판**으로 저장한다. 새로운 독립 프로세스 운영 DB는 만들지 않는다.

| 식별자 | 수명 / 용도 |
|---|---|
| `configuration_id` | 한 회사·범위·모드의 업무지도 식별자; 개정해도 유지 |
| `profile_id` | ECM의 개별 구성판 ID; 새 승인판마다 새 ID |
| `process_id` | 회사 업무의 안정 ID; 이름·순서·담당자 변경 시 유지 |
| `template_key` | 표준 업무와의 의미 대응; 다른 회사 비교의 후보 기준 |
| `placement_id` | 정본/바로가기의 화면 배치 식별자; 업무 ID와 별개 |
| `kit_instance_id` | 데이터 키트 설치 인스턴스. 업무지도/회사/앱 ID와 혼용 금지 |

내부 ID는 기존 ID 할당 체계를 재사용·확장한다. 이미 존재하는 ThreadNode `key`는 마이그레이션 시 process_id로 보존하고, 사용자에게 보이는 코드/이름과 분리한다. 바인딩은 명칭이 아닌 `(configuration_id, process_id)`를 가리킨다. 앱·증빙에는 사용한 `profile_id`도 고정한다.

`schema_version`은 payload 형식, profile `version`은 서버가 발급하는 구성 개정번호다. 둘을 혼용하거나 사용자가 임의 개정번호를 정하지 않는다. 승인 후 ARCHIVED로 전환한 판도 영구 불변이며 구 승인 API로 재활성화하지 않는다. 복원은 새 판으로 만든다.

### 6.2 문맥 키와 v2 저장 항목

승인 head의 유일 경계는 `(tenant_id, context_root_id, entity_mode, scope_node_id, configuration_kind)`다. `context_root_id`는 선택한 회사/가상기업/경쟁사 루트이며 서버가 검증한다. `scope_node_id=''`는 **그 문맥 루트 전체**를 뜻하고 무제한 접근을 뜻하지 않는다.

현재 `EnterpriseProfile`에는 entity_mode/context_root_id 경계가 없으므로 이것은 추가 설계다. payload에만 넣고 기존 tenant/scope 승인 쿼리를 그대로 쓰면 REAL과 VIRTUAL의 승인판이 서로 보관 처리될 수 있다. head와 저장·목록·승인·상속 쿼리 모두 같은 경계를 강제해야 한다.

`payload` 주요 구조:

| 필드 | 내용 |
|---|---|
| `schema_version`, `configuration_id` | 버전과 안정 지도 ID |
| `base_profile_id`, `base_fingerprint` | 편집 시작 시점의 승인판; 동시 수정 검사 |
| `template_sources[]` | 최초 설치 원본과 마지막 수용 표준의 ID·버전·digest, 선택 업무키트 |
| `nodes[]` | L1/L2 정본 업무: ID·부모·정의·origin·사용 여부·담당 참조 |
| `placements[]` | 정본 카드·다른 L1의 바로가기·표시 순서·개별 숨김 |
| `relations[]` | `informs`, `handoff_to`, `related_to` 등 의미 관계; 자동 실행하지 않음 |
| `bindings[]` | 데이터 요구, 실제 키트/앱/시스템 참조; 관계 종류 명시 |
| `local_overrides[]` | 사용자가 바꾼 필드·명시적 미사용·이유·기준 표준판 |
| `migration_map[]` | 구 ID→새 ID 또는 분리/통합 대응; 감사·이전 연결 설명 |

원본 데이터·데이터셋 스키마·비밀·실제 승인 정책 본문은 복사하지 않는다. 승인된 원래 자산을 참조한다. `bindings.kind`는 `DATA_REQUIREMENT`, `DATA_INSTANCE`, `APP_BLUEPRINT`, `APP_RELEASE`, `EXTERNAL_SYSTEM`, `KNOWLEDGE_REF`를 구분한다.

노드·관계·바인딩에는 근거/source_ref, 기록 시각과 적용 시점을 남긴다. 첫 구현은 승인 시점부터 적용하며 예약·소급 적용은 지원하지 않는다. 과거 사건은 당시 고정 profile_id로 설명하고 현재 승인판으로 과거 이력을 다시 쓰지 않는다.

### 6.3 ECM 안에 필요한 보조 저장 구조

프로필 payload가 업무 내용의 유일 정본이다. 같은 ECM DB 안에 다음 메타데이터/작업표를 추가한다.

- `enterprise_process_heads`: configuration_id·문맥 키·active_profile_id·head_version. 문맥 유일 제약과 CAS 대상.
- `enterprise_process_changes`: change_id·base_head_version·draft_profile_id·patch·작성자·사유·검토·상태·request_fingerprint. 재시도와 승인 대상을 고정.
- `enterprise_process_installations`: operation_id·kit_instance_ref·문맥·plan_digest·단계·오류·멱등키. 업무 본문은 저장하지 않음.
- `enterprise_process_outbox`: 승인/설치 사건의 불변 event_id·payload digest·전송 상태. 감사·이벤트 복구용.

승인 트랜잭션에서 새 profile 판, head CAS, 변경 상태, 감사 outbox를 함께 저장한다. 설치 승인이라면 같은 트랜잭션에서 installation의 `APPLIED`, `applied_profile_id`, `change_id`, `applied_at`도 확정한다. 업데이트라면 마지막 수용 표준과 override 기준판, 검증된 바인딩 참조 집합도 함께 확정한다. 감사 기록의 로컬 영속화 실패 시 승인은 실패한다. 외부 원장/이벤트 전달은 멱등 재시도하며 전송 대기를 완료 송신으로 표시하지 않는다.

설치 완료 이력과 현재 구성 head는 별개다. 후속 정상 개정으로 head가 달라져도 과거 operation의 APPLIED를 취소하지 않는다. 재개는 operation에 고정된 applied_profile_id와 감사 사건으로 이전 성공을 확인한다. 현재 유효 업무 여부는 현재 head로 판정한다.

### 6.4 상속과 회사별 차이

첫 구현은 회사 기본 구성과 명시적으로 선택한 조직 변형을 지원한다. 일반 profile resolver의 `nodes` 리스트 교체 병합을 재사용하지 않는다.

1. 상위 승인판을 정확한 profile_id로 고정한다.
2. process_id 기준으로 검증된 변경 명령을 적용해 완전한 유효 업무지도를 만든다.
3. 부모·참조·문맥·미사용·권한 검증 후 별도 승인판으로 저장한다.
4. 런타임은 이 완전한 승인판을 읽는다. 요청마다 최신 상위 구성과 임의 병합하지 않는다.
5. 상위 변경은 하위 구성의 업데이트 후보가 된다. 검토 전까지 하위 운영 구성을 바꾸지 않는다.

해석 응답에 sources/profile_id/digest를 반환한다. 상속 없음과 조회 실패는 다르다. v2 적용 조직에서 v2 읽기 실패 시 옛 평면 모델이나 조직도를 업무지도처럼 대체하지 않는다.

## 7. 키트 설치·적용 흐름

### 7.1 사용자 흐름

1. 현재 회사·조직·REAL/VIRTUAL 문맥과 키트 판본을 확인한다.
2. 설치 미리보기에서 제공 L1/L2, 선택 업무, 연결 업무, 데이터 요구, 앱 후보를 확인한다.
3. 기존 업무가 있으면 동일 template_key 매핑을 제안한다. 이름 유사성은 후보일 뿐 자동 합치지 않는다.
4. 적용 업무·표시명·기존 시스템·담당 역할 후보를 조정한다. 나중에 해도 되는 항목은 미지정으로 둔다.
5. `구성 초안 생성` 또는 권한이 있는 사용자의 `검토 후 적용`을 실행한다.
6. 설치 결과에 `골격 구성`, `업무 적용 승인`, `데이터 준비`, `앱 연결`을 따로 표시한다.

담당자가 없거나 데이터가 부족해도 골격 초안은 만들 수 있다. 적격 업무 구성 승인자는 필요하지만, 미해결 데이터 계약·도구·업무 담당 역할은 승인된 지도에도 미준비 상태로 남길 수 있다. **APPLIED는 업무지도 승인이지 데이터/앱 실행 가능 판정이 아니다.** 필수 데이터·인증·실행 계약이 없으면 해당 실행 단계만 막는다. 표준이 있다는 이유로 담당자나 인증자를 만들어 넣지 않는다.

제안 권한만 있는 현업은 데이터 인스턴스를 만들지 않고 셋업 제안만 저장한다. 설치 실행권한이 있는 담당자가 명시적으로 인수하여 진행한다. 원 작성자와 설치 행위자는 따로 기록하며 각 단계는 현재 행위자의 권한으로 판정한다.

### 7.2 설치 상태와 멱등성

설치 작업 상태 제안: `PLANNED → PREPARING → DRAFT_READY → AWAITING_APPROVAL → APPLIED`. 제안만 가능한 사용자의 작업은 `AWAITING_INSTALLER`에서 적격 설치자 인수를 기다린다. 단계별 `FAILED_RETRYABLE`, 복구 불가능한 `FAILED_BLOCKED`, 미적용 `CANCELLED`를 구분한다. `DRAFT_READY`는 적용된 업무지도가 아니다. APPLIED 이후에도 데이터/앱은 미준비일 수 있다.

- 멱등키 범위: `(tenant, context_root, mode, scope, client_request_id)`.
- 같은 키·같은 요청 digest는 같은 operation/result를 반환한다. 같은 키·다른 요청은 409.
- 선택한 키트 판본·팩 digest·현재 head·기존 매핑을 plan_digest에 포함한다. 대상이 달라지면 재미리보기한다.
- 같은 키트의 반복 데이터 설치를 새 업무지도의 요청으로 해석하지 않는다. 동일 문맥에 이미 연결된 프로세스는 재사용 후보로 제시한다.
- 여러 키트의 같은 template_key는 같은 의미/호환 판본일 때만 재사용한다. 불일치 시 충돌을 숨기지 않는다.

### 7.3 서로 다른 DB 사이의 실패 처리

DataPreparationStore와 ECM은 현재 서로 다른 DB다. 하나의 트랜잭션으로 설치 전체가 원자적이라고 주장하지 않는다.

1. ECM에 plan_digest와 operation_id를 영속화하고 예약한다.
2. 데이터 저장소에서 operation_id 유일 키로 인스턴스를 생성 또는 재조회한다. 기존 인스턴스 연결이면 문맥·판본·접근권한을 검증한다.
3. ECM에서 인스턴스 참조, 템플릿 매핑, 프로세스 초안을 한 트랜잭션으로 저장한다.
4. 사용자 승인 시 §6.3의 ECM 원자 승인으로 head와 operation=APPLIED를 함께 전환한다. 데이터 인증/앱 생성은 수행하지 않는다.
5. 인스턴스만 만들어지고 실패했다면 `설정 미완료`로 노출하고 같은 operation_id로 재개한다. 재시도가 인스턴스·L2를 중복 생성하면 안 된다.
6. ECM 적용 후 결과 알림이 실패해도 적용 자체를 되돌리거나 중복 적용하지 않는다. outbox를 재전송한다.

현재 인스턴스 생성은 즉시 `active`로 저장하므로 v2 소비자는 이 값만으로 업무 셋업 완료를 판단하지 않는다. 새 설치에서 파생되는 공식 프로세스 문맥은 APPLIED 이후 발급하며, 실제 데이터/앱 실행은 §10·§12의 별도 게이트도 통과해야 한다. 미완료 설치에서도 데이터 준비·요구사항 초안은 가능하다. 기존 인스턴스에 프로세스를 추가하는 실패가 기존 앱의 독립적인 정상 실행을 중단시키지는 않는다.

두 저장소를 가로지르는 키트 전체 삭제/롤백은 자동 보상하지 않는다. 사용자가 입력한 데이터가 있을 수 있으므로 생성된 초안·인스턴스를 보존하고 연결 상태를 복구한다. 설치 완료 판정의 정본은 operation 상태와 실제 ECM head이며, 인스턴스 존재만으로 완료를 표시하지 않는다.

### 7.4 합성 체험과 운영 셋업

- 현재 Starter `1.0.0`은 VIRTUAL/SYNTHETIC 체험 자산이다. 이것을 REAL/ACTUAL로 복제해 운영 설치했다고 부르지 않는다.
- 운영 셋업은 데이터가 없는 같은 업무 템플릿을 적용하고, 실제 원천 바인딩을 별도로 승인한다.
- 가상기업 복제 시 업무 정의는 복사 가능하지만 live connector, 승인 토큰, 데이터 권한, 실제 책임자 서명을 자동 복사하지 않는다.

| 변경 | ID / 과거 이력 | 적용 규칙 |
|---|---|---|
| 이름·설명·표시 순서 | process_id 유지, 이전 이름 보존 | 낮은 위험 변경; 위임된 편집/발행 권한 내 적용 |
| 바로가기 추가·숨김 | 정본 업무 불변 | 대상 조회 권한 확인; 바로가기는 권한을 넓히지 않음 |
| 새 L2 추가 | 새 process_id, origin=CUSTOM | 기존 업무와 중복 후보 제시; 강제 병합 금지 |
| L2 미사용 | tombstone/disabled 유지 | 필수 앱·데이터·연결 영향 확인 후 승인; 조용한 분모 축소 금지 |
| 부모 L1 이동 | process_id 유지 | 같은 문맥 안에서만; 책임/바로가기/참조 영향 확인 |
| 담당 조직·책임 변경 | 업무 ID 유지 | 업무 책임만 변경; 데이터 권한과 데이터 오너 변경은 별도 |
| 업무 분리 | 새 ID 여러 개 + split_from | 기존 앱/결정은 이전 ID 유지; 미래 연결의 이전 계획 필수 |
| 업무 통합 | 새 ID + merged_from 여러 개 | 기존 업무 보관; 기존 데이터·앱을 삭제/합산하지 않음 |
| 다른 회사로 복사 | 새 configuration/process ID | 표준 대응만 유지; 원천·권한·운영 바인딩 복사 금지 |
| 표준 연결 해제 | 회사 ID 유지, template_ref 이력 보존 | CUSTOM 전환과 업데이트 제외를 명시적으로 승인 |
| 삭제 | 승인·참조된 업무는 보관 처리 | 미발행·미참조 초안만 폐기 가능; 감사는 유지 |

개인 숨김은 개인 표시 설정이며 회사 표준의 미사용과 분리한다. 회사별 추가 업무도 합법적인 업무이며 표준 대비 차이를 오류로 표시하지 않는다. 대신 `표준`, `회사 수정`, `회사 추가`, `연결 업무`, `미사용`을 구별한다.

프로세스 비활성화는 기존 앱·운영계 업무를 자동 정지시키지 않는다. 새 연결·생성은 막고 기존 연결의 유지/전환 계획을 요구한다. 안전상 실행을 중단해야 하는 경우는 별도 앱/정책 중지 절차를 사용한다.

## 9. 표준 업데이트와 되돌림

### 9.1 3-way 비교

비교 입력: **마지막 수용 표준 B / 현재 회사 구성 C / 새 표준 N**. 첫 업데이트의 B는 설치 당시 표준이며 이후에는 직전 수용 표준이다. 최초 설치 원본은 별도로 영구 보존한다. 표준 전체 덮어쓰기나 사용자 변경분 삭제 초기화는 금지한다.

| 비교 결과 | 제안 |
|---|---|
| 회사가 안 바꾼 필드만 표준에서 변경 | 새 기본값 채택 후보 |
| 회사만 변경 | 회사 값 유지 |
| 양쪽이 같은 결과로 변경 | 충돌 없음 |
| 같은 필드를 서로 다르게 변경 | 사용자 선택 필요 |
| 표준에 새 업무 추가 | 사용 후보로 제안; 자동 생성·자동 활성화 금지 |
| 표준에서 업무 폐기 | 기존 업무·앱·이력 보존, 후속 업무 대응 제안 |
| 회사가 명시적으로 미사용 | 미사용 유지; 새 표준의 default_selected로 되살리지 않음 |
| 분리·통합된 회사 업무 | 자동 remap 금지; migration_map 검토 |

목록은 위치가 아니라 template_key/process_id로 비교한다. 회사가 기존 순서를 수정했다면 상대 순서 변경도 충돌로 취급한다. 필드 삭제·명시적 빈 값·상속값은 서로 다르므로 override에서 `SET`, `CLEAR`, `DISABLE`, `RESET_TO_TEMPLATE`를 구분한다.

N 수용 시 사용자가 유지한 회사 값은 N을 기준으로 override를 다시 계산하고, 마지막 수용 표준 포인터를 N으로 전진시킨다. 두 포인터/override 변경은 승인판과 같은 트랜잭션이다. 각 팩은 전체 판 단위로 수용하며 일부 업무의 기존 값을 유지하는 선택은 새 기준판 위의 override로 표현한다. 한 번의 미리보기에서 여러 팩을 묶었다면 전체 결과를 하나의 승인판으로 적용한다.

### 9.2 승인과 운영 영향

업데이트 미리보기에 변경 업무·앱·데이터 요구·영향 조직·기존 불일치를 표시한다. 승인 전에는 현 승인판과 실행 앱을 유지한다. 승인된 plan_digest와 현재 head가 달라지면 409로 재검토를 요구한다.

표시명 변경은 앱 코드 재생성이나 데이터 계약 재승인 사유가 아니다. 의미·입출력·데이터 요구·capability가 바뀌면 관련 앱 계약 차이를 별도로 검토한다. 키트 전체 판번 상승만으로 7개 앱을 일괄 재생성하지 않는다.

업데이트 계획에는 새 팩뿐 아니라 `target_bundle_digest`, 구성요소별 고정 참조와 각 바인딩의 `KEEP`, `REPLACE`, `UNRESOLVED_REQUIREMENT` 결정을 포함한다. 기본은 **프로세스만 업데이트**하고 기존 데이터 인스턴스·계약·앱 릴리스의 digest를 유지하는 것이다.

- KEEP은 새 프로세스의 입출력/데이터 요구와 기존 바인딩이 호환될 때만 실행 가능 상태를 유지한다. 호환 검증 근거를 plan_digest에 포함한다.
- 호환되지 않으면 기존 릴리스 자체를 삭제/정지하지 않고, 새 프로세스와의 연결을 `REVALIDATION_REQUIRED`로 둔다. 업무지도 승인은 가능하지만 그 조합의 실행 문맥 발급은 막는다.
- REPLACE는 별도 계약·권한·데이터 검증을 통과한 새 자산을 먼저 준비한 뒤 해당 참조 집합 전체를 ECM head와 한 번에 활성화한다. 외부 DB를 같은 트랜잭션에서 변경한다고 가정하지 않는다.
- 실제 자산 참조는 존재·접근 가능해야 하고 검증 결과의 버전/지문이 계획과 같아야 한다. 승인 시 변동/실패하면 적용하지 않고 재검토한다. 이후 보류/권한 회수는 실행 시 동적 검사한다.
- 참조 교체 준비가 실패하면 현 head와 기존 실행 연결은 유지한다. 이름만 같은 최신 자산으로 폴백하지 않는다.

### 9.3 되돌림

이전 승인판을 지우거나 head만 과거로 덮지 않는다. 이전 내용을 바탕으로 **새 복구판**을 만들고 현존 앱·바인딩·정책과 재검증 후 승인한다. 과거에 허용되던 데이터가 현재 보류되었다면 복구로 보류를 해제하지 않는다. 감사와 과거 계산·결정의 고정 참조는 유지한다.

## 10. 앱 생성·기존 시스템 연결

### 10.1 업무 카드의 기본 행동

- `연결된 도구 열기`: 접근 가능한 기존 앱/시스템만 표시한다.
- `앱 만들기`: 현재 L2를 중심으로 요구사항 초안을 시작한다.
- `기존 시스템 연결`: 승인된 connector/query 계약 후보를 선택한다. 자격증명을 업무지도에 저장하지 않는다.
- `업무 구성 수정`: 권한에 따라 직접 초안 편집 또는 변경 제안을 한다.
- `데이터 준비`: 사용 중인 키트 인스턴스의 준비도와 차단 이유로 연결한다.

하나의 L2에 여러 앱, 하나의 앱에 여러 L2를 연결할 수 있다. 앱 ID는 패키지마다 반복될 수 있으므로 `APP-01` 문자열만 저장하지 않고 kit_instance_id·프로젝트/앱/릴리스 식별자까지 결속한다.

### 10.2 생성기에 전달하는 문맥

서버가 `ProcessContext`를 구성한다. 클라이언트의 설명문이나 process_id만 믿지 않는다.

- configuration_id, process_id 목록, 고정 profile_id, template_sources, 문맥 키.
- 업무 목적·입력·결과·인접 업무·책임 참조·관련 기존 앱.
- 데이터 요구와 선택한 instance/binding/snapshot 참조, 준비도·usage hold·미해결 계약.
- 허용된 capability/정책 참조, 요청 사용자와 문맥 검증 결과.
- 요구사항 출처·사용자 확인·표준 대비 변경사항.

승인된 명세·문서에 들어 있는 자연어는 요구사항 데이터이며 시스템 지시나 권한 근거가 아니다. 앱 생성기는 이 문맥을 근거로 후보를 만들되 필요한 데이터나 인증값을 지어내지 않는다.

### 10.3 데이터가 없는 골격에서 시작할 때

`요구사항 초안 → 데이터/계약 보완 → 실행 계약 초안 → 별도 승인 → 생성/릴리스 검증 → 연결`로 분리한다.

현재 `kit_app_contract.draft()`는 인증판에서 스키마를 얻으므로, L2 선택 직후 이를 무조건 호출하지 않는다. 데이터가 없으면 Solution Blueprint/요구사항 수준에서 저장하고 `계약 준비 필요`로 남긴다. Mock UI가 필요한 경우 별도 SYNTHETIC 실험으로 표시하며 운영 앱 준비도와 합치지 않는다.

### 10.4 문맥 고정과 변경 검사

앱 계약에 승인된 `process_context`의 의미 지문을 포함하는 명시적 schema 확장이 필요하다. 기존 엄격 schema에 임의 필드를 끼워 넣거나 labels에 숨기지 않는다.

- `configuration_fingerprint`: 표시명·배치 등을 포함한 전체 승인판 추적용.
- `process_semantic_fingerprint`: 목적·입출력·데이터 요구·정책 참조·선택 업무 ID 등 생성 의미용. 표시 순서·별칭 제외.
- 앱 계약 지문은 해당 의미 문맥을 포함해 계산하며 계약 schema 버전을 함께 올린다.
- 생성 시작과 릴리스 승인 시 현재 변경 영향을 재확인한다. 의미가 달라졌으면 재검토하고, 표시만 달라졌으면 기존 계약을 보존한다.
- 실행 시 데이터 접근은 항상 현재 Host 정책·인증·usage hold를 확인한다. 과거 프로세스 승인판을 고정했다고 과거 권한을 복원하지 않는다.

기존 앱은 자동 수정하지 않는다. 명시적 업무 연결은 기존 app/release ID를 보존하는 메타데이터 작업이며, 기능 변경과 분리한다.

## 11. UI 상세

### 11.1 업무키트 설치 패널

기존 KitOperationsPanel에 `제공 업무`와 `회사에 적용할 구성` 단계를 추가한다. L1별 L2 목록, 표준/회사 수정/연결 업무 배지, 선택 업무, 데이터 계약 보완 표시를 제공한다. 최종 확인에는 추가·재사용·미사용·충돌·미설치 연결 업무 개수를 표시한다.

기존 사용자의 업무가 이미 있으면 기본 동작은 `기존 업무에 연결` 제안이다. 전체 초기화 버튼을 기본 동작으로 두지 않는다.

### 11.2 경영 홈 → L1 → L2

경영 홈은 기존 L1 중심 시야를 유지한다. L1을 선택하면 해당 L2 목록/상세 패널을 연다. 전사 화면에 29개 L2를 한꺼번에 펼치지 않는다. 선택한 업무의 URL/라우팅 상태에 configuration_id/process_id를 넣어 새로고침·뒤로가기·직접 링크가 유지되게 한다. 실제 전역 라우트 연결은 통합 담당자가 수행한다.

L2 카드에는 다음을 표시한다.

- 업무명과 한 줄 목적, 정본 위치/연결 업무 여부.
- 책임 조직·담당 역할 또는 `담당 미지정`.
- 구성 상태와 표준 대비 변경 여부.
- 데이터 상태·기준시점·보류 사유, 앱/시스템 연결 상태.
- 다음 행동 하나를 우선 표시하고 나머지는 상세에서 제공.

### 11.3 회사 설정 → 업무 구성 편집

기존 ThreadTab을 v2 편집기로 확장한다. L1/L2 추가·순서 변경·미사용·바로가기·관련 데이터·앱 후보 편집, 변경 diff, 영향받는 업무/앱 확인, 승인/반려/복구를 제공한다. 모바일·키보드 사용자를 위해 드래그 외에 위/아래 이동 버튼을 유지한다.

오류 시 편집 중 값을 잃지 않는다. 회사/모드 전환 시 미저장 변경 확인과 캐시 분리를 수행하고 이전 회사의 자료를 잠깐이라도 표시하지 않는다.

### 11.4 상태와 진척 표시

| 상태 축 | 표시 예 | 해석 |
|---|---|---|
| 골격 구성 | 표준 제공 / 회사 초안 / 승인 적용 / 미사용 | 업무 정의의 준비 상태 |
| 데이터 | 미연결 / 준비 중 / 사용 가능 / 보류 / 확인 실패 | 실제 준비도 API의 판정 |
| 도구 | 미연결 / 기존 시스템 / 앱 초안 / 검증 대기 / 실행 가능 | 실제 앱·릴리스 상태 |
| 운영 검증 | 미검증 / 실험 검증 / 현업 검증 | 사용 증거의 성격 |

L2 29개 설치를 `업무 29개 완성` 또는 `100%`로 표시하지 않는다. 화면의 셋업 현황은 `적용 대상 L2 중 골격 적용 n/N`, `데이터 충족 n/N`, `도구 연결 n/N`, `현업 검증 n/N`을 별도로 표시한다. 바로가기는 제외하고, N은 승인된 적용 범위로 고정한다. 미사용 전환으로 N이 줄면 사유·이전 N을 기록한다.

데이터 불필요 업무는 정당한 예외를 명시하고 해당 지표에서 N/A로 처리한다. 현재 앱/계산 경로가 데이터 계약을 요구하는 경우에는 예외 표시로 게이트를 우회할 수 없다. 조회 실패는 0건이나 충족 상태가 아니다.

## 12. 권한·승인·무결성

### 12.1 역할별 경계

| 주체 | 허용 제안 | 금지 |
|---|---|---|
| 현업 사용자 | 허용 범위 열람·앱 요청·업무 변경 제안 | 회사 전체 표준·타 조직 업무 임의 변경 |
| 위임된 업무 편집자 | 지정 L1/L2의 초안 편집, 낮은 위험 표시 변경 발행 | 데이터 오너/권한 정책 변경 |
| 업무 구성 책임자 | 구조·분리·통합·공식 업무 구성 승인 | 이 승인으로 데이터 사용·외부 실행 승인 대체 |
| 데이터/앱 승인권자 | 기존 절차에 따른 계약·데이터·앱 승인 | 업무지도 설치만으로 자동 승인 |

권한 이름 후보는 `process_config.read/propose/edit/publish`다. 기존 권한 등록부와 route_authority에 정식 매핑하며 별도 비공식 권한 DB를 만들지 않는다. 현재 조직 편집 권한만 요구하는 API를 현업 편집에 그대로 노출하지 않는다. 위임 기능 미구현 시 현업은 변경 제안을 만들고 기존 권한자가 적용하는 경로를 제공한다.

설치 단계별 권한은 합치지 않는다.

| 단계 | 서버에서 확인할 권한 / 조건 |
|---|---|
| 미리보기·제안 저장 | 대상 문맥 조회 + process_config.propose; 데이터 인스턴스 쓰기 없음 |
| 신규 인스턴스를 포함한 셋업 시작 | process_config.edit + 기존 PROJECT_CREATE 및 데이터 준비 인스턴스 생성 정책 |
| 기존 인스턴스에 연결 | process_config.edit + 해당 인스턴스 조회·연결에 대한 기존 도메인 정책; 원천 접근 권한은 부여하지 않음 |
| 실패 작업 재개·인수 | 현재 행위자에 대해 다음 단계의 위 권한을 다시 검사; 과거 작성자 토큰/권한 사용 금지 |
| 업무지도 승인 | process_config.publish + 문맥/위험도별 적격 승인 조건; 데이터 인증과 별개 |

적격 설치자가 아직 없으면 AWAITING_INSTALLER로 남긴다. 제안자가 승인자에게 전달했다는 이유로 PROJECT_CREATE나 타 조직 편집권을 얻지 않는다.

초기 설치·구조 변경·범위/책임 변경은 작성자와 다른 적격 승인자의 검토를 요구한다. 낮은 위험 표시 변경은 위임 범위 내 자기 발행을 허용할 수 있으나 감사·동시성 검사는 동일하다. 엄격한 회사 정책이 있으면 그것이 우선한다.

### 12.2 승인 불변식

- DRAFT는 공식 조회·생성 문맥에 자동 참여하지 않는다. 요구사항 실험에는 초안임을 표시하고 승인판과 분리한다.
- 승인 요청은 change_id, expected_head_version, draft_digest, 검토 이유에 결속한다.
- SQLite에서는 승인 시 `BEGIN IMMEDIATE` 후 head/권한 대상/초안 지문을 다시 확인하고 CAS한다. Postgres 이식 시 동등한 행 잠금/CAS·유일 제약을 사용한다.
- 같은 문맥의 활성 head는 하나다. 승인 후 payload 직접 수정과 클라이언트의 approved_by/approved_at 지정은 거절한다.
- 연결 대상은 tenant·context root·mode·허용 scope를 검증한다. 타 회사 대상은 존재 여부를 숨기는 404를 사용한다.
- 연결 목록·검색·충돌 미리보기·개수·이벤트도 권한으로 필터한다. 화면에서 숨기는 것만으로 충분하지 않다.
- 실제 데이터·앱 실행 바인딩은 영향 분석과 기존 계약의 별도 승인이 필요하다. 요구/청사진 후보는 아래처럼 구분한다. 단순 책임자 표시로 권한을 획득할 수 없다.
- payload 오류/지원 안 되는 schema/부모 순환/교차 회사 참조/알 수 없는 상태는 fail-closed다.

| 바인딩 종류 | 업무지도 승인 | 실제 사용 |
|---|---|---|
| DATA_REQUIREMENT / APP_BLUEPRINT | 미해결 요구 또는 검증된 템플릿 후보로 승인 가능 | 데이터/앱 존재·실행 가능으로 집계 금지 |
| DATA_INSTANCE | 존재·문맥·연결 권한 확인 후 참조; 미인증/보류 표시 가능 | 조회/계산 목적별 기존 인증·usage hold·권한 검증 |
| APP_RELEASE | 존재·문맥·앱 접근권한 확인 후 참조; 검증 대기 표시 가능 | release eligibility·수락·Host capability·프로세스 호환성 검증 |
| EXTERNAL_SYSTEM | 허용된 시스템 참조 또는 미연결 요구로 저장 | 승인 connector/query·자격증명 참조·실행 정책 필요 |
| KNOWLEDGE_REF | 문서 접근·근거 참조 검증 | 데이터 인증/정책 권한 근거로 자동 승격 금지 |

모르는 실제 자산 ID를 후보 상태로 감춰 승인하지 않는다. 실제 대상이 없으면 자산 참조가 아닌 논리 요구로 전환해 명확히 표시한다.

## 13. API 계약 제안

아래 경로는 새 설계이며 현재 존재하는 API라고 표시하지 않는다. 기존 ECM 및 data-preparation 라우터에 추가하고 공통 권한표·오류 봉투·감사를 따른다.

| API | 입력 핵심 | 반환 / 주요 조건 |
|---|---|---|
| `GET /api/v1/data-preparation/kits/{kit_id}/versions/{version}/process-pack` | 정확한 판본 | 검증된 팩·digest·호환성·29개 중 제공 범위 |
| `POST /api/v1/enterprise-context/process-setups/plan` | kit/version, 대상 scope/mode, 기존 instance 선택, 업무 선택 | dry-run diff·미해결 참조·base token·plan_digest; 운영 데이터 쓰기 없음 |
| `POST /api/v1/enterprise-context/process-setups/proposals` | 계획·사유·멱등키 | AWAITING_INSTALLER 제안; 데이터 인스턴스 생성 없음 |
| `POST /api/v1/enterprise-context/process-setups` | 계획 입력, plan_digest, idempotency key | operation_id·현재 단계·초안 참조; 202/200 |
| `GET /api/v1/enterprise-context/process-setups/{operation_id}` | operation ID | 상태·재시도 가능 여부·생성/재사용 대상 |
| `POST /api/v1/enterprise-context/process-setups/{operation_id}/resume` | expected state/version, 동일 요청 digest | 같은 작업 재개; 새로운 인스턴스 생성 방지 |
| `GET /api/v1/enterprise-context/process-configurations/resolved` | 현재 인증 문맥, 선택 scope, 선택 승인판 | 유효 지도·sources·digest·권한별 행동 |
| `POST /api/v1/enterprise-context/process-configurations/{id}/changes` | base version, 변경 명령, 이유, idempotency key | change_id·draft_profile_id·위험 분류 |
| `POST /api/v1/enterprise-context/process-changes/{id}/validate` | draft_digest | 구조/권한/참조·영향 분석·승인 요구 |
| `POST /api/v1/enterprise-context/process-changes/{id}/approve` | expected head, draft_digest, 이유 | 새 승인판/head; 원자 적용·멱등 |
| `POST /api/v1/enterprise-context/process-changes/{id}/reject` | 이유 | 초안 반려; 현 승인판 유지 |
| `POST /api/v1/enterprise-context/process-configurations/{id}/upgrade-plan` | 새 팩/번들 판본·digest, 바인딩 유지/교체 계획 | B/C/N diff·충돌·참조 집합·호환성 근거 |
| `POST /api/v1/enterprise-context/process-configurations/{id}/restore-plan` | 이전 profile_id | 현 상태에 대한 복구 초안 후보 |
| `GET /api/v1/enterprise-context/process-configurations/{id}/processes/{process_id}/context` | 선택 instance·승인판 | 생성기 문맥·차단 이유; 자격증명 없음 |

공통 오류: 401 미인증, 403 보이는 자원에 대한 행동 권한 부족, 404 비가시/없는 대상, 409 head/digest/멱등 충돌, 422 구조·계약 불충족, 503 의존 조회/정책 판정 불가. 오류에는 안정 reason_code와 사용자가 할 다음 행동을 제공하되 비가시 대상 정보는 넣지 않는다.

일반 PATCH로 payload 전체를 교체하지 않는다. 변경 명령은 `RENAME`, `ADD_NODE`, `MOVE_NODE`, `SET_USAGE`, `ADD_SHORTCUT`, `REMOVE_SHORTCUT`, `SET_BINDING`, `SPLIT`, `MERGE`, `RESET_TO_TEMPLATE`의 검증된 형태로 받는다. 복잡한 변경 명령을 지원하지 않는 버전은 명시적으로 거절한다.

## 14. 기존 자산 이관과 호환성

1. 기존 `process_profile`은 v1로 간주하되 자동 덮어쓰지 않는다. 선택 회사별 미리보기에서만 이관 초안을 만든다.
2. 기존 key/label/note/명시적 overlay null을 그대로 보존한다. 기존 평면 노드를 L1 후보로 두고 표준 대응은 사용자가 확인한다.
3. 회사 전체 v1 프로필의 적용 mode/root가 불명확하면 `CONTEXT_REVIEW_REQUIRED`. 현재 화면이 VIRTUAL이라는 이유로 과거 프로필을 가상기업 자산으로 추정하지 않는다.
4. 기존 `sourcing` 등 이름/키와 BK-01의 대응도 명시적으로 확인한다. 같은 label을 ID처럼 사용하지 않는다.
5. 기존 35개 데이터 계약·인스턴스·RAW·snapshot·앱/릴리스 ID·승인은 보존한다. 프로세스 매핑만 추가하고 소급해 인증하지 않는다.
6. v2 head가 있는 문맥에서는 구 `POST /profiles` 및 구 승인 경로의 process_profile 쓰기를 409 `PROCESS_SCHEMA_UPGRADE_REQUIRED`로 막거나 같은 v2 서비스에 위임한다. 다른 profile_kind는 영향받지 않는다.
7. v2를 못 읽는 구 UI에는 읽기 전용 L1 projection과 `편집기 업데이트 필요`를 제공한다. projection을 다시 저장할 수 없다.
8. 지원 reader/editor 배포 확인 → feature flag를 제한 문맥에서 켬 → 새 팩 설치 순서로 진행한다. 구 서버는 프로세스 팩을 선언한 새 키트를 조용히 부분 설치하지 않는다.
9. 롤백 시 기존 v1을 읽을 수 있어도 v2 문맥을 v1 편집에 다시 열지 않는다. v2는 읽기 전용 보존하고 호환 서버를 복구한다.

최초 전환 경쟁도 막는다. 이관 계획에 원본 v1의 적용 자리(tenant/scope/종류), active profile_id, 원문 digest를 고정한다. 첫 v2 승인 트랜잭션에서 해당 자리의 현재 v1 ID/digest를 다시 읽어 비교한다. v1의 저장·승인도 **동일 ECM DB 쓰기 트랜잭션 안에서** v2 전환 여부를 재확인한다. v1이 먼저 바뀌면 v2 승인은 409, v2가 먼저 적용되면 v1 쓰기는 409다. v1의 빈 scope가 여러 루트에 대응하는 경우 자동 이관하지 않고 범위 검토 후 대상 대응을 기록한다.
