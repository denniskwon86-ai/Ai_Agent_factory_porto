# [D-017 §9 P4-3 / P4-4] 추천 기능 설계 — 전사 승격 추천 · 미사용·중복 정리 제안

- 날짜: 2026-08-07
- 상태: **설계 확정 전** — 아래 §6 의 결정 2건을 받아야 착수한다
- 근거: `docs/design_agent_governance_scope_permissions_2026-08-04.md` §9 P4
- 관련 구현: `core/agent_operations.py`(P4-1) · `core/org_operations.py`(P4-2)

---

## 1. 왜 설계를 먼저 하는가

P4-1·P4-2 는 **집계**였다. 집계는 틀려도 「숫자가 이상하다」로 드러난다.

P4-3·P4-4 는 **추천**이다. 추천은 다르다 — 사람이 그것을 근거로 **되돌리기 어려운 행동**을
한다. 전사 승격은 회수해도 이미 본 사람이 있고, 자산 정리는 지운 뒤에 필요했다는 것을 안다.

★ **틀린 추천은 침묵보다 나쁘다.** 아무 추천이 없으면 사람이 직접 판단하지만, 틀린 추천이
있으면 사람은 판단을 그것에 위임한다. 그래서 「무엇을 근거로 추천하는가」를 코드보다 먼저
정해야 한다.

---

## 2. 실측 — 지금 있는 근거와 없는 근거

착수 전에 원천을 셌다. **추측하지 않고 실제로 읽었다**(2026-08-07).

| 원천 | 상태 | 추천에 쓸 수 있는가 |
|---|---|---|
| 승격 게이트 `workspace.evaluate_gate` | ✅ 4개 검사, `pass`/`fail`/**`unverifiable`** | **쓸 수 있다** |
| 승격 신청 `release_promotions` | ✅ 미완료 3건 | 쓸 수 있다 |
| 품질 결과 `quality_outcomes.jsonl` | ✅ 게이트별 통과·실패·사람 수용 | 쓸 수 있다 |
| LLM 호출 `llm_call_log.jsonl` — **에이전트 축** | ⚠️ 관측률 **8%**(89/1133) | **사용량 판단 불가** |
| LLM 호출 — **부서 축** | ❌ 귀속률 **0%**(0/1133) | 조직별 판단 불가 |
| 자산 저장소 `agent_assets` | ⚠️ **사용 이력 필드가 없다**(`last_used_at`·`usage_count` 없음) | **미사용 판단 불가** |
| 자산 재고 | agent 2건 · skill 0건 · workflow 0건 · 파일 스킬 31개 | 중복 판단은 가능 |

### ★★ 이 표에서 나오는 결론 하나

**「미사용」을 판단할 근거가 없다.**

자산에 사용 이력이 없고, 텔레메트리의 에이전트 축은 8%만 관측된다. 이 상태에서
「호출 0건 = 미사용」이라고 추천하면 **관측되지 않았을 뿐인 자산을 지우라고 말하게 된다.**
그리고 그 제안을 받은 사람은 확인할 방법이 없다 — 화면이 「0건」이라고 하니까.

⚠️ 이것이 P4-1 에서 이미 확인한 함정과 같다: **숫자가 있으면 사람은 그것을 전부라고 읽는다.**

## 3. P4-3 — 전사 승격 추천

### 3.1 무엇을 추천하는가

**「지금 승격 신청하면 게이트를 통과할 릴리스」** 를 추천한다. 그 이상을 말하지 않는다.

★ 「좋은 자산」이나 「가치 있는 자산」을 추천하지 않는다. 그것은 사람의 판단이고, 우리가 가진
데이터로는 근사조차 할 수 없다. 우리가 답할 수 있는 질문은 **「형식 요건이 갖춰졌는가」** 뿐이다.

### 3.2 판정 규칙 — `unverifiable` 은 통과가 아니다

게이트는 네 검사에 `pass` / `fail` / `unverifiable` 을 준다.

```
추천한다   ← 네 검사가 **전부 pass**
추천 안 함 ← 하나라도 fail
추천 안 함 ← 하나라도 unverifiable   ★★ 여기가 핵심이다
```

⚠️⚠️ **`unverifiable` 을 «아직 문제 없음» 으로 세지 않는다.** `evaluate_gate` 의 docstring 이
이미 못박았다 — 「`unverifiable` 은 통과가 아니라 확인하지 못한 것이며 승격을 막는다」.
추천에서 이것을 완화하면, 화면은 「승격 준비됨」이라고 하는데 실제로 신청하면 막힌다.
그때 사용자는 **추천을 신뢰하지 않게 되고**, 그러면 이 기능은 있으나 마나다.

실측 근거: 게이트의 `unverifiable` 은 대부분 「사용 자산을 모르므로 검사할 수 없다」이다.
즉 **가장 흔한 상태가 `unverifiable`** 이고, 그것을 통과로 세면 거의 전부가 추천된다.

### 3.3 추천하지 않는 것도 말한다

추천 목록만 주면 「내 릴리스는 왜 없나」에 답할 수 없다. 그래서 **가까운 것**을 함께 준다:

```json
{
  "recommended": [ … 네 검사 전부 pass … ],
  "almost": [ { "release_id": "...", "blocking": [
      {"key": "data_contract", "state": "unverifiable",
       "why": "…", "action": "계약을 등록하십시오"} ] } ],
  "coverage": { "evaluated": 12, "unreadable": 1,
                "note": "1건은 게이트를 읽지 못해 판정에서 빠졌습니다 — 「추천 대상 아님」이 아닙니다." }
}
```

★ `action` 은 게이트가 이미 만들어 준다(`add(key, state, why, action)`). **여기서 새로 짓지
않는다** — 두 곳에서 지으면 화면과 실제 게이트가 다른 말을 한다.

⚠️ `coverage.unreadable` 을 반드시 낸다. 게이트를 못 읽은 릴리스를 조용히 빼면 「추천 없음」이
「검사했는데 없음」과 「검사를 못 함」을 뭉갠다.

### 3.4 권한

`assert_governance_readable` — P4-2 와 같다. 「어디가 비어 있는지」는 그 자체로 보호 대상이다.
승격 신청·승인은 기존 `workspace_control` 이 담당하며 **추천이 그것을 대신하지 않는다.**

## 4. P4-4 — 미사용·중복 정리 제안

### 4.1 ★★ 「미사용」은 지금 만들지 않는다

§2 에서 확인했듯 근거가 없다. 만들려면 **먼저 관측이 서야 한다.**

선행 조건 두 가지 (별건):
1. `agent_assets` 에 사용 이력을 남긴다 — `resolve_workflow`/자산 해석 시점에 기록
2. 텔레메트리 에이전트 귀속률을 올린다(현재 8%)

⬜ 그때까지 「미사용」 항목은 **만들지 않는다.** 근거 없는 삭제 제안은 이 기능이 줄 수 있는
가장 큰 해악이다 — 한 번 잘못 지우면 사람들은 다시는 이 목록을 쓰지 않는다.

⚠️ 대신 **관측률을 화면에 그대로 낸다.** 「사용 이력이 없어 미사용 판단을 제공하지 않습니다」를
빈 목록 대신 문장으로 쓴다. 빈 목록은 「정리할 것이 없다」로 읽힌다.

### 4.2 「중복」은 지금 만들 수 있다

중복은 **내용 비교**이므로 사용 이력이 필요 없다.

대상: 파일 스킬 31개 + DB 자산(agent 2 · skill 0 · workflow 0).

판정:
```
동일   ← 정규화 후 내용 해시가 같다        (확신 높음 — 제안한다)
유사   ← 정규화 후 유사도 ≥ 임계값          (확신 낮음 — «검토» 로만 제안한다)
```

정규화: 공백·줄바꿈·주석 헤더 제거. ⚠️ **의미까지 비교하지 않는다** — LLM 으로 「비슷한
스킬」을 판정하면 근거를 설명할 수 없고, 설명할 수 없는 삭제 제안은 아무도 실행하지 않는다.
그리고 §6.1 이 품질 판정에 대해 「단순 LLM 평가 금지」를 못박았다. LLM 0콜로 만든다.

★ **제안은 «지워라» 가 아니라 «둘 중 하나를 고르라» 다.** 어느 쪽이 정본인지는 사람이 안다.
  화면은 둘을 나란히 보여 주고, 각각이 어디서 쓰이는지(알 수 있는 만큼) 붙인다.

⚠️ 자동 삭제 버튼을 만들지 않는다. 스킬 파일은 에이전트 정의가 이름으로 참조하므로, 지우는
순간 그 에이전트는 **기본 스킬로 조용히 강등**된다(`agent_skill(…, default=…)`).
그 강등은 오류를 내지 않는다.

## 5. 두 기능이 공통으로 지키는 것

P4-1·P4-2 에서 세운 규칙을 그대로 잇는다.

1. **모르면 «없음» 이라고 말하지 않는다** — 못 읽은 원천은 `known=False` 로 낸다
2. **관측률을 함께 낸다** — 숫자와 **문장** 둘 다
3. **판정은 한 곳에** — 게이트 판정은 `evaluate_gate`, 자격은 `assert_governance_readable`
4. **행동 문구를 새로 짓지 않는다** — 원천이 준 `action` 을 그대로 쓴다
5. **표본이 적으면 말한다** — P4-1 의 `min_calls` 와 같은 태도

## 6. ★ 받아야 할 결정 2건

### 결정 ① — 「유사」 임계값과 그 취급

중복 판정에서 «동일» 은 안전하다. **«유사» 를 제안 목록에 넣을 것인가?**

| 안 | 내용 | 대가 |
|---|---|---|
| A (보수) | **동일만** 제안. 유사는 만들지 않는다 | 실제 중복 일부를 놓친다 |
| B (권장) | 동일은 «정리 제안», 유사는 **«검토 대상»** 으로 분리해 표시 | 화면이 두 단계가 된다 |
| C | 유사도 하나로 합쳐 순위만 매긴다 | 확신 없는 항목이 확신 있는 것과 섞인다 — **반대** |

권장은 **B** 다. 확신의 차이를 화면에서 지우면 사람은 목록 전체를 같은 무게로 읽는다.

### 결정 ② — P4-4 를 지금 절반만 낼 것인가

「미사용」 없이 「중복」만 내는 것은 **P4-4 의 절반**이다.

| 안 | 내용 |
|---|---|
| A (권장) | 지금 «중복» 만 내고, «미사용» 은 관측이 선 뒤에 얹는다. 화면은 미사용 칸에 «사용 이력이 없어 제공하지 않습니다» 를 쓴다 |
| B | 관측(사용 이력 기록)을 먼저 만들고 P4-4 를 한 번에 낸다 |

권장은 **A** 다. 중복 정리는 지금 근거가 있고, 미사용을 기다리느라 미루면 둘 다 안 나온다.
⚠️ 단 진척은 **P4-4 를 «완료» 로 세지 않는다** — 0.5 로 세거나 «중복만 완료» 로 적는다.
