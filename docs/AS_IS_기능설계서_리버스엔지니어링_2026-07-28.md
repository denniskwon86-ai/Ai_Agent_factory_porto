# AI Factory Studio As-Is 기능설계서

> 작성 방식: 현재 `dev` 브랜치의 FastAPI/LangGraph/React 소스를 역추적한 As-Is 문서다. 목표 아키텍처나 제안 기능은 구현 완료처럼 기재하지 않는다.
>
> 기준일: 2026-07-28 / 범위: `main.py`, `api/routes/`, `core/`, `nodes/`, `state_models.py`, `frontend/src/`

## 1. 목적·범위·판독 규칙

### 1.1 목적

이 문서는 현재 시스템이 실제로 제공하는 업무 기능, API 계약, 데이터 상태, 처리 흐름, 실패 처리와 한계를 정의한다. 이후 기능 변경 시에는 이 문서를 기준선으로 삼아 영향 분석과 회귀 테스트를 수행한다.

### 1.2 판독 규칙

- **구현됨**: 라우트/컴포넌트/상태 전이가 코드에 존재하고 호출 경로가 확인된 기능.
- **부분 구현**: 저장소·API·UI 중 일부만 있거나 운영 경로가 제한된 기능.
- **미구현**: 설계 문서 또는 목표 설명에만 있으며 런타임 경로가 없는 기능.
- 시스템은 현 시점에 **AI 업무 SW 생산·검토 공장**이다. 완성된 ERP/MES, 부서별 운영 앱 런타임, 전사 디지털트윈으로 기술하면 안 된다.

## 2. 시스템 개요

### 2.1 논리 구성

```text
React/Vite UI
  ├─ REST fetch (Zustand store)
  ├─ SSE EventSource (/ws/timeline)
  └─ 생성 결과 Preview iframe
        ↓
FastAPI API
  ├─ Factory control / 지식 / MDM / Crosswalk / MCP / 기준 / 텔레메트리
  └─ SSE broadcaster
        ↓
AsyncFactoryOrchestrator
  ├─ 프로젝트별 LangGraph 실행/일시정지/재개/중단
  ├─ 최신 상태 파일 저장
  └─ 이벤트 송신
        ↓
LangGraph Agent Pipeline
  ├─ 요구사항 정제·기획·설계·WBS
  ├─ 구현·빌드·리뷰·QA·수용검수·매뉴얼
  └─ HOTL/쿼터/실패/재작업 라우팅
        ↓
LLM Gateway + Context Engine + Knowledge/Master/MCP
```

### 2.2 기동·통신

| 항목 | 현재 동작 |
|---|---|
| 백엔드 | `run.py` → `main:app`, 기본 8080 포트 |
| 프런트엔드 | Vite, 기본 5173 포트 |
| REST 기본 주소 | 프런트 `VITE_API_BASE_URL` 또는 `http://localhost:8080` |
| 실시간 통신 | `/ws/timeline`의 **SSE**. 경로에 `/ws`가 있어도 WebSocket은 아니다. |
| CORS | `CORS_ALLOWED_ORIGINS` 환경 변수 또는 로컬 기본값 |
| 인증/조직 권한 | 현재 전역 인증·SSO·백엔드 강제 RBAC는 구현 범위가 아니다. |

### 2.3 주요 행위자

| 행위자 | 현재 시스템에서의 역할 |
|---|---|
| 현업 요청자 | 프로젝트를 만들고 아이디어/피드백/승인을 입력한다. |
| 전문가(HOTL) | 요구사항 정제, RFP, 기획, UI, PMO 등 게이트에서 승인 또는 수정 요구를 준다. |
| 프로젝트 통제자 | WBS 작업 시작/일시정지/재개/중단, 결과물 배포·내보내기를 수행한다. |
| 에이전트 관리자 | 에이전트 레지스트리·워크플로 템플릿·출력 양식을 관리한다. |
| 지식/데이터 관리자 | 지식팩, 기준정보, 외부 스키마 매핑, 업무표준을 관리한다. |
| 슈퍼바이저 데몬 | 선택 노드 완료 시 사업·아키텍처상 위험을 평가하고 필요하면 중단/개선 제안을 만든다. |

## 3. 핵심 도메인 모델과 영속화

### 3.1 프로젝트

프로젝트는 `projects/<project_id>/` 작업공간과 `project_meta.json`으로 식별된다. 프로젝트 생성 시 템플릿, 출력 양식, 지식팩, M1 도메인, M3 실시간 참조 여부를 메타데이터로 저장한다.

| 필드 | 의미 |
|---|---|
| `project_id` | 영문/숫자/`_`/`-`만 허용하는 파일시스템 안전 식별자 |
| `template_id` | 에이전트 레지스트리/스킬/파이프라인 선택 기준 |
| `output_format_id`, `view_type` | 결과 렌더링 방식과 프롬프트 주입 양식 |
| `knowledge_pack_ids` | 프로젝트 컨텍스트에 주입할 지식팩 목록 |
| `master_domains` | 프로젝트에 주입할 기준정보 도메인 태그 |
| `mcp_live_grounding` | 외부 시스템 실시간 참조 허용 여부, 기본 `false` |

### 3.2 LangGraph 상태: `ProjectState`

`state_models.py`의 `ProjectState`가 실행 SSOT다. 스키마는 `extra='forbid'`이므로 정의되지 않은 상태 키를 노드가 반환하면 오류/무시 위험이 있다.

| 상태군 | 핵심 필드 |
|---|---|
| 실행 모드 | `factory_mode`: `PLANNING`, `EXECUTION`, `REVISION`, `REVIEW`, `QA_RELEASE`, `HOTL_PAUSED`, `SUSPENDED_QUOTA` |
| 스프린트 | `current_sprint`, `current_sprint_task_id`, `current_required_agents` |
| 빌드·재작업 | `build_status`, `build_error_log`, `developer_retry_count`, `failed_node`, `terminal_reason`, `failure_bundle_path` |
| 리뷰 | `reviewer_decision`, `reviewer_feedback`, `supervisor_hops`, `rework_history`, `needs_revision` |
| 산출물 | RFP/PRD/아키텍처/UI/기술명세/프런트·백엔드 코드/리뷰/QA/수용/매뉴얼 요약 |
| HOTL | `human_feedback_queue`, `clarification_questions`, `clarification_summary` |
| 지식·데이터 | `knowledge_pack_ids`, `master_domains`, `mcp_live_grounding`, `master_data` |
| Mega | `is_mega_project`, `parent_project_id`, `sub_projects_map`, `shared_ledger`, `domain_agents` |
| 품질 관측 | `current_stage`, `stage_attempt_counts`, `stage_scores`, `debate_rounds_used`, `criteria_log` |

### 3.3 영속화

| 저장소 | 용도 |
|---|---|
| LangGraph SQLite/Postgres checkpoint | 태스크별 실행 재개 상태. thread ID는 프로젝트/태스크 조합이다. |
| `latest_state.json` | 프로젝트 작업공간의 사람이 읽을 수 있는 최근 상태 스냅샷 |
| 프로젝트 내부 Git | 생성 파일의 변경·회귀 감시·안전 롤백 기준 |
| `library/<release_id>/release.json` | 배포 결과물/문서 스냅샷 |
| `data/chroma_db`, 지식팩 파일 | RAG 지식 검색 |
| `data/master/master.db` | M1 경량 기준정보 |
| `data/skill_proposals/` | 스킬 진화 제안의 pending/approved/rejected 상태 |
| `data/llm_call_log.jsonl` | 모델 사용·비용/지연 분석의 원천 텔레메트리 |

## 4. 기능 영역 A — 프로젝트·템플릿·Mega 관리

### F-A01. 독립 프로젝트 생성

| 항목 | 정의 |
|---|---|
| 목적 | 단일 업무 아이디어를 AI 생산 파이프라인으로 수행할 작업공간을 만든다. |
| 입력 | 프로젝트 ID, 템플릿, 지식팩, M1 도메인, MCP 실시간 참조 설정 |
| API | `POST /api/v1/factory/projects` |
| 처리 | ID 검증 → 작업공간/Git 초기화 → `project_meta.json` 기록 → 프로젝트 목록 갱신 |
| 결과 | 독립 프로젝트가 선택되며 통제실로 진입 가능 |
| 제약 | 프로젝트 ID는 경로 이탈 방지를 위해 제한 문자만 허용한다. |

### F-A02. Mega 프로젝트

| 항목 | 정의 |
|---|---|
| 목적 | 복수 도메인 서브 프로젝트를 마스터 프로젝트 아래에 구성한다. |
| API | `POST /projects/mega`, `POST /projects/{id}/mega/plan`, `POST /projects/{id}/mega/start_all` |
| 처리 | 마스터/서브 프로젝트 메타데이터와 `sub_projects_map`을 사용하며, 계획 및 일괄 실행을 제공한다. |
| 화면 | 런처의 Mega 탭, MegaBoardroomPanel |
| 한계 | 전사 운영 시스템의 실시간 공유 원장이 아니라 AI 생산 프로젝트의 병렬 관리 기능이다. |

### F-A03. 프로젝트 복제·삭제·지식 연결 변경

| 기능 | API | 비고 |
|---|---|---|
| 복제 | `POST /projects/{id}/copy` | 새 프로젝트 ID 필요 |
| 삭제 | `DELETE /projects/{id}` | 작업공간과 관련 checkpoint 정리. 화면에서 복구 불가 경고를 준다. |
| 지식/도메인 변경 | `PUT /projects/{id}/knowledge` | 지식팩·M1 도메인을 프로젝트 메타데이터에 반영 |
| 최신 상태 | `GET /{id}/state/latest` | UI 상태 복구/폴링에 사용 |

### F-A04. 템플릿·에이전트 레지스트리·출력 양식

| 대상 | 기능 | API |
|---|---|---|
| 기본/사용자 템플릿 | 목록·상세·복제·저장·삭제 | `/templates` |
| 에이전트 레지스트리 | 조회·저장·기본값 초기화 | `/agents` |
| AI 추천 | 파이프라인/스킬 구성 초안 생성 | `/ai-recommend/pipeline`, `/ai-recommend/skill` |
| 출력 양식 | 목록·생성·수정·삭제 | `/api/v1/factory/formats` |

템플릿의 enabled 에이전트가 기본 SW 노드 집합이면 하드코딩된 SW 그래프를 쓴다. 그렇지 않은 레지스트리는 Universal Node 기반 선형 파이프라인으로 전환한다. 따라서 현재 그래프 토폴로지는 완전한 데이터 주도형이 아니다.

## 5. 기능 영역 B — 요구사항 정제·기획·WBS

### F-B01. 선택형 요구사항 정제(Clarification)

| 항목 | 정의 |
|---|---|
| 진입 | 계획 스프린트 시작 후 `Requirement_Interviewer` 노드 |
| 출력 | `clarification_questions`: 보통 2~4개 질문, 선택지, 추천안, 이유, 다중 선택 여부 |
| 사용자 조작 | HOTL UI에서 선택지를 클릭하고 선택적 자유 텍스트를 보낸다. |
| 결과 | 답변을 `clarification_summary`로 정리해 이후 RFP/PRD 컨텍스트에 반영한다. |
| 설계 의도 | 사용자가 장문의 요구사항을 다시 작성하지 않도록 방향·제약만 빠르게 결정하게 한다. |

### F-B02. 계획 파이프라인

```text
Requirement Interviewer
  → RFP Analyst → HOTL(RFP)
  → Master PM → HOTL(기획)
  → UI Designer → Vision QA → HOTL(UI)
  → Architect → HOTL(아키텍처)
  → Master PMO(WBS) → HOTL(PMO)
  → WBS Approved / 계획 종료
```

| 노드 | 주요 산출물/판정 |
|---|---|
| RFP Analyst | RFP, 요구사항 범위와 확인사항 |
| Master PM | PRD/기획, 상위 의사결정, PM 에스컬레이션 처리 |
| UI Designer | UI mockup 산출물 |
| Vision QA | Playwright 스크린샷 + Vision 평가. 현재는 무한 재작업 방지를 위해 advisory 성격이 강하다. |
| Architect | 서비스 경계, 기술 방향, ADR/아키텍처 요약 |
| Master PMO | WBS와 태스크 분할, 계획 단계 점수/판정 |

기획 단계의 debate/scoring은 노드 내부 서브루프이며 LangGraph 사이클을 추가하지 않는다. 기준 미달이면 제한된 재작업 후 판정한다.

### F-B03. WBS

| 기능 | API/화면 | 설명 |
|---|---|---|
| WBS 조회 | `GET /{id}/wbs`, ControlPanel | 태스크별 상태, 역할, 필요 에이전트를 표시 |
| WBS 단독 재분할 | `POST /{id}/wbs/replan` | 기획 전체를 다시 돌리지 않고 Master PMO만 재수행 |
| 태스크 시작 | `POST /{id}/sprint/start` | 선택한 WBS 태스크의 실행 스프린트 시작 |
| 작업 단위 재시작 | UI의 신규 가동/이어서 재가동 | 상태별 시작/재개 버튼 노출 |

## 6. 기능 영역 C — 실행·품질·실패 복구

### F-C01. 실행 파이프라인

```text
Architect → Tech Lead → Backend / Frontend
→ Code Builder → Reviewer → QA → Supervisor → Manual Writer
```

| 노드 | 핵심 책임 |
|---|---|
| Tech Lead | 기술 명세·개발 경계·후속 개발 지시 |
| Backend/Frontend | Micro-swarm 기반 코드 생성, 소유 파일 문맥 사용 |
| Code Builder | 파일 원자 쓰기, 파일 인덱스 갱신, 구문 확인 |
| Reviewer | 렌더/상호작용/백엔드 스모크/회귀/LLM 리뷰를 묶어 PASS·REWORK_DEV·ESCALATE_PM 결정 |
| QA | 테스트·보안·빌드 스캔의 결정론적 결과와 QA 판정 |
| Supervisor | 수용검수 성격의 최종 요약/판정 |
| Manual Writer | 사용자 매뉴얼 문서 생성 |

### F-C02. 품질 게이트

| 게이트 | 방식 | 차단 여부 |
|---|---|---|
| 구문 검사 | Python AST, JS/TS 괄호·인용부호 점검 | 빌드 실패 |
| 프런트 렌더 | React server render 검사 | 재작업 |
| 상호작용 | `value`만 있고 `onChange` 없는 frozen input 탐지 | 재작업 |
| 백엔드 스모크 | 임시 패키지에서 FastAPI 부팅/라우트 점검 | 재작업 |
| 회귀 검사 | Git 기준 export/handler/input/route/def 순감소 탐지 | 안전망 |
| 품질 조언 | 모놀리식 파일, 빈 상태, 토큰 위반 등 | advisory |
| 단계 점수 | rubric + 필요 시 LLM judge | PASS/REWORK/ROLLBACK |

### F-C03. 실패·중단·재개

| 경우 | 시스템 동작 | 사용자 동작 |
|---|---|---|
| HOTL 필요 | `HOTL_PAUSED`, `needs_revision` 설정, SSE `HOTL_PAUSED` | 승인/수정 피드백 후 재개 |
| 쿼터 소진 | `SUSPENDED_QUOTA`, 중단 전 모드 보관 | 쿼터 회복 후 `resume-quota` 또는 알림 닫기 |
| 빌드 실패 | 오류·실패 노드·retry count 기록 | 오류 포함 재시도, 추가 지시 재시도, 보류 |
| 강제 일시정지 | 실행 태스크 cancel + 피드백 상태 기록 | 다시 시작/재개 |
| 서버/스트림 예외 | 실패 이벤트·WBS 실패 상태로 전환하도록 보강됨 | ControlPanel 실패 카드에서 조치 |
| Preview 렌더 오류 | self-heal API를 제한 횟수로 호출 | 자동 복구 실패 시 사용자 판단 |

### F-C04. 무한 루프 차단 규칙

- Code Builder 재시도는 `developer_retry_count` 기준 최대 3회다. 상한 도달 시 안전 Git 상태로 롤백하고 `HOTL_PAUSED`/실패 종결 경로로 보낸다.
- Reviewer 재작업/PM 에스컬레이션 왕복은 `supervisor_hops`와 `GLOBAL_MAX_SUPERVISOR_HOPS`(기본 8)로 제한한다.
- Supervisor 반복 REJECT도 제한 횟수 후 종결한다.
- 이 규칙은 성공을 보장하는 복구가 아니라, 비용·쿼터·시간을 소진하는 무한 ping-pong을 막는 안전장치다.

## 7. 기능 영역 D — 결과물·시뮬레이션·추적성

### F-D01. 수용검수·릴리스·라이브러리

| 기능 | API | 결과 |
|---|---|---|
| 결과물 저장 | `POST /{id}/release` | release ID, 문서/코드 요약/메타데이터를 `library/`에 스냅샷 |
| 결과물 목록 | `GET /library/list` | 런처의 결과물 라이브러리 카드 |

### F-D02. 재시뮬레이션

`POST /{id}/resimulate`는 기존 프로젝트 상태에 `sim_cycle_count`, 변경 파라미터, 기준 cycle을 주입해 시뮬레이션 템플릿/워크플로를 다시 실행하는 API다. 현재는 생성 파이프라인을 재가동하는 기능이며, 운영·재무 계산이 검증된 경영 디지털트윈 엔진은 아니다.

### F-D03. 추적성·영향 분석

| 기능 | API | 설명 |
|---|---|---|
| 추적 그래프 | `GET /{id}/traceability` | 요구사항, WBS, 산출물, 파일의 연결 그래프 |
| 영향 분석 | `GET /{id}/traceability/impact` | 요구사항/파일/피드백 변경 시 영향 후보 |
| UI | PreviewPanel `TRACE` 탭 | 그래프와 영향 분석 표시 |

## 8. 기능 영역 E — 지식·기준정보·외부 연계

### F-E01. 지식 허브

| 기능 | API |
|---|---|
| 지식팩 목록/생성/상세/삭제 | `/api/v1/knowledge/packs` |
| 문서 업로드/삭제 | `/packs/{pack_id}/documents` |
| 팩 내부 검색 | `/packs/{pack_id}/search` |

업로드 가능한 문서는 지식팩 파일 저장소와 검색 인덱스에 반영된다. 프로젝트 생성 시 선택한 지식팩은 ContextEngine이 프롬프트 근거로 사용한다.

### F-E02. M1 경량 기준정보

| 기능 | API |
|---|---|
| 타입 관리 | `/api/v1/master/types` |
| 레코드·별칭 관리 | `/api/v1/master/records`, `/aliases` |
| CSV 적재 | `/api/v1/master/import/csv` |
| 프롬프트 주입 미리보기 | `/api/v1/master/grounding/preview` |

M1은 품목·설비·공정·서비스·KPI 등의 기준값을 결정론적으로 주입하기 위한 경량 저장소다. 완성형 전사 MDM·데이터 카탈로그·품질 관리 시스템으로 오해하면 안 된다.

### F-E03. M2 Crosswalk

외부 시스템을 등록하고, 스키마 필드를 만들거나 파일에서 가져온 후 M1 기준정보와 매핑한다. 매핑 후보는 결정론적 또는 선택적으로 LLM 초안으로 만들며, 사용자가 승인/기각한다.

| 기능 | API |
|---|---|
| 시스템 CRUD | `/api/v1/crosswalk/systems` |
| 스키마 필드/가져오기 | `/systems/{id}/schema/*` |
| 매핑 설정·후보·승인 | `/schema/mapping`, `/propose`, `/proposals/*` |
| 매핑 조회 | `/systems/{id}/mappings` |

### F-E04. M3 MCP 브로커

| 기능 | API |
|---|---|
| 단건/일괄 해석 | `/api/v1/mcp/resolve`, `/resolve-batch` |
| 캐시 무효화 | `/invalidate` |
| 외부 시스템 헬스 | `/systems/{system_id}/health` |

M3은 온디맨드 읽기와 TTL 캐시 기반이다. 외부 시스템 전체를 복제하거나 쓰기 연계를 완성한 기능이 아니다.

### F-E05. 업무표준

`/api/v1/standards`는 단계별 필수 포함 항목, 원칙, 금지사항, 점수 기준, 개정 이력을 M1 레코드로 관리한다. WorkStandardPanel에서 기준 조회와 코드 기준값 재시드가 가능하다.

## 11. 보안·운영·제약사항

1. 파일 경로를 받는 프로젝트/릴리스 ID는 `_safe_id()` 정규식으로 제한한다.
2. 생성 코드 Preview iframe은 `allow-scripts allow-same-origin`을 사용한다. 현재 코드가 localStorage 등을 쓰는 호환성 이유가 있으나, 생성 코드에 대한 보안 경계로 충분하지 않다. 운영 배포 전 별도 격리 전략이 필요하다.
3. SSE는 프로젝트 ID 기반 UI 필터가 있으나, 현재 사용자 인증·조직 권한을 서버에서 강제하지 않는다.
4. `pipeline_state.db`는 checkpoint가 누적되므로 프로젝트 삭제 시 checkpoint 정리와 운영 규모의 DB 유지보수 정책이 필요하다.
5. LLM 공급자/패키지/API 키 미설치 시 해당 tier는 비활성화된다. UI/로그의 모델 사용 사실은 텔레메트리로 확인해야 한다.
6. 생성 앱은 현재 산출물·Preview·릴리스 스냅샷 중심이며, 독립적인 지속 운영 런타임/공용 업무 DB가 아니다.
