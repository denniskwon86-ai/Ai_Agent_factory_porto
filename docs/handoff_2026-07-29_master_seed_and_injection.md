## 1. 한 것 — 기준정보 시드 (`core/master_data_seed.py` 신규)

`docs/master_data/*.json` 4개 문서를 `master_records` 로 적재하고 ECM 조직 범위에 바인딩한다.

| 문서 | 내용 | 바인딩 범위 | 상속 |
|---|---|---|---|
| `battery_material_m1.json` | 배터리소재 자재·설비·품질·BOM·재무 | `MNM_BATTERY` | 하위 공장 |
| `copper_smelting_m2.json` | 동제련 정광·부산물·제련마진 | `MNM_COPPER` | 하위 |
| `global_standard_m3.json` | ISO22400 KPI·ISA95/SAP·ERP 산식·CBAM | `LS_MNM`(법인) | 전 사업부 |
| `digital_twin_simulation_m4.json` | DES 확률분포·3D 레이아웃·동기화 충실도 | `LS_MNM` | 전 사업부 |

**설계 원칙 3가지** (사용자 지시 반영 — *"데이터 수치가 맞냐, 정확도가 얼마냐는 구현 단계에서
확인할 수 없다. 실사용 전 또는 사용 과정에서 보정되어야 한다"*):

1. **계수를 코드에 박지 않는다.** 전부 문서에서 읽는다. 변형하면 나중에 문서를 고쳐도 반영되지
   않고 무엇이 원본인지 알 수 없다. `source="master_document_seed"` 로 사용자 입력과 구분한다.
2. **값을 자동 보정하지 않는다.** 대신 `inspect_data_quality()` 가 **보정 목록**을 만든다.
   근거 없는 숫자를 시스템이 만들어내면 안 된다(명세서 §16).
3. **시드는 초기 공급이지 진실원본이 아니다.** 재실행이 현업 개정값을 덮지 않는다(멱등).

## 2. 발견한 결함 3건 — **테스트는 통과하고 있었다**

### 결함 1 — 주입 상한 12건이 산식을 잘라내고 있었다 (D-010, 설계서 §F4 해소)

사용자 질문("조직별로 12건씩 나온 건 누가 왜 정한거야")에서 시작해 `git log -S` 로 추적했다.

- **출처**: 커밋 `169612ccc`(2026-07-22) — Claude Code 가 토큰 폭주를 막는 가드레일로 **임의로
  고른 값**. 실측·토큰 예산 계산 근거 없음. `docs/design_master_data_m1.md` §4 에 기재.
- **이미 결함으로 지목돼 있었다**: `design_org_permission_enterprise.md` §F4 가 *"전 부서
  기준정보에 절대 부족하고 `break`(continue 아님)라 긴 레코드 하나가 뒤를 전부 잘라낸다"* 며
  파라미터화 + 예산 자동 스케일을 처방했는데 **미구현**이었다(`max_items`·`skip_oversize` 0건).

**실측 피해** (시드 44건 적재 후):

| 조직 | 적용 가능 | 실제 주입 | 문자수 |
|---|---|---|---|
| 배터리소재 | 30건 | **12건** | 2,225자 |
| 동제련 | 31건 | **12건** | 2,196자 |
| 전사 | 17건 | **12건** | 2,538자 |

- 잘린 18건에 `M3-ERP-COST-MANAGEMENT`(표준원가 산식)·`M3-ERP-PRODUCTION-PLANNING-MPS`·
  `M3-ROUTING`·`M3-EMIS-01`·`M4-DES-*`(시뮬 확률분포)가 **전부** 포함
  → **"LLM 이 산식을 지어내지 못하게 확정 주입한다"는 M1 의 존재 이유가 무력화**되고 있었다.
- 3,000자 예산은 **한 번도 도달하지 않았다**(2,196~2,538자). 두 상한이 서로 맞지 않아
  문자 예산의 약 25%를 버렸다.
- tie-break 가 `master_code` 알파벳순이라 `RM-MHP-001`·`RM-H2SO4-001`·`WIP-*` 는 **철자 때문에**
  항상 탈락했다 → **무엇이 버려지는지가 중요도가 아니라 이름으로 결정**됐다.

**조치**(사용자 지시: *"실제 적용가능한 문서가 있는데 왜 임의로 잘라서 적용해? 넣을 수 있는건
모두 다 전수 다 적용해"*):

1. **기본 상한 없음(전수 주입)** — `_INJECT_MAX_ITEMS = _INJECT_MAX_CHARS = None`.
   전량은 배터리소재 ≈6,000자 / 전 문서 44건 ≈8,700자로 컨텍스트 부담이 없다.
2. `select_for_injection(..., max_items=-1, max_chars=-1, with_stats=False)` —
   `-1`=모듈 기본, `None`=무조건 전수, 양수=명시 상한. 환경변수
   `MASTER_INJECT_MAX_ITEMS`/`MASTER_INJECT_MAX_CHARS` 로 운영 비상 상한.
3. **`break` → `continue`** — 긴 레코드 하나가 뒤를 전부 잘라내지 않는다.
4. **`is_core` 를 관문에서 정렬 신호로 강등** — 종전에는 관문이어서 비핵심 레코드가 도메인이
   맞아도 영원히 주입되지 않았다. 우선순위 3계층: 별칭 히트 → 전사 표준·산식 → 도메인 핵심.
5. **절단 가시화** — 상한이 실제로 걸리면 주입 블록에
   `[주의] … N건 중 M건만 표시 … 추정하지 말 것` 을 적고 `/scope-bindings/allowed` 가
   `injection_capped` 를 반환. **조용히 잘리는 것이 가장 위험하다.**

**수정 후 실측**: 적용 가능 30건 → 주입 30건, `dropped: 0`.

### 결함 2 — 별칭 히트 경로가 죽어 있었다 (D-011)

`_alias_hit` 은 단어경계(`\b`)로 **문자열 전체**를 찾는데, 시드가 문서 정식명
`"Mixed Hydroxide Precipitate (MHP)"` 를 그대로 별칭에 넣었다. 실제 프롬프트에 이 괄호 표기가
나올 일이 없으므로 **시드 44건 전부에서 별칭 매칭이 영원히 실패**했다. 그래서 선정이
`is_core` + 알파벳순으로만 이뤄져 결함 1의 편향이 그대로 노출됐다.

→ `derive_aliases()` 가 괄호 앞 본문·괄호 안 토큰·문서상 식별자로 분해한다.
`"Sulfuric Acid (H2SO4, 98%)"` → `Sulfuric Acid` · `H2SO4` (`98%` 는 오탐 유발로 탈락).
**새 문자열은 창작하지 않고 문서에 이미 적힌 부분만 쓴다.**

### 결함 3 — 재시드가 격리를 조용히 무너뜨렸다

R-001 의 점진 도입 규칙은 **"바인딩 없는 코드는 전사 공통으로 통과"** 다(하위호환).
그런데 시드가 기존 레코드를 건너뛸 때 **바인딩 확인까지 건너뛰어**, ECM 조직 없이 먼저 적재된
레코드가 미바인딩으로 남고 → 통과 규칙을 타고 **모든 조직에 노출**됐다.

실제 DB 에서 **바인딩 26건 < 레코드 45건**으로 재현. 쓰기만 건너뛰고 바인딩은 항상 확인하도록
수정 → **44/44**, LS전선 노출 0건.

> ★ 이것이 `TEAM_BOARD` 의 `MDM-SCOPE-01` 검토 요청 ①("점진 도입 규칙이 유출 창구가 되지
> 않는지")에 대한 답이다: **됐다.** 규칙 자체는 유지하되 **미바인딩 레코드 수를 상시 관측**해야
> 한다. 관측 지표 추가는 미구현(§4 잔여 항목).

### 결함 4 — 전수 주입이 기술 명세를 굶겼다 (D-010 의 2차 효과, 같은 세션에서 발견·수정)

**푸시 직전 마지막 전체 테스트에서 3건이 깨져 발견했다.** 원인은 테스트 오염이 아니라 실제 회귀다.

D-010 으로 상한을 없앤 뒤, **도메인·조직범위가 선언되지 않은 프로젝트**에서는 "전수"가 곧
"DB 전체"가 됐다. 실측: 개발 DB 70건 = **21,877자** > 컨텍스트 예산 **20,000자**.
`build_core_context` 는 마지막에 `_clip(..., ctx_max)` 로 꼬리를 자르므로, 기준정보 뒤에 붙는
**기술 명세(화면 구성·API 계약·DB 스키마)가 통째로 사라졌다** → 코더가 API 계약을 못 본다.

→ **기준정보에 컨텍스트 예산의 몫을 명시 배정**한다:
`_master_budget = max(8000, int(ctx_max * 0.5))` 을 `get_master_context(state, max_chars=...)` 로
넘기고, 잘릴 때는 레코드 경계에서 끊고 블록에 그 사실을 적는다.
수정 후 실측: ctx 21,877 → 10,539자, `OVERVIEW`·`FE`·`API` 전부 생존(`DB` 는 프론트 태스크라
정상 제외), 블록 끝에 *"70건 중 47건만 표시됐다 … 추정하지 말 것"* 명시.

> **판단 근거**: 기준정보가 중요하다는 것과 기준정보가 나머지 전부를 굶겨도 된다는 것은 다르다.
> 상한을 되살린 것이 아니라 **호출자가 자기 예산의 몫을 배정**하는 구조로 바꾼 것이다 —
> 조직·도메인이 제대로 선언된 실제 경로(30건 ≈5,300자)에서는 여전히 전량이 들어간다.

⚠️ **부수 발견**: `tests/test_context_full_files.py` 의 기존 테스트들은 **실제
`data/master/master.db` 를 읽는다.** 그래서 DB 가 비어 있으면 이 회귀를 못 잡는다(내가 실제 DB 에
시드를 넣은 뒤에야 드러났다). `test_master_block_cannot_starve_the_rest` 는 거대한 블록을 직접
주입해 **DB 상태와 무관하게** 배선을 검증한다. 나머지 테스트의 실제 DB 의존은 잔여 부채다.

### 결함들의 공통점

전부 **생산자→소비자 배선 누락** 유형이다(이 프로젝트에서 반복되는 결함 계열, `TEAM_PROTOCOL`
§8-2). 만들기는 했는데 **소비자가 쓸 수 있는 형태인지 확인하지 않았다.**
그리고 네 건 다 **단위 테스트로는 드러나지 않았다** — 실제 데이터를 넣고 실제 주입 결과를
눈으로 봐야 나왔다. 교훈: **기능 완성의 판정 기준에 "실제 데이터로 최종 산출물 확인"을 포함해야
한다.**

결함 4 는 특히 **내가 고친 것이 만든 2차 결함**이다. 상한을 없애는 결정(D-010) 자체는 근거가
있었지만, 그 블록을 소비하는 쪽(컨텍스트 엔진)의 예산을 확인하지 않았다. 같은 배선 누락을
**고치는 과정에서 반복**했다는 뜻이다 — 앞으로 주입량·크기를 바꿀 때는 **소비자의 예산까지
같은 커밋에서 확인**한다.

### R-001 잔여 완료 — 버전 고정 · 적용 기간 평가

`master_version`·`effective_from`·`effective_to` 는 **컬럼만 있고 아무도 읽지 않았다.**
컬럼이 있으니 동작한다고 오해하기 딱 좋은 상태였고, 실제로는 미래 시작일도 즉시 적용되고
종료일이 지나도 계속 적용됐으며 개정 후 재현이 불가능했다.

| 추가 | 내용 |
|---|---|
| `_in_effect(binding, as_of)` | 기간 평가. 경계는 `from <= as_of < to`, 빈 값은 무제한 |
| `bindings_for_scope(...) -> {code: 고정버전 or None}` | 상속·기간을 함께 해석. **자기 노드 > 조상**(하위가 상위를 덮는다) |
| `get_record_version(code, v)` | 폐기된 구판을 꺼낸다 — 개정은 물리 삭제가 아니라 스탬프라 남아 있다 |
| 주입 경로 치환 | 고정 버전이 있으면 캐시(현행판)를 건드리지 않고 **이 요청에서만** 구판으로 바꾼다 |
| `_fmt_record` 표시 | `버전 v1 고정(현행판 아님)` — 표시하지 않으면 왜 최신값과 다른지 아무도 모른다 |
| 겹치는 기간 결정론 | 같은 노드·같은 코드에 기간이 겹치면 **늦게 시작한 것이 이긴다**. 순회 순서에 맡기면 같은 입력에 다른 결과 |
| `unbind_master_from_scope` + `DELETE /scope-bindings/{id}` | 소프트 해제. **해제는 차단이 아니다** — 마지막 바인딩을 풀면 전사 공통이 된다 |
| API | `POST /scope-bindings` 에 `effective_from/to`, `GET /scope-bindings/allowed` 에 `as_of`·`pinned_versions` |

실측(실제 API): 현행 v2(price 99999)인 상태에서 v1 고정 → 주입된 줄이
`버전 v1 고정(현행판 아님) | … base_price_usd=15000`. `as_of=2031` 로 조회하면 2030 시작
바인딩이 이겨 고정이 풀린다. 테스트 14건 추가(`tests/test_master_binding_version_period.py`).

> ⚠️ **작업 중 발견한 함정**: `bind_master_to_scope` 의 UNIQUE 키가 `effective_from` 을 포함해서
> **기간이 같으면 새 바인딩이 아니라 기존 바인딩을 덮어쓴다**(upsert). "v1 고정을 추가한다"고
> 호출했다가 시드 바인딩을 갈아치웠다. docstring 에 경고를 남겼고, 관리 UI 에서 '추가'와 '수정'이
> 같은 호출임을 사용자에게 드러내야 한다.
> 부수 효과로 **결함 3의 수정이 실제로 복구에 작동함**을 확인했다 — 재시드 한 번으로 44/44 복원.

### 미바인딩 노출 상시 관측 — `GET /scope-bindings/coverage`

같은 유형의 사고가 **네 번** 났다(재시드 건너뜀 / 조직 코드 불일치 / 바인딩 해제 / ECM 시드 전
적재). 규칙 자체는 유지할 가치가 있으므로 — 전부 막으면 도입 전 기능이 통째로 멈춘다 —
**노출 건수를 상시 보이게** 만들었다. 위험한 건 규칙이 아니라 조용한 노출이다.

`scope_coverage()`: `exposed_codes` · `bound/total` · `coverage_ratio` · `by_scope_node`.
폐기 레코드는 주입되지 않으므로 노출로 세지 않는다(허위 경보 방지).

**실측**: 개발 DB 70건 중 바인딩 44 / **노출 26** (커버리지 62.9%). 노출 26건은 전부
2026-07-25 에 수동 입력된 `source="user"` 레코드이고 저장소 어느 스크립트도 만들지 않는다.

### 중복 기준정보 후보 탐지 — `GET /records/duplicates`

위 26건을 보다 발견한 것: 문제는 미바인딩만이 아니라 **같은 대상이 두 벌**이라는 점이다.
둘 다 활성이면 **둘 다 주입되어 LLM 이 서로 다른 두 기준값을 동시에 본다.**
명세서 §14 M1 이 「MDM 확장 — 중복 후보」로 지정해 뒀는데 미구현이라 아무도 몰랐다.

판정은 LLM 0콜, 문자열 비교만: `same_normalized_code`(접두사·동의약어 제거 후 동일) ·
`same_name`(괄호 주석·구분자 제거 후 동일) · `shared_alias`.
**자동 병합하지 않는다** — 정본 판단은 현업 몫이다.

> ★ **오탐에 다른 조치를 안내하는 것이 이 탐지기의 값어치다.** 초안은
> `M1-FIN-COST-STRUCTURE`(배터리소재 원가구조)와 `M2-FIN-COST-STRUCTURE`(동제련 원가구조)를
> high 중복으로 올렸다. 이건 의도된 사업부별 분리이고 "정본을 정해 하나를 폐기하라"는 조치가
> 여기서는 **데이터 손실을 유도한다.** → 조직 범위를 함께 보고 서로 다른 조직에만 적용 중이면
> `same_code_different_scope`/low + "병합하지 마십시오". `shared_alias` 도 레코드 중복이 아니라
> "별칭이 대상을 특정하지 못한다"로 조치를 분리했다.

**실측**: 13건 — high 6(전부 진성 중복) / medium 2 / low 5. 초안 대비 오탐 3건이 low 로
내려가고 조치 문구가 반대로 바뀌었다.

> ⚠️ **라우팅 결함 하나**: `/records/duplicates` 를 `/records/{master_code}` **아래**에 정의해
> 경로 변수가 `duplicates` 를 코드로 잡아먹었다 — 단위 테스트 10건 전부 통과하는데 HTTP 로는

## 4-6. 데이터 카탈로그 · 용어사전 (M1 4·5번 완료)

### 데이터 카탈로그 — `/api/v1/catalog`

§6.1 은 카탈로그를 MDM 으로도 Graph RAG 로도 **대체 불가**로 규정한다.
MDM = 값 그 자체 / 카탈로그 = **그 값이 어디 있고 누가 책임지며 얼마나 자주 갱신되나.**

**크로스워크와 병렬 테이블을 만들지 않았다.** `external_schemas(system_id, entity, field)`
(M2 연계 계약)와 `data_assets`/`data_asset_fields`(거버넌스)는 같은 물리 대상을 다른 목적으로
기술한다. 병렬로 만들면 같은 테이블이 두 벌로 등록되고, 그건 이 문서 §4-5 에서 기준정보로
실제 겪은 문제다. 그래서 크로스워크 **위에 얹는 계층**으로 만들었다 — `(system_id, entity)`
링크, `sync_from_crosswalk()` 단방향 멱등 임포트, `origin='crosswalk'` 필드의 **스키마 속성은
편집 금지**(편집해도 다음 동기화에 되돌아가므로 허용하면 같은 수정을 반복하게 된다).

`governance_gaps()` — `no_owner` / `no_refresh_cadence` / `no_fields` / `sensitivity_below_pii`.
**자동으로 메우지 않는다.** 소유자를 시스템이 추측해 넣으면 아무도 책임지지 않는 자산이
책임자가 있는 것처럼 보인다 — 없는 것보다 나쁘다. PII 가 있는데 민감도가 낮아도 자동 상향하지
않고 표시만 한다(조용히 바뀌면 사람이 검토하지 않는다).

> ⚠️ **실측에서 잡은 결함**: 폐기(소프트 삭제)된 자산이 UNIQUE 인덱스를 계속 점유해서
> ① 한 번 폐기한 테이블을 영원히 다시 등록할 수 없고 ② 동기화가 폐기된 자산을 '재사용'해
> **목록에 안 보이는 자산에 필드만 써넣고 성공했다고 보고**했다. 인덱스에 `status='active'`
> 조건을 추가하고, 동기화는 폐기된 링크 자산을 재활성한다(원천에 다시 나타났다 = 되살아난
> 것). 사람이 붙인 이름은 동기화가 덮지 않는다.
> 단위 테스트 20건 전부 통과하는 상태에서 **실제 API 프로브로만** 드러났다.

### 용어사전 + §6.4 매칭 — `/api/v1/glossary`

MDM 은 **값**이고 용어사전은 **말**이다. "가동률"이 부서마다 다르게 계산되는 것이 제조 현장의
실제 문제이고, 합의된 계산 정의(`business_terms.calculation`)를 적어두지 않으면 LLM 이
그때그때 지어낸다.

**테이블만 만들지 않고 소비자까지 붙였다** — 이번 세션에서 "생산자만 있고 소비자가 없는"
결함을 네 번 겪었으므로, 용어사전을 단독으로 넣지 않고 §6.4 흐름을 함께 구현했다:
`업무 용어 → 동의어 확장 → 카탈로그 후보 검색 → MDM 연결 확인 → 품질·권한 확인 → 요구사항 상태 갱신`

**자동 확정하지 않는다**(§6.4: "최종 매칭 확정은 데이터 오너 또는 승인된 규칙"). `match` 는
후보·근거와 `blockers` 만 만들고, 상태 갱신은 `confirm` 이라는 별도의 사람 행위다. 자동으로
`held` 로 바꾸면 준비도가 근거 없이 올라가고, 준비도는 착수 판단에 쓰이므로 그게 가장 위험하다.

blockers 3종: 책임자·갱신주기 없음(5단계 불가) / 기준정보 연결 필드 없음(4단계) /
미승인 동의어로 매칭됨(확정 근거 약함).

> ⚠️ **실측에서 잡은 것**: `ORG_ENFORCE` 가 꺼져 있으면(기본값) `user_id` 가 비어 승인·확정
> 엔드포인트가 **전부 400 으로 사용 불가**였다. 가짜 승인자를 넣으면 아무도 승인하지 않은 것이
> 승인된 것처럼 기록되므로 거절이 맞지만, 이유 없는 400 은 무엇을 해야 할지 알려주지 않는다
> → **401 + 해결 방법**(X-User-Id 헤더 또는 ORG_ENFORCE). 라우트 테스트로 잠금.

실측: 미승인 동의어 `OEE` 로 걸린 후보가 `confirmable=False` → 동의어·용어 승인 후 `True`.

## 4-7. 데이터 품질 · 계보 (M1 6번 완료)

§6.1 이 이 둘에 붙인 제약이 설계의 전부다 — 품질은 **"단순 LLM 평가 금지"**, 계보는
**"추적성 그래프의 근거"**. 그래서 이 두 기능에서 지킨 것은 "동작하는가"가 아니라
**"거짓을 만들지 않는가"** 다.

### 품질 — 핵심 인자는 점수가 아니라 `method`

| method | 뜻 | 제약 |
|---|---|---|
| `measured` | 실제로 읽어 센 값 | **`evidence_ref` 없이 기록 불가** — 무엇을 실행해 얻었는지 없으면 "측정했다"를 검증할 수 없다 |
| `declared` | 오너 신고값 | 근거가 사람임을 전제로 읽는다(막으면 아무도 등록하지 않는다) |
| `computed` | 메타데이터만으로 계산 | 원본을 읽지 않았다 |

**측정하지 않은 항목은 `0.0` 이 아니라 `NULL`.** 0점과 미측정은 다르고, 0 으로 채우면
"완전성 0%"라는 없는 사실이 생긴다.

### 최신성 — 모르는 것을 좋게 치지 않는다

`last_refreshed_at` + `refresh_cadence` 로 **계산한다**(추정하지 않는다). 이 둘은 우리가 실제로
가진 사실이라 계산에 근거가 있다. 둘 중 하나라도 없거나 `adhoc` 이거나 시각이 깨졌으면
`unknown` 이고 **`fresh` 로 낙관하지 않는다** — 모르는 것을 좋게 치면 §6.4 의 최신성 확인이
형식만 남는다. 주기 1배 초과 `late`, 2배 초과 `stale`.

### 계보 — 근거 없는 선을 긋지 않는다

> 추측으로 만든 영향 분석은 **"영향 없음"을 잘못 말해서** 사고를 만든다. 틀린 영향 분석은
> 없는 영향 분석보다 위험하다. 그래서 **LLM 이 긋는 간선은 만들지 않았다.**

- `derive_edges()` 는 **명시된 링크에서만** 도출한다(system→asset, asset→field,
  field→master, term→master). 이름 유사도로는 잇지 않는다.
- `impact_of()` 는 순환 가드 + 깊이·노드 상한. 조직 데이터에 순환이 없다고 가정하면 언젠가
  무한 루프로 서버가 멈춘다. 잘리면 `truncated` 로 알린다.
- 응답에 `limitation` 을 **항상** 넣는다: *"계보는 등록된 관계만 안다. 영향 0건이 곧 안전을
  뜻하지 않는다."* 이게 없으면 미등록 자산에 대한 변경이 안전하다고 오독된다.

### §6.4 와 배선했다 (테이블만 만들지 않는다)

- `match_requirement` 가 **최신성을 blocker 로** 쓴다 — 오래된 자산을 확정하면 준비도만
  올라가고 실제로는 낡은 값을 쓰게 된다. 후보에 품질 프로파일도 함께 노출한다.
- `confirm_match` 가 **계보 간선을 남긴다**(`asset -confirms-> requirement`). 확정은 "이
  요구사항은 이 자산으로 충족한다"고 사람이 선언한 **사건**이므로, 여기서 안 남기면 나중에 그
  자산이 바뀔 때 무엇이 영향받는지 알 수 없다.

실측(실제 API): 근거 없는 `measured` 400 / 미측정 `validity` null 유지 / 도출 3건 /
`FG-NISO4-001` 상류에 field·term·asset / 미등록 노드는 영향 0건 + 한계 문구 동반.
