## 1. 결론

AI Factory Studio가 성공할 수 있는 길은 더 많은 AI 기능을 한 화면에 모으는 것이 아니다. **회사의 실제 데이터와 업무 규칙을 이용해 현업 앱을 만들고, 그 앱에서 발생한 운영 데이터로 경영 시나리오를 계산하며, 검토·승인·실행·효과 측정까지 하나의 추적 가능한 순환으로 닫는 것**이다.

우리가 만들어야 할 제품 범주는 다음과 같다.

> **Manufacturing Management Twin & Operational App Factory**  
> 제조기업의 실제 업무와 경영 의사결정을 연결하는 운영 앱 공장 겸 경영 디지털트윈

이 정의는 의도적으로 범용 `AgentOS`, 범용 `App Builder`, 범용 `Ontology Platform`과 거리를 둔다. 이 세 기능은 필수 기반이지만 제품의 정체성은 아니다. 정체성은 아래 폐루프에 있다.

```text
회사 구조·업무 의미·실제 데이터
        ↓
현업이 생성한 운영 앱과 업무 입력
        ↓
확정 계산식 기반 경영 시뮬레이션
        ↓
근거·영향·대안을 갖춘 의사결정 패키지
        ↓
승인·업무 배포·실행 증빙
        ↓
실적·효과 측정과 지식 환류
        ↺
```

이 순환이 실제 데이터로 한 번도 완주하지 못한다면, 기능 수와 에이전트 수가 많아도 제품은 완성되지 않은 것이다.

## 2. 이번 재검토의 판단 기준

이번 평가는 다음 네 층을 섞지 않는다.

1. **구현 완료**: 현재 소스와 테스트로 동작이 확인되는 것
2. **부분 구현**: 저장 구조나 API는 있으나 실제 사용자 폐루프가 닫히지 않은 것
3. **설계 완료**: 문서와 프로토타입은 있으나 제품 코드가 없는 것
4. **전략 가설**: 시장·고객·운영 환경에서 아직 증명하지 않은 것

또한 경쟁사의 공개 기능을 우리의 완성도처럼 간주하지 않는다. 경쟁사의 웹사이트는 방향과 시장 기준을 확인하는 자료이고, 고객 성과 수치는 독립 검증 전까지 공개 주장으로 취급한다.

## 3. 경쟁 기준점 재평가

### 3.1 Enhans와 겹치는 영역

Enhans의 최신 공식 설명은 AgentOS를 다음 다섯 층으로 제시한다.

1. Pipeline Builder: 데이터 연결·준비
2. Ontology Manager: 업무 의미와 관계 정의
3. Agent Builder: 에이전트·도구·조건·HITL 흐름 구성
4. App Builder: 자연어 기반 대시보드·입력 폼·운영 앱 생성
5. ACT-2: 브라우저와 업무 시스템에서 실제 실행

공식 자료:

- AgentOS: https://www.enhans.ai/agent-os
- Ontology: https://www.enhans.ai/ontology
- Agent Builder: https://www.enhans.ai/agent-builder
- App Builder: https://www.enhans.ai/app-builder
- ACT-2: https://www.enhans.ai/act-2

따라서 다음 문장은 더 이상 차별화 문장이 아니다.

- “기업 데이터를 연결한다.”
- “온톨로지 또는 GraphRAG로 의미를 이해한다.”
- “여러 에이전트를 워크플로우로 연결한다.”
- “자연어로 업무 앱을 만든다.”
- “AI가 외부 시스템에서 행동한다.”

이 기능들은 경쟁 참가 자격이지 승리 조건이 아니다.

### 3.2 우리가 추격해야 할 경쟁사의 강점

현재 공개 제품 서사 기준으로 Enhans가 앞선 부분은 다음과 같다.

- 데이터에서 실행까지 이어지는 제품 설명이 단순하고 일관된다.
- 앱 생성이 정적 화면이 아니라 온톨로지·에이전트·워크플로우와 연결된다고 명확히 설명한다.
- 실제 UI 또는 API가 없는 환경에서 행동하는 실행 계층을 별도 제품으로 제시한다.
- 온프레미스·하이브리드·클라우드 배포를 상용 제품의 전제로 설명한다.
- 여러 산업과 고객 적용을 전면에 내세워 시장 검증 인상을 만든다.

우리는 이 강점을 부정하거나 용어로 덮어서는 안 된다. 실행 안정성, 제품 서사, 배포·보안, 레퍼런스는 따라잡아야 한다.

### 3.3 우리가 이겨야 할 다른 경기장

우리의 승부처는 “에이전트를 더 잘 만드는 도구”가 아니다.

| 범용 AgentOS의 질문 | AI Factory Studio가 답해야 할 질문 |
|---|---|
| 어떤 에이전트를 만들 것인가? | 이 결정이 생산·재고·현금·손익에 얼마의 영향을 주는가? |
| 어떤 데이터에 연결할 것인가? | 이 수치의 소유자·기준시점·계산식·품질·계보는 무엇인가? |
| 어떤 앱을 생성할 것인가? | 이 앱이 어느 조직의 어떤 업무 책임과 데이터를 이어받는가? |
| 어떤 행동을 자동화할 것인가? | 누가 어떤 근거로 승인했고 실행 전후 효과는 얼마였는가? |
| 어떤 답을 생성할 것인가? | 같은 기준선과 가정에서 다시 계산해도 같은 결과가 나오는가? |

## 4. 독자 제품을 만드는 다섯 개 해자

### 4.1 제조 경영 온톨로지(경영 의미 모델)

단순 용어집이 아니라 `회사 구조 → 조직 책임 → 가치사슬 → 업무 사건 → KPI → 재무 영향`을 연결하는 **제조 경영 온톨로지(Manufacturing Management Ontology)**를 만든다. `경영 의미 모델`은 제품·사업 설명에서 쓰는 쉬운 표현이고, 사용자 화면에서는 `기업 경영 의미지도`로 설명한다.

최소 연결 예시는 다음과 같다.

```text
원료 구매계획
  → 계약·발주
  → 선적·통관·입고
  → 재고 가용량
  → 생산 투입·수율
  → 제품 생산량
  → 판매·매출
  → 운전자본·현금흐름·손익
```

필수 요소:

- 그룹·법인·사업부·사업장·공장의 계층과 REAL/VIRTUAL/COMPETITOR 구분
- 품목·고객·공급사·공정·설비·계정·원가요소·KPI의 마스터와 유효기간
- 동의어·유사어·코드 크로스워크와 출처
- 데이터 소유자·품질 규칙·계보·계약
- 계산식과 정책 규칙의 버전
- 조직 범위와 사용 권한

책임 경계는 다음과 같이 고정한다.

- MDM은 공식 업무 대상과 기준값을 관리한다.
- 데이터 카탈로그는 데이터 자산의 위치·책임·품질·계약·사용처를 관리한다.
- 용어사전과 Crosswalk는 언어·코드·외부 스키마를 표준 개체에 대응시킨다.
- 제조 경영 온톨로지는 개체·업무 사건·조직 책임·KPI·정책·영향 관계의 의미와 제약을 관리한다.
- 지식 그래프는 온톨로지를 따르는 관계 인스턴스와 근거를 저장한다.
- Graph RAG는 관계를 따라 근거와 영향 경로를 찾는 검색 방식이며 온톨로지 자체가 아니다.
- 계산 그래프는 온톨로지에서 발견한 영향 경로 중 승인된 산식만 수치로 계산한다.

현재 ECM, MDM, 카탈로그, 용어사전, 계보, 계약, `entity_types`는 좋은 기반이다. 하지만 `entity_types`와 허용 관계 목록만으로 완성형 온톨로지라고 부르지 않는다. 아직 이들을 한 번에 질의·검증하는 **명시적 제조 경영 온톨로지 런타임**이 부족하다. Graph RAG라는 이름을 붙이는 것보다, 실제 업무 질문에 어떤 엔터티와 관계를 통해 답했는지 증명하는 것이 우선이다.

### 4.2 Host-governed Operational App Factory

생성 앱은 독립 제품이 아니라 AI Factory Studio 안에서 실행되는 `App-in-App`이다. 인증, 조직 범위, 감사, 데이터 접근, 알림, 의사결정은 호스트 플랫폼을 상속해야 한다.

고유 가치는 코드 생성 속도가 아니라 다음 계약의 자동 준수다.

- 생성 앱은 별도 로그인·사용자 DB·JWT 발급자를 만들지 않는다.
- 데이터는 직접 DB 접속이 아니라 권한 평가를 거친 Host Runtime API로 접근한다.
- 앱 Manifest가 필요한 데이터·행동·외부연계 능력을 선언한다.
- 선언되지 않은 능력은 런타임에서 차단한다.
- 앱 전달은 화면 소유권 이전이지 데이터 권한 부여가 아니다.
- 업데이트 시 Manifest와 데이터 계약 차이를 다시 승인한다.
- 릴리스·실행·입력·승인·오류가 동일 감사 체계에 남는다.

### 4.3 결정론적 경영 디지털트윈

LLM은 가정과 설명을 돕지만 숫자를 임의 생성하지 않는다. 예측·시뮬레이션의 핵심 결과는 버전이 고정된 입력, 계산식, 모델, 기준선으로 재현되어야 한다.

필수 구조:

- 기준선 스냅샷
- 가정 세트와 변경 이력
- 외부지표 관측값·전망값·시나리오값 분리
- 단위·통화·기간·조직 범위
- 결정론적 계산 엔진
- 민감도·기여도·불확실성 구간
- 과거시점 백테스트
- 실제 실적과 예측 오차 분해
- 수식·데이터·결과의 계보

“시뮬레이션”이라는 이름으로 LLM이 그럴듯한 숫자를 만드는 순간 제품 신뢰는 무너진다.

### 4.4 Decision-to-Execution-to-Learning 폐루프

분석 결과는 보고서로 끝나지 않는다.

1. 의사결정 요청자가 근거·대안·긴급도를 제출한다.
2. 의사결정권자는 기준선·영향·불확실성·타 부서 관점을 본다.
3. 승인 결과는 실행 업무와 담당자에게 배포된다.
4. 실행 증빙과 결과 데이터가 연결된다.
5. 사전에 약속한 효과와 실제 효과를 비교한다.
6. 차이를 데이터 품질, 가정, 계산식, 실행 편차로 분해한다.
7. 검증된 학습만 플레이북·스킬·정책 후보로 승격한다.

이 폐루프가 우리의 가장 강한 제품 서사다. 앱 전달·수락, 의사결정 회의, 세 관점 검토서, 대내외 보고서 발간은 각각 독립 기능이 아니라 이 폐루프의 단계여야 한다.

### 4.5 측정 가능한 비용·품질 최적화

저렴한 모델을 많이 쓰는 것이 목표가 아니다. 업무 위험과 산출물 난이도에 따라 최소 비용으로 목표 품질과 완료시간을 만족시키는 것이 목표다.

필수 계측:

- 에이전트·단계·업무유형별 입력/출력 토큰과 실제 비용
- 모델·공급자·재시도·폴백 경로
- 성공률, 재작업률, 사용자 수정량, 산출물 결함
- 지연시간과 한도 대기시간
- 컨텍스트 출처별 사용량과 기여
- 같은 테스트셋에서 모델 조합별 품질·비용 곡선

라우팅은 감이 아니라 실측으로 바뀌어야 한다. 반복 업무는 캐시·결정론적 규칙·소형 모델을 우선하고, 고위험 판단과 복잡한 코드에만 강한 모델을 사용한다.

### 4.6 다섯 해자를 작동시키는 두 가지 진입 기반

#### A. Minimum Viable Actual 부트스트래핑

디지털트윈은 데이터가 충분히 쌓인 뒤에만 시작하는 제품이어서는 안 된다. 반대로 시드·샘플·LLM 생성 수치를 Actual로 가장해서도 안 된다. 첫 파일럿은 필요한 전체 ERP를 복제하지 않고, 결정과 계산에 필요한 **최소 실제 데이터(Minimum Viable Actual, MVA)**를 안전하게 확보하는 절차를 제품 기능으로 제공해야 한다.

MVA 부트스트랩 순서:

1. ERP/MES/WMS/TMS/LIMS, Excel, 계약·선적 문서의 원천 목록과 소유자를 등록한다.
2. 원천을 복제하기 전에 스키마·기간·건수·품질을 읽기 전용으로 프로파일링한다.
3. 파일럿에 필요한 엔터티·필드·기간만 최소 추출한다.
4. 원본을 `RAW`, 오류·미매핑을 `QUARANTINE`, 표준화 결과를 `STANDARDIZED`, 오너 승인 결과를 `CERTIFIED`로 분리한다.
5. 코드·단위·통화·기간·조직을 MDM·Crosswalk와 매핑한다.
6. 집계값·건수·금액을 원천 시스템과 대사한다.
7. 승인된 시점 스냅샷을 첫 기준선으로 고정한다.
8. 이후 증분 데이터는 동일 계약으로 반복 적재하고 품질 변화를 감시한다.

핵심 원칙:

- 시드·합성 데이터는 기능 검증용이며 경영 정확도 증명에 사용하지 않는다.
- 문서·파일만으로 시작할 수 있지만 `Actual`, `Plan`, `Forecast`, `Scenario`, `Synthetic`을 절대 섞지 않는다.
- 데이터가 부족하면 가능한 계산 범위와 막힌 결과, 다음 확보 작업을 함께 제시한다.
- 원천 전체를 무거운 인터페이스로 복제하지 않고 파일럿 최소 범위와 읽기 전용 Snapshot부터 시작한다.
- 데이터 오너 승인 없는 값은 `CERTIFIED` 또는 공식 경영 수치가 될 수 없다.

#### B. 기존 외부 협업 시스템과의 공존 — External Engagement Integration Boundary

거래처·관세사·포워더·운송사 등 외부 참여자는 고객사가 이미 운영하는 공급사 포털·물류/통관 시스템·협력사 웹시스템에서 데이터를 입력한다고 전제한다. LS 환경의 LPL(LS Partner's Lounge)은 그 첫 사례다. AI Factory Studio는 이 기능을 다시 만들거나 외부 참여자에게 자체 화면·계정·앱을 제공하지 않는다.

제품 경계를 다음처럼 고정한다.

```text
외부 참여자
   ↓ 입력·수정
고객사 기존 외부 협업 System of Engagement
   ↓ 승인된 Read-only API/MCP/배치 계약
AI Factory Studio — 표준화·연계·시뮬레이션·의사결정
   ↓ 내부 승인된 실행 지시 또는 결과
ERP/MES/외부 협업·기간계 시스템 등 고객사 기존 운영 시스템
```

외부 협업 레거시 연계 원칙:

- 고객사 기존 시스템은 외부 참여자 신원, 입력 화면, 원본 업무 사건의 책임을 유지한다.
- AI Factory Studio에는 외부 계정과 파트너용 UI를 만들지 않는다.
- 첫 연계는 승인된 Query Contract를 가진 **읽기 전용 MCP/API**로 한다.
- API가 없으면 승인된 파일 Export 또는 Read Replica를 사용하고 화면 스크래핑은 최후 수단으로 둔다.
- 원천 전체를 복제하지 않고 파일럿에 필요한 계약·선적·통관·운송·도착 사건만 조회한다.
- `source_system_id`, 원천 업무키, 사건 ID, 원천 버전, 발생·수정·조회 시각을 보존한다.
- 원천 필드는 MDM·Crosswalk를 통해 표준 엔터티와 연결하고, 미매핑·충돌은 QUARANTINE에 둔다.
- 원천 값은 출처가 명확해도 내부 경영 계산에 쓰기 전 데이터 계약·대사·상태 규칙을 통과해야 한다.
- 데이터가 정정·취소되면 기존 값을 덮어쓰지 않고 새 버전·사건으로 반영한다.
- 기존 시스템으로 결과를 되돌릴 때도 별도 승인된 쓰기 계약과 사용자 확인 없이는 실행하지 않는다.

이 결정은 AI Factory Studio가 모든 시스템과 모든 사용자를 흡수하는 거대한 ERP가 아니라, 기존 시스템의 책임을 존중하면서 데이터를 의미·계산·결정으로 연결하는 상위 지능 계층임을 명확히 한다.

제품 코어에는 특정 시스템명을 하드코딩하지 않는다. LPL은 `ls_lpl` Reference Profile로 격리하고, 다른 회사에서는 해당 회사의 Supplier Portal·Logistics Portal·Customs System Profile로 교체한다.

## 5. 현재 문서 체계에 대한 냉정한 평가

### 5.1 Product Bible

**유효한 점**

- 실제 데이터, 사용자 생성 앱, 시뮬레이션, 설명 가능한 의사결정이라는 북극성이 명확하다.
- AI를 진실의 원천으로 두지 않는 원칙이 올바르다.
- 범용 플랫폼 조기 구축과 기능 나열을 경계한다.

**미비점**

- 경쟁 제품이 동일한 기반 기능을 주장하는 상황에서 제품 범주를 더 날카롭게 정의하지 못했다.
- 첫 번째 완전한 업무 폐루프가 한 문장으로 고정되지 않았다.
- 실행·효과 측정이 제품 가치의 마지막 단계라는 선언이 약하다.

### 5.2 LLM 구현 마스터 명세

**유효한 점**

- 상담, Blueprint, MDM, 카탈로그, 권한, 시뮬레이션, 외부지표, Jarvis를 구현 가능한 단위로 분해했다.
- 데이터·권한·비용·품질의 비협상 조건이 포함되어 있다.

**미비점**

- 기능별 상세도가 높아질수록 전체 완성 순서와 시장 검증 순서가 흐려졌다.
- 구현된 것과 설계만 된 것의 상태가 시점에 따라 섞여 있다.
- 제조 경영 온톨로지(경영 의미 모델) 런타임, 앱 Host SDK, 실운영 실행 계층, 상용 배포 기반이 충분히 구체화되지 않았다.
- 마일스톤 완료를 API·테스트 수로 판단하기 쉽고, 현업 폐루프 완주와 ROI 증명이 약하다.

### 5.3 UI/UX 및 폐루프 설계

**유효한 점**

- Living Enterprise Canvas, 전용 Studio, 전역 Jarvis, 진행 투명성은 제품 철학과 맞는다.
- 앱 전달·수락, 의사결정 검토, 보고서 발간이 구체적인 화면과 작업서로 정리됐다.

**미비점**

- 화면 완성도가 런타임·권한·데이터 계약보다 앞서갈 위험이 있다.
- 기능 수가 늘면서 하나의 사용자 여정이 여러 오버레이와 전용 화면으로 분산됐다.
- 실제 수치, 기준선, 근거, 실행 결과가 없는 상태에서 화면만 구현하면 데모 제품으로 보일 수 있다.

### 5.4 결론

기존 문서를 폐기할 필요는 없다. 철학과 기능 정의는 유지하되, 최신 실행 우선순위는 본 문서와 [`AI_FACTORY_STUDIO_FINAL_COMPLETION_EXECUTION_PLAN_2026-08-03.md`](../roadmap/AI_FACTORY_STUDIO_FINAL_COMPLETION_EXECUTION_PLAN_2026-08-03.md)를 기준으로 한다.

## 7. Claude Code 최신 CL-0 구현 재검토

### 7.1 확인 결과

- 커밋: `a484c6f63 feat(cl-0): App-in-App Manifest·자체 인증 정적 게이트`
- 집중 테스트: 45건 통과
- Manifest에 플랫폼 인증·조직 컨텍스트·감사 상속 계약을 저장한다.
- 생성 코드에서 로컬 로그인, 사용자 저장소, JWT 발급자 등의 패턴을 찾는다.
- 릴리스 스냅샷에 Manifest와 검사 결과를 기록한다.

방향은 정확하다. 생성 앱이 플랫폼 권한을 상속하도록 만드는 첫 계약이 생겼다.

### 7.2 통합 전 반드시 보강할 항목: CL-0.5

현재 정적 검사는 보안 경계가 아니라 린트와 증빙이다. 다음 문제를 해결하기 전에는 “자체 인증 방지 완료”로 표현하면 안 된다.

1. 문자열 분리, 간접 호출, 함수명 변경으로 정규식 검사를 우회할 수 있다.
2. 한 줄에 `test`, `example`, `external_api` 같은 허용 단어를 섞으면 차단이 약화될 수 있다.
3. 프로젝트의 `.archive`까지 검사할 수 있어 과거 코드가 현재 릴리스를 오염시킨다.
4. 실제 릴리스 파일 목록이 아니라 전체 프로젝트를 검사해 소유하지 않은 파일과 잔여물이 섞인다.
5. 빈 capability 목록도 유효한 Manifest가 되어 실제 사용 능력과 선언의 차이를 잡지 못한다.
6. 검사 실패 또는 차단 상태여도 릴리스 생성 자체는 가능하다.
7. 런타임에서 생성 앱이 직접 DB 자격증명이나 상위 토큰을 얻지 못하게 하는 강제가 아직 없다.

CL-0.5 완료 조건:

- 현재 릴리스의 `file_index` 또는 확정 Manifest 파일만 검사
- `.archive`, 임시물, 이전 릴리스 제외
- 허용 문맥 규칙을 파일·AST·명시적 주석 지시자로 제한
- 읽지 못한 파일 또는 검사 오류는 Fail-closed
- 차단 결과면 릴리스가 `INELIGIBLE`이고 전달·실행 불가
- 선언 capability와 정적/런타임 관측 capability 차이 검출
- Manifest fingerprint와 업데이트 diff 저장
- Host Runtime API와 단기·범위 제한 토큰 설계 확정
- 우회·오염·빈 선언·불완전 검사 테스트 추가

### 7.3 CL-1 이후의 필수 구조

정적 검사만 강화해서는 충분하지 않다. 생성 앱에는 원천 DB와 플랫폼 권한을 주지 않고 다음 구조를 강제해야 한다.

```text
Generated App
   │  app_id + release_id + requested capability
   ▼
Host Runtime SDK
   ▼
Policy Decision / Enterprise Scope / Data Contract
   ▼
Scoped Data·Action API
   ▼
Audit + Decision Ledger + Telemetry
```

이 구조가 있어야 App-in-App 원칙이 실제 보안과 운영 자산이 된다.

## 8. 먼저 증명할 단 하나의 수직 폐루프

### 8.1 권고 파일럿

**원료 구매·도입 계획에서 경영 영향과 실행 결정까지**를 첫 수직 폐루프로 고정한다.

선정 이유:

- 구매, 물류, 생산, 재고, 판매, 재무가 자연스럽게 연결된다.
- 환율·원료가격·해상운임·전기료 같은 외부지표 영향을 설명하기 쉽다.
- 앱 전달·타 부서 입력·시뮬레이션·의사결정·실행·효과 측정을 모두 검증할 수 있다.
- 제조업 경영 디지털트윈의 차별성이 가장 잘 드러난다.

### 8.2 완주 시나리오

1. 데이터 준비 보드가 파일럿 MVA와 원천·소유자·결손을 먼저 제안한다.
2. 읽기 전용 ERP/파일 추출을 표준화·대사해 승인된 첫 기준선 Snapshot을 만든다.
3. 구매 담당자가 원료 도입 계획 앱을 생성한다.
4. 앱은 회사 품목·공급사·계약·조직 마스터와 데이터 계약을 상속한다.
5. 도착·이동 입력 기능을 내부 물류 담당자에게 전달한다.
6. 거래처·관세사·포워더·운송사는 고객사의 기존 외부 협업 시스템에서 통관·선적·운송 데이터를 입력한다. LS 파일럿에서는 LPL이 이에 해당한다.
7. AI Factory Studio는 고객사별 승인 Query Contract를 통해 필요한 업무 사건만 읽어온다.
8. 원천 시스템 키·버전·시점을 보존하고 MDM·Crosswalk 매핑과 대사를 거쳐 계산 가능한 운영 데이터로 승격한다.
9. 입력된 실제/예정 데이터가 재고·생산 가능량·현금흐름에 연결된다.
10. 환율, 원료가격, 운임, 전기료 변화를 시나리오로 적용한다.
11. 계산 엔진이 생산·매출·운전자본·손익 영향을 재현 가능하게 계산한다.
12. 시스템이 요청자·결정권자·영향부서 관점의 검토서를 만든다.
13. 회의와 승인 결과가 실행 업무로 배포된다.
14. 실제 입고·생산·재무 결과를 수집해 예상 대비 효과를 측정한다.
15. 차이를 데이터·가정·모델·실행 편차로 분해한다.

### 8.3 이 파일럿이 증명해야 하는 수치

- 업무 앱 생성부터 사용 가능 상태까지의 시간
- 기존 대비 수작업·중복 입력 감소 시간
- 전달·수락·조직 범위 오류 0건
- MVA 원천 대사 차이와 미매핑률
- AI Factory Studio 외부 계정·파트너용 화면 0건
- 외부 원천키·버전·정정·취소 사건 추적률 100%
- 고객사 Query Contract 허용 범위 밖 필드·행 조회 0건
- 동일 입력·모델 버전에서 결과 재현율 100%
- 예측값의 오차와 오차 원인 설명 가능 비율
- 결정 요청부터 승인까지 걸린 시간
- 실행 전후 목표 효과와 실제 효과의 연결률
- 앱/시뮬레이션 1회당 LLM 비용과 전체 운영 비용
- 사용자 수정량과 재작업률

---

## 9. 지금 하지 않을 것

독자 제품을 만들려면 포기할 범위가 필요하다.

- 모든 산업을 동시에 지원하지 않는다.
- 모든 업무를 범용 온톨로지로 먼저 모델링하지 않는다.
- 에이전트 수나 LLM 공급자 수를 제품 우위로 제시하지 않는다.
- 실제 인증·권한 강제 전에 외부 고객 배포를 약속하지 않는다.
- 실제 데이터 대사 없이 경영 예측 정확도를 홍보하지 않는다.
- 사용자 승인 없는 외부 쓰기와 자동 발간을 허용하지 않는다.
- 폐루프보다 화면 수를 늘리지 않는다.
- 범용 컴퓨터 사용 에이전트를 먼저 만들지 않는다. API·MCP·확정 커넥터를 우선한다.

---

## 10. 제품 메시지

### 내부 현업에게

> 필요한 업무 앱을 직접 만들되, 회사 데이터·권한·감사 기준을 자동으로 상속합니다. 다른 부서와 이어지는 입력과 의사결정도 하나의 흐름으로 관리합니다.

### 경영진에게

> 회사의 실제 운영 데이터를 기준으로 외부환경 변화가 생산·재고·현금·손익에 미치는 영향을 계산하고, 의사결정 이후 실제 효과까지 추적합니다.

### IT·보안 조직에게

> 현업 앱이 난립하지 않도록 모든 생성 앱을 호스트 런타임, 데이터 계약, 조직 권한, 감사, 릴리스 게이트 안에서 통제합니다.

### 시장에게

> AI Factory Studio는 범용 챗봇이나 앱 빌더가 아닙니다. 제조기업의 현업 앱, 경영 시뮬레이션, 의사결정과 실행 결과를 하나의 검증 가능한 운영체계로 연결합니다.

## 11. 전략 의사결정 원칙

새 기능이나 일정 변경은 다음 순서로 판단한다.

1. 첫 수직 폐루프 완주에 직접 필요한가?
2. 실제 데이터·권한·계산·증빙 중 하나를 강화하는가?
3. 경쟁사가 쉽게 복제하기 어려운 회사별 지식과 실행 이력을 축적하는가?
4. 사용자에게 측정 가능한 시간·품질·재무 효과가 있는가?
5. LLM 비용과 운영 복잡도를 감당할 수 있는가?

앞의 질문에 답하지 못하는 기능은 P2 이후로 미룬다.

---

## 12. 최종 선언

AI Factory Studio의 독자성은 온톨로지, 에이전트, 앱 생성, 디지털트윈이라는 단어에 있지 않다. **회사의 실제 업무가 앱으로 실행되고, 그 데이터가 경영 계산으로 이어지며, 의사결정과 실행 효과가 다시 회사 지식으로 돌아오는 구조**에 있다.

최종 완성의 기준은 기능 체크리스트가 아니라 다음 질문에 대한 증거다.

> “이 회사가 이 결정을 왜 내렸고, 어떤 데이터와 가정을 썼으며, 누가 실행했고, 실제로 무엇이 얼마나 달라졌는가?”

제품이 이 질문에 권한 범위 안에서 즉시, 재현 가능하게, 근거와 함께 답할 수 있을 때 AI Factory Studio는 독자적인 제품이 된다.
