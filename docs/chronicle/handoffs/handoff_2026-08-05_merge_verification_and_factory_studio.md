### 2.1 자동 점검이 4번을 놓친 이유 — 반드시 읽을 것

라우트에 `current_principal` 의존성이 **있으므로** 자동 점검은 「통제됨」으로 셌다.
**의존성이 있다는 것과 판정이 있다는 것은 다르다.** 주체를 받아 놓고 아무것도 판정하지 않는
라우트가 가장 안전해 보인다.

반대 방향 오탐도 있다. 판정을 헬퍼에 위임하는 라우트(`create_asset(..., p)` ·
`visible_tree(p, ...)`)는 자동 점검이 「판정 없음」으로 읽는다. **정규식으로 판정 유무를
판별하려는 시도는 실패했다** — 상한 21개를 뽑아 검산했더니 대부분 오탐이었다.

→ 그래서 병합 검증은 **네 가지를 따로** 본다.

1. **같은 이름이 두 번 정의됐는가**(AST 로 최상위 `def`/`class`/상수 대조)
2. **한쪽에서 통제되던 라우트가 무방비가 됐는가**(37개 라우트 파일 전수 → **0건**)
3. **한쪽의 정의·라우트가 사라졌는가**(병합으로 바뀐 16개 비테스트 `.py` 전수 → **0건**)
4. **테스트를 실제로 돌린다** — 4·5번은 **오직 이것만** 잡았다

## 3. 익명이 경영계획 금액을 읽고 있었다 — 「빈 파라미터가 가장 넓은 조회」

승인 계정으로 화면 진입 계약을 확인하다가 **같은 호출을 익명으로도** 해 봤다.
`GET /api/v1/planning/facts` 가 200 으로 경영계획 사실 **20건(금액 포함)** 을 줬다.
`dev` 원본도 같았다 — 병합 회귀가 아니라 기존 결함이다. 같은 라우터의 다른 GET 5개는
404(범위 은폐)로 막히는데 **가장 민감한 하나만** 열려 있었다.

원인이 두 겹이다.

1. **`_assert_identified` 를 부르지 않았다.** 30개 라우트 중 17개가 그랬다. 대부분은 범위 판정에
   걸려 **우연히** 막혀 있었다 — 「불러 보니 401 이다」는 「통제가 있다」가 아니다.
2. **빈 범위 요청이 통제를 우회한다.** `org_id`·`scope_node_id` 를 비우면 `assert_scope_allowed`
   는 «전사 요청» 으로 보고 정규화할 대상이 없어 통과시키고, 저장소로 넘어가는 범위도 빈 값이라
   행 필터가 걸리지 않는다. → **파라미터를 주지 않는 것이 가장 넓은 조회다.**

왜 기존 테스트가 놓쳤나: `test_planning_control_gate.py` 의 `READ_PATHS` 목록에 `/facts` 가
없었다. 목록을 손으로 관리했고 「새 라우트를 추가하면 여기 넣어야 한다」는 주석은 지켜지지 않았다.

**조치**: 17개 전부에 식별 확인을 넣고, `READ_PATHS` 를 채우고, **라우터를 읽어 누락을 잡는
테스트**(`test_every_planning_get_is_covered_here`)를 더했다. 차단 메시지의 조사도 맞췄다
(«경영계획를» → «경영계획을» — 통제 메시지가 어설퍼 보이면 사용자는 그 통제도 어설프다고 읽는다).

가장 심각한 것: `useConfirm` 이 `open` 을 돌려주지 않는데 사용처 8곳이 `x.open` 을 읽었다
(`AgentMasterPanel` 4 · `OrgChartPanel` 2 · `SkillEvolutionPanel` 2 · `WorkStandardPanel` 1).
`ConfirmInline` 은 `if (!open) return null` 이므로 **확인창이 한 번도 열리지 않았다** —

⚠️ **왜 아무도 못 봤나.** `vite dev` 는 타입을 보지 않는다. 개발 중에는 화면이 정상으로 보이고
`npm run build` 만 실패한다. 그리고 버튼을 눌러 «아무 일도 없음» 은 화면에서 «권한이 없어 막힘»
과 구분되지 않는다. → **화면이 뜬다는 것과 기능이 동작한다는 것은 다르다.**
⚠️ `npx tsc --noEmit -p tsconfig.json` 은 **0개 파일을 검사하고 조용히 통과한다**(솔루션 파일).

함께 고친 것: `SystemsCoverage.hidden_unscoped`·`ContractEvaluation.note` 타입 누락(서버는 주고
있었다), 미사용 import 2개, `OrgChartPanel` 이 `orgApi.tree()` 를 불러 **결과를 한 번도 읽지

## 5. 프로젝트 작업공간 경로가 상대경로였다 — 그리고 그것이 테스트 격리 지점이었다

D-018 ① 에서 **DB 경로를** `core/paths.py` 로 고정했는데 **생성 프로젝트 작업공간은 남아

발견 경로: 트랙 E 2단계를 검증하려고 워크트리에서 백엔드를 띄웠더니
`GET /api/v1/factory/projects` 가 실제 프로젝트 대신 테스트 잔여물 1개만 돌려줬다.

⚠️ 「목록이 비어 보인다」로 끝나지 않는다. 이 경로 중 일부는 `os.makedirs(exist_ok=True)` 를
한다. 즉 **엉뚱한 위치에 빈 작업공간을 새로 만들고**, 그 뒤 사용자 산출물이 그쪽에 쌓인다.
원래 위치에서 보면 «사라진» 상태다.
⚠️ `core/org_seed.py:reconcile_ownership` 의 기본값도 상대경로였다. 이 함수는 **소유권 미러를
재구축**하므로 잘못된 디렉터리를 읽으면 미러가 0건이 되고, 미러가 비면 목록 API 의 부서 필터가
«소유권 미기록» 으로 전부 통과시킨다(하위호환 규칙). **경로 하나가 틀리면 권한 필터가 조용히
열린다.**

### 5.1 절대경로로 고치자 테스트 20건이 깨졌다

원인은 `monkeypatch.chdir(tmp_path)` — 즉 **테스트가 「제품 코드는 cwd 에 의존한다」를 전제로
격리**하고 있었다. 격리가 잘못된 것이 아니라 **격리 지점이 cwd 였다.**

그래서 지점을 `core.paths.PROJECTS_DIR` 하나로 모았다. 호출부는 `workspace_path()` 를 부른다 —
`from core.paths import PROJECTS_DIR` 로 **값을 복사하면 그 순간 굳어 덮을 수 없다.**
`chdir` 을 쓰던 7곳에 아래 한 줄을 넣었다(`chdir` 자체는 남겼다 — `./library` 처럼 아직
상대경로인 곳이 있다).

```python
monkeypatch.setattr(core.paths, "PROJECTS_DIR", str(tmp_path / "projects"))
```

**실측 증거**: 수정 전 워크트리 스위트에서 `P_ALL`·`P_CTX`·`P_DUP`·`P_IDEA`·`P_KEEP`·
`P_NOWBS`·`P_OK`·`P_PLAIN`·`P_WBS` **9개**가 제품 형태의 `projects/` 에 생기고 정리되지 않았다.
수정 후 원본에서 스위트를 완주해도 **새 디렉터리 0개**(`ls projects/` 전후 diff).
