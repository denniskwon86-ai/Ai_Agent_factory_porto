### 2.1 기존 자산을 다시 쓰지 않고 **재사용**한 세 곳

이 세 판단이 이번 작업에서 가장 중요하다. 옮겨 적었다면 회귀가 났을 곳이다.

1. **iframe 런타임** — `PreviewPanel.tsx`(658행)에는 샌드박스 iframe, 여러 파일을 순서대로
   등록하는 가상 모듈 레지스트리, `IFRAME_READY`/`EXECUTE_FILES` 프로토콜, 새 창 팝업 싱글톤,
   「우리 iframe 이 보낸 메시지만 처리」하는 출처 검증이 있다. **옮겨 적으면 회귀가 날 곳이 여덟
   군데다.** 그래서 `GeneratedAppRuntime` 은 라이트 실행 프레임만 만들고 실행은 그 컴포넌트에
   맡긴다. `rawCode` 도 종전 화면이 받던 값(`state.frontend_code_summary`)과 **같다**.
2. **답변 직렬화** — `[요구 확인 인터뷰 답변]` / `N. 질문` / `→ 선택: …` 형식은 **백엔드
   `RFP_Analyst` 가 파싱하는 계약**이다. `HOTLInput.tsx` 안에만 있던 것을 `clarifyAnswers.ts`
   로 추출하고 **양쪽이 같은 함수를 부른다.**
   ⚠️ 형식을 바꾸면 백엔드 파서도 함께 봐야 한다. 화면만 고치면 답변이 **오류 없이 「선택 없음」
   으로 읽힌다** — 가장 찾기 어려운 종류다.
3. **마크다운 렌더러** — `PreviewPanel.tsx` 의 `ManualRenderer` 에 `export` 를 붙여 재사용한다.
   복사하면 같은 문서가 두 화면에서 다르게 보인다.

### 2.2 명세가 요구했지만 **만들지 않은** 것들 — 그리고 그 이유

**없는 것을 채우면 그것이 곧 거짓이 된다.** 그래서 각각 «무엇이 없는지» 를 화면에 적었다.

| 명세 요구 | 왜 안 만들었나 | 화면이 하는 말 |
|---|---|---|
| 답변 준비도(%) | 서버가 충분성을 계산해 주지 않는다 | 「준비도 점수는 아직 없습니다. 지금 임의로 채우면 그 숫자가 판단을 왜곡합니다」 |
| 권장 데이터 | 같음 | 표시하지 않는다 |
| 다음 자동 전환 **조건** | 서버 로직이고 화면이 알 수 없다 | 「전환 조건은 서버가 판단합니다 — 이 화면은 순서만 알고 있으므로 조건을 짐작해 적지 않습니다」 |
| RFP 대비 Diff · 변경점 · 영향 분석 · 수정 전후 | 서버가 재료를 주지 않는다 | 각 Canvas 하단 「보조 검토」에 무엇이 없는지 적는다 |
| 누적 LLM 비용 | store 에 없다 | 「— / 누적 비용 미측정」. **₩0 으로 쓰면 「공짜로 돌고 있다」로 읽힌다** |
| 빌드 번호(Build #14) | 프로토타입의 **예시 데이터**였다 | 「최신 산출물」/「갱신 중」 |
| 8칸 고정 단계 지도 | 같음 — 실제로는 프로젝트마다 14칸·16칸 | 레지스트리에서 파생한다 |

### 2.3 세 상태를 구분한다 (§8 신뢰성)

「비어 있음」을 한 가지로 묶지 않았다. 사용자가 해야 할 일이 다르다.

- **아직 없다** → 기다리면 생긴다. 「지금 비어 있는 것은 «아직»이며 «서버가 주지 않는다»가
  아닙니다 — 진행되면 채워집니다」
- **서버가 아예 주지 않는다** → 기다려도 안 생긴다. 「기다려도 이 자리에는 생기지 않습니다」
  (화면 설계·화면 검증은 이미지·스크린샷 판정이라 텍스트 요약이 없다)
- **못 읽었다** → 권한·오류. `loadState` 가 `forbidden`/`error` 로 구분한다

## 3. 이번 세션에 잡은 결함 4건 — 발견 경로까지

### 3.1 `small` 태그가 9.6px 이 됐다 (3단계에서 발견)

브라우저 기본이 **부모의 80%** 다. 컨테이너가 12px 이면 `small` 은 9.6px — §6(가시 텍스트 최소
12px) 위반. 2단계 검증에서는 **WBS 가 비어 있어 그 요소가 렌더되지 않았고**, 3단계에서 실제
WBS 가 들어오자 8건이 걸렸다.

→ 규칙마다 `font-size` 를 적는 대신 `.afs-studio small { font-size: 12px }` **하나로** 되돌렸다.
개별 규칙으로 막으면 다음에 추가되는 `small` 에서 또 빠진다.

### 3.2 단계 라벨이 에이전트 한 명 이름이었다 (3단계)

`EXECUTION` 은 백엔드·프론트엔드가 **함께** 쓰는데 화면에는 「백엔드 개발자」만 나왔다 —
프론트엔드가 그 단계에 없는 것처럼 보인다.

→ 단계명은 용어 사전 `STAGE_KO`(「구현」), 담당 에이전트는 칸의 셋째 줄에 따로.
⚠️ `stageKo()` 함수를 쓰지 않았다 — 사전에 없는 값에 `console.error` 를 내는데, 커스텀 템플릿의
낯선 stage 는 「오류」가 아니라 정상이다(그때는 에이전트 이름을 쓴다).

### 3.3 ★★★ WBS 진행 상태가 틀리게 표시되고 있었다 (5단계에서 발견)

화면은 「완료 2 · **진행 0** · 대기 3(**차단 3**)」이라고 말했지만 실제 데이터는
완료 2 · **진행 1** · 대기 1 · 차단 1 이었다. **3단계 스크린샷에 이미 있었는데 놓쳤다.**

원인은 **판정이 두 벌**:
- `WbsSpine` 은 `status` 를 보고 종류를 정했다 — `'COMPLETED' || 'DONE'` 둘 다 완료로 인정
- `factoryViewModel` 은 `blockedBy` 를 따로 계산했다 — `!== 'COMPLETED'` 만 비교
- **실제 데이터는 `'DONE'`** 이었다 → ViewModel 이 끝난 선행을 「미완」으로 세고, 완료·진행
  중인 작업에까지 `blockedBy` 를 붙였다
- `WbsSpine` 은 완료를 먼저 보므로 「완료」로, Inspector 는 `blockedBy` 만 보므로 「차단」으로 —
  **같은 작업이 두 곳에서 다르게 보였다**

→ 완료 판정을 `isTaskDone()` 하나로 모으고, 종류(`kind`)를 **ViewModel 에서만** 정한다. 컴포넌트는
표시만 한다. Inspector 의 「무엇이 막고 있는가」에는 `kind === 'blocked'` 만 넣는다.

⚠️ **왜 늦게 잡혔나**: 두 표시가 서로 모순인데 **각각은 그럴듯했다.** 「차단 3」도 말이 되고
「완료」도 말이 됐다. Inspector 가 같은 데이터를 다른 각도로 보여 주자 비로소 나란히 놓였다.

### 3.4 `UI_DESIGN`·`VISION_QA` 가 거짓말을 했다 (6단계)

산출물 집합에서 빼 두었더니 「작업면이 아직 이 화면에 없습니다 — 올 예정입니다」로 나갔다.
**거짓이다** — 서버가 그 단계 요약을 주지 않으므로 기다려도 생기지 않는다.

→ 둘도 산출물 집합에 넣고 **판정을 한 곳으로** 모았다. 그리고 `NOT_YET_PLAN` 을 **비웠다** —
기본 14단계가 모두 Canvas 를 갖게 됐으므로 남겨 두면 도달하지 않는 죽은 문구가 된다.

### 4.1 Sprint 시작을 옮길 때의 위험 — 다음 사람이 가장 조심할 것

`ControlPanel:234` 는 이런 payload 를 조립한다.

```js
project_state_payload: {
  schema_version: "5.1.0",
  project_name: currentProjectId,
  initial_idea: idea,
  master_data: masterData,
  factory_mode: "PLANNING",
}
```

⚠️ **이것을 복사하면 두 화면이 서로 다른 payload 를 보낸다.** 스키마 버전·모드·`master_data` 를
한쪽만 고치는 날이 오고, 그때 「두 화면이 다른 프로젝트를 만든다」가 된다. 이 저장소에서 가장
비쌌던 결함 유형이다(§3.3 과 같은 구조).
→ **먼저 `factory/sprintStart.ts` 같은 공용 모듈로 payload 조립을 추출하고**, `ControlPanel` 과
  Studio 가 그것을 부르게 해야 한다. `clarifyAnswers.ts` 와 같은 방식이다.

## 5. 검증 방법 — 이번 세션에 쓴 것

`scripts/capture_screens.py` 와 같은 방식으로 헤드리스 Chrome 을 띄운다. Browser 패널이 표시되지
않아 `computer{screenshot}` 이 실패하므로 이 경로가 유일하다.

- 검증 스크립트는 세션 스크래치패드에 있다(`verify_studio3.py` ~ `verify_studio6.py`).
  **저장소에 커밋하지 않았다** — 프로젝트 id·단계 index 같은 실측 환경에 묶여 있다.
- 검증 계정은 승인된 `hikwon@lsmnm.com` 하나. `page.add_init_script` 로 **첫 로드 전에** 심는다
  (나중에 심고 reload 하면 첫 로드가 익명으로 나가고 그때의 401/403 이 콘솔에 남아 「Studio 가
  오류를 냈다」로 오독된다).
- 검증 대상 프로젝트는 `test_a1_unitconv` — **두 극단을 다 갖고 있다**(요구 확인 질문 3개 +
  요약 231자 + 생성 코드 14,188자, 현재 단계는 코드 심사).

### 5.1 콘솔 오류 판정 기준 — 반드시 이 기준을 쓸 것

403·401 은 **통제가 작동한 것**이고 브라우저는 그것도 콘솔 오류로 적는다. 게이트에 넣으면
「권한 통제가 있는 화면」은 영원히 통과하지 못하고, 그러면 사람이 게이트를 끈다.
→ `401`·`403`·연결 거부·App-in-App iframe sandbox 경고·CDN 경고는 **분류해서 제외**하고 나머지는
전부 실패로 센다. 숨기는 것이 아니라 **세는 대상을 밝히는 것**이다.

### 5.2 단계 index 함정

검증 스크립트에서 한 번 틀렸다. 단계 index 를 **레지스트리 order** 로 잡았는데 `EXECUTION` 을
백엔드·프론트엔드가 공유해 **한 칸으로 합쳐지므로** 하나씩 어긋난다. 「코드 심사」를 누른다고
생각한 것이 실제로는 「빌드」였다(구현 Canvas 가 나와서 알았다). **화면 칸 순서**로 세야 한다.

## 6. 아직 확인하지 못한 것 — 정직하게

전부 「그 상태의 프로젝트가 없다」가 이유다. 실행하려면 파이프라인을 돌려야 하고 그것은
**사용자 승인 사안**이다(LLM 비용·되돌리기 어려움).

| 미확인 | 왜 |
|---|---|
| 요구 확인 **대기** 상태(질문 카드가 실제로 뜨는 경로) | 지금 있는 프로젝트는 전부 요약이 채워져 있다 |
| Decision Dock 이 **표시**되는 상태(결정 1건 이상) | HOTL 대기 프로젝트가 없다. **접힘만** 확인했다 |
| 「제출하고 재개」의 실제 동작 | 누르면 파이프라인이 재개된다 |
| 「질문하기」의 실제 응답 | 누르면 LLM 을 호출해 회사 비용이 나간다 |
| 「선택 ≠ 현재」의 강한 검증 | 실행 중 프로젝트가 없어 「진행」 단계가 0개인 상태로만 확인했다 |

→ 제출 경로의 안전은 「기존 `HOTLInput` 과 **같은 엔드포인트·같은 직렬화**」로 담보한다.
  다르게 보내면 백엔드가 한쪽만 이해하므로 그 위험이 가장 컸다.
