# 기간계 업무시스템 플랫폼 전환 설계 (ERP/MES 급)

> **문서 상태**: 구상·로드맵 확정 / **①②는 설계 수준, ③④는 방향과 착수 조건만** · **전 단계 미착수**
> **작성일**: 2026-07-26
> **기준 커밋**: `7a57b0263` (`v5.1.0-pre-enterprise`)
> **선행 문서**: `docs/design_org_permission_enterprise.md` (조직·권한·부서게시·전사 표준/검색/시뮬)
> **선행 조건**: A-1 완주 실측 → 데이터 표준 실질 작동. 그 전에는 ③④ 착수 금지(§6 게이트)

---

## 1. 이 문서가 나온 질문

> "여러 주체가 동시다발적으로 또는 순차적으로 데이터를 입력해서 상호 연계해 종합 계산·결과를 도출하는 **기간계 업무시스템(ERP/MES 같은)** 을 우리 시스템으로 만들어낼 수 있느냐."
>
> 구체 사례 — **원료수입관리**: 구매(발주) → 물류(선적·입고) → 통관 외부인력(신고) → 재무(정산). 하나의 수입 건을 여럿이 나눠 채우고, 물류가 입력한 데이터를 원료팀 SW가 읽어 가공하며, "어느 탭에 들어와 입력해달라"고 지시가 가야 한다.

**결론부터: 지금은 만들 수 없다.** 그리고 이유는 기능 부족이 아니라 **구조적**이다.

## 2. 종합 진단

### 2-1. 정체성 격차 — 만드는 물건이 다르다

| | 현재 시스템 | 요구되는 것 |
|---|---|---|
| 산출물 | **돌아가는 데모** | **운영되는 업무 시스템** |
| 수명 | 게시하면 끝 | 계속 데이터가 쌓이고 스키마가 진화 |
| 사용자 | 만든 사람(1인/1부서) | 다부서 + 외부 인력 |
| 데이터 | 앱 안에 갇힘 | 전사 공용, 상호 참조 |
| 성공 기준 | 산출물 품질 점수 | **업무가 돌아가는가** |

`AI_HANDOFF.md`의 현 정체성 선언은 *"도메인 지식 기반 업무 산출물·시뮬레이션 팩토리"*다. 기간계를 목표로 한다면 이 정의로는 부족하며, **"업무 시스템 팩토리"로 재정의**해야 한다. 이는 문구 수정이 아니라 성공 기준·벤치마크·테스트 시나리오가 전부 바뀐다는 뜻이다.

### 2-2. ★ "한 판 DB"가 사실은 두 개였다 (가장 중요한 오해)

사용자의 원래 구상은 *"모든 데이터베이스는 동일한 한 판에 구성·저장되어 전사 기준으로 다 합쳐진다"* 였다. 그런데 선행 설계서에서 내가 "이미 한 판이다"라고 답한 것은 **다른 것**이었다.

| | 대상 | 현재 |
|---|---|---|
| **(가) 팩토리의 데이터** | `data/master/master.db`(M1+M2), `data/chroma_db`, `data/mcp_cache.db` | ✅ **이미 한 판** — project_id 컬럼조차 없는 전역 저장소 |
| **(나) 생성된 앱들의 업무 데이터** | 원료수입 건, 선적 기록, 통관 신고… | ❌ **존재하지 않음** |

**사용자가 말한 것은 (나)다.** 선행 설계서 전체가 (가)만 다뤘다. 이 간극이 원료수입관리 질문으로 드러났다.

### 2-3. ★ 진짜 병목 — 생성된 앱에 런타임이 없다

코드로 확인한 사실:

| 항목 | 실태 | 근거 |
|---|---|---|
| 프론트 실행 | iframe 샌드박스에서 렌더만 (React UMD + Babel standalone, srcdoc) | `frontend/src/components/PreviewPanel.tsx:178-244, 427-434` |
| **백엔드 실행** | **실행되지 않는다.** import 해서 부팅 여부만 스모크 검사하고 버린다 | `tools/backend_smoke_run.py`, 호출부 `nodes/execution.py:549-554` |
| **앱의 DB** | **단 한 개도 생성된 적 없다** (`find projects -name "*.db"` → 0건) | 실측 |
| 배포 | `library/<release_id>/release.json` 에 **코드가 텍스트로** 저장 | `factory_control.py:932-953` |
| 앱 간 통신 | 경로 없음 | 전수 확인 |

**이것이 모든 것의 상위 병목이다.** 조직·권한·표준·검색·롤업을 전부 만들어도 **앱이 실제로 돌면서 데이터를 쌓지 않으면 전부 가정 위에 서 있다.** 선행 설계서 Phase 1~11 중 상당수가 "게시된 앱이 데이터를 갖고 있다"를 암묵 전제한다.

### 2-4. ★ 선행 설계서와의 모순 3건 (반드시 조정 필요)

**모순 1 — 데이터 표준의 강제 시점**
- 선행 설계서 결정: *"생성 시 권장만, 게시 시 매핑으로 정합화, 코드는 안 고친다"*(Phase 6)
- **③공용 쓰기 저장소 단계에서는 성립하지 않는다.** 여러 앱이 같은 테이블에 쓰려면 필드가 **생성 시점에** 표준을 따라야 한다. 게시 후 매핑은 이미 각자 다른 테이블을 만든 뒤다.
- → **①②까지는 현 결정이 유효. ③ 진입 시 "생성 시 강제"로 재판정**해야 한다. 이 전환점을 문서에 못 박는다(§6 G3).

**모순 2 — `visibility='personal'` 과 공용 저장소**
- 개인 편의 도구도 공용 저장소에 쓰는가? 아니라면 **앱이 두 종류**(개인용 로컬 / 기간계 공용)가 되고 **생성 파이프라인이 갈라져야** 한다.
- → 프로젝트 생성 시 **`app_class`(personal | departmental | backbone)** 를 1급 속성으로 두고, `backbone` 만 공용 저장소·워크플로·표준 강제 대상으로 삼는다. 나머지는 현재 방식 유지.

**⚠️ 단, `app_class` 를 그냥 추가하면 분류축이 4개가 된다 — 반드시 정리하고 도입할 것.**
선행 설계서와 합치면 `visibility`(Phase 1) · `nature`(Phase 6-7 사용자 선언) · `relevance`(6-7 자동 판정) · `app_class`(여기) 가 공존하고 **값까지 겹친다**(`personal` 이 셋에 등장). 아무도 어느 것을 봐야 할지 모르게 된다. 축을 3개로 확정한다:

| 축 | 질문 | 값 | 결정 주체 |
|---|---|---|---|
| **`app_class`** | 이 앱은 **어떤 종류인가** (생성 파이프라인·저장소·표준 강제를 가름) | personal / departmental / **backbone** | 사람(생성 시 선택) |
| **`visibility`** | **누가 볼 수 있나** (접근 제어) | personal / dept / company | 사람(게시 시) |
| **`relevance`** | **데이터가 전사적인가** (표준화 큐 진입 판정) | island / local / enterprise | 자동 계산(재계산됨) |

→ **선행 설계서의 `nature` 컬럼은 삭제한다.** 사용자 선언은 `app_class` 선택으로 흡수되며 별도 축이 불필요하다. 자동 판정(`relevance`)과 사람 선택(`app_class`)이 어긋나면 DA 화면에 표시한다(선행 설계서 6-7의 취지는 유지).

**모순 3 — 사일로 정의**
- Phase 8은 "부서마다 비슷한 걸 중복 생성"을 사일로로 본다.
- 그런데 **진짜 사일로는 하나의 프로세스를 부서마다 잘라 각자 만들고 엑셀로 주고받는 것**이다. 구매는 발주 앱, 물류는 입고 앱, 통관사는 스프레드시트.
- → **다부서 기간계 지원이 최상위 사일로 방지책**이고 재사용·포크는 그 하위다. 우선순위를 뒤집어야 한다.

### 2-5. ★ 두 축이 만나는 지점 — 기간계가 시뮬레이션의 근본 해법이다

지금까지 SW 생성과 시뮬레이션을 **병렬 두 축**으로만 봐왔다. 그런데:

- 현재 시뮬은 전부 `gateway.aexecute(output_mode="document")` **순수 LLM 추론**이다(`nodes/universal.py:102`). "몬테카를로"는 프롬프트 지시어일 뿐 수치 엔진이 없다.
- **기간계에 실 운영 데이터가 쌓이면 시뮬레이션의 입력이 실측이 된다.** 그럴듯한 숫자를 지어내는 것에서 **진짜 디지털 트윈**으로 바뀐다.
- 즉 **기간계 전환은 시뮬 품질 문제의 근본 해결책**이며, 두 축을 잇는 다리다.

이 관점에서 선행 설계서의 전사 롤업(Phase 9)·전사 시뮬(Phase 10)은 **기간계 이후에 훨씬 강력해진다.** 순서상 기간계가 앞이면 좋지만, 규모 때문에 그럴 수 없다는 것이 §6의 딜레마다.

### 2-6. 놓치고 있던 요구 4건

기간계에는 있고 지금 설계 어디에도 없는 것:

1. **동시성 제어** — 여러 주체가 같은 레코드를 동시에 건드린다. 락·낙관적 동시성·충돌 해소. **LLM이 생성한 코드가 이걸 제대로 할 리 없다** → 앱이 아니라 **런타임이 제공**해야 한다.
2. **감사 로그** — 누가 언제 무엇을 바꿨나. 기간계의 필수 요건이며 분쟁 해결의 근거.
3. **스키마 진화** — 운영 중인 앱을 고치면 이미 쌓인 데이터는? 현 `revision`/`resimulate`는 **코드만** 다시 만든다. 마이그레이션 개념이 없다.
4. **보존·기밀 등급** — 이미 표준 데이터에 답이 있다. `ks_x_9101_national_standard.data_management_system_part2` = `{data_ownership, security_level, retention_period_years}`. 다만 현재는 전역 1건짜리라 **엔티티별로 확장**해야 쓸 수 있다.

## 3. 목표 상태 정의

**"우리 시스템으로 만든 여러 앱이, 하나의 업무 프로세스를 나눠 수행하고, 같은 데이터를 공유하며, 전사 기준으로 자동 집계된다."**

성립 조건 5가지:

| # | 조건 | 무엇이 필요한가 |
|---|---|---|
| C1 | **데이터가 한 곳에** | 공용 업무 데이터 저장소 |
| C2 | **어휘가 공통** | 데이터 표준(선행 설계서 Phase 6) |
| C3 | **각자 자기 몫만** | 참여자·단계·필드 단위 권한 |
| C4 | **차례가 돌아감** | 워크플로 + 작업 지시 인박스 |
| C5 | **앱이 실제로 돎** | 생성 앱 런타임·배포 |

**C5가 0순위다.** C1~C4는 C5 위에서만 의미를 갖는다.

## 4. 로드맵 — 4단계 + 권한 확장

### ① 읽기 연계 (앱은 자기 DB 유지, 공용 읽기 뷰로 노출)

**목표**: "물류 SW에 입력된 데이터를 원료 SW가 읽어와 가공한다"를 성립시킨다.

**①은 두 갈래로 나눈다 — G1(앱 런타임) 없이도 되는 쪽이 있다.**

| | 방식 | G1 필요? | 실시간성 |
|---|---|:-:|---|
| **①-a 스냅샷 복제** | 게시 시점에 앱 데이터를 **공용 읽기 테이블로 밀어넣는다** | **불필요** | 게시 시점 기준 |
| **①-b 온디맨드 조회** | MCP 브로커가 살아있는 앱을 조회 | **필요** | 실시간(TTL 내) |

**①-a 를 먼저 한다.** G1(앱 런타임)은 §9-2에서 보듯 사실상 미니 PaaS라 큰 벽인데, ①-a 는 그 벽을 우회하고도 "물류 데이터를 원료 SW가 읽는다"의 상당 부분을 만족시킨다. 대신 데이터가 게시 시점에 고정되므로 `as_of` 병기가 필수다.

**①-b 는 M3 MCP 브로커의 대상만 바꾸면 된다** — `MCPAdapter`(`core/mcp_broker.py:41-48`)가 `set_adapter()`(`:253-255`)로 교체되므로 `InternalAppAdapter` 를 구현한다.

> ⚠️ **자기 정정**: 초판에 *"어댑터 하나 구현하면 끝"* 이라고 썼으나 **과소평가였다.** `fetch(system_id, endpoint, entity, selector)` 는 **selector 로 식별되는 단일 인스턴스**를 반환하고(`:43-45`), `resolve_batch`(`:192-199`)도 단순 루프라 N+1 이다. 앱 간 연계는 대개 **목록 조회·필터·조인**을 요구하므로 **어댑터 인터페이스 확장이 필요하다**(`query(entity, filters, fields, limit)` 급). 재사용 가치는 여전히 크지만 "그대로 쓰면 된다"는 아니다.

- 게시 시 앱을 `external_systems`에 등록하는 것은 **선행 설계서 Phase 6-4에서 이미 하기로 했다**(카탈로그 등재). 그 등록에 `endpoint`만 실주소로 채우면 조회 대상이 된다.
- `key_crosswalk` 승인 매핑 게이트(`crosswalk.update_system:92-96` — 승인 매핑 ≥1 없으면 활성화 거부)가 그대로 **"연계 가능 상태" 판정**이 된다.
- TTL 캐시·`as_of` 타임스탬프·"비신뢰 입력" 인젝션 방어가 **이미 구현돼 있다**(`mcp_broker.py:96-136, 201-236`).
- 읽기 전용이라 파괴적 사고가 원천 차단된다.

**해결되는 것**: 앱 간 데이터 참조, 전사 조회.
**해결 안 되는 것**: 동시 입력, 워크플로, 종합 계산의 정합성(각 앱 DB가 진실원본이라 시점 불일치 발생).

**선행**: C5(앱 런타임) — 앱이 안 돌면 읽을 데이터가 없다.

### ② 작업 지시 인박스 (워크플로 엔진 없이)

**목표**: "이 릴리스의 이 탭에 들어와 입력해주세요"가 실제로 전달된다.

최소판 — 엔진 없이 **사람이 지시를 만들고 시스템이 배달**한다:
- `work_items` — `(id, release_id, target_dept_id, target_user_id, tab/FR 참조, 상태, 기한, 요청자, 메모)`
- **내 할 일 인박스** — 로그인 시 나에게 온 지시 목록. 클릭하면 해당 릴리스의 해당 탭으로 딥링크
- 알림 — **`core/broadcaster.py` SSE 재사용**(선행 설계서 Phase 2에서 사용자별 predicate를 이미 붙인다)
- 상태: 대기 → 진행 → 완료. 완료 판정은 사람이(자동 판정은 ④에서)

**재사용**: HOTL 게이트가 이미 "사람이 개입할 차례"를 다루는 메커니즘이다(`hotl/check`, `hotl/resume`, SSE 방송). **개념 구조는 그대로 쓰되 대상만 파이프라인 → 업무로 바꾼다.**

**해결되는 것**: 순차 협업, 담당 배정.
**해결 안 되는 것**: 자동 배정, 선행조건 판정.

**선행**: 조직·사용자(선행 설계서 Phase 1~2).

### ③ 공용 쓰기 저장소 (진짜 전환점)

**목표**: 앱이 자기 DB를 만들지 않고 **전사 공용 저장소의 테이블을 할당받아** 읽고 쓴다.

```
지금:  앱 A → 자기 SQLite        앱 B → 자기 SQLite      (연결 없음)
①:    앱 A → 자기 SQLite ←읽기── 앱 B                    (읽기만, 시점 불일치)
③:    앱 A ──┐                                            (한 판. 조인·집계가 SQL 하나)
       앱 B ──┴→ 공용 업무 데이터 저장소 (표준 스키마)
```

**이 순간 데이터 표준의 역할이 바뀐다** — "게시 후 정합화하는 후처리"에서 **"공용 저장소의 DDL 그 자체"**로. `standard_field` 레코드가 곧 컬럼 정의가 된다.

구성:
- **공용 저장소** — 표준 필드 사전에서 결정론 생성한 스키마. `data_standard.scaffold_*()`(선행 설계서 Phase 6-1)가 참조용이 아니라 **실 DDL 생성기**로 승격
- **데이터 접근 런타임** — 앱은 SQL을 직접 쓰지 않고 런타임 API로 접근. **동시성·감사 로그·권한(C3)을 여기서 일괄 제공**(2-6의 요구 1·2 해결). LLM 생성 코드에 맡기지 않는 것이 핵심
- **생성 규약 변경** — Architect/Tech_Lead/Backend 스킬이 "자체 DB 설계" 대신 "공용 스키마 사용"을 산출하도록 전면 수정
- **`app_class='backbone'` 만 대상**(모순 2 해소)

**⚠️ 여기서 데이터 표준 정책을 재판정한다** — 생성 시 권장 → **생성 시 강제**(모순 1).

### ④ 워크플로 엔진

**목표**: 프로세스 정의로 차례가 자동으로 흐른다.

- **프로세스 정의** — 단계 · 담당(부서/역할) · 선행조건 · 필수 입력 필드
- **인스턴스** — "수입 건 #123은 현재 통관 단계"
- **자동 배정** — 단계 진입 시 담당에게 `work_item` 자동 생성(②의 수동 지시를 대체)
- **완료 조건·집계** — 필수 입력이 다 찼는지 판정 후 다음 단계로. 종합 계산 트리거

**★ 프로세스 정의를 어디서 얻는가 — 새 개념을 안 만드는 방법**
PRD에 **FR-ID가 이미 있고** G1 추적성 엔진이 정규식으로 뽑는다(`nodes/utils/traceability_manager.py:15 extract_ids`). 여기에 **담당 부서 태그만 붙이면** 된다:

```
FR-003 [물류] 선적 정보 입력
FR-007 [통관] 수입신고번호·HS코드 등록
```

그러면 `FR → 담당 부서 → 구현 파일·필드`가 **기존 추적성 맵으로 자동 도출**된다. 워크플로 정의의 절반이 기획 산출물에서 공짜로 나온다.

### ⑤ 권한 모델 확장 (①~④와 병행, 독립 단계 아님)

앞선 논의(다부서 권한)는 이 문서의 문제와 **같은 문제의 두 얼굴**이다 — 다부서가 한 프로세스를 쓰려면 (가) 데이터가 한 곳에 있고 (나) 각자 자기 몫만 건드려야 한다. (가)가 저장소, (나)가 권한. **분리 설계 금지.**

- **`participants`** — `(resource_kind, resource_id, dept_id, role, scope_tag, valid_to)`. `scope_tag`가 FR 그룹과 연결되어 "물류는 FR-003만" 성립
- **authz 런타임** — `GET /api/v1/authz/context?release_id=`(내 역할·scope), `POST /api/v1/authz/check`. ③의 데이터 접근 런타임과 **같은 지점에서 강제**
- **외부 인력** — 조직도에 `external/` 서브트리 + **만료(`valid_to`) 있는 게스트**. 상속이 상위→하위 단방향이라 외부 노드가 위를 못 보는 것은 이미 보장됨

**⚠️ 미결 — 외부 인력을 시스템 사용자로 볼 것인가**

| 선택 | 결과 |
|---|---|
| **게스트 계정으로 직접 입력** | 실시간 협업 가능. 단 **실제 인증이 필요**해져 선행 설계서 요구 1(경량 사용자 전환)과 충돌 |
| **파일·API 인터페이스로 수령** | 기존 설계와 정합적(M2/M3 연계). 단 실시간 협업 불가 |

이 결정이 인증 아키텍처 전체를 가른다. **③ 착수 전까지 확정 필요.**

## 9. 리스크와 정직한 한계

1. **규모** — 이것은 기능 추가가 아니라 **제품 전환**이다. 앱 런타임·공용 저장소·데이터 접근 런타임·워크플로 엔진이 전부 신규 서브시스템이고, 코드 생성 규약(Architect/Backend 스킬)이 전면 수정된다. 현 시스템 규모의 배수를 각오해야 한다.
2. **G0가 아직 안 됐다** — A-1 관문 시나리오가 아직 완주하지 못했다(TECH_SPEC 도달 후 SUSPENDED). 파이프라인이 한 번도 끝까지 못 간 상태다.
3. **G3가 멀다** — `standard_field` 3건. 표준 사전 확충이 실질적 대공사이며, 이것 없이 ③은 불가능하다.
4. **LLM 생성 코드에 기간계 품질을 기대할 수 없다** — 동시성·트랜잭션·감사·마이그레이션은 생성 코드가 아니라 **런타임이 제공**해야 한다. 이 경계를 흐리면 실패한다.
5. **스키마 진화 미해결** — 운영 중 앱을 고쳤을 때 기존 데이터 마이그레이션 방법이 이 문서에 없다. ③ 설계 시 반드시 포함해야 한다.
6. **①의 시점 불일치** — 각 앱 DB가 진실원본이라 TTL 캐시 기반 조회는 실시간 정합을 보장하지 않는다. 종합 계산의 정확도가 필요하면 ③까지 가야 한다.
7. **외부 인력 정책 미결**(G4) — 인증 아키텍처 전체가 갈리는 결정인데 아직 안 정해졌다.
8. **시뮬레이션은 여전히 LLM 추론** — ③ 이후 입력이 실측이 되어도 계산 엔진 자체는 없다. 수치 시뮬 엔진 도입은 이 문서의 범위 밖이며 별도 판단이 필요하다.

## 9-2. ⚠️ G1(앱 런타임)의 난이도를 과소평가하고 있다 — 과거 기각 결정과 충돌

이 문서는 G1 을 *"생성된 백엔드가 실제로 기동되고 데이터를 쌓는다"* 한 줄로 적었다. 실제로 요구되는 것:

프로세스 수명주기 관리 · 포트 할당 · **테넌트 격리** · 재시작·헬스체크 · 로그 수집 · 리소스 제한 · 비밀정보 주입 · 버전 전환. **이것은 사실상 미니 PaaS 다.**

그리고 `AI_HANDOFF.md:251-253` 의 **기각 기록과 정면으로 충돌**한다:

> *"[기각 기록] … Docker·Wasm MicroVM 샌드박스(격리 서브프로세스 스모크가 이미 동작, 현 단계 인프라 과투자)"*

당시 판단은 "데모만 만들면 되므로 격리 인프라는 과투자"였고 **그 전제에서는 옳았다.** 기간계로 목표가 바뀌면 **그 기각을 재판정해야 한다.** 이 문서는 재판정을 요구하되 결론은 내지 않는다 — G1 착수 시점에 별도 검토가 필요하다.

**G1 우회 경로가 있다는 점이 중요하다**: ②작업지시와 ①-a스냅샷복제는 G1 없이 가능하다(§4·§6). 즉 **G1 을 최대한 뒤로 미룰 수 있고, 그동안 얻는 것이 적지 않다.**

| **M4** | **카탈로그 등재 대상 불일치** — 선행 설계서 6-4 는 "게시되는 전부 등재", 본 문서 ③은 "backbone 만 공용 저장소". 같은 `external_systems` 를 쓰면 personal 앱도 "등록된 DB"가 되어 의미가 흐려짐 | `external_systems` 에 **`catalog_only` 플래그** 필요(실 데이터 보유 여부 구분). ③ 설계 시 반영 |
| **M5** | **`key_crosswalk` PK 한계가 ③에서 선택이 아니라 필수** — PK `(master_code, system_id)` 로는 한 앱의 여러 엔티티×여러 표준필드 매핑을 표현 못 함. 선행 설계서는 이를 "리스크"로만 적었음 | ③ 진입 시 **PK 를 `(master_code, system_id, entity)` 로 확장**하거나 별도 매핑 테이블. **필수 항목으로 승격** |
| **M6** | **Phase 5(프롬프트 주입 권한)가 다부서 앱 생성을 막는다** — 주입 규칙이 "자기 부서+조상만" fail-closed 인데, 원료수입관리를 구매부서가 만들면 **물류·통관 필드 정의를 참조해야 한다** | `participants` 에 등록된 부서의 스코프도 **주입 허용 대상에 포함**. ⑤ 설계 시 Phase 5 규칙 개정 |

### 10-3. 위험한 가정

- **A-1. FR-ID 부서 태그의 신뢰도** — ④의 프로세스 정의를 `FR-003 [물류]` 형태로 LLM 이 일관되게 붙일 것이라 가정한다. 그러나 **현재 FR-ID 인용조차 소프트 게이트**이고(`criteria.py:86-103` 의 `_check_fr_coverage` 는 감점이지 차단이 아님) 완전하지 않다. → **부서 태그는 사람이 확정하는 HOTL 게이트**를 두는 편이 안전하다.
- **A-2. LLM 생성 코드가 공용 저장소 규약을 지킬 것이라는 가정** — ③에서 "런타임 API 로만 접근"을 규약으로 두지만, 선행 설계서 Phase 6 의 결론대로 **프롬프트 지시만으로는 강제되지 않는다.** 런타임이 **직접 DB 접근을 물리적으로 차단**해야 한다(자격증명을 앱에 주지 않는 방식).
- **A-3. "①②만으로 시나리오 상당 부분이 돈다"** — 읽기 연계와 수동 지시로 원료수입관리가 실제로 굴러가는지는 **검증되지 않은 주장**이다. ② 완료 후 실제 업무 1건으로 파일럿해 확인해야 한다.

### 10-4. 재사용하지 말아야 할 것 (오용 방지)

- **`WBSManager` 를 `work_items` 로 쓰지 말 것.** 둘 다 "태스크"지만 WBS 는 *프로젝트를 만드는* 작업 단위이고 `work_items` 는 *업무를 수행하는* 지시다. 섞으면 파이프라인 상태와 업무 상태가 얽혀 양쪽 다 망가진다. **별도 모델로 둔다.**
- **HOTL 게이트를 업무 승인으로 전용하지 말 것.** 개념 구조(차례가 왔다·SSE 알림)는 참고하되, HOTL 은 LangGraph interrupt 에 묶여 있어 업무 워크플로의 수명주기와 맞지 않는다.

### 10-5. 검토 총평

**설계의 뼈대는 타당하다** — 특히 "이미 통합된 데이터 위에 권한 뷰를 씌운다", "카탈로그를 M2 재사용으로 신규 테이블 0", "전사 시뮬 엔진은 코드 변경 0", "관련성은 판단이 아니라 계산" 은 기존 자산을 정확히 활용한 판단이다.

**가장 큰 약점은 두 가지다.**
1. **G1(앱 런타임)의 규모를 문서가 계속 축소해 다뤘다.** 이것이 전체 로드맵의 임계 경로인데 한 줄로 처리돼 있었다(§9-2 로 보강). 다만 ①-a·② 우회 경로를 찾아 **임계 경로에서 빼낼 수 있음**을 확인한 것은 이번 검토의 실질 소득이다.
2. **성능·규모 가정이 전무하다**(G-c). 기간계는 정의상 규모가 커지는데, 현재 구현은 전량 파일 스캔·전건 메모리 로드가 곳곳에 있다. **목표 규모를 숫자로 정하지 않으면 어떤 설계도 검증할 수 없다.**

**착수 전 반드시 결정할 것**: G4(외부 인력 정책) · 목표 규모(G-c) · G1 재판정(§9-2).
