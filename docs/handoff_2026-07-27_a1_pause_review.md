# A-1 테스트 중단·재개 전 수정 계획 (2026-07-27)

> 상태: **의도적으로 중단**. 이 문서는 A-1을 통과로 처리하지 않고, 재실행 전 필요한 수정과 검증 순서를 고정하기 위한 인수인계다.
> 브랜치: `dev` | 기준 프로젝트: `test_a1_v4` | 중단 태스크: `E2E-01`

## 1. 결론

`test_a1_v4`는 기획 파이프라인과 기술명세까지는 정상적으로 진행했지만, 첫 구현 태스크에서 코드 생성 및 빌드 자가복구가 신뢰성 있게 완주하지 못했다. 따라서 A-1의 현재 판정은 다음과 같다.

| 항목 | 판정 | 근거 |
|---|---|---|
| 기획·HOTL·WBS | 부분 통과 | 요구 확인, RFP, PRD, UI/Vision, 아키텍처, PMO/WBS가 진행됨 |
| 기술명세 정합성 | 개선 확인 | 실제 워크스페이스 파일 목록을 강제 주입한 뒤, 이전의 `index.tsx`·가상 API 환각이 줄어든 명세가 생성됨 |
| E2E-01 구현·빌드 | 실패/중단 | 생성된 `main.py`에 `def get_history):`, `def load_data):` 같은 구문 오류가 연속 발생 |
| 자가복구 3회 한도 | 미검증 | 중단 시점은 `developer_retry_count=2`; 세 번째 복구와 최종 실패 전파를 관찰하지 않음 |
| A-1 전체 | **FAIL (재수정 후 동일 시나리오 재실행)** | 모든 WBS DONE, QA, Release, UI 증거를 충족하지 못함 |

기존 `test_a1_v3`는 `supervisor_hops=8` 뒤 best-effort PASS가 섞여 있어, 깨끗한 수용 증거로 사용할 수 없다. v4도 위 사유로 PASS 증거가 아니다.

## 2. v4에서 확인한 사실

### 정상으로 확인된 부분

- Requirement Interviewer HOTL, RFP, PRD, UI/VisionQA, Architecture, PMO/WBS가 순서대로 진행됐다.
- WBS는 `E2E-01`부터 `E2E-06`까지 6개 태스크로 생성됐다.
- Tech Lead의 실제 파일 인벤토리·태스크 범위 강제 규칙 적용 뒤 기술명세 점수는 `0.725`로 통과했다.
- 이번 변경에 대해 `py_compile nodes/execution.py` 및 `tests/test_registry_graph_consistency.py` 6개가 통과했다.

### 중단을 결정한 부분

1. Backend 생성 결과가 두 번 연속 Python 구문 오류였다. 빌드 게이트는 오류를 탐지하고 재시도 카운터를 2까지 올렸으나, 유효한 코드로 회복하지 못했다.
2. 구조화 `CodeOutput` 응답이 정확히 8,192 토큰 한도에 도달해 파싱에 실패했다. 단순 출력 상한 증가는 이미 근본 해결이 아님이 확인되어 있다.
3. 공급자 폴백 과정에서 OpenRouter Llama 호출이 총 420초 타임아웃까지 대기했다. 이 상태는 사용자에게 복구 중인지, 공급자 대기인지, 최종 실패인지 명확하게 전파되지 않는다.

중단 당시 상태 스냅샷은 `factory_mode=EXECUTION`, `current_stage=TECH_SPEC`, `current_sprint_task_id=E2E-01`, `developer_retry_count=2`, `build_status=failed`, 실패 노드 `Backend`였다. 자동 실행 드라이버와 해당 태스크는 중단했다. 백엔드 서버는 사용자가 별도 테스트에 활용할 수 있도록 유지했다.

## 3. 이번 세션에서 반영한 변경

### Tech Lead 명세 환각 방지

- `skills/tech_lead_skill.md`
  - 현재 WBS 범위·실제 파일·실제 인터페이스를 단일 사실원천으로 삼도록 강화했다.
  - 가상 파일, 가상 import, 근거 없는 서버 API를 명세에 재도입하지 못하게 했다.
  - 파일별 FR-ID와 인터페이스 계약, 서버 API가 없을 때의 명시를 요구한다.
- `nodes/execution.py`
  - 기술명세 실행 시 `file_index`와 워크스페이스 디스크를 합쳐 실제 파일 인벤토리를 만들고 프롬프트에 강제 주입한다.
  - 현재 WBS task의 goal/scope를 함께 주입하여 다른 기능을 재설계하는 일을 제한한다.

이 변경은 코드 생성 자체의 구문 품질을 보장하지 않는다. 그 책임은 아래의 출력 계약·복구 정책 개선으로 분리한다.

## 4. 재실행 전 필수 수정 순서

### F-1. 코드 생성 출력 계약 축소 (최우선)

문제: 큰 코드 문자열, ADR, 기술부채, 파일 인덱스, 상태 업데이트를 하나의 `CodeOutput` 구조화 응답에 강제하면 모델이 끝맺지 못하고 출력 상한을 모두 소진할 수 있다.

수정 방향:

1. 생성 코드(`files`)와 메타데이터(ADR, debt, state updates)를 분리하거나, 코드 생성에는 자유 JSON + 엄격한 자체 파서를 사용한다.
2. 구조화 응답 파싱 실패는 동일 형식의 장시간 폴백만 반복하지 말고, 축소된 출력 계약의 단일 복구 경로로 전환한다.
3. 파일별 최대 크기·전체 응답 예산을 명시하고, 초과 시 어떤 파일부터 재시도할지 기록한다.

수용 기준: 의도적으로 긴 코드 응답·파싱 실패를 주입한 단위 테스트에서, 8,192 토큰 파싱 실패가 무한/장시간 폴백으로 이어지지 않고 원인과 다음 행동을 남긴다.

### F-2. 빌드 자가복구의 종료 계약 완성

문제: 현재 v4에서는 두 번의 구문 오류 탐지까지만 확인했다. "3회 복구"가 실제로 세 번의 유효한 수정 시도를 뜻하는지, 한도 초과 때 사용자에게 어떤 상태가 보이는지 증거가 없다.

수정 방향:

1. 최초 생성 포함/미포함 여부를 포함해 시도 횟수 정의를 코드와 UI에서 동일하게 고정한다.
2. 매 시도마다 실패 파일, 검사기, 오류 전문, 마지막 유효 checkpoint를 실패 번들로 저장한다.
3. 한도 초과 시 안전 상태 롤백 후 `SPRINT_FAILED` 이벤트, WBS `FAILED`, UI의 실행 상태 해제를 원자적으로 처리한다.
4. 자동 반복은 종료하고, 사용자가 실패 번들을 보고 `수정 지시 후 재시도` / `새 태스크로 분할` / `종료` 중 선택하게 한다.

수용 기준: 항상 잘못된 Python을 내는 테스트 더블로 세 번의 복구 경로를 실행했을 때, 네 번째 생성 루프 없이 실패 번들·WBS FAILED·`SPRINT_FAILED`·UI 정상 해제가 모두 확인된다.

### F-3. 공급자 실패를 파이프라인 상태로 승격

문제: 420초 누적 타임아웃은 사용자에게 진행 중처럼 보일 수 있다.

수정 방향:

1. 공급자별 호출 제한과 전체 요청 예산을 별도 기록한다.
2. 최종 폴백 실패는 `SPRINT_FAILED` 또는 명시적 `SUSPENDED_QUOTA`로 분류해 SSE·WBS·최신 상태에 일관되게 반영한다.
3. 재시도 가능 시각/사용 가능한 공급자를 UI와 실패 번들에 노출한다.

수용 기준: 모의 429/timeout에서 작업이 `IN_PROGRESS`에 고정되지 않고, 사용자 조치가 가능한 최종 상태로 끝난다.
