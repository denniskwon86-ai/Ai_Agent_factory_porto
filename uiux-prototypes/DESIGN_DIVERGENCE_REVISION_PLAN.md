## 1. 리비전 사유

현재 시안은 기능 배치와 정보구조에는 차이가 있으나, 대부분이 `상단 바 + 좌측 내비게이션 + 흰 카드 + 파란 포인트 + CSS Grid`라는 동일한 관리자 대시보드 문법을 사용한다. V8의 편집형 개인 포털과 일부 다크 화면을 제외하면 시각적으로는 사실상 2~3개 계열에 불과하다.

따라서 앞으로는 색상·카드 배치가 아니라 아래 여섯 요소가 서로 달라야 별개의 시안으로 인정한다.

1. 화면의 공간 모델
2. 전역 탐색 방식
3. 정보 밀도와 읽는 순서
4. 핵심 상호작용
5. 타이포그래피·형태·색상 문법
6. 해당 화면이 해결하는 대표 업무

## 3. 버전별 금지 규칙

### V2

- 고정 좌측 사이드바 금지
- 일반 카드 대시보드 금지
- 업무는 독립 창·Dock·검색 명령으로 열어야 한다.

### V3

- 지표 카드 여러 개 나열 금지
- 한 화면에 두 개 이상의 핵심 승인 금지
- 핵심 선택안은 전체 화면의 60% 이상을 사용한다.

### V4

- 일반 경영 KPI 대시보드처럼 만들지 않는다.
- 설비·공정·물류 흐름과 경보가 화면의 주인공이어야 한다.
- 조작 가능한 것과 단순 모니터링 정보를 명확히 구분한다.

### V5

- 앱 런처와 관제 패널 금지
- 실제 문서 작성·근거 인용·버전 비교·승인 흔적이 보여야 한다.

### V6

- 공간 지도 위에 다시 카드 대시보드를 겹치지 않는다.
- 노드 관계와 회사 계층이 화면 면적의 대부분을 차지해야 한다.

### V7

- 전역 홈으로 사용하지 않는다.
- 프로젝트 내부에서 주체·단계·병목을 보는 하위 기능 모듈로 한정한다.

### V8

- 11px 미만 본문 남용 금지
- 개인화 추천의 이유와 전체 기능으로 돌아가는 경로를 표시한다.

### V9

- 가치사슬 각 단계를 독립 카드로 나열하지 않는다.
- 실제 흐름량·재고·원가·현금의 연결이 선 굵기와 색으로 보여야 한다.

### V10

- 일반 챗봇 화면으로 끝내지 않는다.
- 상담 결과가 데이터셋·업무 절차·에이전트·SW/Twin 설계 블록으로 생성되는 과정을 보여준다.

## 4. 리비전 수행 순서

10. V1은 현 제품 기준선으로 최소 정리

## 5. 완료 판정

각 버전은 다음 조건을 모두 만족해야 한다.

- 흑백 스크린샷만 보아도 다른 버전과 구조가 구분된다.
- 색상만 제거해도 공간 모델과 읽는 순서가 다르다.
- C01~C12 콘텐츠 적용표가 유지된다.
- 핵심 본문 14px 이상, 보조 정보 11px 이상을 원칙으로 한다.
- 핵심 행동이 시선의 중심에 있고 외곽의 작은 버튼에 숨어 있지 않다.
- 예시 데이터·권한 범위·근거 시점이 명확하다.
- 실제 `frontend/`에 적용할 때 재사용할 수 있는 고유 컴포넌트가 최소 하나 정의된다.

## 6. 최종 통합 방식

10개 중 하나를 우승안으로 고르는 방식이 아니라 다음 레이어별로 선택한다.

- 전역 Shell·탐색
- 최초 진입·상담
- 개인 홈
- 프로젝트 실행
- 문서·데이터 작성
- 공장 운영
- 전사 가치사슬·경영
- 디지털 트윈·시나리오
- HOTL 의사결정

각 레이어에서 가장 적합한 시안의 구조를 선택한 뒤, 하나의 디자인 토큰과 회사 브랜딩 체계로 통합한다.
