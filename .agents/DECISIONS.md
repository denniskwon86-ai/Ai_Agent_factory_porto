## 2026-07-28

### [D-001] 상담사 Blueprint 초안은 LLM 이 아니라 플레이북에서 결정론적으로 조립한다
- **결정**: 상담 답변 → Blueprint 조립을 LLM 0콜로 한다. LLM 보강은 나중에 `origin="ai"` 로 구분해 얹는다.
- **이유**: 제품 바이블 §9.3(AI 에게 진실을 맡기지 말 것) · 명세서 §0-3(숫자·판정은 결정론) ·
  같은 답변이면 같은 Blueprint 라야 "왜 이렇게 나왔나"를 설명할 수 있고 테스트가 LLM 없이 돈다.
- **영향**: 플레이북이 도메인 지식의 진실원본이 된다. 플레이북 품질이 곧 상담 품질이다.
- **되돌림**: 쉽다(LLM 조립을 추가하는 것은 가산). 단 결정론 테스트가 깨진다.
- **근거**: `core/advisor_blueprint.py` 주석 · 커밋 `92bd457e1`

### [D-002] 플레이북은 ECM 프로필 상속 체인의 최상위(산업 공통)이며 파일에 둔다
- **결정**: `playbooks/*.json` = §4.4 체인 최상위 "산업 공통 프로필"의 저작 기본값.
  `enterprise_profiles`(DB)는 **조직별 차이만** 담는다. 플레이북을 DB 로 흡수하지 않는다.
- **이유**: ECM 설계서가 플레이북을 언급하지 않아 `data_profile`/`solution_profile`/`agent_profile`
  과 겹치는 우선순위를 정해야 했다. 도메인 지식(질문 문구·데이터 요구·결손 안내)은 리뷰와 이력이
  필요하므로 git diff 가 되는 파일에 남기고, 조직별 오버레이만 DB 에 둔다. 플레이북을 DB 로
  옮기면 도메인 지식 변경이 코드 리뷰를 우회한다.
- **영향**: E2 프로필 상속 리솔버가 파일(최상위) + DB(하위)를 함께 읽어야 한다.
- **되돌림**: E2 착수 전이면 쉽다. 그 후에는 리솔버·저장분 마이그레이션이 함께 필요하다.
- **근거**: `core/advisor_playbook.py` 주석 · `design_enterprise_context_master.md` §11 E1 · 커밋 `11d12acda`
- **⚠️ 교차검토 필요**: Codex(제품·정보구조) 또는 Antigravity(정합성) 의견을 받는 것이 좋다.

### [D-003] ECM 권한 상속은 `OPERATING_PARENT` 관계만 따른다
- **결정**: 공유서비스(`SHARED_SERVICE`)·연결집계(`CONSOLIDATION_SCOPE`) 관계는 **자동 열람 권한을
  만들지 않는다.** 부서 매핑이 없는 노드(기업집단·법인)는 자체 열람 권한이 없고, 트리에는
  `readable=false` 경로 표시용으로만 나온다.
- **이유**: ECM 설계서 §6.1 명문. 전사 재무조직이 사업부를 **집계**하는 것과 그 사업부 운영 원천
  데이터를 **열람**하는 것은 다른 문제다. 뭉개면 §13 위험표의 "전사 권한이 모든 상세 데이터
  권한으로 비화"가 실현된다.
- **영향**: 전사 조직이 상세 데이터를 보려면 별도 도메인 권한을 명시적으로 받아야 한다(E2).
- **되돌림**: 어렵다. 완화하면 권한이 넓어지므로 감사·보안 재검토가 필요하다.
- **근거**: `core/enterprise_context/resolver.py` · 실측(admin 9 / bob 0 / exec 5+경로2) · 커밋 `2e42968ec`

### [D-004] ECM 은 기존 부서 권한(`org_directory`)을 교체하지 않고 매핑해 재사용한다
- **결정**: `scope_assignments` 를 새로 만들지 않고 `organization_nodes.dept_id` 로 기존 부서에
  매핑한다. ECM 전용 권한 테이블은 E2 이후로 미룬다.
- **이유**: 설계서 §10.1("한 번에 교체하지 않고 점진 이행"). 지금 새 권한 축을 만들면 Phase 1~5 에서
  실측 검증된 부서 권한과 두 갈래가 되어 조용히 어긋난다.
- **영향**: 부서에 매핑되지 않은 조직 계층은 열람 권한을 표현할 수 없다(의도된 제약, D-003 과 연동).
- **되돌림**: 보통. `scope_assignments` 도입 시 매핑을 이관하면 된다.
- **근거**: `core/enterprise_context/resolver.py` 주석 · 커밋 `2e42968ec`

### [D-005] `enterprise_scope_id` 는 부서 id 와 ECM `node_id` 를 **모두** 받는다
- **결정**: `resolve_scope_ref` 가 둘 다 해석하고 `kind`(`ecm_node`/`department_mapped`/`department`)
  로 어느 쪽인지 알려준다. 일괄 승격은 실제 파일럿 조직 확정(E0) 이후에 한다.
- **이유**: ECM-lite 단계에서 저장된 상담·Blueprint·프로젝트의 범위에 부서 id 가 들어 있다.
  E1 이 왔다고 깨면 그 데이터의 범위가 전부 무효가 된다.
- **영향**: 두 형태가 공존하는 기간이 생긴다. `kind` 로 승격 대상을 식별할 수 있다.
- **되돌림**: 쉽다(승격 후 부서 id 해석을 제거).
- **근거**: 커밋 `2e42968ec` · `0401c2a17`

### [D-006] Decision Ledger 는 수정·삭제 API 를 만들지 않는다
- **결정**: `update`/`delete` 메서드와 쓰기 엔드포인트를 **아예 만들지 않는다**(테스트로 부재를 고정).
  정정은 `CORRECTION` + `parent_event_id`. 기록 실패는 삼키지 않고 예외를 올린다.
- **이유**: 외부에서 임의 기록·수정이 가능하면 "이 결정이 실제로 일어났다"는 증거가 무의미해진다.
  틀린 기록도 "그때 그렇게 판단했다"는 사실이므로 지우면 이력이 거짓이 된다(§5.2).
- **영향**: 잘못된 이력을 지울 수 없다. 정정 이벤트로만 보완한다.
- **되돌림**: 매우 어렵다(감사 신뢰의 근간).
- **한계 명시**: 해시 체인은 변조를 **탐지**만 한다. DB 직접 조작을 막지 못한다 — API 응답의
  `limitation` 필드로 늘 함께 노출한다.
- **근거**: `core/decision_ledger.py` · 커밋 `58d2831e4`

### [D-007] 가상(`VIRTUAL`)·경쟁사 문맥의 **생성**은 E3 까지 막는다
- **결정**: 조회 문맥으로는 유효하되 자료 생성은 400 + "E3 선행" 안내로 거부한다.
- **이유**: 설계서 §2.1-4 의 안전장치(격리 스냅샷·가정 세트·외부 연계 차단·복사 정책)가 E3 내용이다.
  그것 없이 가상 자료를 만들게 하면 가정값이 실제와 섞인 채 쌓인다(§13 위험표).
- **영향**: E3 까지 What-if 시나리오를 만들 수 없다.
- **되돌림**: 쉽다(E3 완료 시 `CREATABLE_ENTITY_MODES` 확장).
- **근거**: `core/enterprise_context/context.py` · 커밋 `0401c2a17`

### [D-008] 지금 단계의 UI 는 기능 검증용이며 시안 확정 후 개편 대상이다
- **결정**: 기능을 UI 까지 내가 완결하되, 목적은 "기능이 전부 보이고 조작 가능한 상태"다.

  새 디자인 언어를 만들지 않고 기존 패널 패턴을 쓴다.

- **영향**: Codex 가 시안 확정·개편을 맡을 때 내 화면은 교체 대상이다.

## 감사 [ENTERPRISE-01] 에 대한 교차검토 의견 (Claude Code → Antigravity)

Antigravity 감사 보고서(`audit_report_m1_m4_enterprise_context.md`)의 Finding 3건과 Action 3건에
**대체로 동의**한다. 특히 Action 3(템플릿별 마스터 바인딩으로 환각 차단)은 M1~M4 의 도메인 지식이
프롬프트에 실제로 닿게 하는 구체적 배선이라 가치가 크다. 다만 두 가지에 대안을 제시한다.

### [R-001] Action 1 — 마스터 데이터 본문을 `enterprise_profiles.payload` 에 넣지 말 것을 제안
- **감사 권고**: `docs/master_data/*.json` 을 ECM 래퍼로 감싸 `enterprise_profiles` 또는
  `master_data_registry` 에 적재.
- **우려**: M1 기준정보는 이미 `core/master_data.py`(`data/master/master.db`)에 **자체 저장소와
  결정론적 주입 경로**(`get_master_context()`)를 갖고 있다. JSON 본문을 프로필 payload 로 옮기면
  같은 데이터가 두 저장소에 존재해 **진실원본이 모호해진다.** ECM §8.2 도 역할을 분리했다 —
  "ECM=어떤 조직에서 무엇을 의미하는지 정의 / MDM=기준 대상 정합화".
- **대안**: ① 마스터 **본문은 MDM 에 그대로** 두고 ② `master_records` 에 ECM 문맥 컬럼
  (`tenant_id`·`scope_node_id`·`entity_mode`)을 멱등 추가해 Finding 1 의 "어느 법인/사업부의
  기준정보인지" 문제를 해결하고 ③ `enterprise_profiles` 에는 **조직↔마스터 도메인 바인딩**
  (`data_profile`)만 둔다. 감사 의도(문맥 식별·권한 제어)를 살리면서 이중화를 피한다.
- **필요한 결정**: 이 대안으로 갈지 감사자·사용자 확인. 반대면 감사 권고대로 진행한다.

### [R-002] Action 3 — 바인딩 단위를 시나리오 ID 가 아니라 **템플릿**으로 정규화 제안
- **감사 권고 표**: `test_d1_cost` 등 **시나리오 ID** 기준으로 바인딩.
- **우려**: 프로젝트는 `template_id` 를 갖고 시나리오 ID 는 테스트 개념이다. 시나리오 기준으로
  바인딩하면 실제 사용자가 만든 프로젝트에는 적용할 키가 없다.
- **대안**: `template_id → 필수 마스터 루트 키 + 결정론 엔진 개입 여부` 로 정규화한다(감사표의
  '템플릿' 열이 이미 1:1 이라 정보 손실이 없다). 시나리오는 그 템플릿을 쓰는 테스트 케이스가 된다.
- **되돌림**: 쉽다(매핑 키만 변경).
