### [D-010] 기준정보 주입에 상한을 두지 않는다 — 적용 가능한 것은 전수 주입
- **결정**: `select_for_injection` 의 기본 상한을 **없앤다**(종전 12건/3,000자 폐기). 조직 범위와
  도메인을 통과한 기준정보는 **전부** 프롬프트에 넣는다. `is_core` 는 관문이 아니라 정렬 신호로
  강등하고, 우선순위는 「별칭 히트 → 전사 표준·산식 → 도메인 핵심」 3계층으로 **표시 순서만** 정한다.
  상한은 환경변수 또는 호출자 인자로만 걸 수 있고, 걸리면 `break` 대신 `continue` 로 처리하며
  잘린 건수를 주입 블록에 명시한다.
- **이유**: 종전 12건은 2026-07-22 에 토큰 폭주를 막으려 **임의로 고른 값**이었고 실측 근거가 없었다.
  M1~M4 시드 44건 적재 후 실측하니 배터리소재는 적용 가능 30건 중 12건만 들어가고 **잘린 18건에
  표준원가 산식·MPS·라우팅·배출계수·시뮬 확률분포가 전부** 포함됐다 — 「LLM 이 산식을 지어내지
  못하게 확정 주입한다」는 M1 의 존재 이유가 그 자리에서 무력화되고 있었다. 게다가 tie-break 가
  코드 알파벳순이라 **무엇이 버려지는지가 중요도가 아니라 철자로** 결정됐다(`RM-`/`WIP-` 항상 탈락).
  전량은 배터리소재 ≈6,000자 / 전 문서 44건 ≈8,700자로 컨텍스트 부담이 없어 자를 이유가 없다.
- **영향**: 모든 에이전트 프롬프트의 기준정보 블록이 길어진다(≈2,200자 → ≈5,300자). 도메인이
  어긋난 레코드는 여전히 제외되므로 무관한 내용이 늘지는 않는다. `is_core=False` 레코드가 처음으로
  주입 대상이 된다. `tests/test_master_data.py::test_alias_detection_word_boundary` 는 `is_core`
  관문에 기대어 오탐 부재를 측정하고 있었으므로 도메인 불일치로 측정 방식을 바꿨다.
- **되돌림 비용**: 낮음 — 환경변수로 즉시 상한 복원 가능. 우선순위 계층은 종전 동작의 상위집합.
- **근거**: `docs/design_org_permission_enterprise.md` §F4(해소 기록·실측 수치) ·
  `docs/design_master_data_m1.md` §4 · `core/master_data.py:_INJECT_MAX_ITEMS` 주석 ·
  잠금 테스트 6건(`tests/test_master_document_seed.py`)

### [D-011] 문서 정식명은 별칭으로 그대로 쓰지 않고 매칭 가능한 형태로 파생한다
- **결정**: 시드는 `derive_aliases()` 로 정식명을 분해해 별칭을 만든다
  (`"Mixed Hydroxide Precipitate (MHP)"` → 전체 · `"Mixed Hydroxide Precipitate"` · `"MHP"` · 문서상 식별자).
  **새 문자열을 창작하지 않는다** — 문서에 이미 적힌 부분만 쓰고, 순수 수치·단위 토큰(`"98%"`)은 버린다.
- **이유**: `_alias_hit` 은 단어경계로 **문자열 전체**를 찾는다. 괄호 표기를 통째로 별칭에 넣으면
  실제 프롬프트에 그 형태가 나올 일이 없어 **별칭 히트 경로 전체가 죽는다**(시드 44건 전부 해당).
  그래서 선정이 `is_core` + 알파벳순으로만 이뤄져 D-010 의 절단 편향이 그대로 노출됐다.
  이것도 반복되는 **생산자→소비자 배선 누락**(§8-2) 유형이다 — 별칭을 만들었지만 매칭기가 쓸 수 있는
  형태인지 확인하지 않았다.
- **영향**: 시드 재실행 시 별칭이 늘어난다(멱등 — `INSERT OR IGNORE`). 오탐 위험은 단어경계 + 최소
  2자 + 수치 토큰 배제로 억제.
- **되돌림 비용**: 낮음.
- **근거**: `core/master_data_seed.derive_aliases` docstring · `test_aliases_are_matchable`

### [D-002] 플레이북은 제품 소유의 **업무·솔루션 기준선**이며 파일에 둔다 (개정 2026-07-28)
- **결정**: `playbooks/*.json` = **제품이 제공하는 업무·솔루션 기준선**. 필요할 때 산업 공통
  데이터 프로필 조각을 제공하되 **산업 자체의 공통 프로필과 동일시하지 않는다.**
  `enterprise_profiles`(DB)는 조직별 오버레이만 담는다. 플레이북을 DB 로 흡수하지 않는다.
- **상속 체인**:
  ```
  산업 공통 프로필 → 업무·솔루션 플레이북 기준선 → 기업집단 → 법인 → 사업부 → 공장
    → 프로젝트·시나리오 오버레이
  ```
- **이유(파일 유지)**: 도메인 지식(질문 문구·데이터 요구·결손 안내)은 리뷰·이력·테스트 대상이어야
  하므로 git diff 가 되는 파일에 남기고, 조직별 특수성만 DB 에 둔다. 하위 조직이 상위의 필수
  요구사항을 조용히 삭제하지 못하는 구조도 함께 얻는다.
- **개정 이유**: 초안은 "플레이북 = 산업 공통 프로필"로 등치했는데 **개념적으로 과도했다.**
  `business_planning` 은 업무 유형이라 제조업 외 산업에도 적용되고, 반대로 한 산업 안에도
  경영계획·생산·품질·구매·물류 등 여러 플레이북이 존재한다. 1:1 이 아니다.
- **개정에 따른 보완 요구**(Codex 교차검토):
  ① 플레이북의 `industry_codes` 를 **실제로 사용**한다 — 선택 조직의 `business_profile.industry_code`
     와 검증해 맞지 않는 플레이북은 추천·선택에서 제외하거나 경고한다. 업종 무관 플레이북은
     명시적으로 공통으로 표시한다.
  ② `resolved-profile` 의 `sources` 에 `playbook_id`·`playbook_version`·**파일 해시**를 남긴다.
     지금은 버전·해시가 없어 플레이북이 바뀌면 "당시 어떤 기준으로 추천됐는가"를 재현할 수 없다.
  ③ 프로젝트·Blueprint·Decision Ledger 에 **실행 당시 해석된 프로필 스냅샷을 고정**한다.
- **영향**: E2 리솔버가 파일(기준선) + DB(조직) 을 함께 읽는다. E2 를 되돌릴 사안은 아니다 —
  현재 구현이 `data_profile` 기본값으로만 제한돼 확장 여지가 있다.
- **되돌림**: 문구·검증 규칙 수준이면 쉽다. 스냅샷 고정 후에는 저장분 마이그레이션이 필요하다.

### [D-003] ECM 권한 상속은 `OPERATING_PARENT` 관계만 따른다
- **결정**: 공유서비스(`SHARED_SERVICE`)·연결집계(`CONSOLIDATION_SCOPE`) 관계는 **자동 열람 권한을
  만들지 않는다.** 부서 매핑이 없는 노드(기업집단·법인)는 자체 열람 권한이 없고, 트리에는
  `readable=false` 경로 표시용으로만 나온다.
- **이유**: ECM 설계서 §6.1 명문. 전사 재무조직이 사업부를 **집계**하는 것과 그 사업부 운영 원천
  데이터를 **열람**하는 것은 다른 문제다. 뭉개면 §13 위험표의 "전사 권한이 모든 상세 데이터
  권한으로 비화"가 실현된다.
- **영향**: 전사 조직이 상세 데이터를 보려면 별도 도메인 권한을 명시적으로 받아야 한다(E2).
- **되돌림**: 어렵다. 완화하면 권한이 넓어지므로 감사·보안 재검토가 필요하다.
- **근거**: `core/enterprise_context/resolver.py` · 실측(admin 9 / bob 0 / exec 5+경로2) · 커밋 `2e42968ec`

### [D-006] Decision Ledger 는 수정·삭제 API 를 만들지 않는다

- **되돌림**: 매우 어렵다(감사 신뢰의 근간).
- **한계 명시**: 해시 체인은 변조를 **탐지**만 한다. DB 직접 조작을 막지 못한다 — API 응답의

  ```
  master_records          → 기준정보 본문·버전·유효기간의 진실원본 (MDM)
  master_scope_bindings   → 이 기준정보가 어느 테넌트·조직 범위에서 어떤 상태·기간·승인
                            조건으로 적용되는지 (신규)
  enterprise_profiles     → 조직별 데이터 요구·업무 규칙·템플릿·에이전트 오버레이
                            (기준정보 본문 보관 금지)
  ```
- **★ 내 초안(`master_records` 에 문맥 컬럼 추가)을 폐기한다.** Codex 지적이 정확했다 —
  컬럼 방식은 **1 레코드 : 1 범위**가 되어 동일 자재·공통 설비 기준·환율 기준을 **여러 법인·공장이
  함께 참조**하는 것을 표현할 수 없다. 원본은 하나이고 적용 범위만 여러 개여야 한다.
- **`master_scope_bindings` 필수 필드**: `tenant_id` · `scope_node_id` · `master_code` +
  `master_version`(또는 유효 버전 규칙) · `entity_mode`(현재 `REAL` 만) · `effective_from/to` ·
  `status`·`approved_by`·`approved_at` · `inherit_descendants`(자기 조직만 vs 운영 계층 하위 상속).
- **실행 경로 고정**:
  ```
  사용자·프로젝트 문맥 검증 → ECM 권한 확인 → 적용 가능한 마스터 바인딩 해석
    → 유효한 MDM 버전 선택 → 결정론적 컨텍스트 주입
  ```
- **★ 기준정보의 '적용 가능성'과 사용자의 '열람 권한'은 별개다.** `SHARED_SERVICE`·
  `CONSOLIDATION_SCOPE` 관계가 자동으로 상세 데이터를 열람하게 해서는 안 된다(D-003 유지).
- **★ 캐시 필수 보완**: 현재 `master_data._load_cache()` 는 **전체 활성 레코드**를 담고
  `get_master_context()` 는 `domains` 필터만 쓴다(실측 확인). 범위 필터 없이 주입되므로
  **A 법인 마스터가 B 법인 프롬프트에 섞일 수 있다.** 캐시·필터를 함께 고쳐야 한다.
- **위험도**: `TEAM_PROTOCOL` §3-1 **C등급**(권한·보안 + 데이터 구조 변경) — 통합 전 독립 검토 필요.
- **되돌림**: 어렵다(권한 경계와 주입 경로를 바꾼다). 바인딩이 없는 레코드는 종전대로 통과시키는
  점진 도입으로 회귀 위험을 낮춘다.
- **근거**: Codex 교차검토(2026-07-28) · 아래 [R-001] 원안 · Antigravity 감사 Action 1
- **✅ 구현 완료 (2026-07-29)**: `core/master_data.py`(`master_scope_bindings` + 범위 필터) ·
  `state_models.py`(문맥 3필드) · `factory_control._ACCUMULATED_FIELDS` · `advisor_control`
  부트스트랩 배선 · 테스트 18건(전체 680 통과).
  · **점진 도입**: 바인딩이 없는 레코드는 전사 공통으로 통과하고, **바인딩을 하나 넣는 순간 그
    레코드는 통제 대상**이 된다(fail-closed 전환). 전부 막으면 바인딩 전 기능이 통째로 멈춘다.
  · **캐시 오염 없음**: 캐시는 '전체 레코드'를 담고 **필터를 요청마다 적용**하므로 A 법인 요청이
    B 법인 결과를 오염시킬 수 없다. Codex 가 제안한 캐시 키 분리보다 단순하고 같은 효과다
    (실제 원인은 캐시가 아니라 필터 부재였다). 바인딩 변경 시 `_invalidate()` 로 즉시 반영.
  · **실측**: 같은 기준정보 풀에서 제1공장 3건 / 제2공장·동제련 2건 / **LS전선(다른 법인) 1건**
    (공통만) / 범위 미지정 3건(하위호환). `MAT-P1` 을 두 공장에 바인딩하면 원본 1개에 적용범위
    2건이 되어 공유가 표현된다. 바인딩 테이블에 본문 컬럼이 없음도 확인.
  · **미완**: `master_version` 고정 규칙(현재 NULL=유효 버전만 지원), `effective_from/to` 기간
    판정, MDM/카탈로그/크로스워크/MCP 의 나머지 범위 키, 바인딩 관리 API·화면.

### [R-001] Action 1 — 마스터 데이터 본문을 `enterprise_profiles.payload` 에 넣지 말 것을 제안
> **⚠️ 이 원안은 [D-009] 로 대체되었다.** 방향(본문을 프로필에 넣지 않음)은 채택됐으나
> 구현 방식(`master_records` 문맥 컬럼)은 폐기됐다. 이력 보존을 위해 남긴다.
- **감사 권고**: `docs/master_data/*.json` 을 ECM 래퍼로 감싸 `enterprise_profiles` 또는
  `master_data_registry` 에 적재.
- **우려**: M1 기준정보는 이미 `core/master_data.py`(`data/master/master.db`)에 **자체 저장소와
  결정론적 주입 경로**(`get_master_context()`)를 갖고 있다. JSON 본문을 프로필 payload 로 옮기면
  같은 데이터가 두 저장소에 존재해 **진실원본이 모호해진다.** ECM §8.2 도 역할을 분리했다 —
  "ECM=어떤 조직에서 무엇을 의미하는지 정의 / MDM=기준 대상 정합화".
- **대안**: ① 마스터 **본문은 MDM 에 그대로** 두고 ② `master_records` 에 ECM 문맥 컬럼
  (`tenant_id`·`scope_node_id`·`entity_mode`)을 멱등 추가해 Finding 1 의 "어느 법인/사업부의
  기준정보인지" 문제를 해결하고 ③ `enterprise_profiles` 에는 **조직↔마스터 도메인 바인딩**
  (`data_profile`)만 둔다. 감사 의도(문맥 식별·권한 제어)를 살리면서 이중화를 피한다.
- **필요한 결정**: 이 대안으로 갈지 감사자·사용자 확인. 반대면 감사 권고대로 진행한다.

### [R-002] Action 3 — 바인딩 단위를 시나리오 ID 가 아니라 **템플릿**으로 정규화 제안
- **감사 권고 표**: `test_d1_cost` 등 **시나리오 ID** 기준으로 바인딩.
- **우려**: 프로젝트는 `template_id` 를 갖고 시나리오 ID 는 테스트 개념이다. 시나리오 기준으로
  바인딩하면 실제 사용자가 만든 프로젝트에는 적용할 키가 없다.
- **대안**: `template_id → 필수 마스터 루트 키 + 결정론 엔진 개입 여부` 로 정규화한다(감사표의
  '템플릿' 열이 이미 1:1 이라 정보 손실이 없다). 시나리오는 그 템플릿을 쓰는 테스트 케이스가 된다.
- **되돌림**: 쉽다(매핑 키만 변경).
