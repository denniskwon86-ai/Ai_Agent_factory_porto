# AI Factory Studio 팀 협업·교차검증 프로토콜

> 적용일: 2026-07-28  
> 대상: 사용자(제품 오너), Claude Code, Gemini Antigravity, Codex 및 이후 합류하는 모든 사람·AI 팀원  
> 목적: 역할 분담은 유지하되 역할 경계에 갇히지 않고, 산출물의 품질을 교차검증하며, 인수인계 문서의 난립 없이 하나의 팀으로 작업한다.

## 1. 핵심 원칙

1. **역할은 전문성의 우선순위이지 권한의 경계가 아니다.**
   - 누구나 제품, 설계, 코드, 테스트, 데이터, UI/UX, 사업성에 대해 질문·반대 의견·개선안을 낼 수 있다.
   - 사용자 또는 작업 책임 수행자는 과제 성격과 산출물 품질에 따라 담당자와 검토자를 수시로 바꿀 수 있다.

2. **중요한 산출물은 위험도 기반의 독립 교차검토를 기본값으로 한다.**
   - 제품 방향, 데이터 모델, 외부 연계, 권한·보안, 비용 구조, 핵심 API, 대규모 UI 변경, E2E 실패 원인은 독립 검토 대상이다.
   - 단, 독립 검토는 책임 수행자의 탐색·자체 점검·반복 수정마다 필요한 사전 허가가 아니다. 통합, 배포, 되돌리기 어려운 결정, 또는 다음 마일스톤 완료 전에 수행한다.
   - 교차검토자는 단순 승인 대신 반대 가설, 누락 조건, 회귀 위험, 운영 영향, 대안을 제시한다.

3. **근거와 완료 기준이 역할보다 우선한다.**
   - “누가 작성했는가”보다 요구사항, 변경 범위, 검증 증거, 미해결 위험을 기준으로 결과를 판단한다.
   - 확신이 낮은 주장·외부 사실·추정은 사실, 해석, 가설을 구분해 기록한다.

4. **사용자가 최종 제품 결정권자다.**
   - 제품 방향, 우선순위, 예산·유료 모델 사용, 외부 서비스 연계, 실데이터 사용, 배포는 사용자가 최종 승인한다.
   - 팀원은 선택지·근거·영향을 명확히 제시하되, 사용자의 의도 없이 방향을 확장하지 않는다.

5. **모든 대화·계획·주석·인수인계는 한국어로 작성한다.**

## 2. 작업별 운영 역할

고정된 직책이 아니라, 모든 작업마다 아래 역할을 필요한 만큼 지정한다.

| 역할 | 책임 |
|---|---|
| 책임 수행자 | 설계, 구현, 조사, 테스트 또는 문서의 실제 결과물을 만든다. |
| 교차 검토자 | 독립 관점에서 품질·가정·누락·회귀·운영 위험을 검토한다. 필요 시 대안을 제시한다. |
| 최종 결정자 | 사용자. 우선순위, 제품 의도, 비용과 외부 영향이 있는 선택을 결정한다. |

책임 수행자는 자신의 결과물을 자유롭게 자체 점검·수정·재검증할 수 있으며, 이는 필수 품질 활동이다. 다만 **최종 독립 검토·통합 승인**은 작성자와 다른 팀원이 맡는다. 긴급 장애 대응처럼 즉시 복구가 우선인 경우에는 사후 독립 검토를 수행한다.

## 3. 공통 작업 흐름

1. **착수 전 확인**
   - `AGENTS.md`, `AI_HANDOFF.md`, 현재 관련 설계 문서와 변경 중인 파일을 먼저 확인한다.
   - 목표, 완료 기준(DoD), 영향 범위, 다른 팀원의 진행 작업, 검증 방법을 짧게 공유한다.

2. **수행 중 공유**
   - 다른 팀의 인터페이스나 가정에 영향을 주는 발견은 즉시 공유한다.
   - 작업이 장기화되거나 차단되면 추측으로 확장하지 않고, 차단 원인과 필요한 결정만 명확히 남긴다.

3. **완료·인수인계**
   - 변경 파일·API/데이터 계약·검증 증거·미해결 위험·다음 행동을 남긴다.
   - 중요한 변경은 교차검토 결과까지 포함해야 **통합 완료**로 표시한다. 검토 대기 중에도 책임 수행자는 다음 독립 작업을 진행할 수 있다.

## 3-1. 검토 강도와 진행 규칙

| 등급 | 예시 | 필요한 검토 | 진행 방식 |
|---|---|---|---|
| A. 국소·가역 변경 | 문서 초안, UI 시안, 내부 리팩터링, 테스트 보강 | 자체 검증 | 즉시 수정·진행 가능 |
| B. 계약 영향 변경 | 내부 API·상태 모델·데이터 계약, 재사용 모듈 | 자체 검증 + 비동기 독립 검토 | 검토 요청을 남기고 병렬 진행. 다음 통합 또는 마일스톤 전에 반영 |
| C. 고위험 변경 | 권한·보안, 데이터 마이그레이션·삭제, 외부 연계·배포, 되돌리기 어려운 제품 결정 | 독립 검토 + 사용자 결정이 필요한 경우 승인 | 통합·배포 전 검토 완료. 탐색·안전한 구현 준비는 병렬 진행 가능 |

- 검토자가 즉시 उपलब्ध하지 않다는 이유만으로 책임 수행자가 멈추지 않는다. 검토 대상·가정·검증 증거를 남기고, 안전한 후속 작업을 계속한다.
- B등급 작업은 `검토 대기` 또는 `검토 부채`로 표시할 수 있다. 단, 검토 부채가 남은 상태에서 릴리스·대규모 통합·비가역 변경으로 넘어갈 수 없다.
- 사용자는 일정·위험·우선순위를 고려해 검토를 면제하거나 사후 검토로 전환할 수 있다.

## 4. 단일 현황판과 문서 규칙

인수인계 문서를 팀원별·세션별로 새로 만들지 않는다. 아래 문서가 각각 하나의 역할만 담당한다.

| 문서 | 단일 목적 | 갱신 기준 |
|---|---|---|
| `.agents/AGENTS.md` | 역할, 공통 원칙, 파일 수정·언어 규칙 | 역할 또는 공통 원칙 변경 때만 |
| `.agents/TEAM_PROTOCOL.md` | 이 협업·교차검증 절차 | 절차 자체가 바뀔 때만 |
| `.agents/TEAM_BOARD.md` | 진행 중·차단·검토 대기 작업의 현재 상태 | 작업 상태가 바뀔 때만 |
| `.agents/DECISIONS.md` | 되돌리기 어렵거나 여러 트랙에 영향을 주는 결정 | 핵심 결정이 확정될 때만 |
| `AI_HANDOFF.md` | 저장소 전체의 재개 진입점과 통합 현황 | 의미 있는 통합 변경·마일스톤 완료 시 |
| `docs/` | 상세 설계, 검토 보고서, 테스트 증적 | 산출물이 완성될 때 |

- `TEAM_BOARD.md`는 **현재 상태만** 유지한다. 종료된 세부 로그를 계속 쌓지 않는다.
- 상세 내용은 중복 기재하지 말고 커밋, 코드 파일, 설계 문서, 테스트 증적으로 연결한다.
- 세션별 임시 인수인계 파일은 불가피한 경우에만 `docs/handoff_YYYY-MM-DD_<주제>.md`로 만들며, 다음 통합 시 `AI_HANDOFF.md`에 결론을 반영하고 임시 문서는 증적용으로만 남긴다.

## 5. 현황판 표준 양식

`TEAM_BOARD.md`의 각 작업은 아래 다섯 항목을 넘기지 않는다.

```markdown
### [작업 ID] 제목
- 상태: 진행 중 | 검토 대기 | 차단 | 완료
- 책임 수행자 / 교차 검토자:
- 목표·완료 기준:
- 영향 범위·결정/가정:
- 증거·다음 행동: 관련 파일, 커밋, 테스트, 필요한 결정
```

## 6. 교차검토 기준

| 대상 | 최소 검토 관점 |
|---|---|
| 제품·사업 기획 | 고객 가치, 범위, 차별성, 도입·운영 가능성, 비용 |
| 데이터·MDM·권한 | 기준정보, 계보, 테넌트/조직 경계, 보안, 감사 가능성 |
| AI·에이전트 | 환각·오작동, 인간 승인, 모델 교체성, 품질 대비 비용, 관측성 |
| 백엔드·API | 상태 계약, 실패 처리, 동시성, 회귀, 데이터 무결성 |
| UI/UX | 현업 용어, 최초 사용자 이해도, 오류·대기 상태, 접근성, 구현 가능성 |
| 테스트·E2E | 재현성, 거짓 성공/거짓 실패, 관측 증거, 실제 사용자 경로 |

## 7. 팀 간 요청 양식

팀원에게 검토·구현·조사를 요청할 때는 아래 정보만 명확히 전달한다.

```markdown
- 요청자 / 수신자:
- 목적과 완료 기준:
- 변경 가능 범위 / 건드리면 안 되는 범위:
- 관련 인터페이스·문서·파일:
- 확인 또는 결정이 필요한 쟁점:
```

## 8. 충돌과 품질 이견 처리

1. 이견은 찬반이 아니라 **증거·가정·영향 범위**로 작성한다.
2. 해결되지 않으면 대안 A/B와 각각의 비용·리스크·되돌림 가능성을 정리해 사용자에게 올린다.
3. 사용자 결정 후에는 `DECISIONS.md`에 결론과 이유를 짧게 기록하고, 팀 전체가 그 결정을 기준으로 작업한다.
4. 이후 새 증거가 나오면 기존 결정을 비난하지 않고, 변경 제안으로 다시 검토한다.

## 9. 금지 사항

- 다른 팀원의 진행 중 작업·산출물을 임의로 덮어쓰거나 되돌리지 않는다.
- 검증하지 않은 성공을 완료로 표시하지 않는다.
- 단순 상태 공유를 위해 새 인수인계 파일을 만들지 않는다.
- 자신의 주 담당 분야가 아니라는 이유만으로 문제 제기·검토를 포기하지 않는다.
